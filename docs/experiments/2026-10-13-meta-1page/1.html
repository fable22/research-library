index

전문가 교정을 재학습 없이 검증된 지식 파일 편집으로 바꾸는 Meta 의 자기 개선 루프

전문가가 agent 의 답을 고쳐 주면 누군가 그 교정을 지식 파일 편집으로 옮겨야 한다. Meta 는 이 일이 몇 주씩 걸릴 수 있다고 설명하는데, 의존 관계를 다 따져 보고 다른 곳이 깨지지 않았는지 확인해야 하기 때문이다. Meta 는 compliance 도메인 하나의 전문가 지식을 200 개가 넘는 텍스트 파일로 두고, 그 안에서 도메인의 입장을 적는 knowledge 파일과 분석 절차를 적는 recipe 를 갈라 놓았다. 지식을 이렇게 나눠 두었기 때문에 교정 하나는 모델 재학습 없이 이 파일들의 편집이 된다. 편집은 원인 진단과 최소 편집으로의 컴파일을 거쳐 replay 와 회귀 시험을 받는다. 시험에서 떨어지면 다시 컴파일되고, 시험을 통과한 편집도 사람이 PR 로 검토해야 반영된다. 반영된 교정은 회귀 시험 사례로 남아서, 뒤에 오는 편집이 같은 동작을 다시 깨지 못하게 한다. 다만 Meta 가 밝힌 성과는 숫자가 거의 없는 자기 보고라서, Meta 글에서 바로 가져다 쓸 수 있는 것은 진단과 시험을 엮은 구조다. 효과가 얼마나 나는지는 자기 도메인에서 다시 재 봐야 안다.

tl-dr

기억할 것과 할 일

교정 하나는 원인이 있는 층을 먼저 가린 뒤 그 층의 파일만 고치고, 자동 시험과 사람 검토를 모두 통과해야 반영된다. 이 루프를 빌려 쓰려면 run 마다 어떤 파일을 썼는지 남기는 일부터 시작한다.

  • 분리도메인의 입장은 knowledge 파일에, 분석 절차는 recipe 에 적고 둘을 섞지 않는다. 그래서 실패 하나를 두 층 가운데 한 곳에 돌릴 수 있다 (03)
  • 진단원인은 “agent 가 가진 자료로 정답에 닿을 수 있었나” 하나로 가린다. 닿을 수 있었는데 틀렸으면 recipe 만 고치고 knowledge 파일은 그대로 둔다. 자료에 정답이 없었으면 knowledge 파일을 더하고 routing index 를 갱신하며 recipe 는 그대로 둔다. 전문가끼리 정답이 갈리면 편집 없이 사람 논의로 넘긴다 (03)
  • 할 일run 마다 어떤 파일을 언제 불러 어떻게 썼는지 knowledge manifest 로 남긴다. 원인을 가리는 시험의 입력이 이 기록이다 (03)
  • 할 일Meta 의 첫 시도는 전문가가 정보를 건넸는지 방향을 틀었는지로 원인을 나눴는데, 결론을 고치는 교정 하나가 세 원인 중 어느 것이든 될 수 있어서 실패했다. 그러니 대화의 형태로 원인을 나누는 방식은 처음부터 피하고 위의 시험을 쓴다 (03)
  • 관문편집은 linter 와 diff 만 받는 적대적 리뷰어를 거친 뒤, 원래 장면의 blind replay 와 도메인 회귀 benchmark 를 지나야 한다. 그다음 사람이 PR 로 검토해야 반영된다 (03)
  • 회귀 0건Meta 가 보고한 회귀 0건은 루프가 교정할 때마다 키워 온 그 suite 에서 잰 결과다. 정답이 여럿일 수 있는 도메인에서는 LLM judge 가 “certain criteria” 로만 적힌 기준으로 pass/fail 을 매기므로, 같은 보장을 원하면 판정 기준부터 직접 정해야 한다

자기 개선 루프

교정이 지식 파일 편집이 되기까지

루프는 교정마다 근본 원인을 먼저 진단하고, 그 원인을 고치는 최소 편집을 컴파일한다. 편집은 replay 와 회귀 시험을 통과해야 PR 로 사람 앞에 가고, 반영되고 나면 그 실패 장면이 회귀 시험 사례가 된다.

  • 입력입력은 SME 가 checkpoint 에서 agent 의 중간 추론을 확인하거나 고치거나 방향을 튼 대화 trace 다. agent 가 모호한 지점에서 전문가에게 넘긴 escalation 도 입력이 된다
  • 진단교정에서 의미 있는 신호를 모두 뽑고, 같은 run 의 knowledge manifest(어떤 파일을 언제 불러 어떻게 썼는지)를 옆에 둔다
  • 진단실제 knowledge 파일을 열어 agent 가 가진 자료로 정답에 닿을 수 있었는지 묻는다. 닿을 수 있었는데 틀렸으면 recipe 문제로 본다. 자료에 정답이 없었으면 knowledge gap 으로 본다. 전문가끼리 정답이 갈리면 ambiguity 로 보고 사람 논의로 넘긴다
  • 컴파일진단된 이슈 하나를 최소 파일 편집으로 옮긴다. 이때 sub-agent 들이 병렬로 편집의 영향을 따지는데, 살피는 것은 cross-reference, 기존 입장과의 충돌, token 예산, test coverage, 중복 위험이다. 파일마다 frontmatter 에 적힌 depends_on 과 referenced_by 를 따라가면 영향 범위가 나온다
  • 컴파일별도 agent 가 새 context 에서 편집 이유를 모른 채 diff 만 받아, 새로 생긴 모순과 깨진 edge case, 약해진 입장을 찾는다
  • 컴파일linter 가 끊긴 cross-reference, 파일 크기 예산 초과, id 충돌, 의존 cycle 을 잡는다. 확률이 끼지 않는 검사라 결과는 통과와 실패 둘 중 하나다
  • 평가피드백이 나온 원래 장면에서 agent 를 시험인 줄 모르게 다시 돌린다. 새 출력은 별도 judge 가 무엇이 바뀌었는지 모른 채 원래 피드백에 비춰 판정하고, 떨어지면 다시 컴파일한다
  • 평가도메인 benchmark(대개 Q&A 쌍)를 병렬 독립 세션으로 돌려 회귀를 찾는다. 회귀가 나오면 어디서 회귀했는지와 원래 이슈, 시도한 수정을 담은 prompt 로 다시 컴파일한다
  • 반영결과물은 audit trail 이 붙은 PR 이다. 그래서 사람은 날것의 실패를 붙잡고 디버깅할 필요 없이, 이미 증명된 수정을 검토하면 된다. 승인되어 반영되면 원래 실패 장면과 검증된 정답이 회귀 suite 에 자동으로 더해진다

교정의 원인은 대화의 형태만 봐도 가를 수 있을 것처럼 보인다. Meta 의 첫 시도도 그렇게 해서, 전문가가 정보를 건네면 knowledge gap 으로, 방향을 틀면 절차 문제로 분류했다. 그런데 결론을 고치는 교정 하나가 knowledge gap 일 수도, recipe 결함일 수도, 진짜 모호함일 수도 있어서 대화의 형태로는 원인을 가릴 수 없었다. 그래서 지금은 진단에서 신호 추출과 원인 분류를 떼어 놓는다. 신호를 먼저 다 뽑아 두고, 그다음 agent 가 실제로 읽은 파일을 열어 정답이 거기 있었는지를 본다.

모호한 교정 말고도, Meta 글이 동작을 정해 두지 않아 루프를 빌려 쓰는 쪽이 직접 정해야 하는 곳이 있다.

  • 재시도Meta 글은 replay 나 회귀 시험에서 떨어지면 다시 컴파일한다고만 설명한다. 재시도를 몇 번까지 할지, linter 나 적대적 리뷰어가 막은 편집을 어디로 보낼지는 빌려 쓰는 쪽이 정해야 한다. 재시도 상한을 두고, 끝내 통과하지 못한 교정은 사람에게 넘기는 길을 만들어 둔다
  • 자료의 범위원인 시험이 묻는 “자료”가 그 run 에 불러온 파일만인지 지식 기반 전체인지는 Meta 글에 정해져 있지 않다. 이 차이는 정답이 불러오지 않은 파일에 있었을 때 드러난다. 그때는 단계마다 불러올 파일을 정하는 recipe 와 적용할 파일을 고르는 routing index 가 둘 다 원인 후보가 된다. 그래서 이 경우를 어느 층에 돌릴지 미리 규칙으로 정해 둔다
  • 입장 변화Meta 는 전문가 입장이 계속 바뀐다고 쓴다. 그런데 옛 입장을 담은 회귀 사례를 suite 에서 내리는 방법은 글에 나오지 않는다. 그대로 두면 입장을 바꾸는 교정이 자기가 남긴 옛 사례에서 떨어져 재컴파일을 돈다. 그래서 사례를 퇴역시키는 길을 따로 마련해야 한다
첨언: 원문

네 단계 「The Self-Improvement Flywheel」: “Every expert correction moves through four phases: Diagnose expert feedback into actionable issues with their root cause. Compile issues into minimal verified edits. Validate that fixes work without regressions. Have domain experts review them.” 그림의 단계 이름은 Diagnosis, Compilation, Evaluation, Landing And Enrichment 이고, 사람 검토를 뜻하는 상자는 없다.

진단 「Diagnosis: Attributing Each Correction to a Root Cause」: “This heuristic failed because conversational form is a poor proxy for root cause. An expert correcting a conclusion might be exposing a knowledge gap, a recipe flaw, or a genuine ambiguity.” “First, extract every substantive signal from the expert alongside the agent’s full knowledge manifest (every file loaded, when, and how used). Second, read the actual knowledge files and apply a single attribution test: Could the agent have reached the correct conclusion from its source materials?” “If the materials contained the right answer but the agent still erred: recipe problem. If the materials did not contain the right answer: knowledge gap. If experts themselves disagree on the right answer: ambiguity, flagged for human discussion.”

적대적 리뷰 「Compilation: Surgical Multi-Agent Edits」: “A separate agent, running in a fresh context with no knowledge of the improvement rationale, receives only the proposed diffs to the knowledge base.”

평가 「Evaluation: Proving the Fix Works」: “The agent does not know it is being tested. A separate judge evaluates the new output against the original expert feedback without knowing what was changed. This deliberately blind design prevents confirmation bias. If targeted replay fails, compilation is retried.” “For analytical domains whether there might be multiple correct answers, an independent LLM judge gives each test case a pass/fail based on certain criteria.” “If regression testing fails, compilation is retried with an updated prompt describing where the agent regressed, along with the original issue and attempted fix.”

반영 「Landing and Enrichment: Compounding Returns」: “A human expert reviews a proven fix rather than debugging a raw failure. Once approved and landed (the knowledge file or recipe is updated), the original failing scenario and its validated correct answer are automatically added to the regression test suite.”

원인을 가리는 시험이 knowledge manifest 를 입력으로 받으므로, 이 루프를 빌려 오려면 run 마다 manifest 를 남기는 일부터 한다.
