## 1. 결론

**문제는 번역투가 아니라 압축체다.** 고전적 번역투 지표(`~에 의해`, `~를 통해`, `~에
있어서`, 이중 피동)는 이미 사람 글보다 낮다. 대신 사람 글에는 거의 없는 세 가지가 문서를
채운다. 명사를 가운뎃점(·)과 `의`로 엮은 명사구 사슬, `~라는 뜻은 아니다` 류 면책 문장, 다섯
문장 중 하나꼴인 부정 종결. 이 세 가지가 독자에게 조사를 머릿속에서 끼워 넣고 문장 사이
인과를 스스로 세우게 만든다.

**이 압축체는 2026-08-28~30 에 산문 게이트가 들어온 뒤 생겼다.** 게이트가 세는 항목(연결어미
뒤 쉼표, 것이다, 지시대명사, ~에 대한, ~들)은 0 근처로 떨어졌고 사람 범위 아래로 내려갔다.
세지 않는 항목(가운뎃점, 명사구 사슬, 면책)은 10~30배 늘었다. 측정한 것만 좋아지고 측정하지
않은 곳으로 문제가 옮겨 간 전형적인 Goodhart 다.

**검증 루프는 정확도를 올리지만 문체를 방어적으로 만든다.** 렌즈 B/D 가 "이 수치가 뜻하는
범위"를 묻고, 저자는 주장 옆에 면책 문장을 붙이는 것으로 답한다. 렌즈 C 는 매 라운드 무언가를
찾아야 하는 위치에 있고, 찾은 것은 게이트 지표를 더 내리는 방향으로 고쳐진다. 문체 렌즈가
가독성을 올린다는 근거는 이 저장소의 `docs/method-provenance.md` 자신이 부정한다 (한국어
평가자 간 자연스러움 일치도 ICC .091).

**지시문의 영어 문체가 한국어로 전이된다.** 스킬 본문은 잠언체다 ("Plain is the goal;
simplified is not"). `research-doc/SKILL.md` 한 파일에 `is not` 이 20회다. 문서는 그 리듬을
한국어로 복제한다: "슬로건은 수사가 아니다", "화제성과 설계의 차별성은 같은 질문이 아니다",
"교체 가능성과 교체의 난이도는 다른 문제다". `prose-ko.md` 는 `~습니다` 로 쓴 지시가 그
어미를 부른다고 이미 적어 두었는데, 같은 원리가 문장 구조에도 작동한다.

## 3. 어디서 생기나

### 3.1 규칙의 수

저자 컨텍스트가 한 번에 드는 지시문은 약 10,200단어다 (source + doc + prose-ko + visual +
paper/oss 하나 + AGENTS). 굵은 글씨로 이름 붙은 규칙만 prose-ko 33, visual 20, oss 11,
SKILL 9 이고, 게이트 규칙이 check-doc 29, check-prose 11, check-claims 21 이다.
`docs/method-provenance.md` 는 "약 80개 동시 규칙에서 준수가 무너진다"는 논문을 인용해
두었다. 저자는 이미 그 근처에서 쓰고 있다.

### 3.2 삭제 규칙의 합성

prose-ko 의 규칙은 대부분 "빼라"다. 연결어미 뒤 쉼표를 빼고, 것이다·지시대명사·~에 대한·~들을
빼고, 잉여를 빼고, 문단마다 주장 하나만, 결론을 앞에. 각각은 옳다. 합치면 절을 잇는 수단이
사라지므로 모델은 절 대신 명사구를 쌓고, 접속 대신 마침표를 찍고, 인과를 독자에게 넘긴다.
`hanlint` 가 `factListParagraph` 라고 부르는 형태다: "쉬운 낱말을 골라도 사실만 나란히 놓으면
읽히지 않는다."

이 성향은 모델에 이미 있다. Reinhart 등 (PNAS 2025) 은 instruction-tuned 모델이 사람보다
명사화를 1.5~2배 쓰고 크기가 커져도 사라지지 않는다고 쟀다. 삭제 규칙은 그 성향을 억누르는
게 아니라 출구를 명사화 하나로 좁힌다.

### 3.3 쉼표 규칙의 눈금

`prose-ko.md` 의 "사람 4~13%" 는 KatFishNet 이 형태소 분석으로 잰 값이다. 이 저장소의
어절 끝 근사로 같은 사람 글을 재면 30~38% 가 나온다 (2.2절). 게이트 도입 전 문서는 36~38%
로 사람 글과 같은 자리에 있었고, 게이트가 그것을 17% 로, 최근 문서는 0~2% 로 끌어내렸다.
`method-provenance` 는 "절대값을 논문 수치 옆에 놓을 수 없다"고 적고도 그 밴드를 목표로
썼다. 규칙은 문서를 사람 범위 밖으로 반대쪽으로 밀어냈다.

### 3.4 검증 루프

`research-chain.js` 는 초안 1 + 렌즈 A/B/C 3 + D 1 + (수정 + 재검증) × 최대 3 = 최대 11회
에이전트 호출이다. PR #45 본문은 A3/B4/C2/D1 을 적었으니 워크플로 밖에서도 렌즈를 통째로
다시 돌렸다. 라운드·시간·렌즈별 발견 수는 어디에도 저장되지 않는다 (`fixRounds` 는 반환값에만
있다). 그래서 "너무 오래 걸린다"를 수치로 확인할 길이 없다.

문체에 미치는 효과는 2.2절의 면책·부정 종결 지표가 보여 준다. 렌즈 B/D 는 "이 수치의 범위가
무엇인가"를 묻고, 그 답이 문장 끝의 `~라는 뜻은 아니다` 로 붙는다. 렌즈 C 는 매 라운드 발견을
내야 하고, 발견은 게이트 지표를 더 내리는 쪽으로 고쳐진다.

문헌은 이 구조의 반을 지지하고 반을 부정한다. Kamoi 등 (TACL 2024) 은 프롬프트한 LLM 의
피드백만으로 자기 교정이 성공한 사례가 없고, **신뢰할 수 있는 외부 피드백**이 있을 때만
된다고 정리했다. `check-claims.mjs` 와 렌즈 B 의 수치 대조는 외부 피드백이다. 렌즈 A/C/D 의
판단은 프롬프트한 LLM 피드백이다. Smit 등 (ICML 2024) 은 다중 에이전트 토론이 self-consistency
를 안정적으로 넘지 못한다고 쟀다. 그리고 `method-provenance` 가 인용한 arXiv:2601.19913 은
한국어 평가자들이 LLM 한국어를 루브릭에서 더 높게 주면서 "기계 같다"고 따로 보고했고 자연스러움
항목의 평가자 간 일치가 ICC .091 이라고 했다. 사람도 못 맞추는 항목을 렌즈에 맡기면 소음이다.

### 3.5 지시문의 문체

스킬 여섯 파일에서 `is/are/does not` 이 71회다. "X is not Y. Z is." 꼴의 잠언이 단락마다
있다. 모델은 한국어를 쓸 때도 그 틀을 유지한다. `~가 아니라` 는 게이트가 세기 시작한 뒤
줄었지만, `아니다` 로 끝나는 문장은 그대로 남아 부정 종결 18% 가 됐다.

  사후 재작성 규칙으로 옮겼다. 사후 패스 방식이고 생성 시 규칙이 아니다.
- textlint `preset-ja-technical-writing`: 문장 100자 상한, 조사 중복은 예외 목록 포함, 규칙마다
  severity 를 따로 둔다. 일본어 기술 문서 린터가 하드 블록보다 경고와 예외 목록으로 운영된다는
  점이 참고가 된다.
- 한국어 커뮤니티 (brunch @maven, 2026-06): 주어·목적어 생략, 어순 변화, 문장 길이 섞기를
  프롬프트로 지시. 전후 예시나 측정은 없다.

### 4.3 검증 루프 문헌

- Kamoi 등 (TACL 2024): 외부 피드백 없는 자기 교정은 근거 없음.
- Smit 등 (ICML 2024): 다중 에이전트 토론 ≈ self-consistency.
- arXiv:2601.19913 (`method-provenance` 인용): 한국어 자연스러움 평가 ICC .091.
- Anthropic 의 multi-agent research 글이 다중 에이전트가 채팅 대비 약 15배 토큰을 쓴다고 적은
  것으로 기억하나 이번 세션에서 열어 확인하지 않았다.

조사에서 빠진 것: 검색 8건과 페이지 3건만 열었다. 처음 띄운 조사 에이전트 4개와 생성 실험
6개는 비용 때문에 취소했다. 국립국어원 공공언어 지침, 토스·카카오 문서 가이드, Korean LLM
작문 벤치마크(KoMT-Bench 등)는 열지 않았다.

## 5. 개선 아이디어

근거가 있고 싸게 확인할 수 있는 순서다.

**A. 눈금을 사람 기술 문서 프로파일로 바꾼다.** 지금 게이트는 0건 규칙 11개와 한도 없는 밀도
8개다. 2.2절의 사람 86편(또는 hanlint 의 390편)으로 종류별 백분위 밴드를 만들고
`check-prose.mjs --counts` 에 사람 중앙값·90 백분위 열을 붙인다. **밴드는 양방향**이어야
한다. 쉼표 0%, `~를 통해` 0건, `~들` 0건은 사람 글이 아니다. 새 지표 세 개를 더한다:
가운뎃점 밀도, 명사 사슬(`euiChain`/`nounPile`), 면책·부정 종결 비율. 이건 규칙 추가가 아니라
기존 밀도표의 열 추가다.

**B. 삭제 규칙을 예시 우선으로 바꾼다.** prose-ko 의 ✗/✓ 쌍은 대부분 한 문장이다. 절이 이어지고
쉼표가 자리를 찾고 문장 길이가 섞이는 **사람이 쓴 한다체 문단 두세 개**를 register 예시로 앞에
둔다 (저작권 때문에 블로그 문단을 그대로 넣지 말고, 사람이 직접 쓴 문단을 쓴다). 그리고
"명사를 ·로 잇지 말고 동사로 편다", "한계는 별도 면책 문장 대신 주장의 조건절로 넣는다"
두 줄을 넣는다. 규칙 수는 늘리지 않고 삭제 규칙 두어 개를 이 예시로 대체한다.

**C. 지시문의 잠언체를 뺀다.** AUTHORING.md 에 한 줄: 지시문은 그것이 금지하는 문체로 쓰지
않는다. `is not` 대구를 평서로 풀어 쓰는 것만으로도 전이가 줄어드는지 D 의 실험으로 잰다.

**D. 문체 교정을 검증 루프 밖으로 뺀다.** 렌즈 C 의 문체 부분을 없애고 (구조·참조·접근성
검사는 남긴다), 대신 저자 컨텍스트 마지막에 **읽기 패스 한 번**을 둔다: A 의 밀도표를 보고
사람 밴드 밖인 지표만 고친다. hanlint 의 `spec → 쓰기 → 검사` 나 im-not-ai 의 `사전 점수 →
경로 → 재작성 → 수렴 게이트` 가 같은 구조다. 반복 라운드는 수치·인용(렌즈 B + check-claims)
에만 적용한다.

**E. 검증 라운드를 줄인다.** `MAX_ROUNDS` 를 1로 두고, 두 번째 라운드는 재검증이 낸
`newMustFix` 가 수치·인용·방향 오류일 때만 연다. A/D 는 한 번, D 는 sonnet 그대로.
Kamoi 의 결론대로 외부 피드백이 있는 검사만 반복할 가치가 있다.

**F. 텔레메트리를 남긴다.** `research-chain.js` 가 라운드 수, 렌즈별 발견·기각 수, 단계별
소요 시간을 `.research/<slug>/notes/run.json` 에 쓴다. "너무 오래 걸린다"와 "라운드 2 가
무엇을 찾았나"를 다음부터는 숫자로 말할 수 있다.

**G. 생성 실험 (승인 후).** 같은 fact sheet 로 조건 세 개 (현재 prose-ko / B 의 예시 우선
지시 / 예시 + 사람 문단) × 3회를 **sonnet** 으로 돌리고 A 의 지표로 비교한다. 9회 호출이고
출력은 700자씩이다. 파일은 `/tmp/pilot/` 에 준비돼 있다 (FACTS.md, TASK.md, COND-M.md,
EXEMPLAR.txt).

**H. 사후 humanize 패스 실험.** 최근 문서 두 편에 hanlint primer 또는 im-not-ai 를 저자
컨텍스트에서 한 번 적용한 판과 원판을 사용자가 블라인드로 읽고 고른다. 수치 오류가 생기는지는
check-claims 로 잡는다.

**하지 말 것.** 규칙을 더 넣어 해결하지 않는다. 규칙 수 자체가 원인의 일부다. 사람 밴드 수치를
다른 측정법의 수치와 비교하지 않는다 (3.3절). 영어로 쓰고 번역하는 경로는 명사화를 더
늘릴 가능성이 높아 권하지 않지만 재 보지는 않았다.
