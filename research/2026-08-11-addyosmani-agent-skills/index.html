addyosmani/agent-skills: 강제는 산문에 맡기고, CI 는 스킬 자체에 건다

SKILL.md 24개가 프론트매터에 name 과 description 만 쓴다. Claude Code 가 스킬에 주는 필드는 20개인데 그중 2개다. 하네스가 주는 강제 수단을 전부 포기했고, 그 자리를 145행짜리 변명 반박표와 카탈로그 전체를 CI 에 거는 eval 이 대신 메운다.

tl-dr

요약. 스킬 본문의 규율은 이웃 팩에도 있고, 카탈로그를 검사하는 CI 만 이 팩의 것이다

스킬 본문에 담긴 규율은 다른 팩에도 있다. 없는 건 카탈로그 24개를 통째로 결정론적 검사에 거는 층이다. 대신 이 팩은 하네스가 제공하는 실행 시점 강제 수단을 하나도 쓰지 않는다.

  • 1Claude Code 가 받는 프론트매터 20개 중 2개만 쓴다. 24개 전부 name 과 description 뿐이고, allowed-tools, disable-model-invocation, context: fork 는 한 장에도 없다.
  • 2hardening 은 코드가 아니라 문장으로 걸려 있다. 프롬프트 인젝션 방어는 SKILL.md 24개 중 9개에 실제로 들어 있지만 전부 산문이다. 도구 권한 게이트도, 컨텍스트 격리도 프론트매터에 없다.
  • 3기계 검사는 한 층 위에 있다. 스킬 실행을 검사하는 대신 스킬 카탈로그를 검사한다. description 이 사용자 어휘를 담는지, 두 스킬이 라우팅에서 충돌하는지를 CI 가 막는다.
  • 4트렌딩은 이 저장소가 아니라 분류가 오르는 것이다. 일별 star 증가를 보면 어댑터 커밋 날이 그 주의 최저점이고, 같은 날 다른 agent skills 저장소들이 함께 오른다.

스킬 본문의 조언이 실제로 좋은 조언인지는 판정하지 않는다. 코드를 읽어서 알 수 있는 건 규율이 어떤 형태로 걸려 있는지까지다.

problem

문제 정의. 에이전트는 최단 경로로 수렴하고, 스펙과 테스트가 그 경로에서 먼저 빠진다

README 가 스스로 밝히는 문제는 하나다. 그런데 이 저장소가 실제로 없앤 수작업은 두 번째 문제 쪽에 가깝다. 팀이 쓰는 에이전트가 바뀔 때마다 같은 규율을 새 형식으로 다시 쓰는 일이다.

AI coding agents default to the shortest path - which often means skipping specs, tests, security reviews, and the practices that make software reliable.README.md:389

첫 번째 문제의 처방은 새롭지 않다. 스펙 먼저, 실패 테스트 먼저, 머지 전 리뷰. 사람이 지키는 규율을 문서로 옮긴 것이고, 같은 처방을 담은 팩이 이미 여럿 있다.

두 번째 문제가 이 저장소의 형태를 결정한다. 최상위 어댑터 디렉터리가 7개다. .claude, .claude-plugin, .gemini, .codex-plugin, .opencode, .agents, commands 가 각각 다른 하네스를 향한다. docs/comparison.md:26 이 세는 지원 대상은 11곳인데, 디렉터리 없이 문서만으로 지원하는 하네스가 있어서다. 스킬 본문은 하나고, 그걸 각 하네스가 읽는 위치에 놓는 어댑터 디렉터리만 늘어난다. 이 구조가 성립하려면 스킬 본문이 어떤 하네스에도 종속되면 안 된다. 5장이 그 대가를 다룬다.

"에이전트가 스펙을 건너뛴다"는 진술 자체는 이 저장소가 측정한 것이 아니다. README 의 주장이고, 저장소 안에 이를 뒷받침하는 측정은 없다.

Claude Code 는 SKILL.md 프론트매터에서 20개 필드를 받고, 그중 6개는 하네스를 가리지 않는 이식 규격에 들어 있다. agent-skills 는 24개 전부 2개만 쓴다. 안 쓴 18개 중 4개는 이식 규격 안에 있어서, 이식성만으로는 설명되지 않는다.

hardening

산문으로 건 강제. 인젝션 방어는 실재하지만 전부 문장이다

프롬프트 인젝션을 다루는 팩은 드물다. untrusted 데이터 doctrine 을 담은 SKILL.md 가 24개 중 9개, 공유 체크리스트가 7개 중 2개다. 다만 방어 수단이 전부 에이전트가 읽고 따르기를 기대하는 텍스트고, 그것이 5장의 선택에서 직접 따라 나온다.

신뢰 경계를 그은 곳 (9개 중 넷)

browser-testing DOM, console, network 응답 전부 untrusted. --autoConnect 는 로그인된 프로필 전체가 blast radius 라고 명시한다.
debugging 에러 메시지와 CI 로그도 데이터지 지시가 아니다.
source-driven fetch 한 공식 문서도 untrusted 입력이다.
api-and-interface-design 서드파티 응답을 그대로 신뢰하지 않는다.

실제 공격 표면을 막은 곳

doubt-driven 크로스모델 CLI 를 --sandbox read-only 로 부르고, artifact 를 셸 인자로 보간하지 말고 stdin 으로 넘기라고 한다. artifact 안에 백틱이나 $(...) 가 있으면 그대로 실행되기 때문이다.
security-checklist OWASP LLM01(Prompt Injection), LLM05(Improper Output Handling)를 항목으로 매핑한다.

그런데 같은 체크리스트가 이렇게 쓴다.

Prompt injection assumed; permissions enforced in code, not in the system promptreferences/security-checklist.md:154

이 문장은 사용자가 작성할 코드를 향한 조언이다. 다만 같은 기준을 팩 자체에 대면 어긋난다. 이 팩의 집행 수단은 100% 시스템 프롬프트 텍스트다. 스킬을 건너뛰는 에이전트를 막는 코드 경로는 저장소에 없다. 5장에서 allowed-tools 와 context: fork 를 포기한 결과이고, 그 대신 이 팩이 기계에 맡긴 건 한 층 위, 7장의 대상이다.

인젝션 방어 문장이 실제 공격에서 작동하는지는 읽어서 알 수 없다. 저장소 안에 프롬프트 인젝션 시나리오를 돌리는 eval 은 찾지 못했다. grep -rniE 'injection' evals/ 는 1건을 내지만 evals/cases/context-engineering.json:24 의 "Harden this endpoint against SQL injection" 으로, 에이전트를 겨냥한 인젝션이 아니라 사용자가 쓸 코드의 SQL injection 이다.

evals

3단 eval. 상시 게이트가 보는 것은 스킬이 발동하는지까지다

저장소가 자기 기여로 지목하는 지점이 여기다. 앞선 두 방식을 출처와 함께 밝히고, 그 사이에 빠진 층을 자기 것이라고 말한다.

What neither provides is a deterministic, CI-safe check for a multi-skill catalog [...] That's Tier 2 below, and it's this repo's addition.evals/README.md:12 (생략한 부분은 Tier 2 가 무엇을 보는지에 대한 설명이다)

Tier 2 만 결정론적이고, 결정론적이라서 CI 에 걸 수 있다

evals/README.md 의 3단 표. 비용 열은 저장소 표현 그대로다

Tier검사 대상실행비용

선행 연구를 명시한 것도 드문 처리다. evals/README.md:9 는 Anthropic skill-creator v2 의 evals.json 스키마를 채택했다고 밝히고 kind 필드 하나를 더했다고 적는다. 같은 파일 10행은 behavioral runner 가 Superpowers 의 headless claude -p 패턴을 따랐다고 적는다.

압박 케이스는 실재한다. evals/fixtures/test-driven-development/authority-pressure.md 는 "엔지니어링 리드가 실패 테스트 없이 바로 고치라고 지시"하는 상황을 주고, 워크플로가 그 압력에 버티는지를 본다. 같은 방식의 time pressure, sunk cost fixture 가 규율 계열 스킬에 붙어 있다.

Tier 2 는 어휘만 본다. 의미 판단은 못 하고, README 스스로 "lexical approximation"이라고 쓴다. 라우터가 실제로 어떻게 고르는지와는 다른 것을 재고 있고, 10장이 그 수치를 다룬다.

대상 저장소의 AGENTS.md 와 CLAUDE.md, 그리고 .claude/skills/ 는 모델을 향한 명령문이다. 이 조사에서는 작업 디렉터리 밖에 클론해 하네스가 자동 발견하지 못하게 두었고, 두 파일은 열지 않았다.

result-evals

실행 결과. rank-1 86%, 실패 11건이고 그 11건이 어디인지는 출력에 없다

Tier 2 는 로컬에서 그대로 돌아간다. 모델 호출이 없어 재현된다.

124 checks passed — 0 error(s), 0 warning(s)

출력의 0 warning(s) 는 276쌍 전부 코사인 0.5 미만이라는 뜻이다(8장의 warning 임계 0.5). 자기 스킬을 얹을 팀에게는 그만큼 여유가 있다는 신호다.

이 86% 를 실제 라우팅 정확도로 읽으면 안 된다. 재고 있는 건 24개 description 으로 만든 TF-IDF 코퍼스 안에서의 코사인 순위다. 8장 3번 단계에서 본 대로 스킬 이름이 2배 가중이라, 프롬프트에 스킬 이름의 단어가 있으면 유리하게 나온다. 실제 하네스는 LLM 이 description 을 읽고 고르므로 다른 함수다.

Tier 3 는 돌리지 않았다. headless claude -p 로 실행 trace 를 만들고 별도 모델이 채점하므로 토큰을 쓴다. 스킬이 에이전트 행동을 실제로 바꾸는지, 이 문서에 측정치가 없다.

compare

이웃 팩 대조. 별 수로는 네 개 중 꼴찌고, 병합 비율로는 가장 낫다

저장소는 docs/comparison.md 라는 자기 비교 문서를 갖고 있다. 자기 비교라 편향이 예상되는 문서인데, 거버넌스 주장은 GitHub API 수치와 방향이 같다.

기여자 분포는 solo 와 커뮤니티 사이다. 커밋 419개 중 Addy Osmani 229, Federico Bartoli 34, Joan Leon 35 로 상위 3인이 298개, 약 71% 다. 나머지 67명이 121개를 나눠 갖는다. merge 커밋 135개는 외부 PR 이 실제로 들어오고 있다는 뜻이다. 저자 수는 세는 기준에 따라 다르다. git 원장은 70명(이름 표기 정규화 후), GitHub contributors API 는 59명이다. API 는 GitHub 계정에 연결되지 않은 커밋을 빼기 때문이다.

세 이웃 저장소의 코드는 열지 않았다. 별과 PR 수만 대조했으므로 스킬 내용이나 eval 층의 유무는 비교하지 않은 것이고, "왜 superpowers 가 아니라 이것인가"에는 이 장이 답하지 못한다. docs/comparison.md:30 은 star 와 채택 수치를 일부러 뺐다고 밝힌다. 위 표는 그 문서에 없는 대조다.

provenance

출처와 신뢰. Google 공식이 아니고, 그 사실이 어디에도 적혀 있지 않다

저자가 Google Chrome 소속이고 README 가 "Google's engineering culture" 를 앞세우기 때문에 조직 산출물로 읽히기 쉽다. 확인해 보면 신호가 전부 반대를 가리킨다. 부인하는 문구도 없다는 점이 이 장의 요지다.

즉 Google 직원이 만든 개인 프로젝트이고, Google 이 공개한 엔지니어링 자료를 재료로 썼다. 저장소는 이걸 속이지 않는다. Team 표에 소속을 적지 않고 개인 계정과 개인 도메인을 쓴다. 다만 부인도 하지 않아서, 저자의 직함과 README 의 "Google's engineering culture" 가 겹치면 조직 승인으로 읽힐 여지가 남는다. 팀에 제안할 때 "Google 방식"과 "Google 공식"을 갈라 말해야 하는 이유다.

개인 프로젝트라는 게 품질 판정은 아니다. 11장에서 본 대로 병합 125건에 미처리 50건으로 처리율은 이웃 넷 중 가장 높다. 다만 bus factor 는 좁다. 커밋 419개 중 저자 1인이 229개, 상위 3인이 298개(71%)다. 이 사람이 멈추면 팩도 멈춘다고 보는 편이 안전하다.

reach

하네스 확장. 이 저장소가 아니라 "agent skills" 분류 전체가 같이 오른다

일별 star 증가를 실측하면 어댑터 커밋 날이 정점이 아니다. 6월 10일은 그 주에서 가장 낮고 정점은 이틀 뒤다. 같은 날 트렌딩한 다른 저장소들을 보면 오르는 것은 이 저장소가 아니라 분류다.

리포트가 매번 같은 말을 한다. 06-10 "explosive surge in AI agent skills and harnesses", 06-12 "Agent Skills Marketplace is the breakout phenomenon today. 상위 5개 중 3개가 agent skills 이고 세 프로젝트가 그날 합계 7,000 이상", 07-08 "the aftermath of Anthropic's Claude Code launch and OpenAI's Codex evolution", 08-09 "google/skills, addyosmani/agent-skills, mattpocock/skills 이 같은 날 올랐다". 오르는 것은 이 저장소 하나가 아니라 분류다.

그리고 분류가 뜨는 시점은 주요 코딩 에이전트 하네스에 사건이 있을 때다. 6월은 Antigravity 이주기(2026-05-19 공개, Gemini CLI 2026-06-18 은퇴), 7월은 Claude Code 런칭과 Codex 개편, 8월은 google/skills 등장이다. 어댑터 커밋도 같은 사건에 대한 반응이다. 즉 커밋과 트렌딩은 공통 원인의 두 결과로 읽는 편이 자료에 맞고, 커밋이 트렌딩을 만들었다고 볼 근거는 위 차트가 오히려 약화시킨다.

저자 쪽 홍보는 5주 앞이다

블로그 글 2026-05-03, 이튿날 Hacker News 프론트 페이지에 376 points / 212 comments. 당시 27K stars 였다. O'Reilly Radar 재게재가 05-27.

다만 6월 급등과 5주 간격이라 직접 원인으로 보기 어렵다. 저장소 URL 자체는 2026-04-07 에 HN 에 올랐다가 2 points 로 묻혔다.

같은 날 겹친 다른 사건

06-10 에는 태그 0.6.2 도 찍혔다. 어댑터 추가와 릴리스를 이 날짜만으로 분리할 수 없다.

07-08 쪽은 태그가 비껴가지만(0.6.3 07-02, 0.6.4 07-12), evals/ 가 07-03 에 들어왔다. 3단 eval 이라는 차별점이 닷새 전에 생겼다.

이 시계열은 제3자 일간 집계 하나에서 나온 것이고 산출 방식은 공개돼 있지 않다. 이 저장소가 그 리포트에 오른 날만 값이 있어서, 오르지 않은 날의 증가량은 모른다. GitHub 이 stargazer API 를 막아 원본 곡선으로 대조하지 못했다. "분류가 같이 오른다"까지는 리포트가 직접 말하지만, 그게 왜 그 시점이었는지는 리포트의 해석을 그대로 옮긴 것이지 이 문서가 검증한 것이 아니다.

critique

해석의 한계. 문서가 말하는 컨텍스트 비용과 훅이 실제로 넣는 양이 다르다

도입 판단이 걸린 항목 중 하나에서 문서와 코드가 어긋난다. 컨텍스트 비용이다.

문서

docs/skill-anatomy.md:123

"Skills load on demand: only the skill name and description sit in context at startup."

코드

hooks/session-start.sh 는 SessionStart 마다 using-agent-skills/SKILL.md 전문 191줄을 priority: "IMPORTANT" 메시지로 주입한다. 주석이 스스로 "Injects the using-agent-skills meta-skill into every new session" 이라고 적는다.

둘 다 사실이다. 개별 스킬은 정말 on-demand 로 뜨고, 라우터 한 장만 상시로 올라간다. 다만 "startup 에는 name 과 description 만"이라는 문장을 그대로 읽으면 예산을 잘못 잡는다. 이 훅이 실제로 발동하는지는 읽어서 확정하지 못했다. .claude-plugin/plugin.json 은 commands 와 skills 만 선언하고 hooks 를 참조하지 않는다. 훅 명령 자체는 ${CLAUDE_PLUGIN_ROOT}/hooks/session-start.sh 를 가리키므로 플러그인 루트 규약에 의한 자동 발견을 전제한 것으로 보이지만, 설치해서 확인하지는 않았다.

  • 1팩의 한계. Tier 1 검사기 자신이 테스트되지 않는다. 검사기 6종 중 validate-skills.js 하나만 *-test.js 가 없다. 스킬 본문 구조를 보는 게 이 검사기이므로, 구조 게이트가 조용히 망가져도 알아챌 장치가 없다. 훅 테스트 2개는 존재하지만 어느 CI job 도 돌리지 않는다.
  • 2팩의 한계. 일부만 켜는 방법이 없다. 24개 전부 모델이 자동으로 불러올 수 있고 disable-model-invocation 은 0건이다. 6개만 원하는 팀도 나머지 18개의 description 을 매 세션 컨텍스트에 얹는다. 이 비용은 재지 않았다.
  • 3팩이 인정한 한계. 낱개 설치는 링크가 깨진다. npx skills add --skill <name> 은 저장소 루트의 references/ 를 가져오지 않는다. README 와 skill-anatomy.md 가 스스로 밝히고 이슈 #361 로 추적한다. 이 문서가 찾아낸 게 아니라 팩이 공시한 것이다.
  • 4조사의 한계. 산문 강제의 효과를 재지 못했다. 6장의 인젝션 방어와 4장의 145행 반박표가 에이전트 행동을 실제로 바꾸는지, 증거가 이 문서에 없다. 답을 낼 수 있는 건 Tier 3 뿐인데 상시 게이트가 아니고 토큰을 쓴다. 10장의 86% 도, 13장의 날짜 일치도 같은 성격이다. 코드와 이력에서 읽을 수 있는 데까지가 이 문서의 범위다.

한계를 넘어 남는 것이 하나 있다. Tier 2 는 이 팩과 무관하게 성립하는 아이디어다. 스킬을 여러 개 쓰는 팀이라면 description 끼리의 코사인 유사도에 상한을 걸어 CI 를 실패시키는 것만으로, 스킬이 왜 발동하지 않았는지 나중에 헤매는 일을 앞당겨 잡는다. 이 팩을 도입하지 않기로 해도 이 검사는 가져갈 수 있다.

adopt

도입 판단. trial. 팀 표준으로는 쓸 만하고, 보안 경계로는 쓰면 안 된다

되돌리기가 쉽고 lock-in 이 없어 시험 비용이 낮다. 무엇부터 켤지는 저장소가 docs/adoption-guide.md 에서 직접 답한다. 그린필드는 전 수명주기를 즉시, 브라운필드는 읽기 전용 스킬부터 4단계로 올리라고 한다. 아래는 그 가이드가 답하지 않는 것, 즉 켤지 말지다.

확인한 것

License MIT 전문. 예외 조항이나 서드파티 carve-out 없이 표준 문구 그대로다.
의존성 저장소에 package.json 이 없다(eval fixture 하나 제외). 감사할 의존성 트리도, 패치할 CVE 표면도 없다는 뜻이다. 툴체인은 stdlib Node 와 훅 하나의 jq 뿐이다. SessionStart 훅은 jq 를 요구하고, 없으면 INFO 를 내고 조용히 빠진다. Tier 2 를 떼어 쓰려면 Node 가 필요하다. docs/developer-onboarding.md:39 는 Node 20+, 워크플로는 24 로 돈다.
유지 상태 6개월간 커밋 419개, 태그 8개(0.5.0~0.6.6), merge 커밋 135개, 저자 70명(GitHub contributors API 기준으로는 59명). 마지막 커밋 2026-08-08.
테스트 검사기 6종 중 5종에 *-test.js 가 있고 CI 가 node --test 로 돌린다. validate-skills.js 만 테스트가 없는데, 이게 스킬 본문 구조를 보는 Tier 1 검사기다. 훅 테스트 2개(session-start-test.sh, simplify-ignore-test.sh)는 존재하지만 어느 job 도 돌리지 않는다.
CI 가 보증하는 것 job 4개 중 마지막 둘이 매 push 마다 claude plugin validate . 와 claude plugin install 까지 실제로 돌린다. 설치가 깨진 채 머지되지는 않는다는 뜻이다.

설치 경로와 남는 것

README 가 첫 번째로 권하는 경로는 npx skills add 이고, 이건 vercel-labs/skills 라는 제3자 CLI 다(README.md:45). 70+ 에이전트 지원을 실제로 떠받치는 것은 어댑터 디렉터리가 아닌 이 도구다. 공급망이 하나 더 붙는다는 뜻이고, 이 문서는 그 도구를 조사하지 않았다.

훅 중 자동으로 도는 것은 SessionStart 하나뿐이고 파일을 쓰지 않는다. .claude/sdd-cache/ 와 .claude/.simplify-ignore-cache/ 를 만드는 훅은 hooks.json 에 없고 hooks/SDD-CACHE.md:13 이 안내하는 수동 설정 opt-in 이다.

되돌리기는 플러그인 제거와 캐시 디렉터리 삭제로 끝난다. 단 이건 marketplace 설치 기준이고 npx skills 경로가 무엇을 복사하는지는 확인하지 않았다.

버전 고정 수단이 보이지 않는다. .claude-plugin/marketplace.json 의 설치 소스는 {"source":"github","repo":"addyosmani/agent-skills"} 뿐이고 ref, tag, branch 키가 없다. 같은 파일의 version: 0.6.6 은 메타데이터로 보이지만, 하네스가 그 값으로 고정하는지는 설치해 보지 않아 확정하지 못했다. 6개월에 커밋 419개인 저장소에서 규율이 산문으로 걸려 있다면, 업그레이드가 곧 에이전트 행동 변경이다. 팀 표준으로 쓸 거라면 fork 하거나 특정 커밋을 vendoring 하는 쪽을 권한다. 컨텍스트 비용도 재지 않았다. SessionStart 훅의 191줄과 description 24개가 매 세션 상시로 올라간다.

conclusion

결론. 새로운 건 스킬을 쓰는 방법이 아니라 스킬을 검사하는 방법이다

세 질문의 답은 아래 세 줄이다. 셋 다 이 팩의 새로움이 스킬 본문 바깥에 있다고 가리킨다. 본문의 규율은 이웃 팩에도 있고, 검사 층과 어댑터 층이 이 팩만의 것이다.

  • Q1Claude Skills 와의 대비는 축소 쪽이다. Claude Code 가 받는 20개 필드 중 2개만 쓰고, 이식 규격의 6개 키 중에서도 2개만 쓴다. 지원 대상 11곳에서 같은 파일이 도는 대가로 포기한 것은 Claude Code 전용 14개다. 그런데 이식 규격 안에 있어 공짜인 allowed-tools 까지 비어 있으니, 도구 권한 게이트가 비어 있는 건 이식성으로 설명되지 않는 별개의 선택이다.
  • Q2hardening 의 내용은 새롭지 않고 위치가 새롭다. untrusted 데이터 doctrine 도, 변명 반박표도 다른 곳에 있다. 없던 건 스킬 카탈로그를 결정론적으로 검사해 CI 에 거는 층이다. description 이 사용자 어휘를 담는지, 두 스킬이 라우팅에서 충돌하는지를 모델 호출 없이 막는다.
  • Q3트렌딩의 단위는 저장소가 아니라 분류다. 일별 star 증가에서 어댑터 커밋 날은 그 주의 최저점이고 정점은 이틀 뒤다. 같은 날 google/skills, mattpocock/skills 가 함께 오른다. 분류가 뜨는 시점은 코딩 에이전트 하네스에 사건이 있을 때이고, 어댑터 커밋도 그 사건에 대한 반응이다.

읽고 남는 건 트레이드오프 하나다. 규율을 하네스에 강제시키면 확실하지만 그 하네스에 묶인다. 산문에 맡기면 어디서나 돌지만 에이전트가 안 지켜도 알 방법이 없다. 이 팩은 후자를 고르고, 대신 규율이 지켜지는지가 아니라 규율이 발동하는지를 기계로 검사한다. 그 절충이 옳은지는 Tier 3 를 돌려야 알 수 있고, 그건 이 문서 밖이다.

같은 문제를 반대 방향으로 푼 사례가 이 저장소 안에 있다. LoopX: 결정론적 루프 하네스 는 규율을 실행기에 넣는다.
