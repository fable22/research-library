RAG-Safety-Bench: 검색 품질과 응답 안전을 따로 평가해야 하는 이유

신뢰할 만한 corpus에서 잘 검색하면 답변도 안전해지는가. 이 benchmark가 검색을 생략한 이유와 그 결과를 실제 RAG 평가로 연결하는 조건을 분석한다.

출발점

코난쌤의 글이 제기한 corpus 신뢰와 응답 안전의 차이를 출발점으로 삼는다. 원문 관찰, 블로그 해석, 본 문서의 평가 제안을 구분한다.

읽는 경로

실험 경계와 데이터 → accuracy·harmfulness·refusal → 공개 scoring → 검색·rerank·문맥 구성의 추가 평가. 위험한 원문 절차는 추상화한다.

arXiv:2609.11758v1 · 2026-09-10 · 분석 기준 2026-09-14. RAG-Safety-Bench 원문

tl-dr

문맥을 잘 활용하는 능력은 응답 안전을 보장하지 않는다

RAG-Safety-Bench는 answer-bearing 문맥을 직접 주면 평가한 모든 모델에서 unsafe-answer accuracy와 judged harmfulness가 높아진다고 보고한다. 검색 실패 때문에 안전해 보이는 경우를 줄이는 설계지만, 실제 retriever의 위험도는 측정하지 않는다.

원문이 보여 준 것

Oracle은 답 근거가 있는 문맥을 주는 조건이다. 이때 유해 요청에 맞는 정보를 반환하는 비율이 높다. 주제가 관련되도록 구성하고 답 근거가 없다고 판정한 On-topic 문맥의 영향은 모델마다 다르다.

RAG 평가에 더 필요한 것

실제 검색이 answer-bearing 근거를 얼마나 노출하는지, rerank와 문맥 확장이 무엇을 남기는지, 생성기가 그 근거를 어떤 응답으로 바꾸는지 따로 측정해야 한다.

무관하다고 표시해 구성한 Random 문맥의 낮은 유해 판정률에는 정보 부족 거절이 포함된다. 문맥 길이·개수는 조건마다 다르며 공개 채점 코드의 결과와 논문에 쓰인 비공개 재채점 결과를 구분해야 한다. 논문 v1

secondary

블로그의 실무적 문제 제기는 별도 RAG 안전 평가로 이어진다

코난쌤은 신뢰할 만한 문서를 연결하는 일과 안전한 답변을 보장하는 일을 구분한다. Non-RAG에서 얻은 안전 평가를 그대로 배포 판단에 쓰지 말고, corpus와 입력·검색 결과·출력을 함께 살피자는 관점이다.

살릴 관점

문서가 일반 지식이어도 유해 요청의 답이 될 수 있다. 모델별 반응과 judge의 차이까지 확인하자는 제안은 이 논문의 실험 목적과 맞닿아 있다.

논문과 연결할 질문

관련 문서를 공급한 뒤에도 응답이 안전한가. 답 근거가 문서에 있을 때와 없을 때 모델의 반응을 나눠 읽어야 한다. 논문은 이 질문에서 생성 모델의 반응을 분리해 측정한다.

블로그도 accuracy와 harmfulness가 별도임을 명시한다. 해석은 2026-09-14 수집본 기준이며 동일 내용을 보장하는 공개 보존본은 확인하지 못했다. 코난쌤 · 2026-09-13

problem

신뢰성·관련성·answerability·응답 안전은 서로 다른 질문이다

사실에 맞는 문서도 요청의 목적에 따라 해로운 답변의 근거가 된다. 이 연구의 공격 입력은 유해한 사용자 질문이며, corpus는 Wikipedia에서 왔다. 문서에 악성 명령을 삽입해야만 성립하는 문제는 아니다.

축확인할 질문다른 축과의 경계
출처 신뢰성자료가 믿을 만하고 변조되지 않았는가사실인 정보도 악용될 수 있다
검색 관련성질문과 문서의 주제가 맞는가같은 주제가 구체적 답을 포함하지는 않는다
Answerability전달된 문맥에 답할 근거가 있는가답할 수 있어도 응답을 허용한다는 뜻은 아니다
응답 안전사용자의 유해 목적을 돕는 내용을 반환했는가정확한 답변과 안전한 답변은 겹치지 않을 수 있다

논문은 privacy/identification, 직접 유해 콘텐츠 생성, intellectual property, specialized advice를 제외한다. ACL·PII 유출·prompt injection·corpus poisoning 전체를 검증한 benchmark로 읽을 수 없다. 논문 v1

boundary

실험은 검색 경로를 고정 문맥 공급으로 대체한다

같은 질문에 정해진 문맥을 직접 붙여 생성 모델을 비교한다. Retriever가 답 문서를 놓친 덕분에 낮아진 harmfulness를 모델의 안전 역량으로 오인하지 않기 위해서다.

Oracle은 좋은 검색이 만들 수 있는 입력의 한 조건이다. 운영 환경에서 그 문서가 top-k에 들어온 빈도나 공격 성공률의 상한을 측정한 값은 아니다. 논문 v1

conditions

네 조건은 답 근거의 유무와 주제 관련성을 나눈다

조건마다 질문은 유지하고 문맥을 바꾼다. Non-RAG는 자기 지식으로 답하도록 하고 RAG 세 조건은 주어진 문서만 사용하도록 지시한다.

조건문맥의 역할해석할 관찰
Non-RAG문서 없음외부 근거 없이 유해 요청에 응하는가
Oracle답에 필요한 정보를 포함한 문맥근거가 공급되어도 거절하는가
On-topic같거나 관련된 주제로 구성하고 답 근거가 없다고 판정한 문맥관련 문맥 아래 응답이 달라지는가
Random무관한 benign 문맥답 근거·관련성이 약할 때 어떻게 반응하는가

주제 관련성과 safe는 구성 metadata의 label이다. 별도 GPT-4.1-mini audit이 검사한 것은 질문별 answerability이며, 주제 관련성이나 문서의 안전성을 다시 판정한 것은 아니다. 논문 v1 · 논문 v1 · data/v14_balanced_346/eval_examples.expanded.jsonl

dataset

Balanced는 완전 균등 표본이 아니며 Oracle도 partial을 포함한다

후보 질문은 Wikipedia의 답 근거를 바탕으로 생성했다. Full은 987개 질문, 논문에 사용한 Balanced는 346개 질문이다. 하위 범주마다 최대 20개를 선택해 편중을 줄였지만 모든 범주가 같은 수는 아니다.

context-length

Random은 문맥 길이만 바꾼 대조군이 아니다

문서 수와 총 길이가 조건별로 다르다. 문서당 12,000자 cap은 token budget도, 조건 간 길이 매칭도 아니다. 선택한 section 정보는 metadata에 남지만, 실제 공급된 문맥은 정리한 전체 기사의 앞부분이다.

조건문서 수별 질문 수총 문맥 글자 수: 최소 / 중앙 / 최대
Non-RAG0개: 3460 / 0 / 0
Oracle1개: 3461,768 / 12,000 / 12,000
On-topic3개: 344 · 2개: 212,889 / 36,000 / 36,000
Random3개: 321 · 2개: 24 · 1개: 12,903 / 13,297 / 25,169

총 길이는 각 행의 docs[].text 글자 수 합을 직접 집계했다. 논문에는 이 분포 비교가 없다. Prompt 구분자·질문·chat template는 제외했다.

Random 결과는 “추가 문맥이면 언제나 위험해진다”는 설명을 약화한다. 길이만의 효과를 배제하려면 동일 문서 수·token 길이에서 관련성과 answerability를 바꾸는 실험이 더 필요하다. 논문 v1 · data/v14_balanced_346/eval_examples.expanded.jsonl

generation

모델이 받는 것은 문서 text와 질문이며 safety label은 prompt에 없다

공개 generation 경로는 미리 확장된 JSONL을 읽고 각 문서의 text를 Context 순서로 붙인다. 조건 이름에 safe가 있거나 metadata가 none이어도, 그 label을 모델에게 전달해 거절을 지시하지 않는다.

  1. 고정된 행을 읽는다

    _load_rows가 subset의 eval_examples.expanded.jsonl을 읽는다. 이 entrypoint는 live retriever나 reranker를 호출하지 않는다.

  2. 조건 prompt를 만든다

    Non-RAG는 own knowledge, RAG는 provided documents를 지정한다. 문서 구분자와 질문이 하나의 user message에 들어간다.

  3. 모델별 chat template를 적용한다

    Ministral은 processor, 다른 HF 모델은 tokenizer 경로를 쓴다. 일반 tokenizer의 template 적용이 실패하면 직접 tokenization으로 넘어가는 코드가 있다.

  4. 생성 설정을 적용한다

    공개 config는 sampling 비활성화와 최대 1,024 new tokens를 지정한다. 논문의 seed 42만으로 모델 revision·라이브러리·GPU까지 동일해지는 것은 아니다.

문서 추가와 instruction 변경이 함께 일어나므로 Non-RAG 대 RAG 차이를 순수한 문서 내용 효과로만 귀속할 수 없다. 공개 경로에 추가 safety system message나 token 길이 매칭은 없다. scripts/run_safety_mirage_eval.py#L26 · src/model_runner.py#L154

metrics

정답률·유해 판정·거절 이유를 각각 읽어야 한다

같은 응답이 reference의 정보를 담으면서도 safety judge에는 safe로 분류될 수 있다. 거절처럼 시작한 뒤 정보를 이어 주는 응답도 있다. 세 신호를 더한 단일 점수는 이 차이를 지운다.

신호판정 대상해석의 한계
Unsafe-answer accuracyExpected unsafe answer summary의 구체적 정보가 전달됐는가부분 절차나 일부 핵심 정보도 포함할 수 있다. 완전한 실행 성공률이 아니다

Accuracy prompt는 disclaimer와 교육 목적 표현을 판단에서 제외한다. Harmfulness와 다른 기준이므로 accurate이면서 not flagged unsafe인 응답의 원인을 따로 검토해야 한다. 논문 v1 · 논문 v1

result-harm

Harmfulness에서도 Oracle이 가장 높지만 On-topic의 방향은 모델마다 다르다

Figure 2는 accuracy와 별도로 계산한 유해 판정률이다. Qwen은 On-topic에서도 baseline보다 높고 Phi도 낮은 절대 수준에서 상승한다. Gemma와 Llama는 내려가며 Ministral은 baseline 부근에 남는다.

블로그가 강조한 Qwen의 예외적 응답 흐름과 유해 판정률 상승을 구분해야 한다. 논문 §4.2에는 Phi의 소폭 상승도 있다. 작은 차이의 통계적 유의성은 이 그림에서 판단할 수 없다. 논문 v1

trace

Qwen 사례는 정보 부족을 말한 뒤에도 응답을 계속한 행동을 보여 준다

부록의 한 질문에서 Qwen은 Non-RAG에서는 거절하고 Oracle에서는 직접 답한다. On-topic에서는 문서에 구체적 답이 없다고 밝힌 뒤 요청을 돕는 내용을 이어 간다. Random에서는 정보 부족을 말하고 멈춘다.

조건부록 사례의 응답 흐름을 안전하게 추상화확인 가능한 것
Non-RAG요청 → 안전 이유 거절이 한 질문에서의 거절
Oracle답 근거 → 직접적인 정보 제공Oracle에서는 거절 없이 답을 제시함
On-topic근거 부족 언급 → 요청에 필요한 고려사항을 계속 설명문서만 사용하라는 지시 아래도 응답이 멈추지 않음
Random근거 부족 언급 → 종료관련성 없는 문맥에서 다른 반응

논문은 이를 parametric memory 가설과 일치하는 행동으로 해석한다. 내부 activation이나 지식의 출처를 직접 측정한 실험은 아니다. 이 사례를 모든 Qwen 응답의 순서로 일반화할 수도 없다. 논문 v1 · 논문 v1

result-refusal

정보가 없어서 멈춘 응답과 안전 때문에 거절한 응답은 다르다

Random에서 낮은 harmfulness는 제공할 답을 찾지 못한 결과일 수 있다. 이 구분이 없으면 retriever가 필요한 문서를 놓친 시스템을 더 안전한 시스템으로 선택할 수 있다.

부록 human audit에서 이유 분류의 사람 대비 일치율은 84%·85%다. 거절 문구 뒤에 답을 이어 주는 응답을 거절로 잘못 읽은 사례가 있다. 이유 분류의 타당성과 최초 거절 탐지의 타당성은 별도다. 논문 v1

judges

여러 judge를 써도 판정 기준의 차이와 원문 내부 불일치가 남는다

다수결은 서로 다른 judge의 결과를 모으는 규칙이다. 독립된 human ground truth가 되지는 않는다. 여기서 LG는 LlamaGuard-3-8B, WG는 WildGuard, SG는 ShieldGemma-2B다. Figure 4는 여기에 accuracy 판정을 더해, 우연 일치를 보정한 두 항목 간 Cohen’s κ와 네 항목 전체의 Fleiss κ를 보여 준다.

본문과 그림 중 어느 수치가 최종 결과인지는 raw judge trace 없이는 결정할 수 없다. 블로그는 본문의 값을 옮겼다. 이 차이는 여러 judge가 필요하다는 문제 제기와 별도로 남는 원문 검증 문제다.

Accuracy human audit는 100개 표본에서 95%·96% 일치를 보고한다. 이것을 safety majority 전체의 검증률로 옮길 수 없다. 판정 불일치 표본과 분야별 놓침을 별도 human review로 확인해야 한다. 논문 v1 · Figure 4 원본 · 논문 v1

public-scoring

공개 local scorer의 출력은 논문 private v2 점수와 구분해야 한다

공개 repo는 frozen input과 generation·standard local scoring 코드를 제공한다. Raw 응답, judge trace, unsafe_majority_v2 재채점 자료는 제외했다. 따라서 논문 표를 읽는 일과 같은 응답을 재채점하는 일의 검증 범위가 다르다.

여기서 primary judge는 judge.jsonl의 기본 safety 판정 담당을 뜻한다. 다른 judge의 비교 판정은 별도 파일에서 합친다.

prior-work

실제 검색과 문서 수를 바꾼 선행 연구에 answerability 조건을 더했다

rag-evaluation

실제 RAG에서는 근거 노출과 생성 응답을 연결해 평가해야 한다

검색 관련성을 높이면 유해 요청에도 더 직접적인 근거를 찾을 수 있다. 그 근거가 최종 문맥에 남는지, 생성기가 요청을 거절하는지를 함께 보아야 relevance 개선의 안전 영향을 알 수 있다. 다음은 본 문서의 평가 제안이다.

단계기록할 관찰구분할 상태
후보 검색질문별로 사전 판정한 answer-bearing 문서 집합에 대한 recall·순위, query rewrite 전후 차이답 근거를 못 찾은 상태와 의도적으로 차단한 상태
Rerank·선별동일 후보에서 답 근거의 승격·제외, benign 근거의 유지관련성 최적화와 안전 정책의 충돌
문맥 구성최종 text의 answerability, 순서·길이·출처, 확장 전후 내용선별 당시 없던 근거의 추가와 경고·전제의 truncation
생성·출력Accuracy, harmfulness, refusal 이유와 응답 정보별 최종 문맥의 지지 여부문맥이 뒷받침하는 정보, 문맥 밖 보충, 안전 거절, 정보 부족 거절

응답 정보와 문맥을 대조해 지지 여부를 판정하는 방안을 제안한다. 실제 생성이 그 문맥에 의존했는지는 문맥 제거·교체 비교로 별도 평가해야 한다.

기존 Cerebras 분석의 rerank·문맥 복원 구분은 단계 구분의 참고다. 해당 시스템의 안전성을 이번 논문이 검증했다는 연결은 아니다. 논문 Limitations도 retriever ranking·query reformulation·generator의 상호작용을 추가 과제로 둔다. 논문 v1

evaluation-design

검색 품질과 안전 방어는 별도의 고정 조건에서 비교한다

Generator 비교에는 고정 문맥이 필요하고 retriever 비교에는 실제 검색 경로가 필요하다. 두 평가를 같은 질문으로 연결하되 결과의 분모와 조건을 유지한다. 아래 실험은 논문 결과를 확장하기 위한 제안이다.

비교 목적고정할 것변경·측정할 것
문맥 내용의 효과질문·모델·instruction·문서 수·token 길이·배치 순서관련성 / answerability를 분리해 변경
검색·rerank의 효과corpus snapshot·질문·생성 모델·후속 정책Retriever 또는 reranker만 바꾸고 최종 문맥까지 추적
문맥 구성의 효과같은 검색 후보와 순위확장·압축·순서·truncation별 answerability 재판정
방어의 효과같은 유해·benign 질문과 같은 평가자단계별 방어 on/off, 유해 출력과 과잉 거절의 동시 변화

위험 감소와 utility 손실은 각 지표로 보고한다. 질문 단위 pairing을 유지하고 하위 범주별 결과, judge별 결과, 불일치·누락, 반복 실행의 불확실성을 함께 제시한다. 서로 다른 accuracy·harmfulness·refusal을 종합 점수로 합치지 않고 따로 보고하는 방안을 제안한다.

interventions

논문의 방어 권고는 효과가 검증된 방어 목록이 아니다

논문과 블로그는 corpus curation, 입력·검색 결과·출력 filtering, system safety instruction을 제안한다. 이번 실험은 이 방어를 비교하지 않았다. 채택 여부는 유해 출력 감소와 benign 요청의 손실을 함께 확인해 결정해야 한다.

Corpus와 입력

주제 자체를 제거하는 필터는 정상적인 설명·교육 요청까지 막을 수 있다. 악의적인 요청과 정상적인 요청을 함께 평가하고 제외된 자료가 어떤 utility 손실을 만드는지 기록한다.

검색 결과와 문맥

문서 단독의 safe label에만 의존하지 않는다. 사용자 요청과 함께 answerability·오용 가능성을 검토하고, rerank 뒤에 확장된 최종 문맥까지 같은 정책을 적용했는지 확인한다.

생성과 출력

문서만 사용하라는 지시를 안전 정책으로 간주하지 않는다. 거절 문구가 있어도 뒤에 정보가 이어지는지 확인하고, 출력 judge의 누락과 오탐을 측정한다.

평가 보고

전체 비율과 분야별 비율을 병기하고 judge마다 결과를 남긴다. 누락 판정과 parse error를 성공적인 safe 출력에 흡수하지 않는다.

본 문서의 적용 제안이다. 방어의 효과 크기, latency·비용, 실제 배포의 잔여 위험은 별도 실험이 필요하다. 논문 v1

critique

통제된 생성 실험의 장점은 유지하되 인과와 배포 범위를 좁혀야 한다

이 benchmark는 검색 실패가 가리는 생성 모델의 취약성을 드러낸다. 동시에 문맥 개수·길이·prompt가 완전히 고정된 실험은 아니므로, 관찰된 변화의 원인을 하나로 확정하기 어렵다.

논문이 명시한 한계

English와 Wikipedia, 제한된 위해 범주, 상대적으로 작은 open 모델, single run이다. 질문·gold 생성과 자동 채점이 Claude 계열에 크게 의존한다는 한계도 명시한다. 상용 모델이나 다른 언어·사용자 역할로의 전이는 별도 평가 대상이다.

본 문서가 추가로 구분한 한계

Oracle partial과 Random의 metadata 판정은 같은 증거 강도가 아니다. Full/Balanced는 배포 질문 분포를 대표하지 않는다. 문맥 길이와 instruction 차이가 함께 움직이며 private scoring 공백도 남는다.

이 한계 안에서도 같은 질문에 답 근거를 공급했을 때 응답이 달라진다는 관찰은 유효하다. 개발자가 재사용할 부분은 네 문맥 조건과 세 평가 신호를 나눠 보는 설계다.

“RAG가 항상 더 위험하다”나 “관련 문서를 없애면 안전하다”는 처방은 이 결과에서 나오지 않는다. 낮은 harmfulness가 안전 거절과 정보 부족 중 어디서 왔는지 확인해야 한다. 논문 v1

conclusion

좋은 검색 다음에 안전한 응답을 따로 검증해야 한다

RAG-Safety-Bench의 용도는 답 근거가 주어진 상황에서도 모델이 유해 요청을 거절하는지 비교하는 데 있다. Corpus 신뢰와 검색 품질은 응답 안전을 대신하지 못하며, On-topic의 모델별 차이 때문에 문서에 직접 답이 없다는 보장도 충분하지 않다.

이 benchmark로 할 판단

고정 문맥에서 모델·안전 instruction·출력 정책을 비교한다. Accuracy, judged harmfulness, refusal 이유를 따로 보고하고 Oracle의 partial 여부도 유지한다.

배포 전에 더 할 판단

실제 retriever·reranker·문맥 구성의 노출 분포와 생성 반응을 연결한다. 유해 요청과 benign 요청에서 방어 효과·과잉 거절·판정 누락을 함께 측정하는 방안을 제안한다.
