HarnessDev: LLM이 실행 하네스를 만들고 고치는 능력을 재는 벤치마크

모델은 자신을 감싸는 실행 코드를 만들 수 있다. 그 코드를 고쳐 얻은 개선이 다른 과제와 모델에도 남는지는 별도로 검증해야 한다.

“모델 교체는 공짜가 아니다”@unclejobs.ai · Threads의 실무적 독해

논문이 묻는 것

Creation은 실행 가능한 harness를 만드는 능력, Evolution은 실행 피드백을 읽고 같은 harness를 고치는 능력을 잰다.

개발자가 묻는 것

모델을 바꿔도 정답률·실패 양상·실행 비용이 유지되는가. 게시자의 질문을 이 논문의 통제 실험과 연결한다.

HarnessDev v1 · Yuhao Wu 외 · arXiv:2609.01437v1 · 2026-09-01 제출 preprint. 한국어 분석 기준일 2026-09-07. 읽기 경로: Creation 설계 6장 → Evolution 설계 10장 → 모델 교체 15장 → 도입 판단 20장.

tl-dr

만드는 능력보다 개선을 유지하는 능력이 더 불안정하다

생성된 harness는 여러 과제를 실제로 수행한다. 그러나 실행 모델에 따라 순위가 바뀌고 반복해서 본 평가셋의 개선이 별도 과제로 안정적으로 이어지지는 않는다.

Creation의 성과

빈 실행 루프에서 재사용 가능한 시스템을 만든다. 쓰기·ML의 일부 조건에서는 논문이 고른 성숙한 시스템 조합에 근접하지만 Code·Search에는 격차가 남는다.

Evolution의 성과와 한계

Code에서 피드백을 읽고 유용한 수정을 만든다. 최종 버전 선택과 일반화가 약하므로 “계속 고치면 좋아진다”는 운영 가정은 성립하지 않는다.

Threads 관점의 효용

교체 후 점수만 보는 대신 중복 호출·완료 판단·실행 한도도 함께 확인하게 한다. 모델과 harness의 결합을 평가 단위로 삼을 이유가 있다.

이 문서의 판단

버전 고정, 실행 산출물 채점, 별도 평가셋을 도입하는 데 유용하다. Search 재조정의 회복률이나 총비용을 알려주는 논문으로 사용하기에는 자료가 부족하다.

근거: HarnessDev v1 §3–4, §6. 게시자의 운영 권고와 원문의 직접 측정은 모델 교체 15장과 중복 검색 16장에서 구분한다.

perspective

Threads는 모델 선택을 실행 시스템의 교체 문제로 바꿔 읽는다

이 스레드는 단순한 벤치마크 순위 소개가 아니다. 코드의 양보다 실행되는 제어 장치에 주목하고 다른 모델을 꽂았을 때도 그 장치가 작동할지를 묻는다.

게시자가 강조한 축원문과 연결되는 지점해석할 때 남겨야 할 경계
모델은 충분한데 차체가 모자랐다실패 사례의 harness 결함 분류모델 능력이 충분하다는 인과적 분리 실험은 아니다.
코드 길이보다 실패를 읽고 고친 과정코드량·수정 호출·실행 기록 분석수정 횟수와 성능의 연관성을 개입 효과로 바꾸면 안 된다.
남의 harness에 모델만 바꿔 넣는 비용동일한 생성물을 Gemini executor로 평가행동 변화, 정답률 변화, 금전 비용은 서로 다른 지표다.
점수보다 정지 규칙과 스텝 한도부터종료 실패와 실행 한도에 관한 사례확인 우선순위는 게시자의 실무 권고다. 원문은 그 순서를 시험하지 않았다.

Threads 2번 글–Threads 5번 글의 관점을 재구성했다. 직접 연결된 X 글도 모델과 harness의 공동 적응을 강조한다. 이 방향 제안 자체가 공동 최적화의 효과를 입증하지는 않는다.

problem

한 번의 답변을 개선하는 것과 실행 루프를 만드는 것은 다르다

일반적인 agent 평가는 이미 주어진 실행 시스템 안에서 과제를 푸는 능력을 잰다. HarnessDev는 그 바깥의 반복 실행·도구 연결·상태·완료 판단을 모델이 직접 구현할 수 있는지 묻는다.

HarnessDev v1 §1–3, Figure 1. 파라미터 학습이나 모델 자체의 재훈련을 시험한 연구가 아니다.

method

만드는 모델·실행하는 모델·채점하는 시스템을 분리한다

Creator는 개발 환경에서 harness 코드를 수정한다. 제출된 버전을 고정한 뒤 executor가 과제를 수행하며 scorer는 실제 산출물로 점수를 정한다.

Harness가 맡는 책임

실행 제어, 도구 dispatch, context 관리, state·memory, 종료·예산 관리, 결과 verification이다. 모듈 배치는 자유로우며 정해진 파일 목록을 복제하는 시험이 아니다.

자기 보고를 점수로 인정하지 않는다

Code의 실제 변경 diff, Terminal의 최종 환경, ML 제출 파일, Writing의 본문, Search의 답변을 기준으로 채점한다. 완료했다고 말하는 것과 과제를 통과하는 것을 분리한다.

HarnessDev v1 §3.1–3.4, Appendix C–E. 개발 환경은 같은 creator의 대응 경로에서 유지된다. 고친 harness를 다음 개발 환경으로 다시 사용하는 재귀적 자기 개발은 후속 과제다.

setup-creation

Creation은 약한 seed를 받아 독립적인 harness를 세 번 만든다

compare

인간이 만든 시스템과의 격차에는 모델 차이도 섞여 있다

논문은 성숙한 인간 설계 시스템을 참조점으로 함께 보여 준다. 실행 모델과 시스템이 다른 비교이므로 harness 구현 능력만의 격차나 인간 능력의 상한을 뜻하지 않는다.

diagnostics

코드 양과 함께 실제 실행·수정 기록을 봐야 한다

Threads가 코드 길이보다 실패를 읽는 과정을 강조한 이유는 원문의 실행 감사에서 드러난다. 다만 코드량과 수정 행동은 관찰 지표이므로 어느 행동이 성능을 올렸는지 분리해 입증하지 않는다.

method-evolution

Evolution은 보이는 평가를 반복하고 별도 과제로 일반화를 잰다

Creator는 자신의 Code harness에서 시작해 실패와 점수를 보고 수정한다. 반복 피드백에 쓰인 과제와 최종적으로만 채점하는 과제를 분리해 익숙한 평가에 맞춘 개선인지 확인한다.

↔

SWE 100 + Terminal 89
→

SWE 별도 630

평가 예산과 선택

H₀ 평가를 제외하고 완전한 평가 쌍을 최대 10번 쓸 수 있다. 구간별 제한 probe는 따로 있고 로컬 실행은 제한하지 않는다. controller는 자동으로 개선 버전만 수락하거나 최고 버전으로 되돌리지 않는다.

무엇을 고정하는가

Self-runtime과 fixed-Gemini 진화는 같은 creator·개발 환경·시작 harness를 사용한다. 각 경로 안에서 executor를 고정하고 수정한다. 진화가 끝난 코드에 나중에 모델만 갈아 끼우는 실험과 다르다.

HarnessDev v1 §4.3, Appendix E.2. 피드백 점수는 SWE 100개와 Terminal 89개 점수의 동일 가중 평균이다. 별도 평가는 SWE 630개만 사용하므로 두 개선 폭은 같은 지표가 아니다.

result-evolution

자기 모델로 고친 다섯 경로는 별도 과제에서도 소폭 개선됐다

Self-runtime에서는 모든 경로가 피드백 점수를 올렸다. 별도 SWE 평가에서도 개선이 남지만 실행마다 같은 크기의 효과가 재현된다는 결론은 아니다.

ablation

Gemini를 고정해 다시 진화시켜도 모든 creator가 개선하지는 않는다

Executor를 Gemini로 고정한 별도 경로는 수정 과정의 모델 의존성을 검사한다. 보이는 피드백 점수는 올라도 별도 과제 점수가 내려가는 경우가 있어 재조정을 자동 회복책으로 볼 수 없다.

trace

Opus의 한 진화 경로는 완료 판단을 넓혔지만 점수는 오르내렸다

부록의 실제 creator 기록은 실패를 읽고 수정하고 다시 평가하는 과정을 보여 준다. 각 단계에서 여러 변경이 묶여 있으므로 완료 gate 하나의 독립 효과로 해석할 수 없다.

related

critique

반복 평가에 적응한 코드를 일반적인 자기 개선으로 부르기에는 범위가 좁다

논문 저자는 실행 모델과 평가 예산에 대한 의존성, 제한된 일반화를 인정한다. 여기서 얻을 수 있는 것은 자동 진화의 보장이 아니라 실패를 드러내는 평가 틀이다.

논문이 명시한 한계이 분석에서 추가로 구분하는 것
Evolution은 Code에 한정되고 경로별 반복 실험이 부족하다.인접 전환은 같은 경로에 묶여 있다. 64개를 독립적인 개선 성공 확률의 표본으로 읽지 않는다.
평가 범위와 실행 모델에 따라 결과가 달라진다.Creation의 731개 SWE에서 Evolution의 100개와 별도 630개를 뺀 한 과제의 제외 이유는 특정되지 않았다.
Matched-search 통제와 넓은 일반화는 남은 과제다.중복률의 집계 범위와 회복·비용 측정의 공백은 일반화 범위를 제한한다.
생성 실행물의 안전한 사용에는 별도 조건이 필요하다.논문의 container는 재현 환경이다. 저자도 보안 격리 경계로 검증한 것은 아니라고 밝힌다.

그럼에도 frozen artifact, 실제 산출물 채점, 진화 중 숨기는 별도 평가셋은 다른 agent 개발에도 옮길 수 있다. 이 틀을 채택하는 데 자동 자기 개선이 이미 성공했다는 가정은 필요하지 않다.

HarnessDev v1 §6.1–6.2. 별도 SWE 과제는 creator에게 진화 피드백으로 주지 않았다는 뜻이다. 공개 benchmark이므로 모델의 사전학습에서 본 적이 없다는 보장은 아니다.

adoption

모델을 바꿀 때는 기존 artifact를 고정하고 종료 실패와 품질을 함께 다시 잰다

Threads의 권고는 교체 검증에서 무엇을 관찰할지 정하는 데 유용하다. 아래 절차는 논문 사례에서 도출한 이 분석의 운영 제안이며 논문이 비교 실험으로 입증한 최적 순서는 아니다.

판단할 질문다시 검증할 항목성능·비용·실패율의 연결
모델 교체만으로 무엇이 달라졌는가같은 코드·prompt·도구 버전·과제·예산을 기록하고 executor를 교체한다.정답 점수와 함께 중복 호출, 한도 소진, 미완료 제출, token·지연을 나눠 기록한다.
일찍 끝나는가, 끝나지 않는가수정용 feedback과 분리한 선택용 validation에서 완료 조건과 step cap을 각각 바꾼 비교를 수행한다.한도를 늘리면 해결 기회와 실행량이 함께 늘 수 있다. 조기 종료는 실행량을 줄여도 미완료율을 높일 수 있어 세 지표를 함께 판정한다.
수정 비용을 회수하는가수정·probe·전체 평가·judge 비용을 실행 절감분과 분리해 적는다.17장의 비용 공백을 자체 측정으로 채워야 교체의 이익을 판단할 수 있다.
어떤 버전을 배포할 것인가Validation으로 선택한 버전을 고정하고 마지막에만 최종 test를 연다. Rollback 가능한 artifact도 남긴다.최종 test를 보고 다시 수정하면 그 test도 feedback이 된다. 다음 일반화 판단에는 새 test가 필요하다.

시험 전에 품질 하락 허용폭, 지연·지출 상한, 미완료 허용 범위와 비용 회수 기간을 정한다. 수정용 feedback → 선택용 validation → 선택 후 최종 test를 나누는 것은 이 분석의 운영 제안이다.

Threads 5번 글의 우선 확인 권고를 검증 가능한 질문으로 확장했다. 본 논문은 cap·정지 규칙의 독립적인 성능–비용–실패율 곡선이나 최적값을 제공하지 않는다.

conclusion

배울 것은 자기 개선의 약속보다 개선을 판정하는 방법이다

HarnessDev는 실행 시스템의 생성과 국소적인 수정을 보여 준다. Threads의 “모델 교체는 공짜가 아니다”라는 독해는 이 결과를 모델과 harness 조합의 재검증 문제로 연결한다.

자체 평가에 적용할 것

버전을 고정하고 실제 산출물을 채점하며 최종 test를 선택 과정에서 분리한다. 버전 선택의 불안정성을 고려해 20장의 운영 절차를 시험 적용할 수 있다.

추가 근거를 기다릴 것

모델 교체가 이익인지와 자동 재조정으로 회복되는지는 행동·정답률과 총비용을 함께 측정해야 판단할 수 있다. 배포할 코드의 도입은 재현 자료와 운영 조건 확인까지 보류한다.

중심 실험의 범위는 Creation의 네 분야와 Evolution의 Code다. 게시자의 정지 규칙·step cap 우선 확인 권고는 적용 관점이며 그 우선순위의 효과를 직접 비교한 결과는 아니다.
