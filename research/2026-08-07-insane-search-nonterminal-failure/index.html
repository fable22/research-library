insane-search: 실패를 종료 상태로 인정하지 않는 웹 접근 엔진

차단된 페이지를 가져오는 도구는 많다. 이 프로젝트가 다른 지점은 가져오지 못했을 때 무엇을 보고하는가에 있다. 엔진은 포기하면서 아직 안 해본 경로의 목록과 must_invoke_playwright_mcp 플래그를 함께 돌려주고, 애매한 응답은 성공으로도 실패로도 세지 않는다. 코드를 읽어 그 구조를 추적하고, 도입할 때 무엇을 감수해야 하는지 정리했다.

fivetaku/insane-search 커밋 019ee16bbf471595f9b67b164e4a92208183af2d, 태그 v0.14.0. MIT. 아래 모든 파일:행 은 이 커밋 기준이고, shallow clone 이라 이력에 기반한 서술은 하지 않았다.

코드를 읽어 쓴 문서다. 엔진을 실행하거나 테스트를 돌리지 않았으므로, 런타임 동작이 아니라 코드가 그렇게 쓰여 있다는 것까지만 확인된 내용이다.

tl-dr

포기를 "다 해봤다"로 오해하지 못하게 만드는 것이 이 엔진의 설계 중심이다

일반적인 fetch 라이브러리는 성공 아니면 실패를 돌려준다. 이 엔진은 실패에 왜 여기서 멈췄고 무엇이 남았는지를 붙인다. 그 결정이 판정 체계와 제어 흐름 양쪽에 박혀 있다.

애매함이 종료가 아니다SUSPECT_OK 판정은 성공 집합에도 실패 집합에도 없다. 보관만 하고 격자를 계속 돈다
포기에 목록이 붙는다_untried_routes() 가 아직 안 해본 경로를 문자열로 반환하고, CLI 는 ⛔ NOT EXHAUSTED 를 stderr 로 낸다
예산 절단과 전수 소진을 구분한다grid_exhausted 플래그로 나뉜다. 예산 때문에 멈춘 것을 벽에 부딪힌 것으로 보고하지 않는다
에이전트 재량을 코드로 옮겼다공식 API 시도가 skill 지시문에서 엔진 안으로 들어왔다. 주석이 그 이유를 직접 적는다

도입 판단은 11장에 있다. 결론만 먼저 적으면, 개인 개발 환경에서는 쓸 만하고 공용 환경에서는 설치 스크립트가 전역 settings.json 을 건드리는 방식 때문에 검토가 필요하다.

problem

에이전트가 "차단됐다"고 말할 때, 실제로는 한 가지만 해본 경우가 많다

이 프로젝트가 없앤 수작업은 헤더를 바꿔가며 curl 을 다시 치는 일이 아니다. 어디까지 시도했는지 사람이 기억하는 일이다. 판단을 에이전트에게 맡겨두면 건너뛴다는 것이, 코드 주석에 사례로 남아 있다.

같은 URL 에 .json 과 .rss 두 경로가 있는데 앞의 것만 403 을 받고 뒤의 것은 시도되지 않았다. 결과는 "Reddit 은 차단됨"이라는 잘못된 결론이다. 지시문에 "공식 API 를 먼저 써라"라고 적어두는 방식이 실패한 자리이고, 그래서 그 단계가 파이썬 코드 안으로 옮겨졌다.

두 번째 문제는 판정이다. HTTP 200 은 성공의 증거가 아니다. WAF 챌린지 페이지도 200 으로 온다. skill 문서가 이걸 규칙으로 못박는다.

두 문제 모두 "도구가 약해서"가 아니라 "언제 멈출지를 누가 정하는가"의 문제다. 4장부터는 그 결정이 코드 어디에 있는지 본다.

architecture

단일 진입점 하나에 4개 Phase 가 순서대로 붙어 있다

호출자가 보는 것은 fetch(url) 하나다. 그 안에서 공식 API, probe, 격자 순회, 브라우저 폴백이 차례로 시도되고, 각 단계는 앞 단계가 실패했을 때만 돈다.

4개 Phase 는 _fetch_core() 안의 주석 구분선이다. 표는 그 행 번호를 옮긴 것이고 원문에 이런 표는 없다.

모듈 크기는 고르지 않다. fetch_chain.py 1,276행이 최상위 3,715행의 3분의 1이고 제어 흐름 전체를 들고 있다. 나머지는 validators.py 349, executor.py 347, transport.py 310, phase0.py 273 순이다.

판정은 Verdict enum 9종이다. 이 중 성공으로 세는 것은 STRONG_OK 와 WEAK_OK 둘뿐이고, 격자를 멈추는 종료성 실패는 AUTH_REQUIRED, NOT_FOUND, RATE_LIMITED 셋이다. 나머지 넷은 어느 쪽도 아니다. 8장이 이 빈자리를 다룬다.

transport.py 와 executor.py 는 홉의 존재만 확인했고 내부를 읽지 않았다. 격자 후보가 실제로 어떻게 생성되는지(_plan_for_profile, fetch_chain.py:638)는 확인하지 못했다.

result-verdict

결과 1. 판정 체계에 "애매함"이 독립된 자리를 갖는다

대부분의 fetch 코드는 성공 아니면 실패다. 여기서는 응답이 성공처럼 보이지만 확신할 수 없는 상태에 이름이 붙어 있고, 그 이름이 제어 흐름을 바꾼다.

같은 파일의 ok 프로퍼티가 이걸 성공에서 명시적으로 뺀다.

동시에 격자를 멈추는 집합에도 없다. TERMINAL_NONSUCCESS 는 AUTH_REQUIRED, NOT_FOUND, RATE_LIMITED 셋뿐이다(validators.py:89-91). 그래서 SUSPECT_OK 를 만나면 반환하지도, 중단하지도 않고 보관만 한 뒤 계속 간다.

격자 안에서도 같은 처리인데 and best_suspect is None 조건이 붙어 처음 만난 것만 남긴다(:1015). 뒤에 더 나은 후보가 나와도 교체하지 않는다.

이 설계의 값은 마지막에 드러난다. 전부 실패해도 손에 남은 best_suspect 를 돌려줄 수 있으므로, 빈손과 "확신은 없지만 이건 받았다"가 구분된다.

MCP 가 항상 미시도로 남는 이유가 구조적이다. 엔진은 로컬 Node Chrome 만 띄울 수 있고, Cloudflare 급 챌린지는 그걸 탐지한다. 그래서 terminal 이 아닌 모든 포기에서 must_mcp = True 다(:1126).

이 게이트는 이 문서를 만드는 과정에서 한 번 실제로 관측됐다. 다른 작업 중 논문 PDF 를 받으려다 18개 경로를 소진하고 ⛔ NOT EXHAUSTED 블록이 나왔다. 다만 그건 이 문서를 위해 통제한 실행이 아니므로 재현 가능한 측정으로 취급하지 않는다.

가장 주의할 자리는 설치 스크립트의 파싱 실패 분기다. 훅 주입은 인라인 node 프로그램이 settings.json 을 읽어 객체로 만든 뒤 다시 쓰는 방식인데, 파싱에 실패하면 빈 객체에서 시작한다.

d 가 {} 면 훅이 없으므로 주입 조건이 참이 되고, 121행이 그 객체를 그대로 파일에 쓴다. 깨진 settings.json 은 훅만 남은 파일로 교체된다. 백업을 뜨지 않고 쓰기 실패도 catch{} 로 삼킨다. 유효한 JSON 이면 병합되므로 정상 경로에서는 문제가 없다.

반대 방향으로 세어야 할 것도 있다. engine/safety.py 가 SSRF 와 리다이렉트 가드를 들고 있다. private, loopback, link-local, 그리고 클라우드 메타데이터 주소(169.254.169.254)를 기본 차단하고, 매 홉을 검증하며 DNS rebinding 도 본다. 파일 머리말이 "공식 문서에 내장 가드가 없다"는 것을 이유로 적는다. test_u7.py 가 이걸 오프라인으로 검사한다. 적대적 페이지가 내부망으로 리다이렉트를 유도하는 경로는 막혀 있다.

정리하면 이렇다. 개인 개발 머신에서 trial. 설치 전에 settings.json 을 백업하고, 관측 로그가 무한히 쌓이는 것을 감수할 수 있으면 된다. 팀 공용 환경이나 CI 러너에서는 assess. 전역 설정 변경과 제거 경로 부재, 그리고 세션 트랜스크립트를 읽는다는 사실을 각자 정책에 비춰 판단해야 한다.

엔진만 쓰는 선택지가 있다. python3 -m engine <URL> 은 SKILL.md:40, :68, :263 과 engine/__main__.py 에 문서화돼 있고 setup.sh 없이 돈다. 대신 플러그인 설치를 포기하는 것이므로 skill 트리거, 업데이트 경로, references/ 를 잃고 의존성을 직접 깔아야 한다.

conclusion

결론

이 프로젝트에서 가져갈 만한 것은 접근 기법이 아니라 실패를 다루는 방식이다.

차단을 우회하는 개별 수법은 새롭지 않다. TLS 지문 위장, 모바일 URL 변환, 헤드리스 브라우저는 모두 알려진 것이다. 이 엔진이 다른 자리는 그 수법들을 다 써보고도 실패했을 때 무엇을 말하는가에 있다. 아직 안 해본 경로를 이름으로 돌려주고, 예산 때문에 멈춘 것과 벽에 부딪힌 것을 구분하고, 애매한 응답을 성공으로도 실패로도 세지 않는다.

그 설계가 나온 계기가 코드 주석에 남아 있다는 점도 같이 볼 만하다. 공식 API 를 먼저 쓰라는 지시는 지켜지지 않았고, 그래서 그 단계가 엔진 안으로 들어왔다. 에이전트에게 규율을 문서로 요구하는 것과 코드로 강제하는 것의 차이를 보여주는 사례다.

한계도 그만큼 분명하다. CI 게이트라고 적힌 것이 이 저장소에 없고, 손으로 관리하는 denylist 를 검사하는 테스트도 없다. 관측 로그는 전체 URL 을 경계 없이 쌓는다. 설치 스크립트는 전역 설정을 고치면서 되돌리는 경로를 주지 않는다. 도구를 쓸지 말지보다 어느 환경에 설치할지가 실제 판단 지점이다.

다른 프로젝트로 옮길 만한 것을 하나 고르라면 _untried_routes() 의 형태다. 실패 반환값에 "무엇이 남았는가"를 담는 것은 도메인과 무관하게 성립하고, 호출자가 사람이든 에이전트든 조기 포기를 막는다.

이 문서는 코드를 읽어 쓴 것이고 런타임을 확인하지 않았다. 실행 검증이 붙으면 8장과 9장의 서술이 달라질 수 있다.
