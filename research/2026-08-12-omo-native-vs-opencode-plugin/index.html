tl-dr

요약. 플러그인을 그만둔 게 아니라 호스트를 바꿨다

omo native는 여전히 익스텐션이다. 달라진 건 그 익스텐션이 얹히는 호스트를 omo 쪽이 소유한다는 점이다. npm 패키지 omo-ai 가 버전을 핀 고정한 @code-yeongyu/senpi 엔진을 --extension 으로 띄우고, 브랜드 프로파일을 넘겨 사용자에게는 omo 로 보이게 한다.

달라진 것

주입이 1급 API가 된다. OpenCode에서는 session.prompt 를 감싸는 341줄짜리 게이트를 통해야 했던 내부 메시지 주입이, senpi에서는 pi.sendMessage({display:false}) 한 줄이다.

자식 완료 경로에서 폴링이 빠진다. v4는 자식 세션이 생길 때까지 100ms 간격으로 최대 60초를 폴링했고, 완료는 1초 간격 폴링에 10초 안정과 연속 3회 관측으로 추정했으며, 부모를 깨우는 데 parent-wake-* 모듈 15개를 썼다. v5는 in-process 러너가 부모의 도구 클로저를 그대로 쓰고, 완료는 3분기 라우팅 switch 하나가 처리한다.

한 번의 task 호출로 최대 16개 자식을 팬아웃한다. 자식은 세션이 끊겨도 파기되지 않고 유예되었다가 세션 재개 시 되살아난다.

대가

hashline이 없다. README가 Grok Code Fast 1의 편집 성공률을 6.7%에서 68.3%로 올렸다고 자랑하는 해시 앵커 편집 도구는 native 어댑터에 존재하지 않는다.

Claude Code 호환 계층이 없고, Sisyphus/Atlas/Prometheus/Hephaestus로 이루어진 11개 discipline agent 레지스트리도 없다. native의 builtin subagent는 4개다.

베타 채널 전용이고, 2026-08-12 기준 native 자체를 대상으로 한 열린 버그가 최소 6건이다. 설치하면 178MB짜리 엔진이 따라온다.

한 줄로. Ultimate의 상위집합은 아니다. 같은 철학을 더 얇은 층으로 다시 구현한 별개 제품이다. 오케스트레이션은 얻고 편집 도구와 호환 계층은 잃는다.

problem

플러그인이 메인 루프에 메시지를 밀어 넣을 수 있으면 병이 생긴다

omo가 OpenCode를 떠난 이유는 추측할 필요가 없다. 저장소가 두 곳에 적어 두었다. ROADMAP.md 의 "Why Not OpenCode-Native" 절과 AGENTS.md 의 ARCHITECTURE INVARIANTS 절이다. 둘 다 같은 API를 지목한다.

Session prompt injection (session.prompt, session.promptAsync) returns before the prompt is durably accepted. Later failures arrive as session.error. Multiple hooks observe the same idle or error edge and inject the same internal message into a live parent session. Duplicate work. Infinite loops. State corruption. ROADMAP.md, "Why Not OpenCode-Native" (v5.0.0-beta.6)

같은 문장이 AGENTS.md 에서는 한국어로 적혀 있다. 영어로 쓰인 저장소에서 이 한 항목만 한국어인 것은, 메인테이너가 기여자용 규칙이 아니라 자기에게 남긴 경고를 적었기 때문으로 읽힌다.

OpenCode의 stupid한 설계로 플러그인이 session.prompt / session.promptAsync 같은 메인 세션 메시지 API를 통해 메인 시스템을 망가뜨릴 수 있다. AGENTS.md, ARCHITECTURE INVARIANTS (v5.0.0-beta.6)

대응책의 크기가 문제의 크기다

omo는 이 API를 직접 못 쓰게 막고 게이트를 하나 세웠다. packages/utils/src/prompt-async-gate.ts 는 341줄이고, 그 아래 prompt-async-gate/ 디렉터리에 테스트를 뺀 모듈 11개가 따로 붙는다. 큐, 예약, 최근 디스패치 기록, 의미 기반 중복 제거, idle 디스패치, 라우트 해석, 타이밍, 그리고 메시지 상태와 도구 턴을 다루는 넷이다. AGENTS.md는 게이트의 계약과 금지 패턴까지 명문화한다.

# AGENTS.md 가 규정한 게이트 의미론
reserve per session before dispatch
check active session state
keep a short post-dispatch hold
release only on intentional abort/recovery paths
restore optimistic task/loop state when dispatch is skipped or fails later

# 금지 패턴
raw prompt calls outside the shared gate
postDispatchHoldMs: 0
no-session fallback to raw prompt
new internal message routes without duplicate-injection regression tests

ROADMAP은 여기에 두 줄을 더 붙인다. "The TUI burns CPU." 그리고 "Breaking changes are frequent." 결론 문장은 OpenCode를 겨냥하지 않는다.

These are not OpenCode-specific flaws. Any plugin system that exposes the main loop to arbitrary injection has the same disease. We treat OpenCode as one adapter target among several. Not the center of the architecture. ROADMAP.md (v5.0.0-beta.6)

이 장이 다루지 않는 것. OpenCode 쪽 소스는 읽지 않았다. 위 인용은 omo 저장소가 OpenCode API에 대해 주장하는 내용이며, OpenCode의 promptAsync 구현을 직접 확인한 결과가 아니다. 확인한 것은 omo가 그 주장을 믿고 341줄짜리 게이트를 세웠다는 사실이다.

identity

packages/omo-native 에는 테스트를 빼면 실행 코드가 열 개도 안 된다. 하는 일은 하나다. 버전을 정확히 핀 고정한 senpi CLI를, omo가 만든 익스텐션 페이로드와 브랜드 프로파일을 붙여 띄운다.

엔진의 출신

senpi는 badlogic/pi-mono 의 opinionated fork이고, 저장소 설명이 그렇게 말한다. 그 README는 자기 출신을 이렇게 적는다.

Think of senpi as a light version of OMO that runs as a single pi CLI binary instead of an opencode plugin. github.com/code-yeongyu/senpi README (2026-08-12 조회)

OMO가 영감을 준 경량 포크가 먼저 생기고, 그 위에 OMO 본체를 다시 얹은 것이 omo-ai 다. senpi README가 "No direct senpi counterpart"로 묶은 목록에 ultrawork, Team Mode 와 team_*, 스킬 시스템, 카테고리 라우터가 들어 있는데, 그것들이 정확히 omo-senpi 어댑터가 되돌려 놓는 것이다.

확인하지 않은 것. senpi 저장소는 클론하지 않았다. 엔진의 브랜드 소비 코드, 스크럽 시점, 익스텐션 로더 동작은 omo 쪽 문서와 어댑터 주석이 주장하는 내용이며 엔진 소스에서 확인한 것이 아니다.

layers

어댑터가 얇아진다. 합성 훅 58슬롯 대 등록 컴포넌트 16개

두 에디션은 같은 코어 패키지를 공유하고 어댑터만 다르다. 그런데 어댑터의 두께가 다르다. OpenCode 어댑터는 호스트가 노출한 14개 훅 핸들러 위에 5계층 훅을 합성해야 하고, senpi 어댑터는 배열 하나에 컴포넌트를 나열한다. 두 숫자의 단위는 다르다. 환산으로 읽으면 안 된다. 각 어댑터가 자기 호스트에 붙는 방식의 차이다.

Ultimate (packages/omo-opencode)

OpenCode가 주는 훅 핸들러 14개. 12개는 plugin-interface.ts 에, 2개(experimental.session.compacting, experimental.compaction.autocontinue)는 플러그인 모듈 생성 시점에 직접 배선한다.

그 위에 omo가 5계층으로 훅을 합성한다. Session 24 + ToolGuard 18 + Transform 7 + Continuation 7 + Skill 2 = 58 슬롯. 기본 설정에서는 7개 이상이 config로 꺼져 있어 ~50-51개가 활성이고, team mode를 켜면 이벤트 핸들러 4개가 더 붙어 최대 62개가 된다.

packages/omo-opencode/src/hooks/ 디렉터리 엔트리는 101개다.

Native (packages/omo-senpi)

src/extension/index.ts 의 omoSenpiComponents 배열에 16개가 들어 있다. config-startup, native-badge, onboarding, init-deep-advisor, telemetry, ultrawork, start-work-continuation, ulw-loop, todo-fanout-reminder, fallback-architect, comment-checker, ast-grep, lsp, task, memory, config-watch.

배열 순서가 곧 우선순위다. start-work-continuation 이 ulw-loop 보다 먼저 등록되어, boulder 작업이 있으면 ulw-loop 이어달리기보다 우선한다. memory는 task 뒤, config-watch 앞이다.

rules 컴포넌트는 일부러 없다. senpi에 builtin rules가 있어서, 어댑터가 흉내내지 않는다.

모노레포는 그대로다

packages/AGENTS.md 가 패키지 43개를 6개 역할로 나눈다. Core 20개(순수 TypeScript), MCP 4개(stdio), Skills 1개, Adapters 5개(+어댑터 지원 1개), Platform 12개(생성된 런처), Web 1개. 핀 커밋의 실제 디렉터리는 45개다. 차이는 둘에서 온다. 그 문서가 2026-08-07 기준으로 생성돼 omo-native(2026-08-09 생성)를 담지 못했고, senpi-task 를 어댑터 지원으로 빼서 5+1 로 셌다. 의존은 아래로만 흐르고, 어댑터가 코어를 쓴다. ROADMAP이 소스로 확인된 예외 두 개를 스스로 적어 둔다. omo-senpi → senpi-task 는 같은 층의 어댑터 지원 간선이고, omo-opencode → omo-codex 는 Codex 설치 배포를 위한 과도기 간선이다.

즉 v5는 코어를 다시 쓰지 않았다. 어댑터를 하나 더 만들고, 그 어댑터를 제품으로 포장했다. 실제로 packages/omo-senpi 의 첫 커밋은 2026-07-03, packages/senpi-task 는 2026-07-06이다. packages/omo-native 만 2026-08-09에 생겼다. native는 5.0에서 제품이 되었다. 태어난 것은 그보다 다섯 주 앞이다.

수치의 출처. 58, 24/18/7/7/2, ~50-51, 62는 모두 AGENTS.md 의 ARCHITECTURE INVARIANTS 절이 스스로 밝힌 값이다. 훅을 세어 검증하지는 않았다. 16은 src/extension/index.ts 배열 리터럴을 직접 센 값이다. 참고로 packages/omo-senpi/AGENTS.md 는 "Thirteen live components"라고 적혀 있어 트리보다 뒤처져 있다.

fanout

팬아웃이 도구 호출 한 번으로 압축된다

v4에서 task 는 자식 하나를 만든다. 다섯 갈래로 갈라지려면 다섯 번 부르고 다섯 번의 왕복을 기다린다. v5의 task 는 tasks:[...] 배열을 받아 최대 16개를 한 번에 띄운다.

// packages/senpi-task/src/tools/task/params.ts
export const MAX_TASK_BATCH_ITEMS = 16

// 상위 target/model/skills 는 항목이 생략하면 상속된다
{
  "tasks": [
    { "category": "quick",     "prompt": "Check the API contract.", "name": "contract" },
    { "subagent_type": "librarian", "prompt": "Find the upstream doc.",   "name": "docs" }
  ],
  "run_in_background": true
}

동기 배치는 시작된 자식을 전부 기다려 하나의 결과로 집계한다(execute-batch.ts 가 Promise.allSettled 로 모은다). 백그라운드 배치는 각 자식의 id와 큐 위치를 즉시 돌려준다. 배치 검증을 통과한 뒤 한 항목이 시작에 실패해도, 성공한 형제들과 나란히 실패가 보고된다.

16은 호출당 스폰 수이지 병렬도가 아니다. default_concurrency 기본값은 5 이고(packages/omo-config-core/src/schema/task.ts:25), manager가 모델·프로바이더별 슬롯을 잡아 초과분을 큐에 넣는다. 16개를 한 번에 넣어도 기본 설정에서 동시에 도는 것은 5개다. 큐 위치가 결과에 실려 오는 이유가 이것이다. v4도 같은 기본값 5를 썼으므로, 바뀐 것은 왕복 횟수이지 병렬도가 아니다.

자식을 어디에 띄우는가

러너프로세스도구스티어링기본
in-process같은 senpi 런타임부모의 도구 클로저 그대로함수 호출예
process자식 senpi 프로세스자식이 자기 것을 로드JSON-RPC팀 멤버는 강제

in-process 자식은 부모가 이미 등록해 둔 ToolDefinition 을 그대로 받는다. 같은 프로세스, 같은 execute 클로저, 같은 MCP 클라이언트 인스턴스다. 제외되는 건 task, task_*, team_* 계열뿐이다.

// packages/senpi-task/src/runners/in-process/shared-tool-filter.ts
// The shared-MCP-client mechanism: sharedParentTools are the parent extension's own
// registered ToolDefinitions (same process, same execute closures, same client instances).
export function isTaskOrTeamFamilyTool(name: string): boolean {
  return name === "task" || name.startsWith("task_") || name.startsWith("team_")
}

v4는 같은 자리에서 폴링을 했다

packages/omo-opencode/src/tools/delegate-task/background-task.ts 의 주석이 이유를 밝힌다. BackgroundManager.launch() 가 세션이 만들어지기 전에 반환하기 때문에, 도구는 sessionId가 나타날 때까지 기다려야 한다. 그 뒤에도 늦게 도착한 sessionId를 잡는 별도 패치가 붙어 있고, 주석은 그것이 없으면 OpenCode TUI가 영원히 스피너를 돌린다고 적는다(issue #4252).

상수 (delegate-task/timing.ts)값쓰이는 곳
WAIT_FOR_SESSION_INTERVAL_MS100자식 세션 생성 대기 폴링 간격
WAIT_FOR_SESSION_TIMEOUT_MS60,000같은 대기의 상한
POLL_INTERVAL_MS1,000동기 위임의 완료 폴링
MIN_STABILITY_TIME_MS10,000완료로 판정하기 전 안정 시간

완료를 이벤트로 받지 못하니 휴리스틱으로 추정한다. "1초마다 보고, 10초 이상 조용하고, 3번 연속 그러면 끝난 것으로 친다."

v4에도 깨우는 경로는 있었다. 크기가 다르다

v4가 폴링만 한 것은 아니다. v4.19.4 의 packages/omo-opencode/src/features/background-agent/ 에는 테스트를 뺀 파일이 52개 있고, 그중 15개가 이름에 parent-wake 를 달고 있다(그중 14개는 접두사, 하나는 message-updated-parent-wake-output.ts). dedupe, pending-queue, flush-runner, dispatched-tracker, window-recovery, session-inspector, timer-handle 이 각각 파일 하나씩이다. 3장의 게이트가 필요했던 바로 그 문제를 여기서도 감당하고 있었다.

v5에서 같은 일을 하는 것은 completion/routing.ts 의 switch 하나와 그 위의 notifier다. 줄어든 것은 폴링 여부가 아니라 부모를 깨우는 데 드는 코드의 양이다.

과장하지 말 것. native에도 폴링은 남아 있다. 팀 멤버 익스텐션이 durable mailbox를 MEMBER_POLL_INTERVAL_MS = 1_000, ack를 ACK_POLL_INTERVAL_MS = 100 으로 돌린다(packages/senpi-task/src/team/member-extension/index.ts:13-14). v4를 비판한 바로 그 1초와 100ms다. 폴링이 사라진 곳은 자식 완료 경로 하나다. 그리고 두 방식의 실제 지연 차이는 재지 않았다.

orchestrate

완료는 3분기 라우팅이고, 자식은 세션이 끊겨도 죽지 않는다

오케스트레이션에서 어려운 부분은 회수다. 자식이 끝났을 때 부모가 스트리밍 중이면 어떻게 넣을 것인가, 부모가 컴팩션 중이면, 사용자가 창을 닫으면. packages/senpi-task 는 이 세 질문에 각각 코드를 두었다.

세션 종료가 자식을 유예 상태로 남긴다

session_shutdown 은 quit, reload, new, resume, fork 다섯 사유 모두에서 자식을 죽이지 않는다. 살아 있는 핸들은 정리하되 레코드는 persisted_only(in-process) 또는 rpc_detached(process)로 남고, 상태와 epoch, 실행 통계가 보존된다. 다음에 그 세션을 재개하면 reconcileOnSessionStart(parentSessionId) 가 그 세션의 자식만 되살린다.

  • lease부활은 부모 세션당 하나의 admission lease 아래에서 배치로 일어난다. <stateDir>/locks/session-<id>.lock 에 owner token을 쓰고 1초마다 갱신하며, 3주기 이상 낡은 lease만 token CAS로 뺏는다. 5초 안에 못 잡으면 배치 전체가 deferred/lock_contended 로 미뤄지고 세션 시작 자체는 진행된다.
  • cap정원을 넘긴 후보는 deferred/capacity 로 남는다. evict 되지도 lost 되지도 않는다. 정원은 residency_max_children 이고 기본 스키마 값은 8이지만, 해석 시 Math.max(8, availableParallelism() * 3) 로 올라간다.
  • no-reruntranscript 없이 종료된 레코드는 폐기하고 다시 돌리지 않는다. 세션 파일이 없는 비종료 레코드만 저장된 프롬프트로 정확히 한 번 재실행한다. senpi는 첫 assistant 메시지 전에는 JSONL을 쓰지 않으므로 이 경우 재실행되는 작업이 없다.
  • ttlTTL 삭제는 2단계 tombstone이다. 락 안에서 보존 조건을 다시 확인하고 .expunging 으로 이름을 바꾼 뒤(load/list에서 사라져 부활 요구가 집을 수 없다), 락 밖에서 실제 파일을 지운다. 기본 ttl_ms 는 86,400,000(24시간)이다.

이걸 얼마나 믿을 수 있나. src/__adversarial__/chaos-bench.test.ts 가 시드 고정 200회 반복으로 불변식 13개를 건다. 매 iteration 이 13개를 전부 평가한다. (task_id, run_epoch) 당 정확히 한 번 통지, terminal 멱등, 동시성 슬롯 누수 없음, unhandled rejection 없음, 모든 waitFor 정착, 그리고 suspend/revive 소유권·복구·epoch·pid·의도적 중단·정원·회수·terminal 재실행 금지까지 여덟 개가 더 있다. 참고로 packages/senpi-task/AGENTS.md 는 아직 "the four W1 invariants"라고 적는다. 옆 파일 chaos-lifecycle.test.ts 는 한 걸음 더 간다. 6~13번 각각을 일부러 깨뜨리는 mutation 여덟 개(double_revive→6 … relaunch_terminal_without_session→13)를 두고, 그 불변식이 실제로 터지는지 본다. 검사가 검사되고 있다는 뜻이다. 테스트가 있다는 사실은 확인했고, 실행하지는 않았다.

agents

discipline agent 11개가 curated subagent 4개로 줄고, 그중 둘은 잠겨 있다

Ultimate의 오케스트레이션은 에이전트 레지스트리 위에 서 있다. Prometheus가 인터뷰로 계획을 세우고, Momus와 Oracle이 이중 검토하고, Atlas가 실행을 지휘하고, Sisyphus-Junior가 코드를 쓴다. native에는 그 레지스트리가 없다. 대신 카테고리 라우팅과 네 개의 읽기 전용 subagent가 있다.

Ultimate: 11 agents

primary 넷: sisyphus, hephaestus, prometheus, atlas. subagent 일곱: oracle, librarian, explore, multimodal-looker, metis, momus, sisyphus-junior.

계획과 실행이 서로 다른 세션 에이전트로 분리돼 있고, /start-work 가 세션 에이전트를 Atlas로 바꾼다. 계획은 .omo/plans/*.md 에, 진행은 .omo/boulder.json 에, 누적 학습은 .omo/notepads/ 에 쌓인다.

Native: 4 curated agents

explore, librarian, metis, momus. 넷 다 in-process로 고정되고 execution_mode 오버라이드가 무시된다. 팀 멤버로도 거부된다. process 모드 스폰이 persona 프롬프트와 도구 allowlist를 떨어뜨리기 때문이다.

도구는 9개만 허용된다. read find grep ls bash lsp_diagnostics lsp_goto_definition lsp_find_references lsp_symbols. 그리고 이 중 bash 는 진짜 셸이 아니다.

읽기 전용을 프롬프트가 아니라 실행 경로로 강제한다

curated 자식에게 주는 bash 는 같은 이름의 구조화 브로커로 치환된다. runners/in-process/curated-readonly-bash.ts 가 검증된 read-only GitHub 질의와 HTTPS 조회만 직접 실행하고, 편집/쓰기 도구와 변형을 일으키는 LSP 도구는 애초에 목록에 없다. 프롬프트로 "읽기만 해"라고 부탁하는 대신 실행 경로를 갈아 끼운 것이다.

metis와 momus는 조건이 셋 다 맞아야 뜬다

agents/invocation-guard.ts 가 이 둘을 plan-gated tier로 분류한다. 스폰되려면 세 조건이 모두 참이어야 한다.

// packages/senpi-task/src/agents/invocation-guard.ts 의 판정 조건
hasUserRequested   // 사용자가 raw 입력으로 ulw-plan 을 직접 요청했다
                   //   모델이 스스로 SKILL.md 를 읽은 것은 인정되지 않는다
hasPlanArtifact    // 이번 세션에서 .omo/plans/*.md 를 건드렸다 (worktree 포함)
!hasInvoked        // start-work 가 한 번도 호출되지 않았다

// resolveSkillInvocations 가 배선되지 않으면 fail CLOSED:
//   상태가 없으면 사용자 요청의 증거도 없으므로 거부한다

거부 메시지는 일부러 해제 방법을 알려주지 않는다. 소스 주석이 그 이유를 적는다. start-work 이후의 거부는 최종적이라, 금지된 스킬 검사를 조건 미충족 검사보다 먼저 돌린다. momus는 한 번만 쓸 수 있고, 스폰 프롬프트는 하네스가 표준 plan-review 계약으로 통째로 갈아 끼운다. 계획 파일 경로 외의 내용은 버려진다.

사용자 정의 에이전트가 확장 지점이다

builtin 넷이 전부는 아니다. packages/senpi-task/src/agents/omo-config-agents.ts 의 mapOmoConfigAgents 가 omo.json 의 agents 블록을 senpi-task 의 AgentDefinition 으로 옮긴다. 파일 상단 주석이 목적을 밝힌다. "so subagent_type spawns and team membership can address user-defined agents." 넘어가는 필드는 description, prompt, model, models, variant, reasoning, temperature, tools, disable, background, execution_mode, allowed_subagents, disallowed_tools, max_depth, max_turns 다.

builtin 넷과 달리 사용자 정의 에이전트는 실행 모드를 고를 수 있고 팀 멤버가 될 수 있다. 요구가 어긋났을 때 째는 자리가 여기다.

팀은 lead와 member의 도구가 다르다

lead 세션만 6개 도구를 받는다. team_create, team_delete, task_create, task_get, task_list, task_update. 멤버는 팀 범위의 task_send 하나만 받는다. team_wait 도구는 존재하지 않는다. 답이 필요하면 보내고 턴을 끝내면, steer된 팀 메시지 통지가 대화를 재개시킨다. 전달은 durable mailbox의 예약 기반이고 unread → .delivering-<id> → processed/<id> 로 커밋되며, processed 파일이 exactly-once 원장이다.

줄어든 것은 에이전트 수이고, 스킬은 18개다

Prometheus 인터뷰와 Atlas 실행 계층은 없어진 것이 아니라 스킬로 내려왔다. packages/omo-senpi/src/install/install-senpi.ts 의 REQUIRED_PLUGIN_ARTIFACTS 가 native가 반드시 싣는 스킬 18개를 이름으로 못 박는다.

ast-grep · coding-agent-sessions · debugging · frontend · git-master · init-deep · lsp-setup
programming · refactor · remove-ai-slops · review-work · start-work · ultimate-browsing
ultrawork · ulw-loop · ulw-plan · ulw-research · visual-qa

그래서 13장의 "에이전트 11개 대 4개" 행은 능력의 비교가 아니라 레지스트리 항목 수의 비교로 읽어야 한다. Ultimate가 에이전트로 표현한 것 중 상당수를 native는 스킬로 표현한다. 다만 18개 중 본문을 연 것은 ultrawork 하나뿐이라, 내용까지 같은지는 확인하지 못했다.

이 장이 다루지 않는 것. 스킬 18개의 본문 비교가 없다. hyperplan 과 give-me-tips 는 senpi 전용으로 따로 있고, native의 ulw-plan 은 shared 사본이 아니라 senpi-local 오버라이드다. 어느 쪽 스킬이 더 나은지는 이 문서가 말할 수 없다. start-work-continuation 컴포넌트가 .omo/boulder.json 을 읽어 이어달리는 것(연속 8회 상한, 사용자 입력 시 리셋)까지만 확인했다.

model-place

모델 배치에 게이트가 두 겹 생긴다

카테고리는 v4부터 있었다. 에이전트가 모델 이름 대신 의도를 말하고(quick, deep, ultrabrain) 하네스가 폴백 체인을 타고 내려가 실제 모델을 고른다. v5 native가 더한 것은, 라이브 레지스트리에 없는 카테고리를 아예 목록에서 지우는 두 개의 게이트다.

게이트적용 대상조건미충족 시
requiresModelbuiltin 3개지정 모델 id가 라이브 레지스트리에 있어야 한다model_unavailable. 폴백 체인으로도 안 간다
isCategoryChainViablebuiltin 전부폴백 체인 rung 중 최소 하나가 해석되어야 한다카테고리 자체가 목록에서 사라진다

게이트가 걸린 셋은 architect(claude-fable-5), ultrabrain(gpt-5.6-sol), deep(gpt-5.6-sol)이다. 각각의 폴백 체인이 자기 모델 패밀리로만 잘려 있어서, 다른 패밀리의 rung을 타고 게이트를 우회할 수 없다. 관계없는 모델 하나만 등록된 레지스트리에서는 resolveAvailableCategoryNames 가 빈 배열을 돌려준다.

탈출구는 하나다

omo.json 에 categories.<name> 항목이 하나라도 있으면 설명만 적힌 항목이라도 두 게이트를 모두 우회한다. 사용자가 직접 쓴 설정은 하네스가 판단하지 않는다는 규칙이다. 이 동작은 packages/omo-opencode/src/tools/delegate-task/categories.ts 의 hasExplicitUserConfig 를 그대로 따라간 것이라고 소스가 밝힌다.

도구 설명은 등록 시점에 만들어져 레지스트리를 볼 수 없으므로, 잠긴 카테고리를 목록에서 지우는 대신 (requires <model>) 를 붙인다. 실제 판정은 스폰 시점의 resolveCategory 만이 권위를 갖는다.

native에만 있는 카테고리: architect

packages/model-core/src/category-model-requirements.ts (OpenCode 에디션의 원본)에는 8개가 있다. visual-engineering, ultrabrain, deep, artistry, quick, unspecified-low, unspecified-high, writing. packages/senpi-task/src/category/fallback-chains.ts 에는 여기에 architect 가 더 있고, rung이 하나뿐이다.

architect: [
  { providers: ["anthropic", "anthropic-api", "github-copilot", "opencode", "vercel"],
    model: "claude-fable-5", variant: "xhigh" },
]

이 카테고리는 다음 장의 fallback-architect 장치와 짝이다. 세션이 Fable 5에서 밀려났을 때, 최상급 추론을 잃지 않고 상담 창구로 남겨 두는 통로다.

어긋난 것 하나. senpi 쪽 체인은 model-core를 import 하지 않고 손으로 미러한 사본이다(패키지 의존을 늘리지 않으려는 선택이라고 파일 상단 주석이 밝힌다). 그래서 두 파일이 실제로 어긋나 있다. kimi rung이 senpi에서는 kimi-coding 과 kimi-for-coding 을 둘 다 싣고, writing 의 마지막 rung은 native가 gemini-3.1-pro, OpenCode가 gemini-3.6-flash 다. 앞의 차이는 주석이 의도된 것이라 밝히지만, 뒤의 차이에 대한 언급은 찾지 못했다.

token-cost

토큰을 아끼는 방식이 절단에서 재주입 회피로 바뀐다

v4의 토큰 관리는 delegate-task/token-limiter.ts 한 곳에 있다. 4자를 1토큰으로 추정해 스킬, 카테고리 프롬프트, AGENTS 컨텍스트를 순서대로 잘라 예산에 맞춘다. 잘린 자리에는 [TRUNCATED] 가 남는다. native의 장치 넷은 자르지 않는다. 첫 번째는 같은 지시문을 두 번 보내지 않는 것이다.

이 장치가 성립하려면 "이 세션은 이미 무장됐다"는 기록이 살아 있어야 한다. 주석이 그 어려움을 적는다. senpi는 세션 전환이나 재개마다 익스텐션 러너를 헐고 컴포넌트를 다시 등록하며, 패키지 익스텐션을 캐시 없는 로더로 불러온다. 모듈 스코프에 원장을 두면 그때마다 잊어버리고 전문을 다시 주입한다. 그래서 원장을 다른 곳에 매달았다.

장치 둘. 부모의 프롬프트 캐시가 만료되기 전에 턴을 닫는다

전경 대기에 데드라인이 걸려 있다. tools/task/foreground-wait.ts 는 PI_PROMPT_CACHE_SAFE_WAIT_SECONDS 가 주어지면 그 초만큼만 기다리고, 넘기면 자식을 백그라운드로 승격시킨 뒤 부모 턴을 끝낸다.

const budgetSeconds = resolvePromptCacheSafeWaitSeconds(input.ctx, input.env ?? process.env)
const waiting = input.manager.waitFor(input.taskId, { signal: input.signal })...
if (budgetSeconds === undefined) return waiting

// 예산을 넘기면 기다림을 포기하고 승격한다
input.manager.promoteToBackground(input.taskId)

// 모델이 받는 문구:
// "Foreground wait reached the prompt-cache-safe budget (Ns) for task <id>;
//  the task continues in background."

느린 자식 하나가 부모의 캐시된 프롬프트를 무효화할 만큼 턴을 길게 잡아 두지 못하게 하는 장치다. 저자가 스레드에서 "캐시히트 처리"를 개선점으로 든 것과 같은 자리로 읽힌다.

장치 셋. 비용이 태스크 단위로 계량된다

토큰이 어디로 갔는지를 엔진이 아니라 어댑터가 센다. packages/senpi-task/src/run-stats.ts 가 자식 태스크마다 total_tokens, tokens_per_second, cost_usd, 그리고 cache_hit_rate_last 와 cache_hit_rate_run 을 누적하고, status-line.ts 가 그걸 상태 행에 렌더한다. 캐시 히트율이 실행 중 값과 실행 전체 값 두 개로 나뉘어 있는 것이, 저자가 말한 "캐시히트 처리"에 이름부터 대응하는 자리다.

주석이 조건을 하나 단다. tokens_per_second 는 assistant 스트리밍 구간이 전부 계측될 때만 방출한다. 토큰을 실은 생성 윈도 중 하나라도 0ms로 붕괴하면 수치가 검증 불가능해지므로 아예 생략한다.

장치 넷. 이미 본 장치의 부수 효과다

in-process 러너가 부모의 도구 클로저를 공유하므로, 자식마다 MCP 서버를 다시 띄우거나 도구 정의를 다시 직렬화할 일이 없다. 여기에 memory 컴파일 캐시가 붙는다. packages/memory-core/src/compile/cache.ts 는 컴파일된 메모리 블록을 (sha256(구조버전 + 템플릿), git HEAD) 로 키잉하고, 커밋된 HEAD만 컴파일한다. 작업 중인 변경은 캐시를 깨지 않는다. 컴파일 결과가 compile_warn_tokens 30,000을 넘으면 경고가 뜬다.

넷 밖: 모델이 거절당했을 때의 경로

아래는 토큰을 아끼는 장치가 아니라 거절 이후의 상담 경로다. 위 넷에 넣지 않는다. fallback-architect 컴포넌트는 세션이 claude-fable-5 에서 거절이나 정책 차단으로 밀려났을 때 한 번 발동한다. 약해진 모델에게 문제를 쪼개고, 최상급 추론이 필요한 조각만 task(category: "architect") 로 상담하라고 지시한다. 상담 질의는 대화 맥락이 없는 자기완결형이어야 하고, 독립 상담은 병렬 백그라운드로 돌린 뒤 통합은 본인이 한다.

지시문에는 실무적인 대목이 있다. architect 상담자는 방금 거절한 그 Fable 5이므로, 질의를 "정당한 엔지니어링 작업"으로 읽히게 구성하라고 시킨다. 그래도 거절하면 같은 질의를 다시 보내지 말고 각각 무해한 하위 질문으로 쪼개어 묻고, 연결하는 추론은 직접 하라고 한다. 이 지시문 자체는 숨겨진 메시지(display: false)로 들어가고, 사용자에게는 별도의 짧은 안내만 보인다.

측정하지 않은 것. 장치 넷 중 어느 것도 실행해서 토큰 사용량을 재지 않았다. 확인한 것은 코드에 그 장치가 있다는 사실과, 상수의 값이다. 저자가 스레드에서 말한 "메모리도 덜 먹는다"는 주장의 근거가 되는 측정치는 저장소에서 찾지 못했다.

ui-ux

UI가 도구 스키마 안으로 들어온다

Ultimate의 UI는 OpenCode TUI가 그린다. omo는 metadata를 발행해 TUI가 읽어 가기를 기다린다. native는 senpi를 자기 것으로 다루기 때문에, 무엇을 어떻게 보여줄지가 어댑터 안에 있다.

도구 스키마에 박힌 UI

task 도구의 파라미터에 task_summary 가 있다. 80자 제한이고 넘으면 강제 절단된다. 사용자 footer와 위젯이 raw prompt 대신 보여줄 한 줄이며, 모델의 판단에는 쓰이지 않는다.

도구 설명이 지시한다. "Pass task_summary (one line, <=80 chars) on every spawn: the user's footer/widget UI shows it instead of the raw prompt, so it should say WHAT was delegated." 모델에게 사용자 화면을 채우는 일을 맡긴 것이다.

native 전용 표면

native-badge 컴포넌트가 session_start 와 agent_settled 마다 footer 배지를 발행한다. 문자열은 (😺 OmO Native) 다. 런처가 OMO_NATIVE=1 을 심는 이유가 여기 있다. omo-ai 설치는 --extension 으로 로드되므로 settings 기반 탐지에 걸리지 않는다.

그 밖에 onboarding, init-deep-advisor 컴포넌트, 슬래시 커맨드 /tasks 와 /task-kill, 에디터 아래 라이브 task 상태 위젯이 있다. footer 자체는 goal 표시용으로 예약돼 있다. 유예된 자식은 목록에서 suspended 로 라벨된다.

모델 거절을 사용자에게 승급으로 설명한다

fallback-architect가 발동하면 사용자에게 보이는 메시지가 하나 뜬다. 커스텀 타입 omo-fallback-architect:notice 에 display: true 와 구조화된 details: { from, to } 가 실린다. 문구는 전환을 승급으로 설명한다. 폴백 모델이 실행을 몰고, Fable 5급 추론은 architect 레인으로 계속 닿는다는 것이다.

문구보다 형태가 오래 간다. 안정된 customType과 details가 senpi의 세션 이벤트 스트림을 타므로, 나중에 GUI가 senpi 코어를 고치지 않고 같은 이벤트를 렌더할 수 있다. 소스 주석이 그 GUI를 omo-desktop-app 이라고 이름으로 부른다.

반대 방향은 끊긴다

Ultimate에는 claude-code-compat-core 가 있어 Claude Code의 훅, 커맨드, 스킬, MCP, 플러그인을 그대로 로드한다. native 어댑터의 16개 컴포넌트에는 그 계층이 없다. 이미 Claude Code 설정을 다듬어 놓고 omo가 그것을 읽어 주기를 기대했다면, native로 옮기는 순간 그 자산은 따라오지 않는다.

설치 순서 함정. 같은 머신에 4.19.4 이하가 남긴 전역 omo bin이 있으면 npm이 EEXIST로 거부한다. 먼저 rename 이후 릴리스로 올리거나 제거한 뒤에 npm i -g omo-ai@beta 를 해야 한다. 그리고 bunx omo / npx omo 는 쓰면 안 된다. npm의 omo 는 다른 저자의 무관한 패키지다.

확인하지 않은 것. omo setup 을 실행해 보지 않았다. 위 규칙은 setup-import.js 를 읽어 정리한 것이고, 어떤 provider id 가 매핑을 통과하는지는 같은 디렉터리의 provider-map.json 을 열면 나오지만 열지 않았다. oh-my-pi 와 gajae-code 는 이 저장소 밖 프로젝트라 auth 스키마 버전이 지금도 7과 4인지는 확인할 수 없다.

기록 여섯 곳이 자기 코드보다 낡았고, 라이선스 표기는 침묵한다

이 문서의 주장은 전부 소스를 읽어서 나왔다. 소스를 읽으면 코드가 어떻게 쓰였는지는 알 수 있다. 실행했을 때 무슨 일이 일어나는지는 알 수 없다. 아래는 그 경계와, 조사 중 실제로 어긋난 것들이다.

그래서 실제로 설치되는 패키지는 라이선스를 명시하지 않는다. 저장소의 SUL-1.0이 적용된다고 읽는 게 자연스럽지만, 도구는 MIT라고 표시하고 매니페스트는 침묵한다. 상업적 도입을 검토한다면 이건 확인하고 넘어가야 하는 항목이다. curl -s https://registry.npmjs.org/omo-ai 로 버전별 필드를 직접 볼 수 있다.

설치가 남기는 것

  • sizeomo-ai@5.0.0-0.beta.6 자체는 언팩 7.0MB / 494 파일이다. 의존하는 @code-yeongyu/senpi@2026.8.11-4 는 언팩 178.0MB / 29,277 파일이다. 전역 설치 한 번에 이만큼이 따라온다.
  • home에이전트 상태는 ~/.omo 아래 flat 레이아웃으로 간다. 메모리 저장소는 ~/.omo/memory/agents/<id>/ 의 git repo다. task 레코드는 프로젝트 안 .omo/senpi-task 에 JSONL로 쌓이고 기본 TTL은 24시간이다.
  • authomo setup 을 실행하면 senpi의 auth.json 에 API 키가 병합된다. 실행 전 백업 파일이 남고 권한은 0600이다. 동의를 묻고, 비대화형에서는 아무것도 하지 않는다.
  • net익명 텔레메트리가 기본 켜짐이다. UTC 하루 한 번 omo_senpi_daily_active 이벤트를 보낸다. beta.6부터 이벤트별 허용 목록, primitive 전용 payload, prompt/path/text/IP 필드 명시 거부, DO_NOT_TRACK 지원이 붙었다. {"telemetry": {"enabled": false}} 로 끈다.
  • out되돌리기는 npm uninstall -g omo-ai 다. ~/.omo 와 프로젝트의 .omo 는 남는다. 플러그인 에디션과 달리 남의 설정 파일을 고치지 않으므로 정리할 외부 상태가 적다.

확정된 위험 하나

런북이 스스로 기록한다. omo-ai 의 npm Trusted Publisher 항목이 저장됐는지 확인되지 않았다(2026-08-03에 WebAuthn 저장이 3회 연속 실패). publish 워크플로의 preflight-trust 검사는 모든 패키지에 무조건 돌기 때문에, 이 항목이 미검증인 채로 릴리스가 시작되면 저장소 전체의 다음 릴리스가 실패한다고 문서가 적는다. 이건 프로젝트 쪽 위험이지만, 베타 채널의 업데이트가 끊길 수 있다는 뜻이기도 하다.

trial의 조건. 베타 채널이라는 사실이 이 판정의 대부분을 결정한다. bare npm i -g omo-ai 는 설계상 실패하도록 만들어져 있고(모든 버전이 prerelease), 저자도 "아직은 베타"라고 쓴다. 주력 작업을 옮기기 전에 omo doctor 가 통과하는지, 그리고 자신이 쓰는 편집 패턴이 hashline 없이도 견디는지 먼저 본다.

conclusion

같은 철학을, 자기가 통제하는 경계 위에 다시 구현했다

omo의 선언문은 5.0에서도 바뀌지 않았다. "Human intervention is a failure signal", "Higher token usage is acceptable if it significantly increases productivity". 바뀐 것은 그 선언을 실행하는 층이 남의 API 위에 있느냐 자기 API 위에 있느냐다.

플러그인 시절의 omo는 내부 메시지 하나를 안전하게 넣는 데 341줄짜리 게이트와 그 아래 11개 모듈을 썼다. 내부 메시지를 넣으려면 예약하고, 세션 상태를 확인하고, 디스패치 후 홀드를 걸고, 실패하면 낙관적 상태를 되돌려야 했다. 자식을 띄우면 세션이 생길 때까지 100ms 간격으로 폴링하고, 끝났는지는 10초 안정과 3회 연속 관측으로 추정했다. native에서 그 자리에 있는 것은 pi.sendMessage({display:false}) 한 줄과, 부모 상태를 보는 3분기 switch 하나다.

그 절약분이 어디로 갔는지도 소스에 있다. 배치 팬아웃 16개, 부모 도구를 그대로 쓰는 in-process 러너, 세션이 끊겨도 살아남는 자식 레코드, admission lease와 2단계 tombstone, 라이브 레지스트리에 없는 카테고리를 지우는 두 겹의 게이트, 프롬프트 캐시가 만료되기 전에 턴을 닫는 전경 대기. 어느 것도 플러그인 경계 위에서는 만들기 어려운 것들이다.

동시에 이건 승격이 아니다. hashline이 없고, Claude Code 호환이 없고, discipline agent 레지스트리가 없다. 저장소는 세 에디션을 "same product"라 부르지만, 실제로는 같은 코어 20개를 공유하는 세 개의 다른 제품이다. 어느 것을 고를지는 무엇에 의존하고 있느냐로 갈린다.

프로젝트의 궤적 자체도 남는다. OMO가 영감을 준 경량 pi 포크가 senpi가 되었고, 그 senpi가 이제 OMO의 호스트다. 호스트를 소유하지 못한 하네스는 호스트를 만들거나 남의 호스트를 고르게 되는데, omo는 세 번째 길을 택했다. 자기가 영향을 준 포크를 핀 고정해서 자기 이름을 씌웠다.

이 결론이 서 있는 자리. v5.0.0-beta.6 태그 하나의 스냅샷이다. 베타 여섯 개가 이틀 만에 나갔고, dev 는 이 문서를 쓰는 동안에도 움직였다. 여기 적힌 상수, 컴포넌트 수, 기능 유무는 그 커밋의 사실이며, 다음 베타에서 달라질 수 있다.
