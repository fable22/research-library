Claude Platform 비용·성능: prompt cache, instructions, effort 세 축을 /claude-api 명령 셋이 돌린다

Anthropic 블로그 Reducing cost and improving performance with Claude Platform(Lance Martin, 2026-09-08)을 개발자용으로 다시 세웠다. 글이 말하는 세 축이 각각 무엇이 문제이고 무엇을 고치라는 것인지, 사용자가 실제로 할 일이 무엇인지, 새로 등장한 명령이 무엇인지에 답한다.

읽는 길 1 · 세 축

04~10장. prompt cache, instructions, effort 순서로 각각의 문제와 대책. 원문 숫자는 표와 차트에 있다.

읽는 길 2 · 명령

11~14장. /claude-api prompt-audit, cost-optimize, hillclimb 가 무엇을 하고 무엇을 요구하는지, 고정 커밋의 skill 저장소에 무엇이 있는지.

읽는 길 3 · 할 일

15장 하나로 끝난다. 상황별로 무엇을 하면 되는지 체크리스트로 모았다. 근거 장 번호를 옆에 달았다.

원문 밖의 출처는 원문이 링크한 platform 문서 일곱 페이지와 skill 저장소의 커밋 하나뿐이다. 어느 문장이 어디서 왔는지는 각 장의 note 에, 신원은 19장에 있다.

tl-dr

비용과 성능은 맞바꾸는 것이 아니다. 캐시 적중률, 낡은 지시문, effort 세 곳을 고치면 둘 다 좋아진다는 것이 글의 주장이다

원문은 세 가지 수정으로 성능을 포기하지 않고 비용을 줄일 수 있다고 말한다. prompt cache 적중률을 최대로 올리고, frontier 모델로 올라갈 때 프롬프트의 anti-pattern 을 제거하고, effort 를 과제에 맞춘다. 이 지침을 claude-api skill 에 넣었고, Claude Code 안에서 명령 세 개로 돌린다.

세 수치는 모두 Anthropic 이 자기 벤치마크에서 잰 값이고 원문은 실험 코드를 공개하지 않는다. 이 문서는 그 값을 그대로 옮기고 17장에서 읽는 법을 적는다. hillclimb 는 원문이 명령으로 소개하지만 고정 커밋의 skill 저장소에는 없다. 14장.

problem

낭비는 세 곳에서 따로 생긴다. 다시 계산하는 prefix, 문자 그대로 따르는 낡은 지시문, 과제에 안 맞는 effort

원문 서두는 성능과 비용이 흔히 tradeoff 로 여겨진다는 말로 시작한다. 글은 낭비의 원인을 셋으로 갈라 각각이 성능을 포기하지 않고 줄일 수 있는 비용임을 보인다. 셋 중 effort 는 양쪽으로 틀릴 수 있어 재야 하는 축이다.

1 · prompt cache

prefill 은 입력을 내부 상태(KV cache)로 바꾸는 단계이고 입력 처리 비용의 대부분이 여기서 난다. 같은 prefix 로 시작하는 요청은 이 상태를 다시 읽는다. 읽기는 입력 정가의 일부만 청구된다.

그래서 문제는 prefix 가 같아야 할 때 같지 않은 것이다. 모델이 다르거나, byte 하나가 다르거나, TTL 이 지났으면 다시 계산한다.

2 · instructions

프롬프트에는 모델 약점을 덮으려고 넣은 지시문이 쌓인다. “두 번 확인해라”, “최대한 철저히”, 여섯 단계 절차, scratchpad.

frontier 모델은 이것을 문자 그대로 따른다. 원문의 표현으로는 “hobble frontier Claude model and can inadvertently increase costs”. 토큰이 늘고 어떤 것은 정확도까지 깎는다.

3 · effort

effort 는 “얼마나 열심히 일할지”다. 낮으면 결론에 빨리 닿고, 높으면 숙고하고 검증하고 대안을 본다.

두 방향 모두 틀릴 수 있다. 높으면 과잉 숙고, 낮으면 증거 부족. 각각의 모양은 09장.

원문은 세 축을 “common levers” 라 부르고 더 많은 레버는 platform 문서 Optimizing for cost and intelligence 로 넘긴다. 이 문서도 그 범위를 따른다. batching, 출력 상한, 문서 캐시는 13장의 사례에 나오는 만큼만 다룬다.

cache · 문제

캐시는 모델에 묶이고 byte 단위로 맞아야 하고 시간이 지나면 사라진다. 깨뜨리는 다섯 가지가 이 세 제약에서 나온다

원문이 드는 “practical considerations” 는 셋이다. 캐시는 특정 모델에 pinned 되어 있다. 읽기는 프롬프트 전체 구간이 byte-exact 여야 한다. TTL 이 있다. 그 아래 다섯 가지 팁은 전부 이 셋 중 하나 이상을 어기는 경우다.

cache · 대책

원문의 처방 여덟 개는 셋으로 묶인다. 갈라진 곳을 보고, prefix 를 안정시키고, TTL 안에 있어라

instructions · 문제

anti-pattern 여섯 종. 원문 목록은 넷을 토큰 낭비로, 하나를 성능 저하로, 하나를 platform 의 거부로 적고 08장 실험에서는 셋이 정확도를 깎았다. 어느 쪽이든 frontier 모델이 지시를 더 잘 따라서 생기는 일이다

원문은 “instructions can drift relative to the capabilities of the latest Claude models” 라 하고 여섯 가지를 든다. 표의 3열은 원문이 각 항목에 붙인 결과다. 4열은 08장 실험에서 그 항목이 실제로 어떻게 나타났는지다.

원문은 이 여섯을 비용형과 정확도형으로 나눠 부르지 않는다. 넷/하나/하나는 3열의 결과 표현에서 이 문서가 읽어낸 것이고 08장 결과 문단(“Accuracy rose for three reasons”)은 scratchpad 까지 셋을 정확도 쪽에 둔다. skill 의 prompt-audit.md 는 같은 것을 “Group 1 · Dated prompt text” 아래 1a~1f 로 더 잘게 나눈다.

instructions · 대책

모델만 올리면 비용이 오르고 정확도는 조금 오른다. prompt-audit 를 한 번 돌리면 비용이 내려가고 정확도가 더 오른다

실험 설계는 이렇다. 깨끗한 프롬프트에 anti-pattern 을 하나씩 심어 legacy 프롬프트 여섯 개를 만든다(retired thinking setting, 모순되는 환불 규칙 한 쌍, manual scratchpad, “verify twice”, “be maximally thorough”, 여섯 단계 필수 절차). 각각을 Opus 4.8, 모델 ID 만 바꾼 Opus 5, /claude-api prompt-audit 를 한 번 돌린 Opus 5 에서 돌리고 여섯 개를 평균한다.

retired thinking setting, 모순되는 환불 규칙, manual scratchpad 세 프롬프트에서 났다. 각각이 어떻게 나타났는지는 07장 표 4열에 있다.

prompt-audit 가 훑는 범위

작업 디렉터리 안의 프롬프트, skill, tool description. Claude API 를 부르는 애플리케이션 코드와 Claude Code 자신의 설정(CLAUDE.md, skills)을 포함한다. 14장에 산출물과 실행 규칙이 있다.

“모델만 바꾸면 비용이 오른다” 는 2.52¢ → 3.43¢ 로 +36% 다. 이 비율은 원문 블로그에 없고 같은 실험을 적은 platform 문서 Optimizing for cost and intelligence 가 “36% more per ticket” 으로 적는다. 그 문서의 다른 반올림과 판단은 17장.

effort · 문제

같은 모델에서 effort 를 올리면 어떤 과제는 점수가 2.7배가 되고 어떤 과제는 마지막 단계가 노이즈 안에 묻힌다

effort 는 output_config.effort 로 주고 low / medium / high / xhigh / max 다섯 단계다. 기본은 high. 원문은 곡선이 과제마다 다르다는 것을 두 벤치마크로 보인다.

틀리는 방향 1 · 높을수록 좋다는 가정

과잉 숙고. 과제가 요구하는 것보다 오래 숙고해 비용과 지연이 늘고 답의 질이 나빠질 수 있다. “Deliberation only helps while there's still evidence to find.”

틀리는 방향 2 · 낮은 쪽으로 치우침

증거가 모이기 전에 멈춘다. tool call 이 줄어 세 번째 검색 결과 대신 첫 번째로 답한다. 어려운 단계에서 덜 생각하고 스스로 하던 점검을 건너뛴다.

다섯 단계와 기본값은 원문에 없고 skill 의 SKILL.md Thinking & Effort 표와 platform effort 문서에서 가져왔다. max 는 되지만 xhigh 는 안 되는 모델이 있다(Opus 4.6, Sonnet 4.6, Mythos Preview). 원문은 “At low effort Claude generally reaches conclusions faster” 까지만 말한다.

effort · 대책

더 강한 모델을 낮은 effort 로 돌리는 쪽이 약한 모델을 높은 effort 로 돌리는 것보다 쌀 수 있다

원문의 calibration 방법은 둘이다. 강한 모델을 낮은 effort 로 시험할 것, 그리고 과제의 모양을 알 것. 둘 다 평가를 effort 단계별로 돌려야 알 수 있다. 그 탐색을 /claude-api hillclimb 가 대신한다(11장).

CursorBench 3.2 (원문 Figure 5)

Fable 5.1 low ≈ Fable 5 high, 비용은 1/3. 원문은 두 가지 이유를 갈라 적는다. 낮은 effort 라 과제당 일을 덜 하고 Fable 5.1 의 cache read 가 백만 토큰당 $0.25 로 Fable 5 의 $1.00 보다 싸다. Fable 5 가격을 그대로 적용해도 Fable 5.1 low 가 약 40% 싸다고 한다.

그림에는 값 라벨이 없다. 축은 Score 60~75%, Cost per task $2~$20 로그.

과제의 모양을 알기

effort 를 sweep 하며 애플리케이션 성능을 잰다. 포화되지 않은 평가에서 곡선이 평평하면 그 과제는 thinking compute 에 묶여 있지 않은 것이고 effort 를 올려도 이득이 없다.

09장의 두 벤치마크가 양 끝이다. FrontierCode Diamond 는 가파르고 HLE 는 끝이 평평하다.

“1/3 의 비용” 과 “약 40%” 는 원문 문장이고 그림에서 다시 계산할 수 없다. 원문이 근거로 링크한 것은 Claude Fable 5.1 & Claude Mythos 5.1 System Card PDF 인데 이 문서는 열지 않았다(16장). cache read 가격 $0.25 vs $1.00 은 pricing 문서의 0.025× vs 0.1× 배수와 맞는다.

trace · hillclimb

hillclimb 는 모델을 올리고 audit 한 뒤 모델을 내리고 프롬프트를 고쳤다. 네 단계 뒤 held-out 정확도가 78.6% 에서 90.5% 로, 비용은 약 1/5

원문이 고객지원 벤치마크에서 돌린 사례 하나를 끝까지 따라간다. 시작은 Opus 4.8 의 기본(high) effort. hillclimber 는 평가를 train 과 test 로 나눈다. 설정 변경을 제안하고 실패한 train 티켓을 읽어 고친다.

2단계의 “cleared the Opus 4.8 baseline” 에서 baseline 의 train 정확도 74.4% 는 그림 Figure 6 의 점선 라벨(“starting accuracy, 74.4%”)에만 있다. held-out 의 78.6% 는 같은 baseline 을 test 에서 잰 값이다. 3단계와 4단계의 “1 cent” 는 원문 표현 그대로이고 소수점은 없다.

mechanism · cost-optimize

cost-optimize 는 토큰이 어디로 가는지 세 경로 중 하나로 알아낸 뒤 공짜 레버를 먼저 순위 매기고 평가가 있을 때만 effort 와 모델을 건드린다

원문 “Automating cost reduction” 절의 설명을 흐름으로 그렸다. 원문이 적은 것은 프로파일 소스 세 개와 레버 순서, 그리고 평가 유무에 따른 분기다. skill 의 cost-optimization.md 는 같은 흐름을 Step 0~4 로 적는다.

“평가가 없으면 effort·모델을 손대지 않는다” 는 원문의 “If you supply an evaluation, it goes further” 를 뒤집어 읽은 것이다. skill 문서는 이를 명시한다. 평가 없는 tradeoff 레버는 “needs an eval before applying” 으로 표시하고 적용하지 않는다. 공짜 레버가 평가 없이도 안전하다는 것은 skill 의 단언이지 측정이 아니다. 13장에서 레버 하나만 단독으로 잰 사례는 tau2-bench 의 caching 뿐이고 출력 상한은 SWE-bench 에서 medium effort 와 묶여서만 측정됐다. 평가가 없을 때 skill 은 실제 요청 20~30건짜리 minimal eval 을 함께 만들자고 제안한다. 실행 승인 규칙은 14장.

critique

수치는 전부 Anthropic 의 자기 측정이다. 성능 유지의 근거는 대부분 “노이즈 안” 이며, 명령 하나는 아직 저장소에 없다

한계는 원문의 수치가 무엇을 세우지 못하는지에서 시작한다. 그 위에 원문과 링크 문서를 대조해 찾은 어긋남을 얹는다.

원문 수치가 세우지 못하는 것
  • 1모든 “성능 유지” 는 CI 가 0 을 지난다. 13장의 네 벤치마크 전부, 09장 HLE 의 마지막 단계도 “inside run-to-run noise”. 시행 횟수와 표준편차는 어디에도 없다
  • 2held-out 은 14건이다. 78.6% 는 11/14 로 떨어지지만 90.5% 는 14건 한 번의 정답 수로는 나올 수 없는 값이다(12/14 = 85.7%, 13/14 = 92.9%). 여러 trial 의 평균이거나 분모가 14 가 아닌데 원문은 시행 횟수를 적지 않는다. skill 자신이 production cutover 의 기준으로 적는 “around fifty cases and at least five trials per configuration” 에 못 미친다. train 98.9% 와 test 90.5% 의 차이도 원문은 설명하지 않는다
  • 308장의 여섯 프롬프트는 각각 anti-pattern 하나씩이다. 평균 −14.6% 와 +5.3pt 는 깨끗한 프롬프트에 하나씩 심은 인공 조건의 평균이라 anti-pattern 의 해악을 재지 audit 가 이미 돌아가는 프롬프트에서 anti-pattern 을 찾아내는 비율을 재지 않는다. +5.3pt 의 세 원인 중 하나는 API 가 요청을 거부한 것이라 프롬프트 품질의 문제와 종류가 다르다
  • 4실험 코드와 벤치마크 세부가 없다. 고객지원 벤치마크의 이름, 크기, 채점 방식은 원문에 없다
이 문서가 대조해 찾은 것
  • ahillclimb 는 고정 커밋의 skill 에 없다(14장). 원문 “Getting started” 는 세 명령을 같은 무게로 소개한다
  • b같은 실험을 platform 문서는 다른 숫자로 적는다. 블로그 −14.6% / 97.0% vs 91.7%, 문서 −14% / 97% vs 92%. 반올림 차이로 보이지만 문서 쪽은 “a gain outside the noise” 라 하고 블로그는 그 판단을 적지 않는다
  • ccache diagnostics API 의 플랫폼 제한(first-party 만, beta)을 원문은 적지 않는다(06장)

한계 밖에서 살아남는 것은 04·05장이다. 캐시의 세 제약과 여덟 처방은 측정이 아니라 API 의 문서화된 동작이고 platform 문서와 일치한다. 07장의 anti-pattern 목록도 실험 결과와 별개로 skill 의 prompt-audit.md 가 같은 것을 더 잘게 정의한다. 벤치마크 숫자를 믿지 않아도 그 두 장은 남는다.

conclusion

글의 핵심은 “세 축을 손으로 고쳐라” 가 아니라 “Claude Code 가 세 축을 고치게 하라” 다. 그중 둘은 skill 저장소에 정의가 있고 하나는 원문에만 있다

prompt cache, instructions, effort 는 각각 다시 계산하는 prefix, 문자 그대로 따르는 낡은 지시문, 과제에 안 맞는 숙고량이라는 낭비다. 원문은 셋 다 성능을 포기하지 않고 줄일 수 있는 비용이라 보이고 그 처방을 claude-api skill 에 넣었다.

사용자가 할 일

모델을 올렸으면 prompt-audit. 청구서를 줄이려면 cost-optimize. 캐시는 안정한 것을 앞에 두고 TTL 안에 있으면 된다. 15장 표 한 장이 전부다.

숫자를 읽는 법

audit −14.6% / +5.3pt, cost-optimize −52~−73%, hillclimb 78.6 → 90.5%. 절감은 크고 성능은 “구분할 수 없음” 이다. 모두 Anthropic 의 자기 벤치마크다.

아직 없는 것

/claude-api hillclimb 는 고정 커밋의 skill 에 없다(14장). 평가가 있는 사용자는 당분간 cost-optimize 에 평가를 주는 경로가 원문상 가장 가깝다.

이 저장소의 선행 문서 Claude Code 세션 비용 모델은 같은 블로그 계열에서 세션 하나의 토큰 개수를 다뤘다. 이 문서는 그 위에 API 애플리케이션 쪽의 세 축과 명령을 놓는다.
