problem

파이프라인은 다음에 무엇을 할지는 알지만, 방금 한 것이 여전히 유효한지는 모른다

기존 자율 연구 시스템은 아이디어 생성에서 실험, 분석, 집필로 출력이 넘어가는 순차 파이프라인이다. 각 단계는 앞 단계의 결과물을 입력으로 받지만, 둘 사이의 근거 관계는 어디에도 기록되지 않는다. 기록이 없으니 검사할 것도 없고, 어긋남은 몇 단계를 지나 최종 원고에서야 드러난다.

논문이 드는 세 가지 어긋남은 전부 "단계는 성공했는데 관계가 깨진" 경우다. 가설이 그것을 요구했던 research gap 과 어긋나고, 실험이 개정 이후의 가설을 더 이상 검증하지 않게 되고, 원고의 주장이 기록된 finding 이 지지하는 범위를 넘어선다. 세 경우 모두 각 단계의 출력만 보면 정상이다.

EviGraph 가 이 자리에 넣은 구분이 pipeline completion 대 evidence readiness 다. 앞의 것은 실행할 단계가 남지 않았다는 뜻이고, 뒤의 것은 남아 있는 모든 주장이 근거로 이어진다는 뜻이다. 논문 5.2절이 사례 하나를 두고 이렇게 정리한다. 초기 연구 객체가 전부 성공적으로 생성되어도, 그래프를 검사해 영향받은 subgraph 를 수리하기 전까지 단계 간 관계는 유효하지 않은 채로 남는다.

여기서 말하는 "근거 없는 주장"은 사실이 틀렸다는 뜻이 아니다. 실행 기록까지 되짚어 갈 경로가 없다는 뜻이다. 참인데 이어지지 않는 주장도 Claim Support Rate 에서는 실패로 계산된다.

state

그래프에 들어갈 수 있는 것을 여섯 타입과 다섯 관계로 잘라 놓았다

연구 그래프는 G = (V, E, τ, ρ, α) 다. τ 가 노드에 타입을, ρ 가 엣지에 관계 타입을, α 가 타입별 구조화 속성을 붙인다. 표현할 수 있는 것을 좁힌 게 이 설계의 핵심이다. 자유 형식 메모라면 "이 실험이 저 가설을 검증한다"가 문장으로만 존재하지만, tested-by 엣지라면 통과 조건을 걸 수 있는 대상이 된다.

Problem 에서 Claim 까지, 다섯 관계가 한 줄로 이어진다

표 1과 3.2절(논문). 허용된 관계는 이 다섯 개뿐이고, 각 관계의 양 끝 노드 타입도 고정돼 있다

노드마다 필수 속성이 정해져 있고, 그래프 validator 가 이걸 강제한다(부록 B.5). Hypothesis 는 statement, mechanism, falsifiable_prediction, boundary_conditions 를 다 채워야 하고, Experiment 는 execution_status 와 execution_record_refs 를, Finding 도 execution_record_refs 를 문다. Claim 만 예외적으로 retained 와 retention_reason 을 들고 있다. 버릴 주장도 그래프에 남되 버렸다는 표시와 이유를 달고 남는다.

validator 는 dangling edge, 중복 노드 ID, 잘못된 양 끝 타입, 필수 속성 누락, 입력에서 해소되지 않는 provenance 참조, 그리고 다섯 관계로 이루어진 의존 subgraph 안의 cycle 을 거부한다. Problem 과 Gap 은 일반 수리 루프 동안 불변 anchor 로 취급되고, 잘못된 anchor 는 하위 에이전트가 조용히 고치는 대신 G0 자체를 다시 만들게 한다.

타입과 관계가 이 여섯 개, 다섯 개로 충분한지는 논문이 논증하지 않는다. 이론적 근거 없이 자율 연구 워크플로에서 관찰되는 객체를 나열한 것에 가깝고, 예를 들어 재현 실패나 반증된 가설을 어디에 놓을지는 Finding 과 Claim 의 서술 안에 흡수돼 있다.

check

관계마다 통과 조건이 붙어 있고, 약한 노드는 그 조건을 어긴 지점에서 정의된다

노드 v 가 약하다는 판정은 v 만 봐서는 내릴 수 없다. 연결된 u 와의 속성이 그 엣지의 관계 타입 ρ((u,v)) 가 요구하는 의미 제약을 만족하지 못할 때 v 가 약해진다. 이게 파이프라인이 못 하는 일이다. 단계 하나만 보면 산출물은 다 정상이다.

통과 조건은 부록 C.1 표 7, issue type 은 부록 C.2 의 Graph Inspector 출력 스키마다. 두 열을 짝지은 것은 이 문서이고 논문에는 이 대응표가 없다. 나머지 두 issue type 은 관계가 아니라 그래프 전체에 붙는다. 노드나 엣지가 아예 없으면 MISSING_DEPENDENCY, 남길 주장이 하나도 없으면 NO_RETAINED_CLAIM 이다.

이 표에서 제일 강한 조건은 tested-by 다. 요구 사항이 "실험이 가설과 관련 있다"에서 멈추지 않고 "프로토콜이 예측된 결과를 반증 조건으로부터 구분해 낼 수 있다"까지 간다. 가설을 지지하는 쪽으로만 설계된 실험은 이 조건에서 걸린다. 반대로 검사기가 명시적으로 넘어가야 하는 것도 하나 있다. 기록된 음성 결과는 가설과 모순된다는 이유만으로 약해지지 않는다. Finding 으로 보존하고, 범위를 제한한 음성 Claim 을 만들거나 가설을 unsupported 로 표시하라고 프롬프트에 적혀 있다(부록 C.2 규칙 8).

구조 검사가 의미 검사보다 먼저다. 양 끝 노드가 존재하는지, 타입이 관계 스키마와 맞는지, 필수 속성과 provenance 가 있는지를 통과한 다음에야 의미 제약을 본다. 없는 엣지 위에서 의미 불일치를 보고하는 대신 MISSING_DEPENDENCY 로 분류하기 위해서다.

통과 조건 자체는 LLM 이 판정한다. Graph Inspector 가 그래프와 실행 기록을 받아 JSON 으로 판정을 돌려주고, orchestration 코드는 그 JSON 이 스키마에 맞는지만 검사한다. 즉 "가설이 gap 에서 표류했다"는 판정의 신뢰도는 backbone 모델의 판단력을 넘지 못한다. 이 경계가 어디에 그어져 있는지는 7장에 있다.

repair

약한 노드 하나를 고치면 그 내용에 의존하던 하위 노드가 전부 다시 만들어진다

검사기는 약한 노드 w 와, 내용이 w 의 현재 상태에 의존하는 하위 노드를 묶어 repair group S_w 를 낸다. 수리는 w 를 먼저 고치고, S_w \ {w} 를 지운 다음 의존 순서대로 재생성한다. 옛 내용이 그럴듯해 보여도 다시 만들라고 Repair Planner 프롬프트 규칙 7이 못 박는다.

루프는 검사기로 두 갈래로 되돌아온다

Algorithm 1(논문)과 부록 D. 되돌아오는 경로가 두 개다

어느 group 부터 고칠지는 코드가 정한다. blocking 이슈를 먼저 잡고, 그다음은 Problem → Gap → Hypothesis → Experiment → Finding → Claim 타입 순서에서 깊이가 얕은 root 를, 마지막은 안정적인 노드 ID 순서다(부록 D). 위쪽 노드를 먼저 고치는 이유는 명확하다. 가설이 틀린 채로 그 아래 실험과 주장을 고쳐 봐야 다음 검사에서 다시 걸린다.

Repair Planner 는 노드 타입에 따라 담당 에이전트를 배정한다. Hypothesis 는 Hypothesis Agent 로, Experiment 의 프로토콜이나 코드는 Experiment Agent 로, Finding 과 Claim 은 Analysis Agent 로 간다. 각 액션에는 필요한 선행 노드, 실행 기록, 실패 피드백, 해당 제약만 준다. S_w 바깥의 객체는 전부 보존하고 관련 없는 편집은 아예 일정에 넣지 않는다.

실제 실행에서 Repair Planner 가 하위 노드 집합을 정확히 잡는지, 재생성이 몇 번 만에 수렴하는지, 45개 과제 전체에서 rollback 과 REINITIALIZE 가 각각 몇 번 발동했는지는 논문에 수치가 없다. 루프가 실제로 여러 바퀴 도는지 대부분의 실행이 한 번의 수리로 끝나는지에 따라 이 구조를 도입할 이유의 크기가 달라지는데, 그 값이 없다.

표 6(논문)을 옮긴 것이다. 논문은 오른쪽 열을 "deterministic" 이 아니라 "orchestrated" 라고 부르는데, 문헌 검색과 실험 실행이 외부 서비스와 벤치마크 환경에 의존하기 때문이라고 밝혀 놓았다. 두 그래프 라이브러리는 프롬프트 받는 에이전트가 아니라 데이터 저장소다.

열화 판정

수리가 개선인지 아닌지를 정하는 식은 부록 D 에 산술로 적혀 있다. 둘 중 하나라도 참이면 열화다.

// W(G) 는 검사가 낸 약한 root 집합, P_valid(G) 는 완전하고 유효한 근거 사슬 ID 집합
Degrading(G_cand, G_base) =
    |W(G_cand)| > |W(G_base)|          // 약한 노드가 늘었거나
  or  P_valid(G_base) ⊄ P_valid(G_cand)   // 이미 유효하던 사슬이 사라졌거나

되돌릴 때는 G_base 에서 파생됐고 G_base 의 유효 사슬을 전부 보존하는 checkpoint 중에서 약한 root 수가 최소인 것을 고른다. 동점이면 가장 최근 것. G_base 를 엄밀히 개선하지 못하면 G_base 원본으로 정확히 되돌아간다.

이 식이 하는 일은 하나다. 유창하지만 근거 없는 하위 재작성이 이미 검증된 근거를 밀어내지 못하게 막는 것이다. 모델에게 "이 수리가 나아졌나?"를 묻는 대신 두 그래프의 약한 root 수와 유효 사슬 집합을 비교한다. 같은 이유로 트랜잭션 절차는 S_w 바깥으로의 쓰기, dangling 엣지, 타입이 틀린 엣지, 해소되지 않는 provenance, cycle, 기록에 없는 값을 전부 거부한다.

실행에도 같은 선이 그어져 있다. Experiment Agent 는 도구 실행을 요청할 수 있지만 도구가 기록을 돌려주기 전에 성공이나 결과를 보고할 수 없다. 그럴 때는 needs_execution 과 tool_request 를 반환해야 하고, 이 응답은 그래프를 바꾸지 않는다. orchestrator 가 sandbox 에서 실행해 불변 record ID 로 저장한 뒤 같은 액션을 그 기록과 함께 다시 부른다. 실험 결과를 지어내는 경로가 구조적으로 막혀 있다.

이 식에는 대가가 하나 붙는다. 오른쪽 조건은 "이전에 유효했던 사슬이 하나라도 사라지면 열화"이므로 단조 증가만 허용한다. 과대 주장을 발견해 Claim 을 정당하게 철회하는 수리도 형식상 같은 모양이 된다. 논문은 P_valid 를 "완전하고 유효한 근거 사슬의 식별자 집합"으로만 정의하고, retained 가 거짓으로 바뀐 Claim 의 사슬이 이 집합에서 어떻게 되는지는 규정하지 않는다. 철회가 열화로 잡히는지 아닌지가 명세에서 결정되지 않은 채 남아 있다. 이건 이 문서의 읽기이고 논문이 다루는 논점이 아니다.

막힌 것은 지어내기이고, 막히지 않은 것은 잘못 판정하기다. 어떤 실행 기록이 어떤 Finding 을 뒷받침하는지, 가설이 gap 에서 표류했는지는 여전히 LLM 이 판단한다. 코드가 하는 것은 그 판단의 형식을 강제하고, 판단 사이의 산술을 대신하는 데까지다.

논문을 쓸지 말지가 그래프 상태의 함수다

파이프라인에서 집필은 마지막 단계라서 시작된다. EviGraph 에서 집필은 Ready(G) 가 참이 되어야 시작된다. 예산이 먼저 끝나면 원고를 내는 대신 Incomplete 를 반환하고, Paper Writer 는 아예 호출되지 않는다.

Ready(G) 가 참이려면 넷을 다 만족해야 한다
  1. schema 가 유효하다
  2. retained 된 Claim 이 적어도 하나 있다
  3. 과제 맥락이 요구한 empirical deliverable 을 덮는다
  4. retained 된 모든 Claim 이 약한 노드 없는 완전 유효 근거 사슬을 적어도 하나 가진다

원고 배포 조건은 따로 둘이다
  5. Paper Reviewer 가 ready=true 와 빈 이슈 목록을 반환한다
  6. provenance map validator 가 모든 실질적 주장과 보고된 값을 해소한다
  → 재시도 상한 안에 못 넘기면 미해결 draft 를 내는 대신 Incomplete

2번 조건이 이 정의에서 가장 눈에 안 띄면서 중요한 자리다. 4번은 "retained 된 모든 Claim 에 대하여"라는 전칭 명제라서, retained Claim 이 하나도 없으면 공허하게 참이 된다. 주장을 전부 버린 그래프가 만점짜리 근거 상태로 통과할 수 있다는 뜻이다. 부록 A 가 이 구멍을 명시적으로 막는다. 실행이 방어 가능한 주장을 하나도 내놓지 못하면 그 실행은 Incomplete 로 끝난다.

Paper Writer 는 세 모드로 나뉜다. SKELETON 은 산문을 쓰지 않고 문단마다 어느 노드 ID, Claim ID, artifact ID, 인용 ID, 필수 qualifier 를 쓸지만 반환한다. 근거가 없어 뺀 내용은 omitted_content 에 이유와 함께 남긴다. DRAFT 는 승인된 skeleton 을 펼치되 실질적 주장을 추가할 수 없고, 문장 span 마다 provenance_map 을 함께 낸다. REVISION 은 리뷰 이슈마다 가장 작은 변경을 적용하고 edit_log 를 남긴다.

Paper Reviewer 는 네 기준만 본다. 구조 일관성, novelty 서술이 주어진 Gap 과 문헌의 범위를 넘지 않는가, 인용이 실제로 존재하고 그 명제를 뒷받침하는가, 그리고 GRAPH_FAITHFULNESS. 마지막 것이 그래프와 원고를 잇는 마지막 검사다. 모든 실질적 주장이 retained Claim 의 범위와 qualifier 를 보존하고 완전한 사슬을 가지는지, 모든 실험 서술과 값이 artifact 와 일치하는지를 본다.

이 게이트는 논문이 안 나올 수 있다는 것을 정상 결과로 만든다. 그러면 거부율이 이 아키텍처의 가격표가 되는데 그 값이 논문에 없다. 표 3 의 E2E 100% 를 근거로 쓸 수는 없다. E2E 는 NanoResearch-20 이 자기 하네스로 재는 workflow 완주 지표이고, ARC-Bench-ML 쪽에는 그 열이 아예 없으며, EviGraph 의 Incomplete 반환을 그 지표가 실패로 계상한다고 논문이 적은 적도 없다. 부록 F.1 표 8 은 Incomplete outcomes 를 별도 감사 항목으로 남겨 둔다.

비교 대상은 둘이다. AutoResearchClaw 는 전 단계 파이프라인에 엄격한 출력 평가를 붙인 시스템으로, full-auto 설정으로 돌렸다. NanoResearch 는 실행 간 진화와 시뮬레이션된 과학자 피드백으로 여러 라운드에 걸쳐 자기 개선을 하는 시스템이다. 셋 다 qwen-3.6-plus 백본에 같은 sandbox, 같은 실험당 시간 예산으로 돌렸다.

선행 연구 위치는 두 갈래로 잡는다. 자율 연구 시스템 쪽에는 AI Scientist 계열이 있고, 과학 지식 그래프 쪽에는 ORKG, micropublications, nanopublications 가 있다. EviGraph 가 자기 자리를 잡는 문장은 후자에 대해서다. 기존 구조화 표현이 연구 객체와 provenance 를 표현했다면, EviGraph 는 그래프를 연구 중에 계속 갱신되면서 불일치가 발견되면 새 과학 행동을 지시하는 능동적 제어 구조로 만든다.

이 위치 설정은 논문의 related work 절에서 온 것이다. 자기 기여를 가장 유리하게 서술할 유인이 가장 강한 부분이라, 여기 적힌 대비를 그대로 받아들이면 안 된다. ORKG 나 nanopublication 쪽 문헌은 이번에 열어보지 않았다.

실험이 성공적으로 돌았는데도 가설이 약한 노드로 잡힌다

논문이 끝까지 따라간 실행 하나는 ARC-Bench-ML 의 Lightweight Short-Text Classification via Frozen PLM Representation Calibration 과제다. 장기 그래프 라이브러리에 관련 기록이 없는 cold start 실행이라, 이전 실행에서 넘어온 것 없이 이번 실행 안에서만 벌어진 일이다.

논문의 방어는 방향이 맞지만 검증할 수가 없다. 부록 F.3 이 |C|, |S|, |F|, |K| 원시 카운트를 모든 집계에 동반한다고 규정해 놓고 논문에는 싣지 않았다. 분모가 20개인지 2,000개인지 모르는 상태에서 37.85% 와 27% 의 차이가 얼마나 견고한지는 판단할 수 없다. 같은 stochastic 성질이 이 격차의 불확실성이기도 한데 표 4 는 단일 집계이고 분산도 반복 실행도 없다. 두 벤치마크를 합친 micro-average 라 벤치마크별 분해도 없다.

critique

아키텍처가 원인이라는 주장은 아직 실험으로 확립되지 않았다

논문의 핵심 명제는 "이 문제는 부분적으로 아키텍처 문제다"이고, 이걸 확립하려면 아키텍처를 빼 보는 실험이 있어야 한다. 그게 없다. 아래 왼쪽은 논문이 스스로 밝힌 한계, 오른쪽은 이 문서가 원문을 읽고 주장하는 것이다.

논문이 명시한 한계
  • 1ablation 이 없다. 컴포넌트가 공유 그래프로 강결합돼 있어 하나를 제거하면 나머지의 연구 상태와 동작 조건까지 바뀌어 해석이 어렵다는 이유다. 대신 표 5 가 컴포넌트와 평가 신호를 정성적으로 대응시킨다
  • 2CSR 절대값은 보수적이다. 추출이 stochastic 이라 분모가 실행마다 달라지고 근거 대기 어려운 주장이 섞인다
  • 3Alignment 는 뒤진다. 6.6 대 8.8. 원래 과제 서술을 엄격히 지키는 쪽에 개선 여지가 있다고 적는다
  • 4사례가 rollback 과 장기 검색을 실증하지 않는다. 첫 수리가 성공했고 M_L 이 비어 있었다. 미관측 분기를 결과로 제시하지 않고 명세된 제어 동작만 서술한다
  • 5추정하지 않는다. 하드웨어, 샘플링, seed, timeout 을 부록이 재구성하지 않고 run manifest 의 몫으로 남긴다
이 문서가 주장하는 것
  • 1남은 대안 설명은 계산량이다. 백본과 sandbox 와 시간 예산이 같으니 모델 능력 차이는 배제된다. 그런데 EviGraph 는 pilot 과 full-scale 과 수리 재실행을 한다. 부록 D 가 예산 회계를 세 시스템 동일 정책으로 한다고 적지만, 실제 소비된 토큰과 실행 횟수가 없어 "같은 예산에서 이겼다"를 확인할 방법이 없다. 가장 큰 구멍이 여기다
  • 2재현에 필요한 값이 규정만 남고 빠졌다. 원시 카운트(13장), 실행 횟수, 벤치마크 실행 시의 M_L 상태, 판정 모델명, baseline 재실행 설정. 표 8 이 전부 감사 항목으로 나열해 놓았고 manifest 는 공개되지 않았다(11장)
  • 3코드가 없고 심사도 거치지 않았다. 공개 링크 블록이 주석 처리된 채 나간 v2 preprint 다. 외부 재현 보고도 없다. 셋이 겹친 상태라는 것이 "기다린다"의 근거다
  • 4뒤진 두 칸은 수리 루프의 예상 가능한 부작용으로 읽힌다. Alignment 는 과제 준수를 재는데 수리 루프는 그래프 내부 제약을 맞추려고 가설과 실험을 재작성한다. EDC 는 보고값과 실행 기록의 일치인데 EviGraph 는 Finding 과 Claim 을 반복 재생성한다. 논문은 이 연결을 하지 않는다
  • 5검사기의 신뢰성이 백본에 걸려 있다. 원고를 쓰는 것도 관계를 판정하는 것도 같은 qwen-3.6-plus 다. 그 모델이 못 보는 종류의 표류는 이 아키텍처로도 안 걸리고, 다른 모델로 옮겼을 때 통과 조건 판정이 같은 품질로 나온다는 증거도 없다

한 가지는 반대 방향으로 작동한다. 두 벤치마크 모두 EviGraph 팀이 만든 것이 아니라 비교 대상이 만든 것이다. ARC-Bench-ML 은 AutoResearchClaw 가, NanoResearch-20 은 NanoResearch 가 정의했고 평가도 각자의 공식 하네스를 쓴다. 자기 벤치마크를 들고 나와 이기는 구도가 아니라는 점은 이 결과를 강화한다. 다만 baseline 을 어떤 설정으로 다시 돌렸는지는 저자의 결정이고 공개되지 않았다.

ablation 없이도 남는 것이 있다. 타입 계약(여섯 노드, 다섯 관계, 관계별 통과 조건), 열화 판정을 코드로 내리는 경계, 집필을 상태로 게이팅하는 것. 여기서 근거의 종류를 구분해야 한다. 논문이 강결합을 이유로 ablation 을 건너뛰었다면, 떼어낸 조각이 EviGraph 안에서 얼마나 기여했는지는 이 논문의 수치로 예측되지 않는다. 15장의 권고가 기대는 것은 그쪽이 아니라, 각 조각이 무엇을 구조적으로 막는지가 설계만으로 판정된다는 쪽이다. 타입 계약이 없으면 관계를 검사할 자리가 없고, 열화 판정을 모델에게 물으면 유창한 재작성이 통과하고, 게이트가 없으면 근거 없는 원고가 나간다. 이 셋은 86.45% 와 무관하게 성립한다.

CSR 을 재는 절차도 남는다. 원고를 chunk 로 쪼개 주장을 추출하고 실행 기록과 대조하는 파이프라인은 부록 F 의 서술만으로 만들 수 있고, 지금 돌리는 에이전트에 붙이면 나중에 무엇을 도입하든 비교 기준선이 이미 있는 상태가 된다.

adopt

시스템을 도입할 근거는 아직 없고, 설계를 옮길 근거는 지금 있다

코드도 비용도 실행 횟수도 공개되지 않았으므로 EviGraph 자체를 채택할지는 지금 판단할 수 없다. 반면 부록 A 부터 E 까지가 프롬프트와 출력 스키마와 트랜잭션 절차를 그대로 싣고 있어서, 설계 결정 단위로 떼어 쓸 재료는 대부분 있다. 그래프 생성 이전 단계의 프롬프트(부록 B.4)는 이 문서가 읽지 않은 자리다.

지금 처한 상황권하는 것
자율 연구 또는 다단계 분석 에이전트를 만들고 있다여섯 노드와 다섯 관계의 타입 계약, 그리고 관계별 통과 조건(5장)부터 옮긴다. 자유 형식 메모를 타입 있는 엣지로 바꾸는 것만으로 검사할 대상이 생긴다. 시스템 전체보다 훨씬 싸다
에이전트가 쓴 문서의 주장이 실제 실행과 어긋난다집필을 두 모드로 쪼갠다. 산문 없이 문단마다 근거 ID 만 반환하는 skeleton 단계를 앞에 두고, 초안에서 span 마다 provenance map 을 받는다(8장). 모델을 바꾸지 않고 붙일 수 있다
긴 실행에서 자기 수정이 오히려 상태를 망가뜨린다열화 판정을 코드로 내린다. 수정 전후의 미해결 문제 수와 이미 통과했던 검사 집합을 비교해 후자가 줄면 되돌린다(7장). 도메인이 연구가 아니어도 쓰이지만, 통과한 것을 취소할 수 없게 만드는 단조성이 같이 따라온다는 점은 7장 마지막 문단을 보고 정할 것
수리 루프까지 붙일지 정해야 한다위험을 같이 계산한다. EviGraph 가 뒤진 두 칸(Alignment 6.6 대 8.8, EDC 87.73% 대 96.15%)이 둘 다 반복 재생성의 부작용으로 읽힌다(14장). 과제 준수와 값 충실도가 내려갈 수 있다는 뜻이고, 논문은 이 대가를 계산해 주지 않는다
백본이 qwen 계열이 아니다이 문서만으로 정할 수 없다. 세 시스템 모두 qwen-3.6-plus 한 종류로만 돌았고, 관계 통과 조건 판정이 다른 모델에서 같은 품질로 나온다는 증거가 없다. 옮긴다면 Graph Inspector 판정의 재현성부터 자체 측정할 것
EviGraph 를 그대로 도입할지 정해야 한다기다린다. 코드 공개, 원시 카운트, 그리고 최소한 그래프 검사를 끈 조건 하나를 비교한 실험이 나오기 전까지는 근거가 없다
비용이 감당되는지 알아야 한다판단 근거가 아예 없다. 토큰, 실행 시간, 수리 반복 횟수 중 어느 것도 논문에 없다. pilot 과 수리 재실행이 붙는 구조상 단일 패스보다 비쌀 것은 분명하지만, 얼마나인지는 모른다

떼어 쓸 때 순서가 있다면 첫째가 타입 계약, 둘째가 집필 게이트, 셋째가 수리 루프다. 앞의 둘은 기존 파이프라인을 거의 건드리지 않고 붙고, 효과도 각각 독립적으로 확인된다. 수리 루프는 상태 되감기와 재실행이 필요해 실행 인프라를 바꿔야 하고, 위 표의 위험 두 개가 여기 붙어 있으므로 가장 나중이다.

부록의 프롬프트 원문을 제품 코드에 그대로 복사할 생각이라면 라이선스를 먼저 확인할 것. 이 preprint 는 arXiv 의 기본 배포 라이선스(perpetual non-exclusive license 1.0)로 올라가 있고, 이건 arXiv 에 배포 권리를 준 것이지 읽는 쪽에 재사용 권리를 준 것이 아니다. CC 계열 표기가 없다. 설계를 참고해 다시 쓰는 것과 문자열을 복사하는 것은 다른 문제다.

conclusion

목표를 상태의 술어로 옮겨 놓았다

"근거 없는 주장을 줄인다"는 목표를 프롬프트로 옮기면 "근거 없는 주장을 하지 마라"가 되고, 그건 이미 다들 하고 있다. EviGraph 는 이걸 상태의 술어로 옮겼다. 남길 주장마다 약한 노드 없는 완전한 근거 사슬이 있어야 한다는 조건이고, 이 조건이 참이 될 때까지 집필 단계가 열리지 않는다.

이 번역이 성립하려면 세 가지가 먼저 있어야 했다. 근거 관계를 적어 둘 자리(여섯 타입과 다섯 관계), 그 자리가 채워졌는지 물을 수 있는 질문(관계별 통과 조건), 그리고 그 질문의 답이 나아졌는지 세는 산술(약한 root 수와 유효 사슬 집합). 파이프라인에는 첫 번째가 없어서 나머지 둘이 성립할 수 없었다. 아키텍처 문제라는 진단은 이 뜻이다.

측정된 결과는 방향은 맞고 크기는 확정되지 않았다. ARC-Bench-ML Overall 86.45% 대 60.37% 는 크고, 그 격차의 73%가 결과 해석 지표에서 온다는 분해도 아키텍처 서사와 맞아떨어진다. Claim Support Rate 는 27% 에서 37.85% 로 오르지만 절대값으로는 주장의 60% 이상이 여전히 안 이어지고, Experimental Data Consistency 는 87.73% 로 NanoResearch 의 96.15% 에 진다. ablation 이 없으므로 이 개선이 그래프 상태 유지에서 왔다는 것은 아직 주장이지 확립된 사실이 아니고, 남은 대안 설명인 계산량 차이는 논문에 비용 수치가 없어 배제되지 않는다.

그래도 이 논문에서 지금 가져갈 수 있는 것은 분명하다. 에이전트에게 무엇을 하라고 지시하는 대신 무엇이 참이어야 다음 단계가 열리는지를 코드로 적어 두는 방식, 그리고 그 판정을 모델에게 되묻지 않는 경계다. 이 둘은 연구 자동화 밖에서도 그대로 쓰인다.

4장부터 8장까지의 아키텍처 서술은 전부 명세에 관한 것이다. 부록의 프롬프트, 출력 스키마, 트랜잭션 pseudocode 가 근거이므로, 구현이 그 명세대로 도는지에 대해서는 아무것도 말하지 않는다. 확인할 코드가 없다.
