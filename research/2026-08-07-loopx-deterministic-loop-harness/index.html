LoopX: 에이전트 루프가 할 일을 잊지 않게 만드는 결정론적 제어 평면

긴 작업을 도는 에이전트는 목표를 잊고, 잊었다는 사실도 잊는다. LoopX 의 답은 회계다. 검증된 writeback 이 없으면 그 턴은 진행으로 계상되지 않고, 계상되지 않은 턴이 쌓이면 제어 평면이 계획을 다시 세우라고 강제한다. 그 장치를 코드에서 추적하고, 실증이 어디까지 왔는지까지 정리했다.

LoopX 를 설치해서 돌리지 않았다. 코드와 저장소 문서만 읽었다. 런타임 동작이라고 쓴 문장이 하나도 없도록 표현을 제한했고, 그 경계를 11장에 모아 두었다.

tl-dr

기억을 늘리는 대신, 진행으로 인정받는 조건을 좁혔다

LoopX 는 에이전트 런타임이 아니다. Codex 나 Claude Code 가 한 턴을 실행하는 동안 목표, 게이트, todo, 증거, quota 를 파일에 들고 있는 로컬 제어 평면이다. 핵심 설계는 하나로 요약된다. 턴이 진행으로 계상되려면 검증과 writeback 을 통과해야 하고, 그 판정에는 LLM 이 개입하지 않는다.

판정에 모델을 안 쓴다PROTOCOL_ACTION_PACKET_LLM_POLICY = "no_api". 계속할지 말지는 파일 상태를 읽는 파이썬 코드가 정한다
지출이 마지막에 온다트랜잭션 7단계가 result<validate<writeback<spend 순서로 고정돼 있다. 단계를 건너뛴 영수증은 invalid 로 떨어진다
표면 작업이 누적되면 계약이 바뀐다작은 배치가 2회, 표면 성과가 3회 연속이면 다음 턴에 최소 규모와 금지 항목이 붙은 계약이 주입된다
탈락한 후보를 적게 만든다heartbeat 프롬프트가 매 턴 후보 3개 이상을 나열시키고, 고른 것 말고 버린 고가치 후보를 기록하게 한다
벤치마크 향상은 아직 없다공개된 페어 실행 결과는 0.0/0.0 paired_no_score_uplift. 저장소 스스로 이를 "인프라 증거이지 성능 증거가 아니다"라고 적는다

도입 판단은 12장에 있다. 결론만 먼저 적으면, 개인이 며칠짜리 목표를 돌리는 데는 지금도 쓸 만하고, 여러 프로젝트가 런타임 루트를 공유하는 환경에서는 미해결 레지스트리 경합 버그(issue #2823) 때문에 기다리는 쪽이 낫다.

problem

"잊는다"는 기억의 문제가 아니라 무엇을 진행으로 셀지의 문제다

긴 루프가 망가지는 방식은 목표를 문자 그대로 망각하는 것이 아니다. 매 턴 뭔가를 하긴 하는데 그게 목표를 옮기지 않고, 옮기지 않았다는 사실이 아무 데도 기록되지 않는 것이다. 저장소의 원칙 문서가 이 구분을 직접 적는다.

두 번째 함정이 잊음의 정확한 정의다. 채팅에만 존재하는 계획은 다음 에이전트가 볼 수 없으므로, 존재하지 않는 것과 같다.

세 번째는 회계다. 토큰을 아무리 적게 써도 루프는 사용자의 신뢰를 태울 수 있다. 그래서 quota 는 검증된 전이를 만들었는지만 센다는 원칙이 6번으로 박혀 있다. 말을 얼마나 했는지는 세지 않는다(같은 파일 47-49행).

이 세 문장은 원칙 문서의 주장이지 측정 결과가 아니다. LoopX 가 실제로 드리프트를 줄였다는 공개 수치는 10장에서 다루는데, 결론부터 말하면 아직 없다.

architecture

상태는 6개 층에 나눠 살고, 누가 무엇을 쓸 수 있는지는 4개 역할이 정한다

LoopX 에는 서버도 데이터베이스도 없다. 프로젝트 디렉터리 밑의 .loopx/ 에 JSON 과 Markdown 을 두고, CLI 가 파일 락을 잡고 고친다. 아키텍처 문서는 그 파일들을 6개 층으로 부른다.

docs/architecture.md:6-13. 표는 그 목록을 옮긴 것이다.

goal 상태 파일은 YAML frontmatter 가 붙은 평범한 Markdown 이다. 예시 파일이 섹션 구성을 그대로 보여준다: Objective, Operating Contract, Non-Goals, Next Action, Recent User Feedback, Progress Ledger(examples/active-goal-state.example.md). 사람이 열어서 고칠 수 있고, 파서가 섹션 단위로 읽는다.

층이 상태의 위치라면, 역할은 권한의 경계다. 실행 경로는 Agent → Capability → Provider 로 나가고 제어 경로는 반대로 돌아온다. 그 사이에 한 문장이 끼어 있다.

Kernel 은 goal·todo·claim·gate·monitor·quota·writeback·recovery·scheduling 을 소유하고, 도메인 추론과 provider 구현은 소유하지 못한다. 거꾸로 Capability 는 도메인 정책과 검증을 소유하되 스케줄링·claim·gate·생명주기 직접 쓰기는 못 한다(docs/architecture.md:77-82). 어떤 기능을 추가하든 이 표의 어느 칸에 들어가는지를 먼저 답해야 하는 구조다.

런타임 모델에서 goal 은 goal_id 경계이고 todo 는 그 안의 구조화된 체크박스다. 별도의 issue 객체는 없다(docs/architecture.md:253-256). GitHub issue 를 다루는 capability 는 있지만, 그건 도메인 레인이지 커널 객체가 아니다.

nav-guard

표류를 막는 장치는 여섯 개이고, 전부 파일 상태를 읽는 결정론적 코드다

"이상한 데로 빠지지 않게" 하는 방법은 두 가지다. 프롬프트로 타이르거나, 진행으로 인정하지 않거나. LoopX 는 뒤쪽에 몰려 있다. 아래 여섯 개는 전부 loopx/control_plane/ 안의 순수 함수이고, 판정에 모델을 호출하지 않는다.

원문에 이 여섯 개를 한 표로 묶은 문서는 없다. 모듈을 읽고 만든 표다.

세 번째와 네 번째가 이 질문의 핵심이다. LoopX 는 턴의 결과를 4단계로 분류한다. surface_only, outcome_gap, outcome_progress, primary_goal_outcome(work_items/delivery_outcome.py:7-13). 앞의 둘만 연속되면 회계가 개입한다.

임계를 넘으면 다음 턴 페이로드에 계약이 하나 붙는다. 최소 규모를 올리고, 무엇을 추진해야 하는지와 무엇을 피해야 하는지를 이름으로 적고, 못 하겠으면 blocker 를 쓰되 quota 를 쓰지 말라고 지시한다. 주입되는 문장은 중국어다.

follow-through 는 더 좁다. 직전 턴이 contract_only_preparation 이었으면 다음 턴의 의무가 문자열로 못박힌다.

여섯 번째, decision scope 는 반대 방향의 표류를 막는다. 사람 결정을 기다리느라 전체가 멈추면 루프는 조용히 죽는다. 게이트에 granularity 를 붙여 action 짜리 결정은 그 액션만 막고 나머지 레인은 계속 돌게 한다. 사용자가 미리 goal·project·global 수준 권한을 세워 두는 standing_decision_authority 도 같은 파일에 있다(todos/decision_scope.py:38-40).

기본값에 큰 구멍이 하나 있다. outcome_markers 와 surface_only_hints 가 빈 리스트로 출고된다(execution_profile.py:21-22). 이 둘이 비면 outcome_floor_configured() 가 false 를 돌려주고 outcome_gap_streak 이 항상 0 이 된다(work_items/delivery_signals.py:74-91). outcome floor 는 프로젝트가 분류 문자열을 직접 등록해야 켜지는 opt-in 장치다. 작은 배치 연속 감지 쪽은 분류 문자열 휴리스틱으로 기본 동작한다.

host-binding

Claude Code 에는 네 줄짜리 프로토콜 파일과 선택적 PreToolUse 훅으로 붙는다

LoopX 는 자기 런타임을 만들지 않는다. Claude Code 에서는 네이티브 /loop 가 루프를 돌고, LoopX 는 매 tick 의 게이트만 담당한다. 어댑터 README 가 /goal 을 쓰지 않는 이유를 명시한다.

/loopx <task> 가 하는 일은 goal 을 등록하고 .claude/loop.md 를 쓰는 것뿐이다. 그 파일이 매 iteration 마다 실행되는 프로토콜이고, 표류 방지의 핵심이 여기 네 줄로 압축돼 있다.

"추론으로 성공을 선언하지 말라"와 "todo 밖의 이니셔티브를 시작하지 말라"가 프롬프트 층의 방어다. 프롬프트만으로는 약하니 결정론적 층이 하나 더 있는데, 기본 설치에는 들어가지 않는다. install.py --harden 을 명시적으로 줘야 PreToolUse 훅이 붙는다(hooks/hooks.json:2).

훅이 붙으면 툴 호출마다 세 가지를 본다. 읽기 전용 툴은 무조건 통과, 나머지는 loopx quota should-run 을 물어보고 false 면 거부, Edit/Write 는 경로가 write_scope 밖이면 거부. 프로브가 안 뜨면 fail-closed 다.

읽기 전용 허용 목록에서 Task 가 일부러 빠져 있다. 서브에이전트를 띄우면 그 안에서 쓰기가 일어나므로 게이트를 우회한다는 이유가 주석으로 붙어 있다(goal_policy.py:57-60). 이런 종류의 구멍을 하나씩 막은 흔적이다.

같은 파일이 자기 한계를 먼저 적는다. Bash 는 rm -rf·git push --force 같은 문자열 denylist 로만 막는다. write_scope 로 가두지 않는다(goal_policy.py:63-66). 모듈 docstring 이 "a determined shell command can still write outside write_scope or reach the network"라고 쓰고, 강한 격리가 필요하면 컨테이너나 VM 을 쓰라고 권한다(goal_policy.py:15-18). 훅은 샌드박스가 아니다.

trace

턴 하나가 승인되는 경로: 봉투 검사 → 라우트 → 세션 결속 → 트랜잭션 계획

추적 대상은 build_loopx_turn_plan() 하나다. 입력은 quota 가 만든 TurnEnvelope, 출력은 부작용이 전혀 없는 타입 결정이다. 프로세스 경계를 넘지 않고 loopx/control_plane/turn_driver/ 안에서 끝난다.

hop 1. 봉투가 자기 자신과 맞는지 본다. action signature 의 두 해시가 다르면 그 자리에서 CONTRACT_ERROR 다. 오래된 페이로드나 손댄 페이로드가 턴을 얻지 못한다.

hop 2. 컨텍스트 압축이 예산 안인지 본다. 바로 다음 세 줄이 compaction.within_budget 을 확인하고, 아니면 역시 CONTRACT_ERROR 다(driver.py:71-73). 컨텍스트가 넘친 상태로 실행에 들어가는 경로가 구조적으로 막혀 있다.

hop 3. 라우트를 고른다. should_run 이 true 여도 delivery_allowed 와 must_attempt 가 둘 다 true 가 아니면 BLOCKED 이고, effective action 이 replan·repair 계열이면 각각 REPLAN_REQUIRED·REPAIR_REQUIRED 로 갈라진다(driver.py:82-96). 전체 7종은 4장 표에 있다.

hop 4. 세션이 같은 일을 하는 세션인지 본다. 여기가 "다른 데로 새는 것"을 막는 가장 직접적인 장치다. 재개하려는 세션의 goal_id·agent_id·todo_id 가 지금 턴의 lineage 와 정확히 같지 않으면 재개를 거부한다.

hop 5. 트랜잭션 계획을 만든다. lineage 와 host·실행 모드·스케줄러 소유자·세션 동작을 canonical JSON 으로 직렬화해 sha256 을 뜬 것이 turn_key 다(transaction.py:141-150). 커밋 정책이 문자열 한 줄로 박힌다.

hop 6. 실행 후 영수증을 검사한다. validate_loopx_turn_receipt() 는 completed_phases 가 7단계의 앞에서부터 잘린 접두사인지 본다. 순서를 건너뛰면 에러다(transaction.py:181-184). 그리고 지출을 막는 규칙이 두 줄로 들어간다.

이 경로는 전부 순수 함수다. 계획 payload 가 "host_invoked": False, "state_written": False, "quota_spent": False 를 명시하고 "read_only": True 를 붙인다(driver.py:335-346). 실제로 host 를 부르는 것은 별도의 execute 표면이고, 그건 열지 않았다. 계획과 실행의 분리가 코드에 있다는 것까지가 읽어서 확인한 범위다.

examples/ 의 smoke 655개를 안 읽어서 9장의 규모 서술이 "무엇을 검증하는 코드인지"까지 가지 못한다. 파일명으로 주제는 보이지만(autonomous-replan-obligation-smoke.py, quota-executable-backlog-projection.py), 안에서 실제로 무엇을 단언하는지는 열지 않았다.

loopx/capabilities/ 를 안 읽어서 4장 역할 표에서 Capability 칸이 문서 주장으로만 남는다. issue-fix·content-ops·explore 같은 도메인 레인이 정말 커널 권한을 안 가져가는지는 모듈을 열어야 확인되고, 열지 않았다.

7장 추적은 turn_driver/ 4개 파일 중 driver.py 와 transaction.py 둘만 읽고 썼다. 실제 host 호출이 일어나는 executor.py(1,174행)와 codex_cli.py(502행)는 열지 않았다. 그래서 7장은 계획과 영수증 검사까지이고, 실행 자체는 다루지 않는다.

result-scale

LoopX 는 자기 자신을 LoopX 로 만든다고 말한다. 체크아웃에서 그 규모를 셀 수 있고, 숫자는 두 가지를 동시에 말한다.

구성은 프로덕션 코드보다 검증 스크립트가 더 무겁다. loopx/ 687개 파일 307,915행에 대해 examples/ 의 smoke 스크립트가 655개 222,776행이다. 별도로 regression/ 에 12개 스크립트가 있고, README 는 이쪽을 "릴리스나 큰 제어 평면 변경 때 의도적으로 돌리는" 저빈도 회귀로 정의한다(regression/README.md:3-8).

런타임 의존성은 0이다. pyproject.toml 의 dependencies = [] 이고, 테스트용 extra 에만 pytest·ruff·mypy·jsonschema 가 들어간다. 요구 런타임은 Python 3.11 이상. 벡터 DB 도, 임베딩 모델도, 외부 서비스도 쓰지 않는다. 상태는 JSON 과 Markdown 파일이고 동시성은 fcntl 파일 락으로 잡는다(loopx/file_lock.py, 382행).

같은 숫자의 반대편이 리스크다. 기여자 21명 중 상위 2개 identity 가 커밋의 97.9%를 쓴다. 68일에 60만 행은 사람이 한 줄씩 검토한 속도가 아니다. 저장소의 AGENTS.md 는 이걸 인정하고 절차로 막으려 한다. 모든 변경은 codex/ 브랜치의 전용 worktree 에서 하고 PR 로만 main 에 들어가며, 자기 병합 전에 loopx canary premerge --from-git-diff 로 위험 기반 검증셋을 돌리라고 쓴다(AGENTS.md:7-10, 77-82).

"에이전트가 썼다"는 것은 커밋 메시지 형태(codex/ 브랜치, PR 번호)와 저장소 문서에서 추론한 것이지, 각 커밋의 저자가 사람인지 모델인지 판별할 방법은 체크아웃 안에 없다. 상위 2개 identity(huangruiteng, huangrt01)가 동일인의 두 계정인지도 확인하지 못했다. 저장소가 이 함정을 먼저 적어 둔다. AUTHORS.md:20-23 이 "한 사람이 여러 Git identity 를 가질 수 있고 co-author 는 단순 커밋 수에 안 보인다"며 순위표를 만들지 않는 이유를 밝힌다. 97.9% 는 identity 기준 수치이지 사람 기준이 아니다.

페어 실행 두 건이 이 문서의 핵심이다. baseline 과 treatment 를 나란히 돌렸는데 양쪽 다 0.0 이라 차이를 잴 수 없었다. 문서 스스로 그 조건을 적는다. "ACP blind-loop 행은 non-native 정책 아래에서 setup·prewarm·round·scoring 만 증명한다"(같은 파일 62-63행). 즉 파이프라인이 돌았다는 증거이지 제어 평면이 점수를 올렸다는 증거가 아니다.

README 가 앞세우는 실증은 궤적이다. 벤치마크 점수는 앞세우지 않는다. OpenViking issue-fix 와 Auto ML 실험 각각 "200시간 이상의 loop lifetime". 다만 같은 문단이 그 숫자의 뜻을 좁힌다.

과대 주장을 스스로 금지하는 항목도 있다. 원칙 문서의 함정 7이 "벤치마크 향상을 과대 주장하기"이고, "LoopX 는 자기가 보일 수 있는 더 좁은 값을 주장해야 한다: 긴 작업이 검사·조종·복구·비교하기 쉬워진다"로 끝난다(loop-engineering-principles-and-pitfalls.md:92-97). README 의 현재 상태 절도 다음 마일스톤 중 하나로 "independent adoption and outcome evidence"를 든다(README.md:496-499).

신선도를 확인했다. 벤치마크 연구 폴더의 날짜가 붙은 파일은 20260622 가 마지막이고, docs/update-notes/ 는 2026-07-11 구간에서 끝난다. v0.4.2 는 2026-08-06 릴리스다. 최근 6주치 실행 결과는 공개 트리에 없다. 비공개로 더 돌았는지는 알 수 없다.

critique

내구 상태를 파는 도구인데, 그 내구 상태에 미해결 경합 버그가 열려 있다

한계를 셋으로 나눈다. 코드에 있는 결함, 읽어서는 확인할 수 없는 것, 그리고 설계가 스스로 인정하는 경계다.

1. 전역 레지스트리 동시 쓰기. 2026-08-06 에 올라온 issue #2823 이 sync_project_registry_to_global 의 read-modify-write 에 직렬화가 없다고 지적한다. 체크아웃에서 두 지점을 확인했다. 읽기는 loopx/global_registry.py:450 의 existing = read_json_if_exists(global_path) 이고 쓰기는 :501 의 write_json(global_path, payload) 이며, 그 사이를 감싸는 락이 없다. 같은 common_runtime_root 를 공유하는 프로젝트가 둘 이상이면 나중 writer 가 앞 writer 의 goal 을 지운다. v0.4.2 릴리스 시점에 열린 상태다.

이건 우연한 버그라기보다 알려진 부채의 한 사례다. 아키텍처 문서의 서버 로드맵 1번 항목이 정확히 이 일을 남은 일로 적는다.

2. 표류 방지 장치의 기본값이 절반만 켜져 있다. 5장에서 본 대로 outcome floor 는 outcome_markers·surface_only_hints 가 비어 있어 기본 상태에서 동작하지 않는다. 이 두 리스트는 프로젝트별 분류 문자열이라 범용 기본값을 줄 수가 없는 성격인데, 그러면 가장 중요한 표류 감지가 사용자 설정에 달려 있다는 뜻이 된다. 채우는 예시는 있다. docs/integration.md:139-148 이 outcome_markers 에 eval_metric·experiment 등 5개, surface_only_hints 에 forecast·runbook 등 4개를 넣은 execution_profile 전문을 보여준다. 다만 통합 가이드 안의 JSON 예시 한 덩어리이고, 이 값을 안 채우면 감지가 꺼진다는 설명은 붙어 있지 않다(grep -rn 'outcome_markers' docs/ → 1건).

3. 읽어서 확인할 수 없는 것. LoopX 를 설치해 goal 을 돌리지 않았으므로, 5장의 임계값이 실제 실행에서 의도대로 발화하는지는 이 문서가 답하지 못한다. 테스트로 잠겨 있는지도 확인하지 못했다(tests/ 미열람). 7장의 추적도 계획·영수증 검사까지이고 executor.py 는 열지 않았다. 6장의 Claude Code 훅은 decide() 가 순수 함수라 로직은 읽었지만, Claude Code 가 실제로 그 JSON 을 존중하는지는 실행해야 안다.

4. 문서와 코드의 어긋남 하나. README 는 5개 host 를 표로 안내하는데(README.md:184-192), 이 중 Claude Code 어댑터는 기본 설치에서 아예 빠져 있고 LOOPX_INSTALL_CLAUDE=1 이 필요하다(claude_goal_mode/README.md:23-30). README 표만 보면 설치하면 되는 것처럼 읽힌다. 어댑터 README 를 열어야 알 수 있다.

한계를 넘어 남는 것이 하나 있다. "검증된 writeback 없이는 진행으로 계상하지 않는다"는 회계 규칙 자체는 LoopX 없이도 옮길 수 있다. 7단계 트랜잭션과 NO_SPEND_RESULT_KINDS 는 200행짜리 아이디어이고, 자기 하네스에 "성공 선언 전에 검증 단계를 완료했는가"를 기계적으로 묻는 것만으로 대부분의 값이 나온다. 나머지 60만 행은 그 규칙을 여러 host 에 붙이는 배관이다.

adoption

판정: trial. 개인의 단일 프로젝트 목표에는 지금 써도 되고, 공유 런타임에는 아직 아니다

도입 결정이 걸리는 항목을 하나씩 확인했다. 라이선스와 의존성은 깨끗하고, 되돌리기도 쉽다. 막는 것은 성숙도 한 가지다.

확인 항목결과
라이선스MIT. LICENSE 파일 전문을 열었고 preamble 이나 carve-out 이 없는 표준 MIT 본문이다. 별도로 TRADEMARKS.md 가 이름과 마크를 다루지만 코드 사용 조건을 바꾸지 않는다
의존성 리스크런타임 의존성 0. Python 3.11 이상만 요구한다. 벤더 API·유료 서비스에 묶이지 않는다. Lark/Feishu, OpenViking 연동은 전부 default-off extension 이다
설치가 남기는 것프로젝트에 .loopx/, .codex/goals/, .local/ 이 생기고 직접 gitignore 해야 한다(README.md:179-180). Claude Code 어댑터는 명시적 --scope 없이는 설치되지 않고, ~/.claude 를 건드리려면 --scope user 를 따로 줘야 한다

쓸 만한 경우. 목표가 하나이고 저장소가 하나이며, 며칠에 걸쳐 에이전트를 돌리면서 "지금 뭘 하고 있고 내 결정을 뭘 기다리는지"를 CLI 한 줄로 보고 싶을 때. 이 조합에서는 issue #2823 의 경합 조건이 성립하지 않는다.

기다릴 경우. 여러 프로젝트가 common_runtime_root 를 공유하거나, 여러 에이전트가 같은 레지스트리에 동시에 쓰는 구성. 11장의 1번이 정확히 그 상황이고 아직 열려 있다.

쓰지 않기로 해도 가져갈 것이 있다. .claude/loop.md 네 줄 프로토콜(6장)은 LoopX 없이 직접 쓸 수 있다. "should_run 이 false 면 한 줄 말하고 멈춘다 / 하나의 bounded segment 만 하고 실제 검사로 검증한다 / todo 밖의 이니셔티브를 시작하지 않는다 / 다시 확인하고 멈춘다"는 어떤 하네스에도 붙는다.

conclusion

결론. 진행의 정의를 좁히는 것이 기억을 늘리는 것보다 싸게 먹혔다

이 저장소에서 배울 것은 한 문장이다. 에이전트가 무엇을 했는지 물어보는 대신, 무엇을 진행으로 계상할지를 코드가 정하게 한다. 나머지 장치는 전부 그 결정에서 파생된다.

가장 옮기기 좋은 조각은 크지 않다. 결과 종류에 지출 가능/불가능 딱지를 붙이고, 지출 불가능한 결과가 연속되면 다음 턴의 계약을 바꾸는 것. 이 두 규칙은 60만 행 없이도 자기 하네스에 넣을 수 있다.

이 문서는 코드를 읽어서 썼고 도구를 실행하지 않았다. 5장의 임계값이 실제로 발화하는지, 6장의 훅이 Claude Code 에서 의도대로 작동하는지는 확인하지 않았다. 헤드리스 브라우저를 쓸 수 없어 이 문서의 렌더링 결과도 화면으로 보지 못했고, 정적 게이트만 통과시켰다.
