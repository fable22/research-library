tl-dr

원천별 검색 자료를 공통 row로 모아 tool과 사용 경로에 연결한다

Slack 대화와 코드에서 만든 검색 자료가 같은 table에 모인다. 질문은 필요한 source와 tool을 선택하는 경로를 거치고, 검색한 근거는 Web UI의 답변이나 MCP client의 작업으로 이어진다.

architecture-map

수집과 질의는 공통 검색 자료의 인터페이스로 연결된다

원천별 처리의 차이는 connector가 담당하고 검색 계층은 공통 표현을 재사용한다. 이 연결부를 작게 유지하면 새 source를 붙일 때 기존 검색 경로를 재사용하기 쉽다.

원문 fig-002와 본문을 재구성했다. 공통 인터페이스가 유지되는 변경은 서로 분리할 수 있다. 검색에 새로운 표현·metadata가 필요하면 수집도 바뀐다. 점선 권한 상자는 기능의 존재만 나타내며 실제 적용 위치나 구현 경로를 그린 것이 아니다.Cerebras 원문

problem

원천 DB는 유지하고 검색할 사본을 공통 저장소에 만든다

Custom database를 가진 팀도 원래 시스템을 유지할 수 있다. Python plugin이 그 시스템을 읽어 공통 row 형식으로 쓰면 통합 검색에 참여한다.

  1. 원천을 정의한다

    Data source는 연결 방법, 가져올 자료, 가져올 주기를 정한다. 서로 다른 시스템에 같은 collector를 강제하지 않는다.

  2. 검색 가능한 자료를 만든다

    수집한 자료를 텍스트·vector·metadata로 표현해 shared Postgres에 저장한다. 질문이 들어오기 전 index를 준비하는 경로다.

  3. 공통 검색과 별도 도구를 함께 제공한다

    통합 search 옆에 source repository를 읽는 search_code 등 별도 retrieval primitive가 존재한다.

원문의 custom DB 경로는 수집해서 index하는 구조다. 비교 사례인 Slack enterprise search는 외부 자료를 사용자 OAuth로 원천 search API에 요청하는 federation을 택한다. 두 구조는 저장 사본과 원천 의존 시점이 다르다.Cerebras 원문 · Slack · Federated Enterprise Search

source-shapes

같은 row 인터페이스라도 원천별 검색 단위는 다르다

공통 인터페이스가 원천의 구조를 없애지는 않는다. 무엇을 한 검색 결과로 만들고 원문 어디에 연결하는지가 connector마다 달라진다.

원천검색 자료로 만드는 형태원문의 설명 범위
Slack원문 thread의 lexical index, 구조화한 thread vector, 조건을 통과한 burst vector전체 thread 재수집부터 distillation과 burst 생성까지 설명
Code repositories언어별 경계를 따라 나눈 chunk. 파일·함수 수준 표현과 원천 repo의 ripgrep 경로분할 순서와 CocoIndex의 변경분 갱신을 설명
Wiki / Confluence검색되는 wiki section과 선택 후 인접 section을 더하는 경로검색 결과의 문맥 복원을 설명하며 수집·parser 규칙은 생략

Jira는 원문 도입부에서 지식이 생기는 시스템의 예로 등장한다. Jira ticket의 구체적 수집·저장 schema는 공개되지 않아 별도 구현 사실로 적지 않는다.Cerebras 원문

slack-ingest

Slack의 새 답글은 전체 thread를 다시 읽게 한다

Socket Mode 이벤트는 변경을 알리는 신호다. consumer는 새 메시지만 저장하지 않고 부모 메시지와 모든 답글을 다시 가져와 대화 전체를 갱신한다.

본문은 ACK → event ID 중복 제거 → consumer에 표시 → thread 재수집을 설명한다. 채널별 주기를 조절할 수 있다. 이벤트 수신이 polling을 줄여도 전체 thread 조회에는 Slack API를 계속 사용한다.Cerebras 원문

slack-representations

Thread 요약과 burst는 서로 다른 질문을 찾게 한다

Distillation은 전체 대화에서 질문·요약·해결 내용·시스템·코드 참조를 추출한다. Burst는 요약이 놓친 곁가지 내용을 독립적인 검색 결과로 만든다.

Burst에는 thread 주제를 문맥으로 붙인다. 원문은 IDF 4.0 이상, 길이 200자 이상, reaction에 관한 신호를 설명하며 가중 조합과 threshold를 사용한다고 한다.

세 신호의 가중치와 최종 통과식은 공개하지 않는다. 모두를 반드시 만족하는 AND 규칙으로 재구성할 근거는 부족하다. 원문 transcript는 직접 embedding하지 않고 lexical 검색에 남긴다.Cerebras 원문

code-ingest

코드는 chunk를 나누고 변경된 결과만 다시 계산한다

대화는 thread로 묶지만 코드는 파일 안의 구조에 맞춰 나눈다. Cerebras는 언어별 regex 경계를 큰 단위부터 적용하며 class에서 시작해 chunk가 너무 크면 method와 작은 block으로 내려간다. 한 파일에서 파일·함수 수준의 표현을 만든다.

  1. Source repository와 경로 범위를 선택

    팀이 설정 파일에 repository와 path allowlist·denylist를 등록한다.

  2. Chunk별 표현을 계산

    코드를 분할해 vector를 만들고 Postgres로 내보낸다. 파일 전체를 항상 하나의 vector로 압축하는 구조가 아니다.

  3. 다음 commit의 변경분을 반영

    CocoIndex가 synchronization metadata를 추적한다. 원문은 달라진 chunk의 재계산·재출력과 sync state의 Postgres 저장을 설명한다.

CocoIndex v0 공식 문서는 source 변화에 따른 incremental update를 설명한다. Cerebras가 배포한 버전·chunk key·무효화 범위·transaction 경계는 공개하지 않아, 동일 DB 사용만으로 원자적 갱신을 보장한다고 단정하지 않는다.Cerebras 원문 · CocoIndex v0 · Indexing Basics

storage

공유 table은 검색용 텍스트와 vector, provenance를 연결한다

Thread·burst·code chunk처럼 검색 단위가 달라도 원문으로 돌아갈 연결은 필요하다. 원본 그림의 document, embedding, metadata, source와 timestamps는 후보 탐색부터 중복 제거·인용·문맥 복원까지 쓰일 정보를 묶는다.

정보의 역할어디에 쓰이는가재현 시 확인할 사항

query-map

후보는 search 안에서 줄어들고 마지막에 문맥이 붙는다

Project는 Slack channel·repo·DB·문서 공간을 묶은 검색 범위다. Planner가 이 범위에서 tool을 고르면 search 내부에서는 RRF와 rerank로 후보를 선별한다. 그 결과는 다른 tool의 근거와 함께 executor에서 모인다.

원문 fig-001·007·008과 Reranking 본문을 함께 재구성했다. 여섯 ranking 이름은 원본 그림의 예시다. 매 질의에서 여섯 retriever 또는 모든 tool이 반드시 실행된다는 뜻은 아니다. 마지막 확장은 새 전역 검색이 아니라 선택한 근거의 주변 맥락을 붙이는 단계다.Cerebras 원문

planner

Planner가 선택한 tool의 결과를 executor가 함께 모은다

Web UI의 planner는 질문과 active project, source 목록과 각 source의 용도를 받는다. 어떤 tool을 쓸지 선택하면 executor가 병렬 호출하고 결과를 공통 evidence 형식으로 정리한다.

Tool fan-out과 search 내부의 여러 retriever는 다른 계층이다. 이 그림의 병렬 분기를 RRF에 입력되는 목록 개수로 세면 안 된다.Cerebras 원문

tools

Tool마다 검색 대상과 반환할 근거가 다르다

Planner가 고르는 tool은 검색 대상과 접근 방식이 다르다. 통합 search는 여러 indexed source를 다루고 search_code는 repository에서 문자열을 찾는다. 각 tool의 반환값이 executor의 공통 evidence로 모인다.

hybrid

검색 신호와 retriever 목록을 구분해야 hybrid의 동작이 보인다

통합 search 안에서는 원문·thread·burst 등에서 찾은 후보의 순위를 결합한다. Slack의 full-text, embedding similarity, IDF, age decay는 검색할 자료의 서로 다른 단서를 평가한다. 원본 RRF 예시의 여섯 ranking 목록과 이 신호의 대응 관계는 공개되어 있지 않다.

검색 신호무엇을 보완하는가확인할 경계
Full-text오류 문자열·flag·host 이름 같은 문자 단서Postgres parser·dictionary 설정에 따라 token과 lexeme가 달라짐
Embedding similarity표현이 달라도 같은 문제를 설명하는 내용주제가 비슷해도 질문의 조건을 만족하지 않을 수 있음
IDFcorpus에서 드문 단어에 더 큰 의미를 부여계산 단위와 통계 갱신 방식 미공개
Age decay관련성이 같을 때 최근 내용 우대버전 적합성·정식 문서 여부를 자동 판정하는 규칙은 아님

RRF 그림의 목록 이름은 VECTOR, FTS, THREAD SUMMARIES, GRAPH, WIKI VECTOR, SLACK FTS다. GRAPH의 graph 구성과 탐색 구현은 설명하지 않는다.

정확한 문자열·의미·시점을 함께 고려하는 일은 이런 업무 자료를 다루는 RAG가 이미 해결해야 하는 검색 문제다. 여러 신호를 결합했다는 사실 자체를 Cerebras 설계의 차별점으로 보기는 어렵다. 원문의 vector 단독 검색 실패는 hybrid의 필요성을 보여 준다. 이 사례에서 더 살필 것은 검색 신호의 조합 위에 thread 정규화와 burst를 두어 대화의 어떤 누락을 보완하려 했는지다.

GIN은 full-text index 방식이다. PostgreSQL의 ts_rank 계열은 전역 corpus 통계를 쓰지 않으므로, GIN이나 ts_rank를 곧바로 BM25·IDF 점수 구현으로 읽으면 안 된다.Cerebras 원문 · Anthropic · Contextual Retrieval · PostgreSQL 18 · Full Text Search

rrf

RRF는 점수의 크기 대신 각 목록에서의 순위를 합친다

Vector similarity와 lexical 점수는 같은 척도가 아니다. RRF는 각 목록에서 몇 위였는지만 사용하므로 서로 다른 점수 분포를 직접 정규화할 필요가 없다.

RRF(d) = Σ목록 L에 d가 있을 때 wL / (60 + rankL(d))

d는 후보 문서, L은 검색 목록, rank는 1부터 시작하는 순위다. wL은 목록 L의 가중치이며 기본값은 1.0이다. 분모의 상수 k는 60이다. 목록에 없는 문서는 해당 목록에서 점수를 받지 않는다.

설명용 후보Vector 순위Lexical 순위k = 60의 합산 점수
A: 한 목록에서만 강함1없음1/61 ≈ 0.01639
B: 여러 목록이 지지431/64 + 1/63 ≈ 0.03150

이 예에서는 B가 A를 앞선다. RRF는 문서 내용을 새로 읽어 정답 여부를 판단하지 않는다. 비슷한 retriever를 중복 추가하면 같은 선호가 여러 번 가산될 수도 있다.

표는 원문 수식을 적용한 별도 계산 예다. 실제 검색 결과나 성능 측정이 아니다. RRF 원 논문도 k=60을 pilot에서 정해 후속 검증에 고정했으며, 모든 corpus에서 최적이라고 주장하지 않는다.Cerebras 원문 · RRF 원 논문 · SIGIR 2009

rerank

Rerank 이후에 주변 문맥을 복원한다

순위 목록의 합의만으로 실제 질문에 답할 근거를 확정할 수는 없다. Cerebras는 RRF 결과를 정리한 뒤 작은 reranker 모델로 질문과 후보 내용을 함께 평가한다.

  1. RRF 결과의 중복과 편중을 줄인다

    같은 source의 중복 chunk를 합치고 한 파일이 차지할 결과 수를 제한한다. 이 과정을 거쳐 후보 20개를 만든다.

  2. 질문 기준으로 다시 점수를 매긴다

    원래 질문과 후보를 reranker에 전달한다. 각 후보에 0~10 점수를 매기고 상위 10개를 유지한다. 모델명, prompt, pointwise·listwise 처리 방식은 공개하지 않는다.

  3. 선택된 근거의 맥락을 넓힌다

    Wiki section이 선택되면 이웃 section 두 개를 가져온다. Chunk 경계에서 잘린 제목·전제·주의사항을 답변 근거에 되돌린다.

  4. 근거 packet을 반환한다

    융합·중복 제거·rerank·문맥 확장을 거친 결과가 답변 생성 또는 client의 후속 작업으로 넘어간다.

후보 20개를 10개로 줄였다는 동작만으로는 선별 품질을 판단할 수 없다. 같은 초기 후보에서 정답 근거가 얼마나 남고 비용이 어떻게 달라지는지가 평가 기준이다. Reranker가 후보에 없던 근거를 되살릴 수 없다는 점도 함께 봐야 한다.Cerebras 원문

interfaces

Web UI와 MCP는 orchestration을 맡는 위치가 다르다

검색에서 돌아온 근거는 Web UI의 답변이나 MCP client의 후속 작업에 쓰인다. Web UI는 질문부터 답변까지 연결하고 MCP는 검색 primitive를 tool로 노출해 client가 호출 순서와 근거 사용을 결정하게 한다.

Web UI

Project 범위와 질문 → planner → executor의 병렬 호출과 근거 정규화 → synthesis의 답변·인용. 공개 설명은 이 순서이며 evidence 부족 시 재검색하는 정책은 명시하지 않는다.

MCP client

Client agent → 필요한 retrieval tool 호출 → evidence row 수신 → client가 답변·코드 편집 등에 활용. 반복 탐색의 제어권은 client에 둘 수 있다.

같은 source를 여러 project에서 참조하므로 project마다 자료를 복제할 필요는 없다. Onboarding 때 고른 project를 사용자 기본값으로 저장해 이후 질의의 범위에 적용한다.

원문은 MCP tool을 가능한 한 LLM 없이 가볍게 만든다고 하면서 search의 내부 rerank도 설명한다. 모든 tool이 LLM 호출을 전혀 하지 않는다고 일반화할 수 없다. Project scope 자체를 권한 경계로 동일시해서도 안 된다.Cerebras 원문

trace

장애 관련 질문은 대화·코드·문서가 함께 근거가 되는 경로로 읽을 수 있다

아래는 원문 그림의 checkpoint restore와 NFS 소재를 사용해 처리 순서를 설명한 예다. 실제 장애를 해결한 실행 기록이나 운영 성과 사례는 아니다.

  1. 질문: manifest를 읽은 뒤 restore가 멈춘다

    Active project의 source 목록을 바탕으로 통합 search와 코드 검색 등 필요한 tool을 고른다. 이 tool 선택은 설명용 가정이다.

  2. 표현이 다른 대화를 찾는다

    NFS mount에서 checkpoint가 멈춘다는 thread 표현을 vector 경로에서 찾을 수 있다. 알려진 오류 문자열이나 flag는 lexical·ripgrep 경로의 단서가 된다.

  3. search 내부에서 후보를 선별한다

    통합 search가 자체 retriever의 결과를 RRF로 합치고 파일별 편중을 줄인다. Reranker가 질문과 후보의 관련성을 평가하고 선택한 section의 문맥을 확장한다.

  4. 여러 tool의 근거를 모아 답한다

    Executor는 search의 반환값과 search_code 등 다른 tool의 결과를 공통 evidence로 정규화해 synthesis에 전달한다. 특정 조치가 유효한 버전·환경인지 판단하려면 그 조건을 담은 자료도 검색되어야 한다.

여기서 예측할 수 있는 실패는 “주제는 비슷하지만 버전이 다름”, “해결 flag가 요약에서 빠짐”, “해당 thread가 후보에 없음”이다. 각각 선별, 검색 표현, 수집·retrieval 단계의 평가 질문으로 이어진다.

critique

공개된 흐름은 구현 방향을 주지만 운영 계약까지 정하지는 않는다

동일한 구조를 재현하려면 갱신 일관성과 권한, 실패한 질의의 처리 규칙을 정해야 한다. 아래 항목은 본문과 그림이 확정해 주지 않는 구현 경계다.

경계구체적인 질문설계에서 남는 일
갱신 일관성원문 수정 뒤 thread·burst·vector가 언제 같은 버전을 가리키는가변경 감지, 재처리 상태, stale 결과의 처리 규칙
삭제와 권한원천에서 삭제되거나 접근 권한이 바뀐 자료가 언제 검색에서 빠지는가권한 평가 위치, 전파 지연과 파생 자료 제거
검색 범위Project 밖의 정답을 놓치거나 너무 넓은 범위에서 노이즈가 생기는가기본 scope와 확장·재검색 정책
비용과 지연thread 재수집·distillation·rerank가 각각 얼마를 쓰는가단계별 latency와 호출량, 실패·재시도 측정

이 질문이 남아 있어도 원천별 검색 단위와 검색 단계의 분리는 구현 설계에 참고할 수 있다.

conclusion

공통 row를 만들되 근거의 출처와 검색 목적은 유지한다

이 아키텍처의 재사용 가능한 부분은 원천별 가공을 공통 인터페이스에 연결하고 검색·선별·답변의 책임을 나눈 데 있다. 각 단계를 나누어 보면 새 요구가 어느 경로에 영향을 주는지 판단할 수 있다.

새 source가 생기면

연결·수집·검색 단위와 metadata를 정의한다. 공통 row만 맞춰도 원문 위치와 권한 의미까지 자동 해결되지는 않는다.

검색 품질이 낮으면

후보 자체가 없는지, 순위가 낮은지, 적절한 근거를 답변이 잘못 썼는지 먼저 분리한다. 그 결과에 따라 collector·retriever·reranker·synthesis를 바꾼다.

이 사례는 각 단계가 받을 자료와 반환할 근거를 정하는 데 참고할 수 있다. 파라미터 선택과 품질 평가는 적용할 corpus와 질문에 맞춰 수행한다.Cerebras 원문
