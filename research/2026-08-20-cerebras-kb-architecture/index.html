읽는 길 3

18부터 20까지가 Postgres 다. 복제하려는 사람이 제일 먼저 막히는 지점이 여기 있다.

Cerebras 가 2026년 7월에 공개한 사내 지식베이스를 대상으로 한다. 같은 대상을 도입 판단 쪽에서 다룬 문서가 2026-08-12 Cerebras Knowledge 에 있다.

tl-dr

임베딩 테이블 한 장이 저장소와 인덱스와 대기열과 원장을 겸한다

소스가 무엇이든 같은 모양의 행 하나로 바뀌어 Postgres 테이블 한 장에 들어간다. 수집 계층은 그 테이블에 쓰고, 질의 계층은 거기서 읽고, 서로를 알지 못한다. 그 테이블은 벡터만 담지 않는다. 전문 인덱스가 같은 행에 걸려 있고, 수집이 어디까지 진행됐는지도 같은 행에 적힌다.

하루 질의15,000건+원문 표기는 more than. 사람과 자동화와 agent 를 합친 수치다
embedding 차원3,072원문 fig-001 에 pgvector 와 HNSW 로 함께 표기돼 있다
병렬 검색기6source 와 modality 로 갈라져 있다. 07장 참조
쓰기 단계2이벤트 처리와 embedding 이 분리돼 있다. 08장

메시지 broker 가 없다. Kafka 도 SQS 도 Redis 도 쓰지 않고, 테이블의 컬럼 두 개가 대기열 역할을 한다. 수집 상태와 vector 가 같은 데이터베이스에 있으므로 둘을 한 transaction 으로 묶을 수 있다.

품질 수치는 다루지 않는다. accuracy 도 recall 도 원문에 없다.

problem

정보를 한 플랫폼으로 모으는 방식이 매번 실패한다

사내 정보는 편한 곳에서 만들어진다. 문서의 제안 편집, Slack 스레드, GitHub 의 코드 참조, Jira 의 상태값이 각각 다른 자리에 쌓인다. 분기마다 하나로 모으자는 제안이 나오고 매번 실패한다. 각 플랫폼이 자기 영역에 맞게 다듬어져 있어서 옮기면 쓰기 나빠지기 때문이다.

옮기는 쪽

모든 것을 한 SaaS 로 이전한다. 단일 진실 원천이 생기지만 사람의 작업 방식을 바꿔야 하고, pull request 논의를 문서 도구에서 하게 만드는 결과가 된다.

Cerebras 쪽

데이터를 원래 자리에 둔다. 대신 각 플랫폼에서 직접 뽑아 와 같은 모양의 행으로 바꾼다. 사람의 습관은 그대로 두고 수집만 바꾼다.

두 번째를 고르면 소스 개수가 그대로 남는다. 그 개수를 위층이 모르게 만드는 것이 이 설계의 과제가 된다.

왜 지식베이스가 필요한지는 다루지 않는다. 신규 입사자가 같은 질문을 반복한다는 원문의 동기를 그대로 받는다.

layers

세 계층이 만나는 접점이 테이블 하나뿐이다

원문은 이 시스템이 세 가지를 제공한다고 정리한다. 데이터를 모아 저장하는 계층, 그것을 질의하는 계층, 인증과 인가를 강제하고 감사와 분석을 남기는 계층이다. 세 계층은 서로를 직접 알지 못하고 테이블의 모양만 안다.

가운데가 좁아지는 모래시계 모양이라 narrow waist 라고 부른다. 위와 아래가 서로를 건드리지 않고 각자 바뀔 수 있다. 새 소스를 붙일 때 검색 코드를 고치지 않고, 검색 전략을 바꿀 때 수집 코드를 고치지 않는다. 대가는 스키마를 바꾸는 순간 모든 커넥터가 깨진다는 것이고, 원문도 이 스키마를 의도적으로 단순하게 뒀다고 밝힌다.

인가 계층은 원문에 이름만 있다. 그림의 관문과 감사 로그는 이 문서가 구조상 그 자리를 표시한 것이고, 구현 근거는 없다. 19장에서 다룬다.

원문 fig-002 는 소스 여섯 개가 커넥터를 하나씩 거쳐 embeddings 테이블 하나로 모이고, 거기서 MCP 와 웹 UI 와 agent 가 질의하는 그림을 담고 있다. 그 테이블 상자 안에 적힌 네 줄이 사실상의 스키마다.

팀이 자기 DB 를 그대로 두고 참여하는 경로도 있다. 작은 Python 모듈 하나를 pull request 로 올려 같은 모양의 행을 뱉게 하면 된다. 스키마만 지키면 나머지 스택은 바뀌지 않는다.

PRM DOCS 가 무엇인지는 원문에 설명이 없다. 그림에 적힌 라벨을 그대로 옮겼다.

ingest-slack

Slack 원문은 embedding 하지 않는다

Cerebras 는 Slack 을 가장 중요한 소스로 꼽는다. 처음에는 원문 텍스트를 그대로 embedding 해 봤고 충분하지 않았다. 원문이 든 이유는 셋이다. 정보 밀도가 메시지마다 크게 다르고, 짧은 메시지가 긴 설명을 cosine 유사도에서 이기고, 메시지 하나의 뜻이 앞뒤 대화에 달려 있다.

그래서 embedding 전에 LLM 이 스레드를 읽고 구조를 뽑는다. 원문 fig-004 에 실린 예시다.

{
  "question":   "왜 매니페스트 로드 후에 복원이 멈추나?",
  "summary":    "대규모 복원이 캐시 워밍업 전에 멈춘다.",
  "resolution": "NFS 마운트에서는 CKPT_PREFETCH=4 로 설정할 것.",
  "systems":    ["checkpoint restore", "NFS"],
  "code_refs":  ["CKPT_PREFETCH"]
}

이 다섯을 이어 붙인 것이 document 가 되고 embedding 되는 것은 이 정리본이다. 원문 대화록은 embedding 하지 않는다. 그렇다고 버리지도 않는다. 원문은 raw content 에 Postgres 전문 인덱스를 유지하기 때문에 Slack 원문이 들어오는 즉시 키워드 검색이 된다고 밝힌다.

한 행이 텍스트를 두 벌 들고 있다는 뜻이다. 정리본은 vector 인덱스로 가고 원문은 전문 인덱스로 간다. 두 표현이 막는 실패가 다르다. vector 는 복원이 멈춘다와 체크포인트가 NFS 에서 정지한다를 이어 주지만 ERR_MANIFEST_TIMEOUT 같은 문자열은 뭉갠다. 전문 검색은 그 반대다.

정확도가 얼마나 올랐는지는 원문에 없다. 정규화 후 유의미하게 올랐다는 서술이 전부다.

ingest-write

이벤트 처리와 embedding 이 다른 프로세스에 있다

원문 산문은 수집을 한 흐름으로 서술한다. fig-003 에는 그 흐름이 두 갈래로 쪼개져 있고 산문에 없는 컴포넌트 이름이 적혀 있다. 이 문서가 Cerebras 설계에서 가장 잘 만들어졌다고 보는 부분이다.

Slack bot 을 Socket Mode 로 띄우면 모든 메시지 event 가 WebSocket 으로 밀려 온다. 이벤트가 오면 즉시 확인 응답을 보내고 event ID 로 중복을 걸러낸다. 그다음이 이 설계의 특징이다. 메시지 하나를 따로 저장하지 않고, 그 메시지가 속한 스레드의 부모와 모든 답글을 다시 가져와 스레드 전체를 한 행으로 덮어쓴다.

봇 응답 경로는 이 문서가 다루지 않는다. fig-003 에 상자로만 있고 원문에 설명이 없다.

ingest-queue

워터마크 컬럼이 메시지 broker 를 대신한다

소켓 이벤트 핸들러는 스레드를 저장하고 이 행 다시 처리해야 함이라는 표시를 남기고 끝난다. LLM 정리도 embedding 도 여기서 하지 않는다. 무거운 일은 동기화 워커가 표시된 행을 훑으면서 한다.

스레드를 통째로 다시 읽어 덮어쓰는 방식이 여기서 값을 한다. Socket Mode 의 전달 보장은 at-least-once 다. 3초 안에 확인 응답을 못 보내면 Slack 이 1분 간격으로 최대 세 번 더 같은 이벤트를 보내고, 순서도 보장하지 않는다. 메시지를 뒤에 덧붙이는 방식이었다면 중복과 순서가 곧바로 데이터 손상이 된다. 덮어쓰기는 몇 번을 해도 결과가 같다.

확인 응답 3초

핸들러에서 LLM 을 호출하면 이 시간을 넘긴다. 그러면 같은 이벤트가 재전송되고 그게 또 LLM 을 부른다.

자동 디바운스

활발한 스레드는 답글마다 표시가 남지만 워커가 한 번 훑을 때 여러 표시가 한 번의 정리로 합쳐진다. 따로 짤 로직이 없다.

부분 장애 허용

embedding API 가 죽어도 수집은 계속된다. 원문이 들어와 전문 검색은 되고 vector 만 밀렸다가 따라잡는다.

대기열이 데이터베이스 안에 있으므로 서버가 죽어도 상태가 남는다. broker 를 따로 뒀다면 행은 썼는데 발행이 실패한 상태가 생기고, 그 행은 다시 처리되지 않는다. 워터마크 컬럼은 그런 상태를 표현할 수 없게 만든다.

워터마크가 어떤 컬럼인지, 워커가 polling 인지 LISTEN 인지, 워커끼리 잠금을 어떻게 하는지는 원문에 없다. fig-003 에 이름만 있다.

ingest-burst

저품질 메시지를 랭킹으로 누르지 않고 인덱스에 넣지 않는다

스레드 단위로 정리하면 긴 스레드 안의 중요한 메시지가 요약에 반영되지 않는다. 그래서 같은 사람이 연달아 쓴 메시지 묶음을 버스트로 따로 embedding 한다. 스레드 주제를 앞에 붙여 문맥을 준다.

통과 조건값무엇을 거르는가
희귀 토큰 포함IDF ≥ 4.0ln(N/df) ≥ 4 이면 전체 문서의 1.83% 미만에만 나오는 단어다. 이 계산은 원문에 없고 이 문서가 했다
결합 길이200자 이상한 줄짜리 맞장구
사회적 신호reaction 1개 이상아무도 반응하지 않은 혼잣말

CKPT_PREFETCH 같은 내부 flag 는 통과하고 배포나 클러스터처럼 사내에서 흔한 말은 걸린다. 이 문턱은 수집할 때 평가된다. 넣어 두고 랭킹으로 누르는 대신 인덱스에 넣지 않는다. HNSW 그래프는 노드가 늘수록 탐색 비용과 빌드 메모리가 함께 커지므로, recall 을 조금 포기하고 인덱스 품질과 운영비를 산다.

세 조건이 가중 합산인지 전부 만족해야 하는지는 원문 서술이 모호하다. 가중 조합을 문턱과 비교한다고만 적혀 있다.

ingest-code

동기화 상태를 vector 옆에 두면 둘을 한 transaction 으로 묶을 수 있다

사내 저장소 중에는 40GB 가 넘는 것도 있다. Cerebras 는 CocoIndex 를 골랐고, commit 마다 저장소 전체를 다시 계산하지 않고 바뀐 chunk 만 다시 embedding 한다고 밝힌다. 이유로 든 것이 동기화 상태와 embedding 저장소가 같은 데이터베이스에 산다는 점이다.

그 동기화 상태의 실물이다. CocoIndex v0.3 의 src/execution/db_tracking_setup.rs 에 있는 DDL 에서 핵심 칸만 추렸다.

CREATE TABLE <flow>__cocoindex_tracking (
    source_id                 INTEGER NOT NULL,
    source_key                JSONB   NOT NULL,
    processed_source_fp       BYTEA,   -- 소스 내용의 지문
    process_logic_fingerprint BYTEA,   -- 파이프라인 로직의 지문
    target_keys               JSONB,   -- 이 소스가 만들어낸 행들의 키
    staging_target_keys       JSONB,   -- 반영 직전 단계
    memoization_info          JSONB,
    PRIMARY KEY (source_id, source_key)
);
칸막는 사고
processed_source_fpcommit 은 있었는데 파일 내용이 같으면 embedding 호출을 건너뛴다. rebase 와 merge commit 에서 크게 절약된다
process_logic_fingerprintchunk 크기나 embedding 모델을 바꾸면 소스가 같아도 값이 바뀌어 전체 재계산이 걸린다. 절반은 옛 모델이고 절반은 새 모델인 인덱스가 생기지 않는다
target_keys파일이 지워지거나 함수가 셋에서 둘로 줄면 그 고아 행만 지운다. 반영 도중 죽어도 복구되도록 두 단계로 나뉘어 있다

vector 를 전용 vector DB 에 두고 동기화 상태를 Postgres 에 뒀다면 commit 마다 두 시스템에 나눠 쓰게 된다. 분산 transaction 없이는 vector 는 갱신됐는데 추적 기록은 실패한 상태가 생기고, 그때부터 인덱스가 소스와 어긋난다. 전체를 다시 계산해 보기 전에는 알아차릴 방법이 없다.

청크 경계는 순서대로 시도하지 않고 비용을 최소화해 한 번에 정한다

원문은 언어별 정규식 경계를 큰 단위에서 작은 단위 순으로 시도한다고 설명한다. CocoIndex 의 기본 경로는 tree-sitter 로 구문 트리를 만든 뒤 동적 계획법으로 비용을 최소화한다. 상수가 소스에 박혀 있다.

const SYNTAX_LEVEL_GAP_COST: usize = 512;       // 구문 레벨 하나 건너뛰기
const TOO_SMALL_CHUNK_COST: usize = 1048576;    // chunk 가 너무 작을 때
const PER_LINE_BREAK_LEVEL_GAP_COST: usize = 64;

둘의 비율이 2,048배다. 잘게 자르는 쪽이 구문 경계 하나 건너뛰는 것보다 2,048배 비싸므로 결과적으로 큰 단위가 선호된다. 전체 비용이 최소가 되는 분할을 한 번에 찾는다는 점이 원문 서술과 다르다.

원문 서술이 틀린 것은 아니다. CocoIndex 에는 tree-sitter 문법이 없는 언어를 위한 정규식 경계 경로가 따로 있고, Verilog 와 VHDL 이 그 경우다. 언어 등록표 rust/code_ast/src/prog_langs.rs 에 이렇게 적혀 있다.

add("verilog", &[".vh"], None);          // 세 번째 인자 None 이 문법 없음
add("vhdl",    &[".vhd", ".vhdl"], None);

06장에서 본 소스 목록에 넷리스트가 있다. 하드웨어 설계 코드베이스에서는 실제로 정규식 경계로 떨어지므로, 원문 설명은 그들이 주로 다루는 코드에 대해 정확한 서술이다.

계층 하나가 그 테이블에 시킨 일 · 같은 모양의 행을 쓰고, 워터마크로 다시 처리할 것을 표시한다

Cerebras 가 v0.3 을 썼다는 근거는 없다. 원문이 Postgres 에 추적한다고 쓴 것과 v0.3 동작이 맞아떨어질 뿐이다. 2026년 6월 V1 은 상태 저장소를 LMDB 로컬 파일로 바꿨다. Cerebras 가 어떤 언어에 어느 경로를 탔는지는 확인할 수 없다. 저장소 설정 파일이 공개돼 있지 않다. CocoIndex 쪽 비용 함수와 버전 차이를 더 파고든 문서가 2026-08-12 Cerebras Knowledge 에 있다.

query-path

후보 수가 계속 줄어들다 마지막에만 다시 늘어난다

질문이 들어오면 가벼운 LLM 이 질문과 현재 범위를 보고 어떤 도구를 쓸지 고른다. 고른 도구를 병렬로 실행하고 공통 형식으로 정규화한 뒤 마지막 LLM 이 답을 만든다.

도구는 여섯이다. 통합 vector 검색 search, Slack 전용 search_slack, 저장소에 ripgrep 을 거는 search_code, 파일별 LLM 요약 subsystem_index, 최근 pull request 를 보는 recent_prs, 주제에 밝은 사람을 찾는 who_knows 다.

search_code 만 임베딩 테이블을 지나지 않는다. 정확한 코드 조회는 저장소 파일에 직접 ripgrep 을 건다. 원문도 grep 이면 충분하지 않냐는 반론을 검토한 뒤 둘 다 하기로 했다고 밝힌다. 이 테이블은 유일한 진실 원천이 아니라 유일하게 순위를 매길 수 있는 표면이다.

원문 fig-001 은 검색 단계를 여섯 리스트가 병렬로라고 부르고 fig-008 이 그 여섯의 이름을 적어 놓았다. 산문에는 이 목록이 없다. 이름을 보면 통합 검색이 어떻게 짜여 있는지 드러난다.

query-fusion

점수를 쓰지 않고 순위만 쓰면 정규화 문제가 사라진다

여섯 순위표를 합칠 때 문서마다 각 리스트에서 1 / (60 + 순위) 를 더한다. weight 기본값은 1.0 이다. cosine 유사도와 ts_rank 와 IDF 가중합과 시간 감쇠 계수는 같은 자에 올릴 수 없는 값이다.

억지로 정규화하면 질의마다 눈금이 흔들려 튜닝이 재현되지 않는다. 순위 정수만 쓰면 그 문제가 통째로 사라진다.

k 를 60이 아닌 값으로 시험했는지는 원문에 없다. 60은 RRF 원논문의 값이고 원문은 그 논문을 인용한다. 이 여섯은 원문이 만든 예시 데이터다. 실제 corpus 에서 나온 결과가 아니므로 성능을 말해 주지 않는다. 공식이 그림대로 계산됐다는 것만 확인한 것이다.

authz

세 계층 중 하나인데 구현 서술이 한 줄도 없다

원문이 세 계층으로 명시한 것 중 셋째가 인증과 인가를 강제하고 감사와 분석을 남기는 계층이다. 설명은 그 한 문장이 전부이고 아키텍처 그림에도 나오지 않는다. 사내 지식베이스에서 가장 위험한 부분이 비어 있다.

문제의 뿌리는 근사 최근접 탐색의 동작 방식에 있다. HNSW 는 가까운 것 몇 개를 가져오라는 식으로 후보를 정해진 개수만큼 긁어온다. 거기에 권한 필터를 걸면 남는 개수가 줄어든다. pgvector 기본값 ef_search = 40 에서 볼 수 있는 문서가 전체의 10% 라면 40개 중 평균 4개만 남는다. 상위 10개를 원했는데 4개뿐이다.

에러가 나지 않는다

결과가 조금 나빠질 뿐이다. 사용자는 답을 못 찾네 하고 넘어가고, 개발자는 몇 달 뒤에야 recall 이 무너진 것을 안다.

구조상 있는 경계

Slack 채널 하나가 데이터 소스 하나라는 원문의 결정은 수집 주기를 위한 것이지만, 권한의 단위도 함께 만든다. 프로젝트가 소스의 묶음이므로 권한도 소스 단위로 주면 필터가 source_id IN (...) 형태가 된다.

세 가지 방식이 있고 대가가 각각 다르다

원문에 답이 없으므로 직접 골라야 한다. 세 방식 모두 pgvector 에서 실제로 쓰이는 패턴이고, 어느 것도 공짜가 아니다.

방식어떻게대가
권한별 인덱스 분리부분 인덱스를 권한 그룹마다 만든다정확하고 빠르다. 권한 구조가 바뀔 때마다 재색인이 필요하고 그룹이 많으면 인덱스가 늘어난다. 고정된 소수의 큰 경계에만 쓴다
검색마다 조건pgvector 0.8 의 hnsw.iterative_scan 으로 충분한 개수가 남을 때까지 계속 훑는다유연하다. 필터가 좁을수록 느려지고 max_scan_tuples 상한에 걸리면 조용히 불완전해진다. 대부분 여기서 시작한다
합친 뒤 걸러내기검색은 전부 하고 최종 결과에서 볼 수 없는 것을 뺀다구현이 가장 쉽다. 결과가 비어버릴 수 있고, 볼 수 없는 문서가 순위 계산에 영향을 주며, 권한 없는 데이터가 애플리케이션 메모리까지 올라온다

착수 전에 답해 둘 질문은 하나다. 문서 하나를 볼 수 있는지를 무엇으로 판단하는가. 소속 팀 같은 소수의 고정 그룹이면 설계가 단순해진다. 문서마다 다르거나 Slack 채널 멤버십을 그대로 따른다면 Slack 의 권한 모델을 복제해 계속 동기화한다는 뜻이고 난이도가 한 단계 올라간다.

감사와 분석은 상대적으로 쉽다. 같은 Postgres 안에 질의 로그 테이블 하나면 된다. 누가 언제 무엇을 물었고 어떤 행이 근거로 나갔는지를 남기면 감사 기록이자 품질 개선의 재료가 된다. 나중에 붙이면 과거 데이터가 없으므로 초기에 넣는 편이 낫다.

계층 셋이 그 테이블에 시켜야 할 일 · 볼 수 있는 행만 남기고, 무엇을 물었는지 남긴다

권한 경계를 소스 단위로 두자는 것은 이 문서의 제안이다. Cerebras 가 그렇게 했다는 근거는 없다. 세 방식의 성능 차이를 직접 측정하지 않았다. pgvector 문서가 서술하는 동작에 근거한 정리다.

postgres-roles

세 계층이 그 테이블에 시킨 일을 모으면 네 가지가 된다

여기까지 본 것을 모으면 Postgres 가 맡은 일이 넷이다. 보통의 RAG 스택이 수집 대기열과 vector DB 와 메타데이터 DB 세 개로 나눠 하는 일을 하나로 한다.

1 · 저장소

본문과 정리본과 메타데이터와 vector 를 한 행에 담는다.

2 · 검색 엔진

vector 인덱스와 전문 인덱스가 같은 테이블 위에 공존한다. 융합이 순위 병합만 남는다.

3 · 작업 대기열

워터마크로 아직 처리하지 않은 행을 표시한다. 메시지 broker 가 없다.

4 · 진행 상태 원장

어디까지 수집하고 반영했는지를 데이터 옆에 적는다. 데이터 쓰기와 상태 갱신이 한 transaction 이다.

3번과 4번이 이 설계의 특징이다. 스레드를 저장하면서 동시에 재처리 대상으로 표시하는 일이 한 문장, 한 transaction 으로 끝난다. broker 를 따로 뒀다면 행은 썼는데 발행이 실패한 상태가 생기고 그 행은 다시 처리되지 않는다.

하루 15,000 질의는 평균 0.17 QPS 다. 근무 8시간에 몰린다고 봐도 0.5 QPS 이고 피크를 몇 배로 잡아도 초당 한 자릿수다. 이 규모에서 전용 vector DB 가 주는 초당 수천 QPS 는 쓰이지 않고, 잃는 것은 매일 청구된다.

전용 vector DB 를 뒀다면 이 설계의 장점 절반이 사라진다

Pinecone 이나 Qdrant 같은 전용 vector DB 는 별도로 도는 서버다. pgvector 는 같은 테이블의 한 컬럼이라 일반 컬럼과 같은 transaction 과 backup 과 join 안에 들어온다. 이 차이가 이 문서 곳곳에서 반복해서 나타난다.

장면한 Postgresvector DB 를 따로 둘 때
코드 증분 반영vector 쓰기와 추적 기록 갱신이 한 transaction두 시스템에 나눠 쓰기. 한쪽만 성공한 상태가 생기고 전체 재계산 전에는 알 수 없다
수집 대기열컬럼 두 개로 표시. 서버가 죽어도 상태가 남는다broker 를 추가하거나 vector DB 밖에 상태를 또 둔다
전문 검색 융합같은 행에 두 인덱스. 순위 병합만 하면 된다두 저장소의 결과를 애플리케이션에서 join. 키 정합성을 직접 지켜야 한다
처리량초당 한 자릿수 QPS 면 인스턴스 하나로 충분하다초당 수천 QPS 를 감당한다. 이 규모에서는 쓰이지 않는다

규모가 달라지면 판단도 달라진다. 질의가 초당 수백 건을 넘거나 corpus 가 수억 행이 되면 전용 vector DB 의 처리량이 실제 값이 된다. 15,000 질의라는 숫자를 먼저 환산해 보고 결정할 문제다.

QPS 환산과 피크 배수는 이 문서의 계산이다. 원문은 하루 질의 수만 밝힌다. 실제 인스턴스 사양도 공개돼 있지 않다. 전용 vector DB 를 직접 세워 비교하지 않았다. 표의 왼쪽은 원문과 pgvector 문서에, 오른쪽은 이중 쓰기라는 일반적 성질에 근거한다.

vector(d)4d + 812,296 B2,000차원까지만
halfvec(d)2d + 86,152 B4,000차원까지. 이쪽을 써야 한다

컬럼을 halfvec(3072) 로 두거나 vector(3072) 를 유지한 채 표현식 인덱스를 만든다. 후자를 고르면 질의의 ORDER BY 에도 같은 캐스팅을 써야 한다. 빠뜨리면 인덱스를 타지 않고 전체 스캔으로 떨어지며 에러는 나지 않는다.

운영 부담이 어디에 몰리는지는 16장에서 다룬다. HNSW 에서 행 갱신은 사실상 삭제와 삽입이라 잦은 덮어쓰기가 그래프에 죽은 노드를 쌓는다. pgvector 문서도 HNSW 인덱스의 VACUUM 이 오래 걸리니 먼저 REINDEX 하라고 적는다.

네 신호 중 IDF 는 Postgres 기본 기능으로 만들 수 없다

원문은 Slack 검색의 네 신호 중 하나로 IDF 를 들고 버스트 문턱으로 4.0 이라는 값까지 준다. Postgres 의 ts_rank 는 corpus 전체 통계를 쓰지 않는다. 문서 안에서의 단어 빈도와 가중치만 본다.

IDF 도 길이 정규화도 없으므로 이 신호는 기본 전문 검색 밖에서 조달된다. 단어별 문서 빈도 테이블을 직접 유지하거나 BM25 확장을 얹는 두 길이 있다. 원문은 어느 쪽인지 밝히지 않는다. 버스트 문턱이 수집 시점에 평가되는 것을 보면 자체 빈도 테이블 쪽이 자연스럽다.

호스팅을 정하기 전에 확인할 것

BM25 확장은 관리형 Postgres 에 대부분 없다. RDS 나 Aurora 는 확장 허용 목록 방식이라 pgvector 는 주지만 이쪽은 주지 않는다. 한국어가 섞이면 더 좁아진다. Postgres 에는 한국어 형태소 분석기가 없어 pgroonga 나 pg_bigm 이 필요한데 그것도 없다. 나중에 필요해지면 그때 깔자가 성립하지 않고, 그때는 이사이며 이사는 전체 재색인이다. 후보 인스턴스에서 SELECT * FROM pg_available_extensions 를 먼저 돌려 볼 것.

이 제약이 인프라 선택을 좌우한다. 네 신호를 다 쓰겠다고 정한 순간 호스팅 후보가 좁아지므로, 설계 초기에 결정해 두지 않으면 나중에 되돌리는 비용이 크다.

Cerebras 가 halfvec 을 썼는지 표현식 인덱스를 썼는지는 원문에 없다. 두 방법 중 하나여야 한다는 것만 pgvector 제약에서 따라온다. Cerebras 가 어느 쪽으로 IDF 를 조달하는지 확인할 방법이 없다. 자체 테이블 쪽이라는 것은 추정이다.

result-scale

이 구조가 성립하는 근거의 절반은 규모가 작다는 사실이다

하루 15,000 질의는 무섭게 들리지만 읽기 부하로는 작다. 환산해 보면 왜 인스턴스 하나로 되는지, 그리고 어디에 실제 부담이 있는지가 갈린다.

평균 QPS0.1715,000 나누기 86,400초. 이 문서의 계산이다
근무 8시간 기준0.52질의가 근무 시간에 몰린다고 가정했다
피크 가정1 ~ 3피크를 평균의 3배에서 5배로 잡은 값. 근거 자료는 없다
공개된 품질 수치0건accuracy, recall, 만족도 모두 없다

부담은 쓰기 쪽에 몰린다. Slack 스레드는 답글마다 다시 embedding 되므로 embedding 비용이 대화량에 비례한다. HNSW 는 잦은 갱신에 그래프가 부풀고 재색인이 필요해진다. 인덱스 빌드가 maintenance_work_mem 을 넘으면 성능이 급락하는데, halfvec(3072) 기준 100만 행이면 vector 데이터만 6GB 대다.

원문은 운영 항목을 다루지 않는다. 출시 3개월 시점의 글이라는 점을 감안해야 한다. 위 수치 중 15,000 만 원문의 것이다.

blueprint-table

원문 제약을 pgvector 위에서 실제로 돌아가게 옮기면 이 모양이 된다

아래는 Cerebras 의 DDL 이 아니다. 원문이 밝힌 제약을 이 문서가 옮긴 최소 형태이고, 인스턴스에 올려 돌려 보지는 않았다. 본문에서 나온 제약이 어디에 어떻게 박히는지 한자리에서 보기 위한 것이다.

CREATE TABLE kb_embeddings (
  source        text        NOT NULL,   -- slack_thread | code_chunk | wiki_section
  source_id     text        NOT NULL,   -- 원 시스템의 안정 키. chunk 단위여야 한다
  document      text,                   -- embedding 대상 정리본. 워커가 채운다
  raw_text      text,                   -- 원문. embedding 하지 않고 전문 검색 전용
  metadata      jsonb       NOT NULL DEFAULT '{}'::jsonb,
  embedding     halfvec(3072),          -- vector(3072) 로는 HNSW 를 못 건다

  content_ver   bigint      NOT NULL DEFAULT 1,   -- 쓰기 경로가 올린다
  synced_ver    bigint      NOT NULL DEFAULT 0,   -- 워커가 반영 후 맞춘다

  updated_at    timestamptz NOT NULL DEFAULT now(),
  fts           tsvector GENERATED ALWAYS AS
                  (to_tsvector('simple', coalesce(raw_text, document, ''))) STORED,
  PRIMARY KEY (source, source_id)
);

CREATE INDEX kb_fts   ON kb_embeddings USING gin (fts);
CREATE INDEX kb_meta  ON kb_embeddings USING gin (metadata jsonb_path_ops);
CREATE INDEX kb_dirty ON kb_embeddings (updated_at) WHERE synced_ver < content_ver;

한 행이 텍스트를 두 벌 들고 두 인덱스에 참여한다. content_ver 와 synced_ver 가 대기열이고, 부분 인덱스 kb_dirty 가 아직 처리하지 않은 행만 좁게 잡는다. vector 인덱스는 여기 없다. 대량 적재 전에 만들면 적재가 느려지므로 데이터를 채운 뒤 한 번에 만든다.

이벤트 핸들러는 표시만 남기고, 워커가 겹치지 않게 집어 간다

08장의 두 단계를 SQL 로 옮기면 이렇게 된다. 핸들러 쪽은 embedding 없이 끝나고, 워커 쪽은 여러 개가 동시에 돌아도 같은 행을 두 번 집지 않는다.

-- 소켓 핸들러. LLM 도 embedding 도 부르지 않는다.
INSERT INTO kb_embeddings (source, source_id, raw_text, metadata, updated_at, content_ver)
VALUES ('slack_thread', $1, $2, $3, now(), 1)
ON CONFLICT (source, source_id) DO UPDATE SET
  raw_text    = EXCLUDED.raw_text,      -- 이 순간부터 전문 검색은 즉시 된다
  metadata    = EXCLUDED.metadata,
  updated_at  = now(),
  content_ver = kb_embeddings.content_ver + 1;   -- RESET WATERMARKS
-- 워커. FOR UPDATE SKIP LOCKED 가 워커끼리의 경합을 없앤다.
WITH claimed AS (
  SELECT source, source_id, raw_text, content_ver
  FROM kb_embeddings
  WHERE synced_ver < content_ver
  ORDER BY updated_at LIMIT 32
  FOR UPDATE SKIP LOCKED
)
SELECT * FROM claimed;

-- transaction 밖에서 LLM 정리와 embedding 을 수행한 뒤
UPDATE kb_embeddings SET
  document   = $doc,
  embedding  = $vec,
  synced_ver = $claimed_ver      -- 집어 갈 때의 버전으로만 맞춘다
WHERE source = $1 AND source_id = $2;

마지막 줄이 디바운스를 공짜로 만든다. 처리하는 동안 답글이 또 달렸다면 content_ver 가 더 올라가 있으므로 synced_ver < content_ver 가 유지되고 워커가 한 번 더 돈다. 답글 열 개가 연달아 달려도 정리는 한 번만 돈다.

실행 검증을 하지 않았다. 문법은 검토했고 인스턴스에 올려 돌려 보지는 않았다. 워커 실패 시 재시도 횟수와 backoff 는 여기 없다. 실제로는 시도 횟수 컬럼이 하나 더 필요하다.

blueprint-read

범위 필터를 쓰는 순간 iterative scan 설정이 함께 필요해진다

네 신호 중 셋을 RRF 로 합치는 형태다. IDF 는 여기 없다. ts_rank_cd 가 corpus 통계를 쓰지 않으므로 21장에서 본 대로 별도 빈도 테이블이나 확장이 필요하다.

WITH scope AS (                       -- 프로젝트 범위가 먼저 corpus 를 자른다
  SELECT * FROM kb_embeddings
  WHERE source = 'slack_thread' AND metadata->>'channel' = ANY($channels)
),
vec AS (
  SELECT source_id, row_number() OVER (ORDER BY embedding <=> $qvec) AS rank
  FROM scope ORDER BY embedding <=> $qvec LIMIT 50
),
lex AS (
  SELECT source_id, row_number() OVER (ORDER BY ts_rank_cd(fts, q) DESC) AS rank
  FROM scope, websearch_to_tsquery('simple', $qtext) q
  WHERE fts @@ q ORDER BY ts_rank_cd(fts, q) DESC LIMIT 50
),
fresh AS (
  SELECT source_id, row_number() OVER (ORDER BY updated_at DESC) AS rank
  FROM scope WHERE source_id IN (SELECT source_id FROM vec
                                 UNION SELECT source_id FROM lex)
)
SELECT source_id, sum(w / (60 + rank)) AS rrf
FROM (
  SELECT source_id, rank, 1.0 AS w FROM vec   UNION ALL
  SELECT source_id, rank, 1.0      FROM lex   UNION ALL
  SELECT source_id, rank, 0.5      FROM fresh   -- 감쇠는 동점 처리용이라 낮춘다
) lists
GROUP BY source_id ORDER BY rrf DESC LIMIT 20;
SET hnsw.iterative_scan = relaxed_order;   -- pgvector 0.8+
SET hnsw.max_scan_tuples = 20000;
SET hnsw.ef_search = 100;

마지막 세 줄이 16장에서 본 문제의 대응이다. 범위 필터든 권한 필터든 좁아지는 순간 recall 이 조용히 무너지므로, 필터를 쓰기 시작하면 이 설정이 함께 온다.

가중치 1.0 과 0.5 는 이 문서가 정한 값이다. Cerebras 는 weight 기본값이 1.0 이라고만 밝힌다.

critique

구조는 읽어냈지만 이 구조가 잘 작동하는지는 이 문서가 말할 수 없다

원문은 자기 서술이고 대조할 코드가 없다. 공개된 품질 수치가 하나도 없어서 설계의 좋고 나쁨을 판정할 근거가 없다. 여기 적는 것은 이 문서가 확인하지 못한 것이다.

항목상태
인가 구현세 계층 중 하나로 이름만 있고 구현 서술이 없다. 여러 권한 등급이 있는 조직은 직접 설계해야 한다
GRAPH 검색기존재는 확실하나 무엇의 그래프인지 어떻게 만드는지 어디에도 없다
삭제 전파코드가 지워지면 chunk 는 사라지지만 그 코드를 언급한 Slack 정리본은 남는다. 시간 감쇠는 언제 쓰였나만 볼 뿐 아직 존재하나를 확인하지 않는다
embedding 모델 교체Slack 정규화 프롬프트를 바꾸면 모든 스레드를 LLM 으로 다시 정리한 뒤 다시 embedding 해야 한다. 이 비용을 원문이 언급하지 않는다
모델 이름embedding 은 3,072차원이라는 사실만 있다. 재정렬은 fig-001 에 LLM RERANK 로 적혀 있어 cross-encoder 라는 서술은 맞지 않지만 모델명은 없다
인프라 형태Postgres 버전, 자체 호스팅 여부, 복제와 backup, corpus 총 행수, 비용이 전부 없다

그럼에도 옮겨 갈 수 있는 것이 하나 있다. embedding 전에 정규화한다는 결정은 corpus 종류를 가리지 않는다. 원문 텍스트를 그대로 넣으면 짧고 내용 없는 문서가 상위권을 차지하는 문제는 Slack 만의 것이 아니다.

삭제 전파와 모델 교체 비용과 도입 판단을 더 파고든 문서가 2026-08-12 Cerebras Knowledge 에 있다.

conclusion

이 설계를 지탱하는 규칙은 모든 소스가 같은 행 모양을 지킨다는 것 하나다

vector 검색도 RRF 도 이 시스템의 핵심이 아니다. 둘 다 알려진 기법이고 다른 곳에도 있다. 이 시스템에서만 볼 수 있는 것은 규칙 하나를 정하고 그것을 강제할 수 있는 자리에 놓았다는 점이다.

커넥터가 pull request 하나로 늘어나고, 검색 전략이 수집을 건드리지 않고 바뀌고, 수집 상태와 vector 가 한 transaction 에 묶이는 일이 전부 그 결정 하나에서 나온다. 반대로 그 규칙을 지키지 못하는 순간 나머지 장점도 함께 사라진다.

그 규칙을 강제할 자리로 Postgres 테이블 하나를 고른 대가도 분명하다. 스키마를 바꾸면 모든 커넥터가 깨지고, 3,072차원에 HNSW 를 걸려면 타입부터 골라야 하고, IDF 를 쓰려면 확장이 깔리는 호스팅을 먼저 정해야 한다. 규모가 커지면 전제 자체가 흔들린다.

따라 지을 때 옮겨 가는 것은 기법이 아니라 순서다. embedding 하기 전에 정규화하고, 쓰기를 두 단계로 쪼개고, 대기열을 데이터 옆에 두고, 권한 판단 기준을 먼저 정한다. 네 가지 모두 검색 코드를 한 줄도 쓰기 전에 정해지는 것이다.

이 결론은 구조 분석에서 나온 것이고 성능 근거를 갖고 있지 않다.
