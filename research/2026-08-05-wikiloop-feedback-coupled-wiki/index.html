WikiLoop: Jointly Learning to Build and Navigate Agent-Native Wikis with Downstream Feedback
LLM-Wiki는 위키를 만들어 두고 agent가 읽게 했다. WikiLoop은 여기서 한 단계 더 가서, 편집이 나중의 검색 성능을 얼마나 바꾸는지를 보상으로 삼아 위키를 고치는 정책을 학습시킨다. Navigator(검색)와 Builder(편집)를 역할 조건부 공유 정책 하나로 묶었다.

저자 · 소속

Haoliang Ming, Feifei Li, Wenhui Que

tl-dr

요약

같은 모델(Qwen3.5-9B)에서 LLM-Wiki를 AC 6.3점 앞선다. 이득은 거의 전부 여러 문서를 봐야 하는 질문에서 나온다.

AC(Answer Correctness)는 LLM 채점자가 답변을 0~3점으로 매겨 100점 만점으로 환산한 값이다. 정답률이 아니다. 사람이 블라인드로 다시 채점해도 순위가 같았다(62.8).

  • 02효용 차이로 편집을 채점한다. 편집 전후 위키를 각각 복사해 고정된 Navigator를 돌리고, 그 차이를 보상으로 쓴다. 편집 후 상태가 좋은 게 아니라 편집이 얼마나 바꿨는지를 본다.
평가 방식이 원 논문보다 엄격하다
  • ▸주요 비교마다 paired bootstrap 신뢰구간과 Holm 보정 p값을 붙였다. LLM-Wiki에는 없던 것이다.
  • ▸채점자를 셋 돌렸다. DeepSeek-V4-Flash 62.6, GLM-5.1 62.5, 블라인드 사람 62.8. 순위가 모두 같다.
  • ▸Builder 학습에 쓴 평가자와 다른 시드로 따로 학습시킨 Navigator로 편집의 유용성을 다시 확인했다.
학습 없이 바로 쓸 수 있는 것
  • 01검색 agent의 비용 압박을 뒤로 미룬다. 호출 수를 줄이라는 지시를 항상 걸지 말고, 근거를 다 모았다고 판단되기 전에는 걸지 않는다. 조기 종료 24.2% → 11.1%.
  • 02평가를 전후 차이로 기록한다. 규칙을 바꿨을 때 “바꾼 뒤 정확도”가 아니라 “같은 질문 세트에서 바뀐 폭”을 남긴다. 절대값으로 재면 개선을 절반으로 과소평가한다(6.2 대 12.8).
  • 03무관한 질문을 회귀 테스트로 같이 돌린다. 손상 0.046 → 0.016으로 65% 줄고 목표 이득은 거의 안 깎인다.
  • 04평가 파이프라인을 실험 도중에 바꾸지 않는다. 채점 기준이 같이 변하면 개선인지 기준 변화인지 구분할 수 없다.

넷 다 프롬프트와 평가 스크립트만으로 된다. 나머지 장(04~06)은 RL 파이프라인이 있어야 한다.

WikiLoop 자체는 도입 대상이 아니다. 코드와 학습 데이터와 보상 계수가 모두 비공개이고 RL 파이프라인이 필요하다. 벤치마크도 같은 팀 것이고 학습과 평가가 같은 코퍼스를 공유한다. 가져갈 것은 위 네 가지 설계 원칙이지 시스템이 아니다. 자세한 조건은 11장.

problem

지식베이스를 만드는 일이 쓰이는 방식과 끊겨 있다

기존 구도에서는 검색 agent가 외부에서 고정된 인덱스 위에서 동작하고, 구축 쪽은 다운스트림에서 아무 신호도 받지 못한다. 페이지를 어떻게 쪼갤지, 어떤 링크를 걸지는 컴파일 시점의 추측으로 정해지고, 그 선택이 이후 검색에 도움이 됐는지는 측정되지 않는다.

LLM-Wiki의 처리 방식

Error Book이 오류를 규칙으로 바꿔 다음 배치 프롬프트에 넣는다. 다만 이것이 잡는 것은 끊긴 링크, 잘못된 출처 참조 같은 구조 오류다. “이 페이지를 이렇게 쪼갰을 때 나중 질문에 도움이 되는가”는 판단하지 못한다.

실제로 원 논문 ablation에서 Error Book은 세 구성 요소 중 효과가 가장 작았다(−3.4~4.0 F1). 해당 LLM-Wiki 17장 ablation

WikiLoop의 처리 방식

편집 후보 e마다 영향 받는 질문 집합(최대 3개)과 guard 질문 집합(2개, 페이지·출처가 겹치지 않는 같은 저자 질문)을 짝짓는다.

위키를 복사해 편집 전 상태와 후 상태를 만들고, 고정 Navigator로 두 집합을 각각 실행한다. 영향 받는 질문에서 올라간 만큼 보상하고, guard 질문에서 내려간 만큼 벌점을 준다. 편집의 한계 효용을 직접 측정하는 셈이다.

왜 “전후 차이”여야 하나. 편집 후 위키가 좋아 보이는 이유는 편집 전에 이미 좋았기 때문일 수 있다. 절대 성능으로 채점하면 아무것도 안 한 편집도 높은 점수를 받는다. 실제로 표 2B에서 절대 효용으로 채점했을 때 영향 질문 ΔAC는 6.2에 그치고, 전후 차이로 바꾸면 12.8로 두 배가 된다.

shared-policy

Navigator와 Builder를 파라미터 하나로 묶는다

두 역할은 같은 위키 위에서 읽는 쪽과 쓰는 쪽이다. 둘 다 관련 정보를 찾고, 페이지와 링크 구조를 이해하고, 출처를 추적하고, 어떤 증거가 필요한지 판단해야 한다. 능력이 겹치니 파라미터를 공유하되, 역할별로 프롬프트·관측·행동 공간·보상은 따로 둔다.

학습할 때는 한 묶음에 한 역할만 담는다. 이 학습법은 같은 묶음 안의 여러 시도를 서로 비교해 잘한 쪽을 강화하는 방식이다. 그런데 검색 시도와 편집 시도는 점수 기준 자체가 다르다. 한 묶음에 섞으면 점수 차이가 “어느 역할인가” 때문인지 “얼마나 잘했는가” 때문인지 구분되지 않는다. 그래서 묶음은 역할별로 나누되 학습 결과는 같은 모델에 함께 반영한다. (알고리즘은 GRPO와 GSPO. 직접 학습할 때만 필요한 이름이다.)

nav-reward

Navigator: 증거를 다 모으기 전에는 비용을 묻지 않는다

검색 비용에 계속 페널티를 걸면 agent가 일찍 멈추는 쪽을 학습한다. 짧은 궤적이 싸기 때문이다. WikiLoop은 증거 재현율이 1이 된 뒤에야 비용 항을 켠다.

guard 항의 비용

guard를 넣으면 무관한 질문의 손상이 0.046에서 0.016으로 65.2% 줄어드는데, 영향 질문 이득은 12.8에서 12.1로만 내려간다. 학습에 쓰지 않은 별도 채점자로 다시 재도 0.077에서 0.084로 떨어지지 않는다. 채점자에게만 잘 보이는 편집이 걸러진다는 뜻이다. 다만 이 상승분 자체는 논문이 통계적으로 유의하지 않다고 적었다.

training

학습은 네 단계를 순서대로 밟는다

여기서 읽을 것은 하나다. 편집을 채점하려면 채점자가 필요한데, 채점자가 학습 중에 같이 변하면 점수가 오른 게 편집이 좋아져서인지 채점 기준이 물러져서인지 구분할 수 없다. 그래서 채점자를 특정 시점에 복사해 고정해 놓고 쓴다. 사람이 만든 규칙으로 청킹을 바꿔가며 평가할 때도 같은 원칙이 적용된다. 평가 파이프라인을 실험 도중에 건드리면 안 된다. 아래 4단계 순서는 직접 학습할 때만 필요하다.

3단계에서 Builder를 학습시키고 나면 2단계에서 익힌 검색 성능이 일부 떨어진다. Navigator AC가 60.4에서 59.7로, 조기 종료가 11.1%에서 12.5%로 나빠진다. 4단계 Joint RL은 이 하락을 되돌리는 역할이다. 결과는 60.8 / 10.9로 특화 모델보다도 살짝 낫다.

LLM-Wiki가 빠뜨렸던 숫자

원 논문의 가장 큰 공백이 컴파일 비용 미보고였다. WikiLoop 보충 자료가 이를 채운다.

위키 전체 구축185.15MLLM-Wiki base 194.00M 토큰
질문당 지연15.76초LLM-Wiki base 16.90초

비용 수치를 어떻게 읽어야 하나. AuthTrace 코퍼스(860편) 위키를 짓는 데 약 1.9억 토큰이 든다. 문서 한 편당 21.5만 토큰이다(LLM-Wiki는 194.00M, 편당 22.6만). 손익분기는 여전히 계산할 수 없다. 비교 대상인 “위키 없이 같은 질문을 풀 때 드는 토큰”을 논문이 보고하지 않기 때문이다. 다만 구축 쪽 자릿수는 자기 문서 수에 곱해볼 수 있다. 문서 1,000편이면 약 2.2억 토큰, 5,000편이면 약 11억 토큰이 초기 구축에만 든다. 그리고 WikiLoop이 LLM-Wiki보다 성능은 6.3점 높으면서 구축 토큰은 4.6% 적고 지연도 6.7% 낮다는 점은, 학습된 Builder가 더 적게 쓰면서 더 쓸모 있는 위키를 만든다는 뜻이다.

result-transfer

결과 3. 다른 데이터셋과 더 큰 모델로 전이된다

AuthTrace로만 학습하고 보정했으므로, 학습에 전혀 참여하지 않은 두 벤치마크로 zero-shot 전이를 확인한다.

모델 크기 전이

Qwen3.5-9B에서 Qwen3.5-35B-A3B로 키우면 Joint SFT는 58.2 → 60.7, WikiLoop은 62.6 → 64.8이 된다. 중요한 건 WikiLoop이 지도학습 초기값 대비 갖는 우위가 두 크기에서 유지된다는 점이다(9B에서 +4.4, 35B에서 +4.1).

그리고 두 크기 모두 여러 문서가 필요한 질문에서 우위가 더 크다. 9B에서 2개/3개 이상 구간 +5.5/+7.7, 35B에서 +6.1/+7.2인 반면 1개 구간은 +3.3, +2.6에 그친다.

주의

표 4에는 GLM-5.1로 돌린 참고 수치도 함께 실려 있는데, 논문은 이를 맥락용이며 같은 백본 비교에 쓰지 말라고 명시했다. 그 블록의 LLM-Wiki 0.839 / 0.739는 원 논문 표 1의 값을 그대로 옮긴 것이다.

전이 검증은 벤치마크 2개, 더 큰 백본 1개에 그친다. 논문도 “더 넓은 모델 계열과 규모는 앞으로의 과제”라고 적었다.

critique

해석의 한계

방법론 자체는 LLM-Wiki보다 훨씬 엄격하다. 신뢰구간, 다중 비교 보정, held-out 평가자, 채점자 3종 교차 확인이 모두 있다. 그래도 남는 문제가 넷 있다.

1. 닫힌 고리가 아니다

편집 후보는 위키 사본에 적용해 채점하고 버린다. 실제 위키에 반영되지 않는다. 논문이 한계로 직접 밝힌 대로, 편집과 이후 검색이 하나의 궤적 안에서 최적화되지는 않는다. 편집이 쌓이면서 서로 간섭하거나 오류가 전파되는 상황은 다루지 못한다.

2. 지식베이스 수준에서 transductive

질문과 주석은 엄격히 분리했지만, 학습과 평가가 같은 코퍼스와 같은 초기 위키를 공유한다. 논문이 이 점을 명시한다. 완전히 새로운 코퍼스에서 위키를 처음부터 지었을 때도 같은 이득이 나오는지는 확인되지 않았다.

3. 벤치마크가 여전히 자체 제작

주 평가가 AuthTrace이고, 앞선 문서에서 지적한 대로 같은 팀의 벤치마크다. 게다가 이번에는 구간 정의까지 바꿔서(Low=2, High≥3) 원 논문과 구간별 비교가 불가능하다. 전이 검증에 쓴 HotpotQA와 MuSiQue가 유일한 외부 척도다.

4. 재현 불가

코드, 학습 데이터, 보상 계수가 공개되지 않았다. 보상 함수의 정규화 상수와 계수는 모두 “보충 자료 참조”로 넘어간다. RL 학습은 하이퍼파라미터 민감도가 큰데, 이 상태로는 제3자가 같은 결과를 낼 수 있는지 확인할 방법이 없다.

그럼에도 이 논문에는 다른 상황에 옮겨 쓸 수 있는 결과가 두 개 있다. 첫째, 검색 agent에 비용 페널티를 걸 때는 증거를 다 모은 뒤에 걸어야 한다. 그러지 않으면 조기 종료를 학습한다(24.2% 대 11.1%). 둘째, 지식베이스 편집을 학습시킬 때는 결과 상태가 아니라 전후 차이로 채점해야 한다(6.2 대 12.8). 둘 다 같은 시스템 안의 대조 실험이라 벤치마크 선택과 무관하게 성립한다.

conclusion

결론

LLM-Wiki의 결론이 “컴파일과 순회는 세트로만 작동한다”였다면, WikiLoop의 결론은 “그 세트를 사람이 설계하는 대신 학습시킬 수 있다”이다.

바뀐 것 1

위키 편집이 처음으로 측정 가능해졌다

그동안 “페이지를 어떻게 쪼개야 하나”는 설계자의 감이었다. 이제 편집 전후로 검색을 돌려 차이를 재면 된다. 이 신호가 있으면 학습도 되고, 학습하지 않더라도 사람이 만든 규칙을 검증하는 데 쓸 수 있다.

바뀐 것 2

비용의 자릿수를 알게 됐다

AuthTrace 코퍼스 860편 위키 구축에 185.15M 토큰. 문서당 21.5만 토큰이다. 5월 시점에 계산할 수 없다고 적었던 손익분기를, 이제 자기 워크로드에 대입해 어림잡을 수는 있다.

바뀌지 않은 것

외부 검증은 여전히 없다

평가 방법은 훨씬 엄격해졌지만 평가하는 주체는 그대로다. 벤치마크도, 시스템도, 후속 연구도 전부 같은 팀에서 나온다. 코드 공개가 없어 재현 시도조차 어렵다.

도입 관점에서는. WikiLoop은 RL 학습 파이프라인을 요구하므로 LLM-Wiki 도입 조건보다 문턱이 훨씬 높다. 합성 학습 데이터 생성, 편집마다 위키 사본을 뜨고 Navigator를 두 번 돌리는 롤아웃, 역할별 배치 구성이 전부 필요하다. 반면 sufficiency 스위치은 학습 없이도 바로 쓸 수 있다. 검색 agent의 도구 호출 예산을 다룰 때 “증거가 충분해지기 전에는 비용을 재촉하지 않는다”는 규칙 하나만 옮겨도 된다.
