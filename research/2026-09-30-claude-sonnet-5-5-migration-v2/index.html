Claude Sonnet 5.5 이전 안내: Sonnet 5 코드에서 고칠 곳을 요청부터 응답까지 따라간다

Messages API 를 직접 부르는 Sonnet 5 코드를 Sonnet 5.5 로 옮길 때 어느 줄을 고쳐야 하는지 순서대로 짚는다. 근거는 Anthropic 이 2026-09-28 에 낸 소개 글과 platform 문서 네 쪽이다. 문서 넷은 migration guide(이하 guide), What's new, thinking 문서, effort 문서로 부른다.

  • 03~05무엇이 어떻게 깨지는지, 그리고 요청 하나가 고쳐지는 과정
  • 06~09그대로 두면 400 을 받는 설정 다섯 가지
  • 10~11에러 없이 응답 모양이 바뀌는 두 곳
  • 12~13effort 를 다시 골라야 하는 이유와 시작값
  • 14~17읽은 범위와 한계, 옮기는 순서, 출처

Sonnet 4.6 이하나 Haiku 4.5 에서 옮기는 경우는 다루지 않는다.

tl-dr

모델 ID 만 바꾸면 다섯 가지 설정이 400 을 받고, 응답 쪽 두 곳은 에러 없이 달라진다

Sonnet 5 코드가 아래 설정 가운데 하나라도 쓰면 model 문자열만 바꿔서는 옮겨지지 않는다. 400 을 내는 설정부터 고치고 나서 응답을 그리는 코드와 effort 값을 다시 본다.

  • 400thinking: {"type": "disabled"} 는 between_tools 로 바꾼다. 단 effort 가 high 이하일 때만 받는다
  • 400tool_choice 의 any 와 tool 은 auto 에 strict: true 로 바꾼다
  • 400대화 앞부분을 고친 뒤 thinking 블록을 다시 보내면 막힌다 (2026-08-31 이후 만든 계정, Claude API, Bedrock, Google Cloud)
  • 400computer_20251124 는 Claude API 와 Google Cloud 에서 computer_toolset_20260801 로 옮긴다
  • 400advisor 로 Sonnet 5, Sonnet 4.6, Opus 4.6~4.8 을 붙인 요청은 짝을 바꾼다
  • 200tool call 사이의 긴 메모가 빈 thinking 블록으로 와서 진행 화면이 멈춘다
  • 200거부 부류가 다섯이 됐고 거부는 stop_reason: "refusal" 인 정상 응답으로 온다

가격은 Sonnet 5 와 같다. 그래도 effort 단계가 다시 맞춰져서 같은 값을 옮겨 오면 비용과 품질이 둘 다 달라진다. thinking 을 꺼 두던 코드라면 thinking 이 차지할 몫까지 넣어 max_tokens 도 다시 잡는다(13장).

첨언

guide 「Handle thinking in responses」 는 세 항목을 두고 “Code from Claude Sonnet 5 likely has the first two.” 라고 적는다. 앞의 두 항목은 content block 을 type 으로 읽는 것과 thinking 블록을 그대로 되돌려 보내는 것이고, Sonnet 5 코드는 아마 이미 갖췄으리라는 뜻이다. 「Every starting model」 체크리스트 10항목에서 이 둘을 묶은 항목과 모델 ID, effort 재측정을 빼면 위 일곱 줄이 남는다.

guide 는 “Code that ran without thinking needs all three items.” 라고도 적는다. thinking 을 꺼 두고 돌던 Sonnet 5 코드가 여기에 해당한다고 이 문서는 읽었고, 그렇다면 max_tokens 재검토까지 세 항목이 모두 필요하다.

Amazon Bedrock 에서 달라지는 부분은 해당 장에만 적었다.

problem

400 은 로그에 남지만, 응답 모양과 비용의 변화는 에러 없이 지나간다

옮긴 뒤 에러 로그만 보면 변화의 절반을 놓친다. 스트리밍 화면과 거부 처리, 요청당 비용은 따로 확인해야 한다.

소개 글이 드는 이점은 Sonnet 5 보다 30% 넘게 빠르고 대부분의 작업에서 작업당 비용이 최대 30% 낮다는 것이다. 가격표가 같으니 절감은 전부 토큰 수에서 나온다.

진행 메모가 빈 thinking 블록으로 옴사용자 화면이 tool call 사이에 멈춤10

요청당 비용 변화usage 와 청구서12~13
첨언

소개 글 첫 문단: “It’s a clear upgrade over Claude Sonnet 5, runs 30%+ faster, and costs up to 30% less for most work.” 가격 문단은 입력 100만 토큰당 $2, 출력 $10, cache read $0.20 이 Sonnet 5 와 같다고 적고, 절감은 “it typically needs far fewer tokens to do the same work” 에서 온다고 설명한다.

거부가 200 으로 온다는 것은 What's new 의 「Refusals, fallback, and billing」 절에 있다.

“최대 30%” 가 어느 effort 에서 잰 값인지는 소개 글에 없다.

map

바뀌는 곳은 요청을 만드는 코드, 응답을 그리는 코드, 대화 기록을 다시 보내는 코드 세 층이다

고칠 곳을 찾을 때 세 층을 따로 훑는다. 기록 층은 Sonnet 5 에서 건드릴 일이 없던 곳이라 빠뜨리기 쉽다.

  • 요청thinking, tool_choice, tool 선언, advisor 짝, effort 가 바뀐다
  • 응답tool call 사이 메모의 블록 종류와 거부 부류가 바뀐다
  • 기록블록이 앞선 대화와 계정에 묶여 기록을 고치는 코드가 막힌다

하지만 기록 층의 검사는 계정을 만든 날짜에 따라 기본값이 다르다. 그래서 오래된 개발 계정에서 통과하던 코드가 2026-08-31 이후에 만든 운영 계정에서 처음 400 을 낼 수 있다.

Claude Managed Agents 를 쓰면 guide 는 모델 이름 말고는 바꿀 것이 없다고 적는다.

trace

guide 의 before 요청은 thinking 값을 바꾸는 것만으로는 통과하지 못하고 effort 까지 내려야 한다

thinking 을 끄던 요청은 두 값을 함께 고친다. xhigh 를 지켜야 한다면 thinking 을 끄는 대신 adaptive 로 돌린다.

// migration guide 「Turn off up-front thinking」 의 Before 요청을 한 단계씩 고친다
① model      "claude-sonnet-5"  →  "claude-sonnet-5-5"   날짜 접미사 없음. Bedrock 은 "anthropic.claude-sonnet-5-5"
② thinking   {"type": "disabled"}
             → 400 invalid_request_error
③ thinking   {"type": "between_tools"}        effort 는 아직 "xhigh"
             → 400   between_tools 는 low, medium, high 에서만 받는다
④ effort     "xhigh" → "high"                guide 의 After 가 고른 길
             → 200   tool 이 없는 요청이라 응답은 text 블록뿐
④' 또는      thinking 필드를 빼고 "xhigh" 유지    adaptive 로 돈다
             → 200   앞쪽 thinking 이 다시 켜진다
⑤ fallback   ④ 의 between_tools 요청이 거부로 Sonnet 5 에 넘어가면 거기서 disabled 로 돈다

두 갈래 중 어느 쪽인지는 thinking 을 왜 껐는지로 정한다. 지연과 비용을 줄이려고 껐다면 ④ 가 그 의도를 지키고, xhigh 의 깊이가 필요했다면 ④' 로 가되 앞쪽 thinking 에 드는 토큰을 감수한다.

첨언

② 의 에러 문구는 원문 그대로 “"thinking.type.disabled" is not supported for this model. Use "thinking.type.between_tools" for the lowest thinking setting, or "thinking.type.adaptive" and "output_config.effort" to control thinking behavior.” 이다.

Before 예시는 max_tokens: 16000, thinking: {"type": "disabled"}, output_config: {"effort": "xhigh"} 이고 After 예시는 model 과 thinking 을 바꾸면서 effort 를 "high" 로 적었다. ③ 의 400 은 guide 가 따로 적은 조건 “At `xhigh` or `max`, it returns a 400 error.” 에서 온다. ④' 는 guide 가 같은 문단에서 제시한 대안이다.

⑤ 는 server-side fallback(fallbacks: "default") 을 켰을 때의 이야기다. 11장이 어떤 거부가 넘어가는지 다룬다.

tool 이 없는 요청이라 between_tools 가 돌려주는 진행 메모는 이 예시에 나타나지 않는다.

thinking

between_tools 는 앞쪽 thinking 을 끄는 값이지만, effort 와 함께 보내는 필드에 조건이 붙는다

disabled 를 between_tools 로 한 줄 바꾸는 치환은 effort 가 high 이하이고 thinking 에 다른 필드가 없을 때만 통과한다.

between_tools 와 함께결과
effort low, medium, high받는다
effort xhigh, max400
display, budget_tokens, block_binding400
대화 중간에 다른 effort 를 메시지 단위로 보냄400. 턴마다 바꾸려면 adaptive
tool 없는 요청응답은 text 뿐
tool 을 쓰는 요청tool call 사이 진행 메모가 thinking 블록으로 온다(10장)
server-side fallback 으로 Sonnet 5 에 넘어감거기서 disabled 로 돈다

beta header 는 필요 없고 Sonnet 5.5 를 제공하는 모든 플랫폼에서 받는다. guide 는 이 값을 Sonnet 5.5 의 가장 낮은 thinking 설정이라고 부른다.

따라서 thinking 과 effort 를 서로 다른 설정 파일에서 읽어 오는 코드라면 요청을 보내기 전에 두 값을 함께 검사한다. 따로 보면 둘 다 맞는 값인데, 합치는 순간 400 이 나는 조합이 표의 둘째 줄이다.

첨언

migration guide 「Turn off up-front thinking」 둘째 문단: “`between_tools` works on every platform that offers Claude Sonnet 5.5, with no beta header. It's accepted at `low`, `medium`, and `high` effort. At `xhigh` or `max`, it returns a 400 error.” 이어서 “`between_tools` takes no other field: `display`, `budget_tokens`, or `block_binding` sent with it returns a 400 error.”

셋째 문단: “With `between_tools`, effort can't change mid-conversation: a per-message `output_config.effort` that differs from the level in effect returns a 400 error.” 턴마다 effort 를 바꾸려면 adaptive 로 돌리라고 적는다.

between_tools 와 adaptive 가 답의 품질에서 얼마나 다른지 잰 수치는 이 corpus 에 없다.

tool-choice

tool 호출을 강제하던 요청은 auto 와 strict 로 바꾸고, 언제 부를지는 프롬프트에 적는다

any 와 tool 대신 auto 를 보내고, 언제 부를지는 프롬프트로 옮긴다. strict: true 를 붙이면 입력이 스키마를 따른다.

// Before (Sonnet 5)
"tool_choice": {"type": "tool", "name": "get_weather"}

// After (Sonnet 5.5)
"tools": [{ "name": "get_weather", "input_schema": { …, "additionalProperties": false },
            "strict": true }],
"tool_choice": {"type": "auto"},
"content": "What's the weather in Paris? Use the get_weather tool."

tool 호출을 강제하던 코드는 대개 응답에 tool_use 블록이 있다고 가정한다. 하지만 auto 에서는 모델이 text 로만 답할 수 있어서, 그 가정을 지우고 블록이 없을 때 다시 묻거나 실패로 처리하는 분기를 넣어야 한다.

  • 400token counting endpoint 도 같은 검사를 한다
  • 허용auto(기본값) 와 none 은 그대로 받는다
  • strict모든 object 에 additionalProperties: false 가 있어야 한다
  • 한도strict tool 은 요청당 20개까지이고 MCP, computer use, browser use toolset 에는 붙일 수 없다
  • Bedrockstructured outputs 를 못 쓰므로 strict 없이 auto 를 보내고 입력은 코드에서 검증한다
첨언

guide 「Forced tool use is not supported」: “Every earlier model on this page accepts a `tool_choice` of type `any` or `tool`. Claude Sonnet 5.5 rejects both with a 400 error, including on the token counting endpoint” 이고, 대안은 “The model can then answer without calling the tool, so say in the prompt when to use it.” 라는 단서와 함께 온다.

위 After 는 guide 의 cURL 예시를 줄인 것이다. 원래 예시는 사용자 메시지 끝에 “Use the get_weather tool.” 을 덧붙여 프롬프트로 호출을 유도한다.

스키마를 structured outputs 로 옮기는 길은 What's new 가 한 줄로만 언급해서 여기서도 다루지 않는다.

history

Sonnet 5.5 의 thinking 블록은 만든 대화와 계정에 묶여서, 기록을 고쳐 다시 보내는 코드가 400 을 받는다

대화 기록은 덧붙이기만 하고, 지시나 tool 을 바꿀 때는 중간 system 메시지를 쓴다. 검사는 Claude API, Amazon Bedrock, Google Cloud 에서 2026-08-31 00:00 UTC 이후 만든 계정에 기본으로 켜진다.

상황결과
블록 앞의 system, tools, 이전 메시지를 고친 뒤 다시 보냄400 (새 계정)
같은 상황에서 prefix_mismatch_behavior: "drop_block" (adaptive 만)그 블록만 빠진다
between_tools 로 돌면서 기록을 고쳐야 함고친 턴부터 thinking 블록을 떼어 낸다
2026-08-31 이전 계정기본은 검사 없음. block_binding 을 보내면 검사에 들어간다
연결되지 않은 다른 계정이 블록을 보냄블록이 빠지고 200
Sonnet 5 블록을 Sonnet 5.5 에 보냄읽는다
Opus 5, Opus 5.5 블록을 Sonnet 5.5 에 보냄빠지고 200, 과금 없음
Sonnet 5.5 블록을 다른 모델에 보냄어느 모델도 읽지 않는다

Sonnet 5 에서 이어 온 대화는 reasoning 을 이어받지만, Sonnet 5.5 에서 다른 모델로 넘어간 대화는 그 뒤부터 reasoning 없이 돈다. 모델이 읽지 못해 빠진 블록은 thinking-binding-controls-2026-08-01 beta header 를 보내면 응답의 input_transformations 에 보고된다.

첨언

What's new 「Thinking blocks are tied」 는 검사 대상을 “the `system` prompt, the `tools`, or an earlier message” 셋으로 적는다. guide 는 “For accounts created on or after August 31, 2026, 00:00 UTC, the API enforces this by default, on the Claude API, Amazon Bedrock, and Google Cloud.” 라고 적는다.

drop_block 은 thinking-binding-controls-2026-08-01 beta header 가 있어야 하고 thinking: {"type": "adaptive"} 에서만 된다. between_tools 로 돈다면 기록을 덧붙이기만 하거나, 고친 턴부터 thinking 블록을 떼어 내야 한다. 이전 계정은 이 필드를 어느 값으로든 보내면 검사에 들어간다.

계정 결속은 guide 의 “Thinking blocks that Claude Sonnet 5.5 produces work only in the account that produced them, or in an account linked to it.” 이다. 소개 글은 Claude Code 에서 세션 중간에 계정을 바꾸는 경우를 예로 든다.

블록이 빠졌을 때 답의 품질이 얼마나 떨어지는지는 원문에 없다.

tools

computer use 는 Claude API 와 Google Cloud 에서, advisor 는 받지 않는 짝에서 Sonnet 5 때 쓰던 선언이 400 을 받는다

computer_20251124 를 보내던 코드는 Claude API 와 Google Cloud 에서 toolset 으로 옮기면서 agent loop 도 고친다. advisor 로 Sonnet 5 를 붙였다면 짝을 바꾼다.

  • 없음이미 toolset 을 보내는 코드와 browser use tool 은 바꿀 것이 없다

computer use 는 선언 한 줄을 바꿔서 끝나지 않는다. toolset 은 member tool_use 블록, batch action, 결과의 toolset_name 을 쓰기 때문에 tool_use 를 받아 실행하는 agent loop 까지 손봐야 한다.

첨언

guide 「Computer use needs the toolset」: “On the Claude API and Google Cloud, Claude Sonnet 5.5 supports computer use only through the `computer_toolset_20260801` toolset. There, `computer_20251124` returns a 400 error.” 같은 절의 표는 Bedrock 에서 보낼 값을 computer_20251124 로 적는다.

advisor 목록은 guide 「The advisor tool accepts fewer advisors」 에서 옮겼다. guide 는 advisor 절에 플랫폼 조건을 달지 않아서 Bedrock 에서 같은 짝 조건이 적용되는지는 이 corpus 로 확인할 수 없다.

toolset 으로 옮길 때의 agent loop 변경 절차는 computer use 문서에 있고, 이 corpus 에는 그 문서가 없다.

progress

tool call 사이의 긴 메모가 thinking 블록으로 옮겨 가서, 그걸 보여주던 화면이 에러 없이 멈춘다

진행 상황을 스트리밍하던 앱은 display 값을 정하거나 between_tools 로 돈다. 한두 문장 이하의 짧은 말은 여전히 text 로 온다.

  • 그리기Sonnet 5.5 에서 긴 메모는 어느 설정이든 thinking 블록에 있다. 비어 있지 않은 thinking 블록을 뒤따르는 tool_use 블록 앞에 그린다
  • 되돌림between_tools 에서 진행 메모 블록을 그대로 돌려보내면 모델은 요약 대신 자기가 쓴 메모 전체를 받는다

에러가 나지 않으니 자동 테스트로는 잡히지 않는다. 그래서 옮긴 뒤 tool 을 여러 번 부르는 대화를 한 번 직접 돌려 화면을 보는 것이 가장 싼 확인이다.

첨언

guide 「Text between tool calls」: “On Claude Sonnet 5 and earlier models, all text between tool calls comes back as `text` blocks. No request fails, but an interface that shows those notes goes quiet.”

"updates" 는 thinking-display-updates-2026-08-18 beta header 가 필요하다. 블록을 되돌려 보낼 때 모델이 전체 메모를 받는다는 문장은 What's new 의 between_tools 절에 있다.

“한두 문장보다 긴” 경계가 몇 토큰인지는 원문이 정하지 않았다.

refusal

거부 부류가 다섯으로 늘었고 server-side fallback 이 다시 돌리는 것은 그중 둘이다

stop_reason: "refusal" 인 200 응답을 따로 처리한다. Claude API 에서 fallback 을 켜면 cyber 와 frontier_llm 은 Sonnet 5 로 넘길 수 있지만, 나머지 셋과 다른 플랫폼의 거부는 코드가 받아야 한다.

stop_details 부류걸리는 요청fallback
cybermalware, exploit 개발Sonnet 5 로 재시도
frontier_llm경쟁 AI 모델 개발 지원Sonnet 5 로 재시도
bio생물학적 위해. 소개 글이 일부 오탐을 인정안 함
reasoning_extraction내부 reasoning 을 응답에 옮겨 적게 함안 함
general_harms그 밖의 정책 영역, 무해한 일도 걸릴 수 있음안 함

fallback 은 fallbacks: "default" 로 켜고 beta 이며 Claude API 에서만 된다. 소개 글은 일상적인 버그 수정은 그대로 되고, 위험도가 높은 보안 작업만 눈에 보이게 Sonnet 5 로 넘어간다고 적는다.

그래서 fallback 을 켜도 나머지 세 부류의 거부는 사용자에게 그대로 닿는다. general_harms 는 무해한 요청에도 걸릴 수 있다고 guide 가 적으므로, 거부를 화면에 어떻게 보여줄지는 옮기기 전에 정해 둔다.

첨언

guide 「Safety classifiers and fallback」: “Claude Sonnet 5.5 declines in more categories than Claude Sonnet 5.” 부류 설명은 같은 절의 목록이고, general_harms 에는 “Benign work can also trigger this category.” 가 붙어 있다.

소개 글 안전 절은 bio 분류기에 대해 “some microbiology and virology requests may be flagged in error” 라고 오탐을 인정한다.

거부된 요청이 과금되는지는 부류마다 다르다고만 적혀 있고 이 corpus 에 기준표는 없다.

result-cost

Sonnet 5 최고점은 Sonnet 5.5 의 low 에서 high 사이 단계가 1/9~1/24 비용으로 넘고, max 는 네 벤치마크 모두 Sonnet 5 max 보다 비싸다

effort 를 그대로 옮겨 오면 절감 기회를 놓치거나 비용이 오른다. 자기 eval 로 단계별 점수와 비용을 다시 잰다.

FrontierCode 에서 Sonnet 5.5 는 max 가 46.2% 로 xhigh 52.1% 보다 낮으면서 비용은 13배다. 원문이 밝힌 원인은 15장에 있다.

03장의 “최대 30%” 는 기준 effort 를 밝히지 않은 소개 글의 수치이고, 이 표는 Sonnet 5 최고점을 넘는 가장 싼 단계와 견준 것이라 두 수치를 맞대어 읽으면 안 된다.

하지만 이 비용은 Anthropic 과 평가사가 쓴 harness 와 프롬프트에서 나온 값이다. 자기 작업에서도 같은 비율이 나온다는 근거는 없으니, 표는 어느 단계부터 재 볼지 정하는 데만 쓴다.

첨언

비용 비는 “처음 넘는 단계의 비용 ÷ Sonnet 5 최고점의 비용” 이다. Terminal-Bench 0.76/11.62 = 0.065, FrontierCode 0.42/10.07 = 0.042, CursorBench 0.50/7.17 = 0.070, AA-Briefcase 1.64/14.43 = 0.114. max 끼리의 배수는 1.08, 1.21, 1.35, 2.02 다.

소개 글 본문은 같은 경향을 “On several benchmarks, Sonnet 5.5 at Low or Medium effort beats Sonnet 5’s best score for about a tenth of the cost per task.” 로 적는다. FrontierCode max 의 13배는 $20.78 / $1.59 다. 각주 2 는 max 에서 Claude Code 의 code-review skill 을 더 자주 돌려 timeout 이나 범위 밖 수정이 난 것을 원인으로 든다.

차트 점에는 신뢰구간이 없어서 1~2점 차이는 판단할 수 없다.

effort

effort 는 이름이 같아도 다시 맞춰진 단계라서, 작업 종류로 시작값을 고르고 캐시와 max_tokens 를 함께 본다

agentic coding 은 medium, 길거나 어려운 작업은 high, 채팅은 medium 이나 low 에서 시작한다. xhigh 와 max 는 eval 이 품질 이득을 보일 때만 쓴다.

작업시작 effort
agentic coding, 여러 단계 tool 사용 (명확한 작업)medium
같은 종류의 더 길거나 어려운 작업high
채팅, 지연에 민감한 작업medium 또는 low
그 밖high (Claude API 기본값)
  • 기본값Claude API 는 두 모델 모두 high 다. Claude Code 는 Sonnet 5 의 high 에서 Sonnet 5.5 의 medium 으로 바뀐다
  • 캐시요청마다 top-level effort 를 바꾸면 cache breakpoint 가 깨진다. Sonnet 5.5 는 메시지 단위 effort (beta) 로 캐시를 지킨다
  • 캐시캐시할 수 있는 최소 프롬프트가 1,024 토큰에서 512 토큰으로 줄었다
  • max_tokensthinking 과 답을 합친 요청 하나의 상한이라 tool-use loop 한 턴의 전체 지출은 막지 못한다. agentic coding 은 128,000 에 streaming 을 권한다
첨언

effort 문서 「Recommended effort levels for Claude Sonnet 5.5」: “Its levels are recalibrated, so a level doesn't produce the same amount of thinking as the same level on Claude Sonnet 5.” 같은 절에 “Use `xhigh` or `max` only where your evals show a quality gain.” 이 있다.

Claude Code 기본값은 소개 글의 “In Claude Code and our apps, the default effort is set to Medium” 과 effort 문서의 “Claude Sonnet 5 defaults to `high` effort on the Claude API and Claude Code.” 를 맞대어 본 것이다. 메시지 단위 effort 는 mid-conversation-output-config-2026-07-01 beta header 가 필요하고 Sonnet 5 에는 없던 기능이며, between_tools 에서는 쓸 수 없다(06장).

턴 전체 지출에 대한 문장은 thinking 문서 「Cost control」 의 “each request in the turn has its own `max_tokens`, so it doesn't bound the whole turn's spend” 이다.

Sonnet 5 의 어느 단계가 Sonnet 5.5 의 어느 단계에 맞먹는지 대응표는 원문에 없다.

setup

소개 글과 문서 네 쪽을 2026-09-29 에 받은 바이트로 읽었고, 링크된 하위 문서는 열지 않았다

400 조건과 요청 필드는 원문 문장 그대로 옮겼다. guide 가 링크한 하위 문서는 열지 않았으므로 06, 08, 09, 10, 11, 13장은 guide 와 What's new 의 문장에 기대고, 특히 09장과 11장은 고칠 자리까지만 알려 준다.

  • w1소개 글: 네 절, 각주 4개, 차트 4개의 점, 고객 인용 13개를 모두 읽었다
  • d1migration guide: Sonnet 5 절과 체크리스트, 공통 절을 읽었고 4.6 이하 절은 대조용으로만 봤다
  • d2thinking 문서: effort 표, 캐시, cost control, 가격 절
  • d3effort 문서: Sonnet 5 와 Sonnet 5.5 권장 절, 메시지 단위 effort 절
  • d4What's new: breaking changes, feature support, 거부 절
  • 안 봄prompting guide, refusals-and-fallback, preserved thinking, thinking 개요, mid-conversation system messages, compaction, advisor, computer use, strict tool use 문서와 System Card

API 에 요청을 보내 보지는 않았다. 05장의 400 과 200 은 guide 가 적은 조건을 따라간 것이다.

첨언

요청받은 migration guide 주소는 모델별 가이드를 잇는 목차 페이지였고 거기서 링크된 models/sonnet-5-5/migration-guide 를 읽었다. adaptive-thinking 주소는 thinking-steering-and-cost 로 리다이렉트되었다. 각 출처의 sha256 은 17장과 sources.jsonl 에 있다.

차트 점 80개는 소개 글 HTML 의 SVG aria-label 에서 옮겼다. 같은 다섯 출처로 쓴 앞 판은 2026-09-29 문서 다.

열지 않은 하위 문서가 guide 와 다른 조건을 적고 있다면 이 문서는 그것을 반영하지 못한다.

critique

근거가 전부 Anthropic 자료라서 400 조건은 그대로 쓸 수 있지만, 비용 비교는 벤더 차트 한 벌에 기댄다

에러 조건은 문서대로 고치면 된다. 비용과 품질은 차트를 출발점으로만 쓰고 자기 eval 로 다시 잰다.

  • 원문FrontierCode 의 max 역전은 Claude Code 의 code-review skill 탓이라고 각주 2 가 밝힌다
  • 원문GDPval-AA 와 AA-Briefcase 는 structured outputs 버그가 있던 배포에서 쟀다고 각주 3 이 밝히고, 영향은 작으며 점수를 낮춰 잡는 쪽이라고 본다
  • 원문복잡하고 열린 작업은 여전히 Opus 5.5 가 낫다고 소개 글이 스스로 적는다
  • 이 문서그 skill 을 쓰지 않는 API 호출에서도 max 가 xhigh 보다 낮을지는 알 수 없다
  • 이 문서고객 인용의 수치는 각 회사 자체 eval 이라 다시 잴 수 없다
  • 남는 것400 조건은 guide 가 조건과 대안을 문장으로 적고 있어 체크리스트로 바로 쓸 수 있다. advisor 목록은 What's new 보다 guide 쪽이 넓다
첨언

각주 2: “At Max effort, Sonnet 5.5 more often ran Claude Code’s code-review skill, which splits the review across many subagents, and in two cases Cognition examined, this led to a timeout or to extra edits beyond the task’s scope, and therefore to a lower score.”

각주 3 은 영향이 “if any, to be small and to understate its performance” 라고 보고 버그는 이후 고쳤다고 적는다. 버그의 크기를 잰 수치는 없다.

Sonnet 5 의 지원 종료 날짜처럼 옮길 시점을 정하는 자료는 이 corpus 에 없다.

conclusion

옮기는 순서는 400 을 내는 다섯 곳, 조용히 바뀌는 두 곳, effort 재측정이다

먼저 요청이 통과하게 만들고, 화면과 거부 처리를 확인한 다음 비용 기준선을 새로 잡는다. 아래 표의 왼쪽 열을 코드에서 검색하면 고칠 줄이 나온다.
