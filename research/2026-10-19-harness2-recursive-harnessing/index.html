Harness²의 recursive harnessing이 모델을 고정한 채 agent 성능을 올리는 방식과 입증된 범위

Harness²는 모델 가중치를 그대로 두고 agent가 읽는 지침, skill, script 같은 하네스 파일을 작업마다 고쳐 쓴다. 정답을 모르니 고친 하네스로 같은 작업을 다시 돌려 보고, 실행 기록이 어떻게 달라졌는지를 근거로 편집을 고른다. 그래서 마지막 실행은 앞선 실행이 시행착오로 알아낸 것과 앞 작업들이 쌓은 library를 들고 시작하며, 가중치 대신 같은 작업에 더 쓴 실행이 점수를 올린다. 논문의 12개 설정 모두에서 벤치마크 지시문만 든 기본 하네스보다 점수가 올랐다. 다만 작업 하나에 토큰을 6~8배 쓰고, executor 실행 횟수를 맞춘 best-of-4와의 차이는 1점 안팎이다.

tl-dr

기억할 것

점수가 오르는 까닭은 같은 작업을 여러 번 돌린 실행 기록을 마지막 실행의 지침으로 바꿔 넣는 데 있다. 그래서 효과는 같은 작업을 안전하게 다시 돌릴 수 있을 때 가장 크고, 비용은 실행 횟수에 비례해 늘어난다.

  • →한 단계는 기준 실행 한 번, 성격이 다른 수정안 두 개의 시험 실행, 둘을 합친 하네스의 실행 한 번으로 이뤄진다. k=1에서 executor 실행 4번과 편집 세션 3번이 든다. (04, 06)
  • →정답 대신 쓰는 근거는 같은 조건에서 돌린 실행끼리의 차이다. editor 프롬프트는 기준 실행이 알아낸 작업 공간의 사실을 절차가 아닌 사실 그대로 하네스에 적으라고 지시한다. (05)
  • →작업이 끝나면 채택된 하네스 전체와 실행 대비가 뒷받침하는 교훈 하나를 domain별 library에 넣는다. 다음 작업은 빈 하네스에서 다시 시작하되 그 library를 예시로 읽는다. (07)
  • →다시 돌릴 수 없는 작업에는 Probe가 성립하지 않는다. library 없이 실행 없이 하네스를 고치게 하면 Code와 Web에서 기본보다 떨어졌지만, k=5로 쌓은 library를 주면 실행 없이도 기본보다 0.9~5.1 올랐다. (09)
  • →실측된 것은 벤치마크 지시문과 placeholder만 든 기본 하네스 대비 상승이다. k=1에서 12개 설정 모두 1.2~11.8 올랐고, k=5에서 2.6~6.7이 더 올랐다. (10, 12)
  • →비교 기법 대비 우위는 약하다. 12개 중 8개 설정에서 가장 강한 비교 기법과의 차이가 표준편차보다 작고, executor 실행 횟수를 맞추면 best-of-4와 k=1의 차이가 1점 안팎이다. (10, 12)
  • →DSPy, GEPA, ADAS, Reflexion은 논문 실험에서 돌리지 않았다. 직접 비교된 것은 ReasoningBank, Meta-Harness, Harness Scaling, best-of-k다. (13)
  • →개선하는 방법까지 나아진다는 RSI(recursive self-improvement) 주장은 library ablation으로 간접 확인될 뿐이다. 작업이 쌓일수록 개선 폭이 커지는지는 재지 않았다. (14)
  • →공개 코드는 executor의 네트워크를 막지 않으며, 검증 실행에서 Codex가 JobBench 채점 기준을 지시 없이 내려받았다고 docs가 밝힌다. 직접 돌릴 때는 egress부터 막는다. (15)

problem

가중치를 건드리지 않을 때 남는 손잡이

agent의 성능은 모델과 그 주변 하네스가 함께 정한다. 논문은 하네스를 파일 8개로 나누고, 정답이 없는 새 작업이 줄지어 들어오는 상황에서 이 파일들을 자동으로 고치는 문제를 푼다.

모델을 바꿀 수 없을 때 개발자가 손댈 수 있는 곳은 모델이 받는 지침, 부를 수 있는 tool, 실행 흐름을 감싼 코드다. Harness²는 이 층을 executor가 실행 중에 읽는 파일 8개로 정의하고, 편집은 이 파일들의 diff로 다룬다. Codex에서는 항상 켜진 지침이 AGENTS.md 한 파일에 들어가고, 나머지 부품은 같다.

실험의 출발점인 기본 하네스는 거의 비어 있다. 항상 켜진 파일에는 벤치마크 지시문만 있고, 나머지 디렉터리에는 그 부품이 있다는 것만 알리는 placeholder가 들어 있다. 그래서 논문의 "기본 하네스 대비 상승"은 잘 다듬은 하네스가 아니라 stock OpenCode와 Codex 위에 쌓은 결과다.

논문이 기존 방법에서 짚는 공백은 두 가지 조건이 겹친 곳이다. Meta-Harness나 AHE처럼 학습용 과제와 검증 점수로 하네스를 미리 고르는 offline 방법은 배포 중에 처음 나온 요구를 반영하지 못한다. 작업마다 하네스를 고치는 online 방법은 정답이나 채점기 없이 무엇을 근거로 고칠지가 불안정하고, 한 작업에서 고친 것이 다음 작업의 개선 방식으로 이어지지 않는다.

mechanism-step

수정안을 실행해 보고 합치는 한 단계

한 단계는 기준 실행을 읽고 수정안 두 개를 만들어 같은 작업에 각각 돌려 본 뒤, 실행 기록의 차이가 뒷받침하는 편집만 골라 합친다. 점수와 채점 기준은 어느 세션에도 들어가지 않는다.

기준 실행은 지금 하네스가 어떻게 움직이는지를 보여 줄 뿐, 결과물이 맞았는지는 알려 주지 않는다. 이 기록을 읽은 editor 세션 두 개가 서로 다른 몫을 맡아 수정안을 만든다. invariant 수정안은 계획, tool 사용, context 관리, 위임처럼 어느 domain에서나 반복될 결함을 고치고, domain 수정안은 이 domain의 지식, 절차, 제약을 채운다. 두 수정안 모두 하네스 파일을 직접 고친 실행 가능한 tree다.

Probe는 두 수정안을 같은 작업, 같은 모델, 같은 환경에서 한 번씩 돌린다. 기준 실행과 비교한 trajectory와 결과물의 차이를 논문은 behavioral contrast라 부르고, 이것이 정답 대신 쓰이는 근거다. 논문은 이 대비를 정답 검증에 쓰지 않고 합치기 판단의 재료로만 쓴다고 적는다. 실행마다 결과가 흔들리고 후보끼리 같은 모델의 편향을 공유하기 때문이다.

Compose 세션은 기준 실행, 두 후보, 현재 하네스 대비 diff, 실행 기록을 모두 읽고 하네스 하나를 낸다. 편집을 합치거나, 충돌하는 편집을 고치거나, 후보 하나를 통째로 채택하거나, 현재 하네스를 그대로 둘 수 있다. 결정마다 trajectory의 어느 순간이 그 결정을 뒷받침했는지 한 줄씩 적어야 한다. 그렇게 만든 하네스로 작업을 한 번 더 돌린 결과가 k=1의 제출물이다.

정답이 새지 않게 하는 장치는 코드에 있다. context.py 는 채점기 출력의 흔적이 든 파일이 세션 작업 디렉터리에 들어오면 실행을 멈추고, 모든 프롬프트는 rubric, 점수, 채점기가 context 안에 없다고 적는다.

mechanism-why

같은 작업을 다시 돌리면 점수가 오르는 까닭

기준 실행이 시행착오로 알아낸 것을 하네스에 적어 두고 같은 작업을 다시 돌리므로, 마지막 실행은 첫 실행보다 많이 아는 상태에서 시작한다. 기준 실행이 하나뿐인 k=1의 Propose는 그 실행에서 보인 실패와 위험, 그리고 library를 근거로 편집을 고르고, 실행끼리 갈린 행동을 지침으로 고정하는 편집은 기준 실행이 여럿인 k≥2에서 가장 먼저 고려된다.

가중치를 그대로 둔 채 점수가 오르는 첫 번째 경로는 작업 공간의 사실이다. editor 프롬프트는 기준 실행이 비용을 치르고 알아낸 사실, 예컨대 두 파일의 key column이 어떻게 이어지는지, 어떤 항목은 짝이 없는지, 어떤 필드의 단위가 무엇인지를 다시 찾는 절차가 아니라 사실 그대로 하네스에 적으라고 지시한다. 그러면 마지막 실행은 가장 어려운 단계를 건너뛰고 시작한다. 같은 작업에 계산을 더 써서 그 결과를 context로 넘기는 셈이라, 이 몫의 상승은 test-time compute에서 나온다고 보는 편이 정확하다.

두 번째 경로는 편집 대상을 고르는 순서다. 프롬프트는 편집마다 trajectory의 특정 순간을 대라고 요구하고, 그 순간의 종류에 우선순위를 둔다.

  1. 실행끼리 결과가 갈린 곳. agent가 이미 할 수 있으니 알려 주기만 하면 된다.
  2. 모든 실행에서 반복된 구체적 실패.
  3. trajectory에 보였지만 아직 터지지 않은 위험.

k=1에서는 기준 실행이 한 번뿐이라 Propose 단계에 1순위의 대상이 없다. editor는 그 한 실행의 실패와 위험, 그리고 library에 쌓인 앞 작업의 하네스를 근거로 편집을 고른다. 실행끼리의 대비가 처음 생기는 곳은 Compose다. Compose는 기준 실행과 두 시험 실행을 나란히 읽고 어느 편집이 행동을 바꿨는지 가린다.

세 번째 경로는 지시를 강제로 바꾸는 부품이다. 반복되는 추출과 검사는 script로, 좁은 절차는 필요할 때만 불러오는 skill로, 글로 써도 무시되는 규칙은 tool loop 안의 plugin으로 옮기게 한다. k=5로 다듬은 하네스에서 부품 묶음을 하나씩 빼 보면 skill을 뺄 때 WorkBuddy 평균이 80.8에서 75.5로 가장 크게 떨어지고, script는 77.1, prompt 묶음은 79.3이 된다(Gemini 3.5 Flash, OpenCode).

  • WorkBuddytool 오류율 0.8% → 0.5%, 호출 수 20.0 → 17.8
  • JobBenchtool 오류율 14.4% → 9.1%, 호출 수 27.4 → 32.8
  • LABtool 오류율 2.0% → 1.6%, 호출 수 20.8 → 25.2

위 수치는 k=1 한 단계 전후의 tool 사용이다(Gemini 3.5 Flash, OpenCode). JobBench와 LAB에서는 호출이 늘면서 오류가 줄었으니, 실행을 짧게 줄여서 오른 점수는 아니다. 이 세 경로에서 예측을 하나 끌어낼 수 있다. 기준 실행이 절차 단계에서 실패하는 작업일수록 상승 폭이 크고, 모든 실행이 같은 지식을 모르는 작업에서는 대비가 드러낼 것이 없다는 것이다. 이것은 이 문서의 추론이고, 논문은 실패 유형별 상승 폭을 재지 않았다. 직접 써 볼 작업이 어느 쪽인지 가늠할 때 가설로만 쓴다.

recursion

예산 k를 넓이로 쓸지 깊이로 쓸지

parallel은 기준 실행 k번과 후보 2k개를 한꺼번에 만들고 composer k개가 각자 최종 하네스를 낸다. sequential은 단계를 k번 이어 붙인다. 어느 쪽이든 executor 실행 4k번과 편집 세션 3k번이 들고, k가 2 이상이면 selector가 결과물 하나를 고른다.

설정executor 실행편집 세션그 밖의 세션
k=14 (기준 1, 후보 2, 최종 1)3 (INV, DOM, Compose)reflect 1
k=5 parallel20 (기준 5, 후보 10, 최종 5)15 (INV 5, DOM 5, Compose 5)selector 1, reflect 1
k=5 sequential20 (기준 5, 단계마다 후보 2와 checkpoint 1)15 (단계마다 INV, DOM, Compose)selector 1, reflect 1

parallel에서는 composer k개가 같은 후보 2k개와 기준 실행 k개를 모두 받되 서로의 결과를 보지 못한다. 프롬프트는 합의된 답을 노리지 말고 스스로 변호할 수 있는 하네스를 내라고 시킨다. 논문은 이 구현이 개체군을 한 번만 갱신하므로 k가 깊이가 아닌 넓이를 정한다고 적는다. sequential은 앞 단계의 하네스와 누적된 실행 기록을 다음 단계에 넘기고, 뒤 단계가 앞 단계의 편집을 되돌리거나 버렸던 후보를 다시 살릴 수 있다.

논문은 두 방식을 WB Code와 Office에서 직접 비교했다. 둘 다 k가 1에서 5로 커지는 동안 꾸준히 오르고, k=5에서는 parallel이 sequential보다 높게 끝난다. sequential이 앞선 곳은 k=2의 Code 하나다. 그래서 이 두 domain의 k=5 예산에서는 넓이 쪽이 나았고, 10장과 12장의 k=5 결과도 모두 parallel이다. parallel은 편집 세션을 동시에 돌릴 수 있다는 점도 다르다.

k가 2 이상이면 최종 하네스가 여러 개 생기므로, selector가 어떤 하네스에서 나왔는지 모르는 결과물들을 요청문과 원자료에 대 보고 하나를 고른다. 저장소의 선택 후보에는 기준 실행이 빠져 있다. 그래서 제출물은 언제나 Compose를 거친 하네스의 실행 결과다. Compose가 KEEP_BASE를 골랐다면 기본 하네스를 다시 돌린 결과가 된다.

selector는 정답을 모르는 모델이라 틀린다. 논문의 실패 사례에는 WB-code에서 95점짜리를 두고 55점짜리 결과물을 고른 경우와, LAB에서 범위가 좁은 결과물을 골라 54점이 26점이 된 경우가 있다.

mechanism-library

작업 사이에 남는 improvement harness

작업이 끝나면 reflector가 모든 후보의 편집을 helped, hurt, no observed effect, confounded로 판정하고, 실행 대비가 뒷받침할 때만 교훈 하나와 채택된 하네스 전체를 library에 넣는다. 다음 작업은 빈 하네스에서 다시 시작해 그 library를 예시로 읽는다.

제목의 recursive harnessing은 재귀가 두 층이라는 뜻이다. 작업 하나 안에서 하네스를 고쳐 같은 작업을 다시 돌리는 것이 task-level recursion(04~06장)이고, 작업 사이에서 고치는 방법 쪽을 갱신하는 것이 harnessing-level recursion이다. 논문은 고쳐지는 쪽을 execution harness, 고치는 쪽을 improvement harness라 부른다. improvement harness는 고정된 단계별 프롬프트와 결정 규칙, 그리고 작업이 끝날 때마다 자라는 library로 이뤄진다.

harnessing-level recursion은 실행 하네스를 물려주는 장치가 아니다. 다음 작업의 executor는 매번 같은 기본 하네스에서 출발하고, 바뀌는 것은 editor와 composer가 참고하는 library뿐이다. 앞 작업에 지나치게 맞춘 하네스를 그대로 물려받으면 작업 분포가 바뀔 때 잡음이 쌓인다는 것이 이렇게 설계한 이유다.

  • 무엇을채택된 하네스 tree 전체와 EXPERIENCE.md. 채택 이유, 편집별 판정, 적용할 상황(cue), 교훈, 근거, 확신도를 담는다
  • 언제교훈이 실행 대비로 뒷받침될 때만. 교훈이 없으면 하네스도 저장하지 않는다
  • 어디에벤치마크 domain마다 따로 둔 디렉터리. domain 안의 작업은 순서대로 돌고 앞 작업의 항목만 읽는다
  • 고정모델 가중치, 단계별 프롬프트, 결정 규칙
  • 출발벤치마크 stream마다 빈 library

reflector 프롬프트는 채택 사실을 근거로 삼지 말라고 한다. selector는 하네스를 가린 채 결과물만 비교했으니, 채택은 어떤 결과물이 나아 보였는지를 말할 뿐 어떤 편집이 효과가 있었는지를 말하지 않는다. 그래서 여러 부품을 한꺼번에 바꿨거나 실행 하나만 뒷받침하는 편집은 confounded로 적게 하고, confounded 판정에만 기대는 교훈은 쓰지 말라고 한다.

library가 실제로 쓰인 정도도 논문에 있다. 고쳐진 파일 가운데 library 항목에서 온 줄이 있는 비율은 LAB와 WB-office에서 22%, JobBench에서 47%이고, 줄의 절반 이상을 그대로 가져온 파일은 2~10%다. 통째로 복사하기보다 고쳐 쓰는 쪽이 흔하다는 뜻이다.

critique

숫자를 읽을 때 걸리는 것

테스트 과제가 25~100개이고 세 번만 반복해 1~3점 차이는 잡음과 구별되지 않는다. editor와 selector로 쓴 Claude Opus 4.8이 JobBench의 채점 모델이기도 하고, 공개 코드는 executor의 네트워크를 막지 않는다.

논문이 스스로 밝힌 한계부터 적는다. 저자들은 재귀적 개선에 실행과 editor 세션이 더 들고, k를 늘리면 비용이 는다고 적었다. 정답 없이 쓰는 대비와 모델 판단이 실행의 흔들림과 공유된 모델 편향에 약하고, 채택된 편집이 다른 작업으로 옮겨 간다는 보장이 없다는 것도 명시했다. leave-one-out이 사후 분석이라는 점과 실패 사례 아홉 개도 저자들이 공개했다.

아래는 논문이 다루지 않은 유보다.

  • ·출발점. 기본 하네스는 벤치마크 지시문과 placeholder만 든 거의 빈 하네스다(03장). AGENTS.md 나 skill을 이미 다듬어 쓰는 하네스에서 1.2~11.8만큼 오를지는 논문이 재지 않았고, 손으로 다듬은 지침과의 비교도 없다. 자기 하네스에 붙여 볼 때는 지금 쓰는 하네스를 기준점으로 놓고 상승 폭을 다시 재야 한다.
  • ·표본 크기. 테스트 과제는 WorkBuddy 40, 35, 25개, JobBench 34개, LAB 100개이고 각 설정을 세 번 돌렸다. 유의성 검정이 없고, k=5 행과 ablation 표에는 표준편차도 없다. 비교 기법과의 1~3점 차이를 순위로 읽으면 안 된다.
  • ·채점 모델과 개선 모델의 겹침. editor와 selector가 Claude Opus 4.8이고 JobBench 결과물도 Claude Opus 4.8이 rubric으로 채점한다. WorkBuddy의 LLM 채점 항목은 Gemini 3.5 Flash가 맡는데, 절반 설정에서는 executor와 같은 모델이다. 같은 모델이 좋다고 보는 결과물을 고르고 같은 모델이 채점하면, 점수에는 품질과 함께 취향의 일치가 섞일 수 있다. LAB은 Claude Sonnet 4.6이 채점한다.
  • ·채점 기준 노출. 저장소 docs는 세 벤치마크가 모두 공개되어 있고 JobBench가 과제마다 RUBRICS.json 을 Hugging Face에 올려 두며, 검증 실행에서 Codex가 지시 없이 그 rubric을 내려받았다고 적는다. 공개 코드는 네트워크를 막지 않는다. 논문은 실험에서 네트워크를 막았는지 적지 않았으므로, 재현할 때는 docs가 권하는 대로 egress를 막고 그 설정을 결과와 함께 적어야 한다.
  • ·비교 기법의 구현. ReasoningBank, Harness Scaling, Meta-Harness는 저자들이 같은 부품 구조에 맞춰 다시 구현했다. 원 논문의 설정과 다를 수 있다.
  • ·범위. executor는 Gemini 3.5 Flash와 GLM-5, 하네스는 OpenCode와 Codex, 결과물은 모두 container 안의 파일이다. 대화형 작업, 부작용이 있는 작업, 긴 세션은 실험에 없다.
  • ·비용 단위. 비용은 토큰으로만, 그것도 그림으로만 보고되었다. 위 배수는 그림 좌표에서 계산한 근사값이고, Opus 4.8 세션과 executor 실행의 단가 차이를 반영하지 않는다.
  • ·공개 코드의 기본값. 공개 코드는 editor 모델을 따로 정하지 않으면 executor와 같은 모델을 쓴다. 논문의 Opus 4.8 editor 설정을 재현하려면 HARNESS2_IMPROVER_MODEL 을 직접 지정해야 한다.
  • ·외부 재현. 논문은 2026년 10월에 올라왔고(arXiv 번호 2610), 저자 밖에서 재현한 결과는 찾지 않았다.
