OpsHarness: 자가진화 제안을 이중 게이트로만 들여보내는 RCA 외부 하네스

arXiv:2608.25661v1 (2026-08-26, cs.SE / cs.AI). CUHK 와 ByteDance 공저. 범용 코딩 에이전트(Codex, Claude Code, Open Code)를 그대로 두고 그 바깥에 RCA 전용 지식과 도구를 얹은 뒤, 진단 트라젝토리에서 캔 제안을 inner/outer 두 게이트에 통과시켜야만 하네스에 반영한다.

검증 게이트를 뗀 자가진화가 왜 역효과인가. 논문의 no-verify ablation 이 실제로 보여주는 곡선은 무엇이고, 59.0% / +63.4% / 4.02배가 각각 어떤 분모 위의 값인가. 그리고 도메인 전용 에이전트를 새로 설계하려는 팀이 왜 범용 에이전트 + 외부 하네스를 먼저 기준선으로 잡아야 하는가.

읽는 순서

③ 이 무엇이 모자랐는지, ④ 가 전용 에이전트와의 비교, ⑤~⑦ 이 구조와 게이트 수식이다. ⑪ 이 이 문서의 중심인 ablation 이고, 숫자의 분모만 필요하면 ⑩ 과 ⑫ 로 바로 가도 된다. ⑮ 는 이 논문이 검증 가능한 범위를 정리한다.

피어리뷰 없음. 이 글을 쓴 시점에서 공개 이틀 된 프리프린트다. 심사를 거치지 않았고, 저자 소속인 ByteDance 의 사내 데이터가 실험의 한 축이다. 코드·데이터·아티팩트는 공개되어 있지 않다(⑮).

tl-dr

요약. 게이트를 뗀 자가진화는 12번째 window 에서 진화를 끈 하네스 아래로 내려간다

no-verify 변형의 마지막 window A@1 은 백본 4개 평균 0.33 으로, 진화를 아예 끈 no-evolve 의 0.43 보다 낮다. 자가진화를 표방하는 시스템은 많지만 진화가 검증 없이는 성능을 떨어뜨린다는 것을 ablation 으로 보인 것이 이 논문의 실제 기여다.

  • 2모자란 것은 추론력이 아니라 시스템별 진단 지식이다. 절대 변화폭이 가장 큰 노이즈 카운터를 원인으로 집고, baseline 이 0 근처라 상대적으로 작게 움직인 진짜 원인을 놓치는 실패가 근거다(③).

  • 4표 II 의 no-evolve 열은 본문 수치와 어긋난다. 본문이 네 곳에서 41.4% 라 쓴 값이 표의 네 백본 열(52.8 / 37.8 / 51.2 / 31.6)에서는 43.35% 로 나온다(⑩).

이 요약은 두 공개 벤치마크(OpenRCA, RCAEval) 결과에 한정한다. 사내 데이터셋 Company A 의 0.74 대 0.24 는 데이터가 공개되지 않아 다른 성격의 수치이고 ⑭ 에서 따로 다룬다.

problem

문제 정의. 범용 에이전트가 놓치는 것은 추론 단계가 아니라 이 시스템의 노이즈 프로필이다

Codex 를 GPT-5.5 에 그대로 붙이면 두 벤치마크 Overall 51.2% 로 최고 구성이 되지만 거기서 멈춘다. 논문은 실패 케이스를 뜯어 그 천장이 모델 능력이 아니라 대상 시스템에 대한 무지에서 온다고 본다. 유능하지만 팀의 관행을 모르는 신입 엔지니어에 비유한다.

여기서 갈리는 판단은 추론의 길이나 도구 사용 능력과 무관하다. 0 근처 baseline 에서 벗어난 값이 이미 출렁이던 값의 진폭보다 무겁다는 것은 이 시스템을 겪어 본 사람이 아는 규칙이다. 논문은 이런 규칙을 하네스가 공급해야 할 것으로 두고, 모델이나 에이전트의 일반 능력이 감당할 문제가 아니라고 쓴다.

이 인과 귀속은 논문의 주장이다. 실패 케이스 표본의 크기, 선정 기준, 라벨링 절차는 논문에 없고, 이 케이스 하나가 근거로 제시된 전부다.

baseline

비교. RCA 전용 에이전트는 이미 진 기준선이고, 그 패배는 일반화 실패에서 온다

표 I 은 백본 4개 × 프레임워크 3개다. Overall 열에서는 범용 에이전트가 4개 백본 모두 이긴다. 하지만 열을 갈라 보면 OpenRCA 단독에서는 RCA-Agent 가 4개 중 2개 백본에서 앞서고, 격차는 RCA-Agent 가 설계 대상으로 삼지 않은 RCAEval 에서만 벌어진다.

표 I(논문), top-1 accuracy %. 파란 행이 범용 에이전트다. RCA-Agent 의 OpenRCA 칸에 붙인 색은 같은 백본의 범용 에이전트와 비교한 승패다.

논문 자신이 기전을 명시한다. "The gap is widest on RCAEval, where the specialized RCA-Agent, designed for OpenRCA, fails to generalize and drop to 5.1%, while the general agent holds at 38.0%." 즉 Overall 열의 완승은 전용 에이전트가 자기 벤치마크 밖에서 무너지는 것을 평균에 섞은 결과다. 자기 벤치마크 안에서는 GPT-5.5 에서 31.8 대 44.9 로 지지만 Claude Sonnet 4.6 에서 26.4 대 25.9, DeepSeek-V4 에서 28.0 대 20.2 로 이긴다.

실무로 옮기면 결론의 방향은 그대로다. 도메인 전용 에이전트를 새로 설계할 계획이라면 범용 에이전트 + 외부 하네스를 먼저 기준선으로 잡아야 한다. 전용 설계가 우위를 보이는 구간이 자기가 맞춘 한 벤치마크 안으로 제한된다면, 그 우위는 이식되지 않는 종류의 우위다.

표 I 의 값은 각 백본에 두 프레임워크를 붙여 잰 것이고, 프레임워크와 백본이 완전히 교차되지는 않는다. Claude Sonnet 4.6 만 Claude Code 에 붙고 나머지 셋은 Codex 에 붙는다(논문 §VI-A). 따라서 Claude Sonnet 4.6 행의 낮은 수치에서 모델 몫과 에이전트 몫을 가를 수 없다.

method-state

구조 1. 하네스가 가진 상태는 지식 4층과 아이디어 카드 도구고, 진화가 건드리는 것은 아래 두 층이다

데이터 평면은 h = (K, T) 한 줄로 정의된다. 지식 K 는 4층이고 층마다 공개 정책과 갱신 정책이 다르다. 도구 T 는 스크립트가 아니라 알고리즘 명세 카드라서 에이전트가 진단 시점에 현재 스키마에 맞춰 코드를 새로 쓴다.

도구를 스크립트가 아닌 명세로 두는 이유를 논문이 직접 쓴다. "operational data layouts differ across systems and even across windows, so a once-generated hard-coded script tends to break on a schema it did not anticipate." 이 선택 때문에 도구 106KB 는 실행 코드가 아니라 텍스트 명세의 크기다(⑬).

K₀ 가 실제로 어떤 문장인지, 아이디어 카드의 실제 서식이 무엇인지는 논문의 Fig. 3 에 예시 한 장이 있을 뿐이고 전문은 공개되지 않았다.

method-evolve

구조 2. 자가진화는 3단계고, 세 번째 단계가 앞의 두 단계를 되돌릴 수 있다

트라젝토리 마이닝이 세션을 라벨 붙은 진단 단위로 자르고, 근거 마이닝이 맞은 실행의 공통점과 틀린 실행의 교정 차분을 원자 제안으로 합성하고 단계별 검증이 sandbox 에서 이중 게이트에 통과시킨 것만 승격한다. 실패한 제안은 실패 케이스를 새 negative 로 받아 최대 3라운드까지 재시도한다.

라벨 ℓ(τ) 의 정확도 a 는 진단이 끝난 뒤 사용자가 thumbs-up / thumbs-down 과 실제 root cause 를 입력해 붙는다. 진화 루프는 무감독이 아니고, 사람이 케이스마다 정답을 대 줘야 돈다.

gate

구조 3. inner 게이트는 원본 케이스에서 엄격히 개선하라 하고, outer 게이트는 보류 배치에서 후퇴만 하지 말라 한다

두 게이트의 비대칭이 설계의 요점이다. 안쪽은 강한 조건이고 바깥쪽은 약한 조건인데, 과적합을 잡는 쪽은 약한 바깥쪽이다. 제안이 원본 케이스에 맞춰지는 것은 inner 게이트로는 걸러지지 않기 때문이다.

outer 게이트의 testbed B 는 고정 집합이 아니다

진화 직전마다 누적 케이스를 fault family 와 발생 시각으로 클러스터링해 층화 표본을 새로 뽑는다. 크기는 기본값이 evolve window 와 같다. 논문의 이유: "Resampling ahead of each evolve step keeps B current and disjoint from the mined cases, so a proposal cannot be fit to a static held-out set across iterations." 각 케이스는 정답을 감춘 task prompt 로 저장하고 라이브 하네스가 바뀔 때마다 baseline 을 다시 잰다.

게이트가 실제로 얼마나 막는가

제안의 37% 가 검증 게이트에서 기각된다. 통과한 제안도 평균 1.7회 시도가 필요하다. 재시도 한도는 3라운드고, 그 안에 못 넘으면 폐기하고 stage 환경을 철거한다. 이 세 숫자가 게이트의 작업량을 재는 논문의 전부다. 기각된 제안이 어떤 종류였는지에 대한 분류는 없다.

두 게이트가 모두 같은 방향으로 정확도를 우선한다. costOK 는 비용 폭주를 막는 상한일 뿐이고, 비용만 개선하고 정확도가 그대로인 제안도 inner 게이트를 통과한다(ΔC < 0 절). 즉 이 루프는 정확도와 비용 두 목표의 Pareto 개선만 받아들이는 구조다.

trace

사례 추적. network 가중치를 올리자는 제안은 inner 게이트를 통과하고 outer 게이트에서 걸린다

논문이 no-verify 붕괴를 설명하며 든 실제 제안 하나를 검증 워크플로 안에서 끝까지 따라간 것이다. 이 제안은 자기가 나온 케이스에서는 정확도를 올린다. 게이트가 잡는 자리는 그 뒤다.

이 경로가 보여주는 것은 inner 게이트만으로는 과적합이 걸러지지 않는다는 것이다. 원본 케이스에서 엄격히 개선하라는 강한 조건이 오히려 과적합 제안을 통과시킨다. 과적합의 정의가 원본에서 잘하고 밖에서 못하는 것이기 때문이다. 막는 것은 조건이 약한 outer 게이트고, 그 게이트가 서 있는 근거는 B 가 원본 배치와 겹치지 않고 매 사이클 다시 뽑힌다는 두 성질이다.

논문은 이 제안이 실제로 3라운드 재합성 끝에 어떻게 됐는지는 쓰지 않는다. 게이트가 있는 구성에서 승격 실패로 끝났는지 수정본이 통과했는지는 논문에 없다.

setup

읽은 범위. 본문은 .tex 한 파일이라 전부 열었고, 표 II 의 표본 크기는 벤치마크 원 논문에서 채웠다

코퍼스는 arXiv e-print tarball 이다. 파일 13개이고 본문은 IEEE-conference-template-062824.tex 한 파일 706줄, 주 결과표는 tabs/exp_1.tex 다. HTML 변환본이 아니라 LaTeX 소스에서 표를 읽었기 때문에 셀 병합과 다단 헤더 때문에 값이 어긋날 여지가 없다.

연 것

본문 전 절: Abstract, I Introduction, II Background and Related Work, III Motivation(A·B), IV Design(A~D), V Self-Evolving(A~C), VI Evaluation(setup·RQ1~RQ4), VII Discussion, VIII Threats to Validity, IX Conclusion. 표 I·II·III 전체. 그림 8장 전부. 텍스트 레이어가 있는 7장은 거기서 라벨을 뽑았고, 레이어가 비어 있는 Fig. 1(figs/Intro.pdf, 손그림 teaser)과 마커 위치 자체가 값인 Fig. 5 는 래스터로 렌더해 봤다. 마커는 200dpi 전체 렌더에서 읽었고, GPT-5.5 패널의 초기 window 는 260dpi 로 다시 렌더한 좌상단 700×700 crop 에서 확인했다. ⑪ 에 실은 이미지는 같은 PDF 의 160dpi 렌더다. references.bib 중 정체 확인이 필요한 12개 항목. 부록은 없다.

열지 않은 것과 그 대가

본문이 인용하는 항목은 47개이고 그중 12개만 정체를 확인했으므로 나머지 35건은 따라가지 않았다. 그래서 ④ 의 related work 비교는 이 논문의 프레이밍을 검증한 것이 아니라 표 I 의 수치만 확인한 것이다. microsoft/OpenRCA 와 phamquiluan/RCAEval 은 GitHub API 로 README 와 저장소 메타데이터만 읽고 clone 하지 않았고 벤치마크 데이터도 내려받지 않았다. 따라서 이 문서는 어느 수치도 재실행으로 확인하지 않았다.

렌더 확인. 정적 게이트(check-doc, check-prose)를 통과한 뒤 headless Chrome 으로 슬라이드를 하나씩 열어 읽었다. 그 과정에서 ⑨·⑮·⑯·⑰ 의 표가 가로로 넘쳐 마지막 열이 잘리는 것을 찾아 고쳤다. 확인한 것은 라이트 모드 1400px 폭 한 가지이고, 다크 모드와 좁은 화면은 열어 보지 않았다.

result-main

결과 1. 59.0% 는 백본 4개 × sub-dataset 6개의 이중 평균이고, 그 분해에 쓰인 41.4% 는 표와 맞지 않는다

Final A@1 은 sub-dataset 6개 A@1 의 비가중 평균이고, 헤드라인은 그 값을 백본 4개에서 다시 평균한 것이다. 논문은 그 총 이득 22.9 포인트를 cold-start 5.3 과 자가진화 17.6 으로 가른다. 그 분해의 중간점 41.4% 가 표 II 자신의 no-evolve 열과 어긋난다.

59.0%

Final A@1 을 백본 4개에서 평균한 값. 각 Final A@1 자체가 sub-dataset 6개 A@1 의 비가중 평균이므로 4 × 6 = 24개 값의 이중 평균이다. 케이스 단위로 pooling 한 값이 아니라서 케이스 11개짜리 Telecom 이 케이스 30개짜리 Market 과 같은 무게를 갖는다.

+63.4%

Direct 대비 상대 개선율이다. 59.0 / 36.1 − 1 = 0.6343. 절대 차이는 22.9 포인트다. 분모가 백본 4개 평균 36.1 이라는 점이 중요하다. 최강 구성인 GPT-5.5 만 놓으면 51.2 → 66.0 으로 상대 개선은 +28.9% 로 줄어든다.

4.02배

논문이 분모를 밝히지 않는다. RCA-Agent 17.9 와 mABC 5.6 의 평균 11.75 를 분모로 놓으면 59.0 / 11.75 − 1 = 4.02 로 정확히 맞는다. 즉 4.02배는 비율이 아니라 상대 개선폭이고, 비율로 쓰면 5.02배다. 이 역산은 논문에 없다.

같은 논문이 배(×) 기호를 두 가지 뜻으로 쓴다. abstract 의 4.02× 는 상대 개선폭이고, §VI-E 의 "0.74 A@1 against 0.24 for Direct, roughly a 3× lift" 는 비율이다(0.735 / 0.235 = 3.13). 두 값을 나란히 인용하면 서로 다른 규약을 섞게 된다.

result-cost

결과 3. 케이스당 비용은 Direct 와 동급이지만 진화 1사이클 값을 진단 케이스로 환산하면 22건이다

진단 1건에 106k 토큰 · 325초로 Direct(112k, 317s), ICL(106k, 308s)과 같은 급이다. 전용 에이전트는 토큰 1.7~2.7배, 벽시계 2.3~3.5배다. 그런데 진단 밖 단계인 setup · evolve · verify 는 별도 비용이고, 논문은 이것이 상각된다고만 쓰고 손익분기를 계산하지 않는다.

이 문서가 하는 계산 · 논문에 없음

setup 1회 + 진화 1사이클 = 0.82M + 0.75M + 1.55M = 3.12M 토큰. 진단 1건이 106k 이므로 29.4 케이스분이다. setup 은 데이터셋당 1회뿐이므로 두 번째 사이클부터는 evolve + verify = 2.30M, 즉 21.7 케이스분이 사이클마다 반복된다. 논문이 쓴 상각 주장은 이 손익분기를 넘는 진단 건수를 전제한다.

RQ2 가 실제로 쓴 주기와 대조하면

§VI-C 의 continuous-diagnosis 실험은 window 마다 진화를 1회 돌린다. 두 벤치마크 training split 은 605 × 0.8 ≈ 484 케이스이고 12구간이면 window 당 약 40건이다. window 당 진단 토큰 40 × 106k = 4.24M 에 evolve + verify 2.30M 이 붙는다. 이 주기에서 진단 밖 비용은 진단 비용의 절반가량이지 무시할 수 있는 값이 아니다. (window 당 케이스 수는 논문에 없고 위 나눗셈으로 얻은 값이다.)

진단 밖 비용은 sidecar 로 병렬 실행한다고 논문이 명시하므로 벽시계 지연으로는 진단 경로에 실리지 않는다. 위 계산은 토큰 청구서에 관한 것이고 응답 시간에 관한 것이 아니다. 토큰 단가가 진단과 진화에서 같은지(캐시 적중률, 모델 등급)는 논문에 없다.

result-footprint

결과 4. 시스템별로 학습한 것 전부가 27KB 텍스트다

웜업 후 하네스 온디스크는 228KB 다. 도구 106KB(46.4%), 스킬 라이브러리 95KB(41.5%), 진화 지식 27KB(12.0%). 앞의 둘은 하네스와 함께 배포되는 부분이고, 대상 시스템에 대해 실제로 학습된 것은 마지막 27KB 뿐이다.

27KB 가 뜻하는 것

시스템 전문성이 27KB 텍스트 안에 들어간다. 논문이 이것을 견주는 대상은 "the per-case telemetry" 한 마디뿐이고 어느 벤치마크인지는 쓰지 않는다. 자릿수 감각으로만 붙이면 OpenRCA 의 텔레메트리는 68.5GB 인데 이것은 335 케이스 전체 합계이고 논문이 견주는 per-case 단위가 아니다(원 논문 표 1). 케이스당으로 나누면 약 200MB 이고, 이 나눗셈은 어느 논문에도 없다. 27KB 가 그 벤치마크에서 나온 값인지는 아래 캡션이 적은 대로 논문에 없다. 학습이 모델 가중치가 아니라 텍스트 파일에 쌓이므로 사람이 읽고 지우고 옮길 수 있다. 하네스를 다른 백본에 얹을 때 옮겨야 하는 것도 이 27KB 다.

27KB 가 뜻하지 않는 것

작다는 것이 곧 이식된다는 뜻은 아니다. K₂·K₃ 는 대상 시스템의 컴포넌트 이름과 메트릭 관행에 묶인 규칙이라, 다른 시스템으로 복사하면 §VII 이 말하는 stale knowledge 가 된다. 논문은 시스템이 바뀌면 setup 을 다시 돌려 K₁ 을 재작성하고 진화를 다시 쌓는다고 쓴다.

Precision 의 정의가 "the fraction of correct cases in which it was recalled" 로 되어 있어 통상의 precision 과 서술 순서가 다르다. 어느 쪽으로 읽어도 산출물이 불린 것과 정답이 나온 것 사이의 연관일 뿐 인과가 아니다. 이 산출물을 뺀 대조 실행은 이 표에 없다.

JIT-Agent 열에서 이 문서가 확인한 것은 arXiv id, 제목, 게시일과 초록이 OpenCode·Claude Code 를 성능 비교 대상으로 든다는 것까지다. Pareto 보존 규칙의 형태와 ablation 부재는 원문을 열어 확인하지 않았다.

OpsHarness 의 inner 게이트 accOK ∧ costOK ∧ (ΔA > 0 ∨ ΔC < 0) 는 형태상 Pareto 개선 조건이다. 목표 여럿 중 하나는 엄격히 좋아지고 나머지는 나빠지지 않아야 승격한다. 자가진화 시스템이 이 형태의 규칙에 도달하는 것은 드물지 않다. 드문 것은 그 규칙을 떼고 다시 재는 것이다. no-verify 곡선이 재는 값이 정확히 그것이고, 같은 형태의 보존 규칙을 쓰되 ablation 하지 않은 시스템에는 이 곡선이 대신 답한다.

이 라이브러리의 다른 하네스 문서와도 맞물린다. LoopX 는 루프 제어를 LLM 밖의 결정론적 회계로 빼는 방향이고, OpsHarness 의 게이트도 같은 자리에 있다. 통과 여부를 판정하는 것은 부등식이지 모델이 아니다. deepseek-harness 는 에이전트 루프와 모델 어댑터를 설정 한 행으로 갈아끼우는 합성 구조인데, OpsHarness 는 그 갈아끼움의 대상을 범용 에이전트 전체로 키운 판본이다. 케이스당 106k 토큰이라는 숫자를 감각으로 바꾸려면 Claude Code 세션 비용 모델 쪽이 단가 축을 잡아 준다.

위 세 문서와의 관계는 구조의 유사성이지 계보가 아니다. references.bib 에 deepseekharness26 항목이 실려 있지만 본문 어디에서도 cite 되지 않는다. 본문이 실제로 인용하는 항목은 47개이고, bib 의 86개 중 39개는 한 번도 불리지 않는다.

adopt

도입 판단. 이 논문에서 지금 가져올 수 있는 것은 시스템이 아니라 순서와 규칙이다

OpsHarness 자체는 내려받을 수 없다. 코드도 데이터도 없고 프리프린트뿐이다. 그래서 도입 판단의 대상은 구현물이 아니라 이 논문이 근거를 댄 두 가지 설계 결정이다.

당신의 상황가져갈 것근거의 강도
도메인 전용 에이전트를 새로 설계하려 한다먼저 범용 에이전트(Codex / Claude Code / Open Code) 맨몸을 기준선으로 재라. 그 위에 외부 하네스를 얹는 쪽이 처음부터 짓는 쪽보다 먼저 시도할 순서다표 I·II. 백본 4개 · sub-dataset 6개. 다만 단일 실행이고 벤치마크 2개다
이미 자가진화 루프를 돌리고 있다승격 조건에 분리 보류 집합에서의 비후퇴를 넣어라. 원본 배치에서 엄격히 개선하라는 조건만으로는 과적합이 통과한다⑧ 의 경로와 ⑪ 의 곡선. 이 논문이 실제로 잰 유일한 것
보류 집합을 이미 쓰고 있다매 사이클 다시 뽑아라. 고정 보류 집합은 반복하면 그 자체가 과적합 대상이 된다§V-C 의 설계 근거. 고정 집합 대조군은 논문에 없다
진화 주기를 정하려 한다사이클당 evolve+verify 가 진단 21.7건분 토큰이다. 배치가 그보다 작으면 진화가 진단보다 비싸다⑫ 의 계산. 논문에 없는 계산이고 토큰 단가가 두 경로에서 같다고 가정한다
OpsHarness 를 쓰고 싶다지금은 불가능하다코드·데이터·아티팩트 공개 없음(⑮)

둘째 줄이 이 문서가 남기려는 문장이다. 자가진화를 붙인 시스템에서 승격 조건을 원본 배치 성능으로만 잡으면 그 시스템은 과적합을 통과시키는 구조다. 원본에서 잘하고 밖에서 못하는 것이 과적합의 정의이므로, 원본만 보는 게이트는 정의상 그것을 잡을 수 없다. 이 논문의 no-verify 변형이 그 결과를 12 window 동안 보여준다.

이 판단은 RCA 도메인의 실험 하나에 근거한다. 검증 게이트의 필요성이 다른 도메인에서도 같은 크기로 나타나는지는 이 논문으로 알 수 없다. 다만 게이트가 잡는 실패의 형태(원본에서 개선하고 이웃 fault family 를 망가뜨림)는 도메인에 특정되지 않는다.

conclusion

결론. 이 논문의 기여는 59.0% 가 아니라 0.33 이다

헤드라인 세 숫자는 분모를 알고 나면 크기가 달라진다. 59.0% 는 케이스 pooling 이 아니라 24개 값의 이중 평균이고, +63.4% 는 백본 4개 평균 36.1 대비 상대값이라 최강 구성만 보면 +28.9% 로 줄고, 4.02배는 비율이 아니라 전용 에이전트 두 개의 평균 대비 상대 개선폭이다. 남는 숫자는 ablation 쪽이다.

no-verify, window 120.33진화를 아예 끈 0.43 보다 낮다
게이트가 기각하는 제안37%통과분도 평균 1.7회 시도
시스템별 학습 결과 전부27KB하네스 전체 228KB 중 12.0%

자가진화를 표방하는 시스템이 흔해진 자리에서, 진화가 검증 없이는 이득을 남기지 않는다는 것을 실제로 잰 것이 이 논문의 값이다. 승격 조건을 두 겹으로 나눈 것, 안쪽은 엄격한 개선을 요구하고 바깥쪽은 비후퇴만 요구한 것, 바깥쪽 집합을 매 사이클 다시 뽑은 것, 이 세 가지가 no-verify 곡선이 붙잡는 설계다.

남은 것들은 프리프린트의 조건 그대로다. 심사가 없고, 반복 시행이 없고, sub-dataset 당 test 케이스가 11~30건이고, 산업 데이터는 자사 것이며 공개되지 않았고, 코드가 없다. 표 II 의 no-evolve 열은 본문의 41.4% 와 1.95 포인트 어긋난다. 그럼에도 ablation 의 방향은 이 결함들로 뒤집히지 않는다. 마지막 window 에서 no-verify 가 no-evolve 를 넘는 백본이 넷 중 하나도 없고, full 은 넷 모두에서 둘 위로 올라가기 때문이다.

이 결론이 뒤집히는 조건. no-verify 변형이 게이트 없이도 no-evolve 를 넘기는 재현 실험이 나오거나 표 II 의 값이 반복 시행에서 sub-dataset 당 ±10 포인트대의 분산을 보이면 ⑩ 의 표는 다시 읽어야 한다. 둘 다 원 저자든 제3자든 코드를 공개해야 확인 가능하다.
