tl-dr

요약: 지식은 텍스트 파일에, 학습은 검증된 diff 로

B 의 시스템은 전문가의 교정을 모델 가중치가 아니라 200개 넘는 텍스트 파일의 diff 로 반영한다. 교정 하나는 근본 원인을 지식 쪽과 절차 쪽 중 하나로 귀속하는 진단을 거쳐 최소 편집이 되고, 맥락을 공유하지 않는 리뷰어와 blind replay, 회귀 벤치마크를 통과해야 PR 로 사람 앞에 간다. 수치는 Meta 의 자기 보고뿐이고, 측정된 기준선과 비교한 것은 token 감소 하나이며 표본 수는 어디에도 없다.

  • 구조자주 쓰는 고밀도 지식(입장, 용어, 라우팅, 진입 문턱)은 frontmatter 로 서로를 가리키는 파일에 두고, 가끔 필요한 자료만 RAG 로 찾는다
  • 분리recipe 는 절차만, 지식 파일은 사실만 담는다. 그래서 틀린 답이 나오면 둘 중 어느 쪽을 고칠지 정할 수 있다
  • 루프진단, 컴파일, 평가, 착지. 평가에서 떨어지면 컴파일로 돌아가고, 착지한 교정은 회귀 suite 의 새 시험이 된다
  • 숫자파일 200개 이상, 턴당 token 약 80% 감소(초기 단일 지시 파일 대비), 6주 3 sprint, 회귀 0건, 평가 시간 며칠에서 몇 분. 측정 방법은 하나도 공개되지 않았다

SDLC 렌즈로 보면 B 의 지식 베이스는 playbook 이 CLAUDE.md 와 skills 에 요구하는 규율(버전 관리, 리뷰의 분리, 설정 변경의 회귀 테스트, 사고를 시험으로 남기기)을 지식 자체의 수명주기로 끌어올린 것이다. 갈라지는 곳은 셋이다. 실패 신호가 지표가 아니라 전문가의 말이고, 시험의 판정자가 결정적 테스트가 아니라 LLM 이며, 조직이 입장을 일부러 바꿀 때 지난 교정으로 쌓인 시험을 어떻게 고치는지 B 는 말하지 않는다.

첨언: 확인되지 않은 것

B 는 도메인을 「a specific compliance domain」 이라고만 하고, 개선 사이클이 몇 번 돌았는지, 교정이 몇 건 들어왔는지, 판정 LLM 의 정확도가 얼마인지 밝히지 않는다. 「useful almost all the time」 에는 숫자가 없다. 16장이 숫자마다 빠진 기준을 적는다.

problem

문제: 전문가의 판단은 문서에 없고, chunk 검색은 판단을 매번 다시 만든다

B 가 푸는 문제는 둘이다. 조직의 판단 기준이 몇 사람 머리에만 있어서 같은 질문이 수백 번의 검토에서 반복되고, 문서를 chunk 로 찾아 주는 agent 는 그 판단을 매 실행마다 원자료에서 다시 유도하느라 느리고 결과가 들쭉날쭉하다.

B 가 드는 예는 compliance 다. “the same types of questions can arise across hundreds of product reviews, expert assessments take days of manual research, and inconsistency between assessments creates real organizational risk.” 범용 LLM 은 조직이 무엇을 할 수 있는지는 요약하지만 과거 입장과 사업 방향에 비추어 무엇을 해야 하는지는 가리지 못한다고 B 는 쓴다.

B 의 진단에서 chunk 검색이 실패하는 지점은 반복이다. “An agent that retrieves document chunks at inference time has to re-derive that reasoning from raw sources on every run, which is slow, error-prone, and inconsistent.” 그래서 답은 판단을 미리 꺼내 두는 것이다. 오래 도는 오프라인 과정이 원자료를 읽고 “distills them into structured knowledge files”, 즉 조직이 그 도메인을 어떻게 해석하는지를 기계가 읽을 수 있는 문장으로 증류한다.

이 증류가 B 의 두 번째 문제로 이어진다. 파일이 수백 개가 되고 서로 의존하면, 전문가의 교정 한 건을 정확한 파일 편집으로 옮기는 일이 사람 손으로는 몇 주 걸린다. “This process can take weeks because it requires understanding the full dependency graph, verifying nothing else breaks, and validating the fix actually works.”

첨언: 원문 위치

첫 인용은 B 도입부, 둘째와 셋째는 §Building the Organizational Second Brain, 넷째는 §The Self-Improvement Flywheel 이다. could 와 should 의 구분은 §The Architecture at a Glance: “it will not be able to distinguish between what an organization could do (a summary of general information) and what it should consider doing (based on historic positions, company direction, business context, etc.)”

layers

네 층: 지식, 추론, 평가, 개선

B 의 시스템은 네 층이고 서로 기댄다. 파일 구조가 있어야 자동 편집이 되고, 절차가 명시돼야 실패를 귀속할 수 있고, 평가가 모든 변경을 막아서고, 개선 루프가 다시 지식과 절차를 고친다. B 는 하나를 빼면 나머지도 약해진다고 쓴다.

네 층의 의존은 한 방향이 아니다. 지식 층의 파일 경계와 frontmatter 가 개선 루프의 자동 편집을 가능하게 하고, 추론 층의 절차 분리가 개선 루프의 진단을 가능하게 하며, 평가 층이 개선 루프의 출력을 걸러 낸다. 그래서 이 문서는 네 층을 따로 설명한 뒤 개선 루프에서 다시 모은다.

The evaluation framework gates every change.” 이어서 “Remove any one layer and the others degrade.” 표 그림의 영어 원문 전체는 notes/figures.md 에 있다.

files

파일 분류: position, vocabulary, routing index, gateway

지식 층은 200개 넘는 파일을 네 종류로 나눈다. 조직의 입장(position), 용어집(vocabulary), 입력을 해당 파일로 보내는 색인(routing index), 분석 영역에 들어가기 전의 문턱(gateway)이다. 모든 파일이 frontmatter 에 자기가 기대는 파일과 자기를 쓰는 파일을 적으므로, 한 파일을 고치면 영향받는 파일을 추적할 수 있다.

  • position조직이 그 도메인 질문을 어떻게 해석하기로 했는지, 제약과 경계 조건, 언제 적용하는지를 알려 주는 라우팅 함의까지. 그림에서는 「Supreme authority articles」
  • vocabulary개체 유형, 활동 범주, 분류 등급 같은 조직 용어의 단일 정본. agent 와 조직이 같은 낱말을 쓰게 한다
  • routing index입력의 특징을 해당 position 과 절차에 잇는다. embedding 유사도에만 기대지 않으므로 어떤 파일이 왜 불렸는지 감사할 수 있다
  • gateway분석 영역에 들어가기 전에 통과해야 하는 문턱 시험. 전문 지식이 해당하지 않는 곳에 적용되는 것을 막는다

이 frontmatter 로 독자가 예측할 수 있는 것이 있다. ps-position-1 의 문장을 고치면 영향 범위는 referenced_by 세 파일이고, 그 셋을 쓰는 recipe 단계의 출력이 달라질 수 있다. 반대로 ps-position-5 를 고치면 ps-position-1 이 기대는 전제가 바뀐다. B 가 양방향 그래프를 강조하는 이유도 여기 있다. 자동 편집기가 한 파일만 보고 고치면 의존하는 파일과 모순이 생기는데, 그래프가 있으면 편집기가 검사할 파일 목록을 기계적으로 얻는다. B 가 계보로 대는 Karpathy 의 LLM Wiki 와 Google 의 OKF 도 파일을 링크로 잇지만, 의존과 사용처를 frontmatter 에 양쪽으로 선언하는 필드는 두 자료에 없다.

B 의 설명에서 비는 곳도 이 그림에서 보인다. 「언제 이 파일을 싣는가」 를 정하는 장치가 셋이다. position 자신의 triggers, 입력을 position 에 잇는 routing index, 분석 영역의 문턱인 gateway 다. B 는 position 이 「언제 적용할지」 를 스스로 담는다고도 쓰고 routing index 가 어떤 파일이 적용될지 정한다고도 쓰지만, 둘이 어긋날 때 어느 쪽이 이기는지, gateway 의 문턱 시험을 LLM 이 판정하는지 코드가 판정하는지는 말하지 않는다. 그래서 「이 position 이 불렸어야 했다」 는 교정이 triggers 를 고치는지 routing index 를 고치는지도 B 만으로는 정해지지 않는다(14장).

첨언: 원문

§Building the Organizational Second Brain: “Every file declares its dependencies (depends_on) and consumers (referenced_by) in YAML frontmatter, forming a bidirectional dependency graph.” 그리고 “When one file changes, you can trace exactly what else might be affected, which matters when the self-improvement loop proposes automated edits.” routing index: “Routing indexes map input characteristics to the relevant positions and procedures, determining which files apply without relying on embedding similarity alone. This makes retrieval deterministic and auditable.” gateway: “Gateway files define threshold tests the agent must pass before entering an analytical domain, preventing it from applying specialized knowledge where it does not belong.”

B 가 계보로 대는 두 자료와 비교하면, Karpathy 의 LLM Wiki 는 index.md 와 log.md 두 특수 파일로 탐색하고 “This works surprisingly well at moderate scale (~100 sources, ~hundreds of pages) and avoids the need for embedding-based RAG infrastructure.” 라고 쓴다. Google 의 Open Knowledge Format(OKF) v0.1 은 “OKF requires exactly one thing of every concept: a type field.” OKF 는 개념 사이를 “Concepts link to each other with normal markdown links, turning the directory into a graph of relationships” 로 잇는다. position 의 라우팅 함의: “machine-actionable routing implications that tell the reasoning layer when to apply it.”

density

wiki 와 RAG 의 경계: 정보 밀도와 사용 빈도

B 는 어떤 자료를 큐레이션한 wiki 에 넣고 어떤 자료를 RAG 로 찾을지를 두 축으로 정한다. 밀도가 높고 거의 매 턴 참조되는 증류 지식은 wiki 로 가고, 해당할 때만 깊이 중요한 희소 자료는 semantic 또는 lexical 검색으로 간다. 밀도는 높은데 드물게 쓰이는 자료가 어디로 가는지는 B 에 없다. 이 문서는 빈도 쪽이 경계를 정한다고 읽고, 그래서 도메인이 넓어지면 같은 자료가 반대편으로 옮겨 갈 수 있다고 예측한다.

B 가 RAG 를 남겨 두는 이유는 부피와 주의 분산이다. 희소 자료까지 wiki 에 넣으면 “Loading all of them into the wiki would bloat the system and dilute attention.” wiki 쪽은 조직의 생각이 바뀔 때마다 고쳐야 하므로 버전 관리와 검증이 쉬운 형태여야 하고, RAG 쪽은 원본 그대로 두어도 된다. 개선 루프가 편집한다고 B 가 쓰는 대상도 knowledge 파일과 recipe 이고, RAG 쪽 원자료를 고친다는 말은 없다.

사례: Cerebras 사내 지식 베이스(2026-07-15). 반대편 선택을 한 공개 사례다. Cerebras 는 Slack, 코드, 문서를 “a single Postgres table that holds embeddings, raw summaries, and metadata from many sources” 하나에 넣고 하루 15,000개 넘는 질문에 답한다. 그런데 이 시스템도 밀도 문제를 만난다. “Information density varies enormously: “hey yeah sure mike” and a detailed kernel explanation are both messages.” Cerebras 의 해법은 thread 를 LLM 으로 정규화해 질문 한 줄과 시스템 참조로 증류한 뒤 embedding 하는 것이었다. 증류는 B 와 같은데, 증류 결과를 검색 대상으로 둘 뿐 사람이 고치는 정본으로 두지 않는다.

두 사례로 경계를 예측하면 이렇다. 질문 분포가 좁고 같은 판단 기준이 매번 쓰이는 도메인(한 compliance 영역)에서는 그 기준을 wiki 정본으로 두는 편이 맞다. 질문 분포가 회사 전체로 넓고 답이 시간에 따라 낡는 경우(Cerebras 는 Slack 답이 만료된다고 쓴다)에는 전부를 정본으로 관리할 사람이 없으므로 검색 쪽에 남는다. B 의 시스템을 회사 전체로 넓히면 지금 wiki 에 있는 일부 position 이 「거의 매 턴」 조건을 잃고 RAG 쪽으로 옮겨 가야 한다.

첨언: 원문

B: “High-density, frequently referenced sources go into the wiki: Distilled files capturing how the organization reasons, such as positions, decision frameworks, boundary examples, and strategic interpretations. The agent consults these on nearly every turn.” 그리고 “Sparse, situationally relevant sources are served through semantic or lexical search (RAG): documents that matter deeply when they apply but are not needed in detail on most runs”

Cerebras(c2): “The original transcript is not embedded directly. In our experiments, accuracy increased significantly when the thread was normalized into a consistent format.” 신선도: “encodes that Slack answers expire. Two threads can answer the same question, and the one from six months ago may describe infrastructure that no longer exists.” Cerebras 페이지는 라이브 URL 이 HTTP 500 을 내면서 본문을 응답 payload 에 담아 보냈고, 사본은 그 payload 에서 뽑았다.

recipes

recipe: 아는 것과 추론하는 방법을 다른 파일에 둔다

recipe 는 분석 절차를 적은 명령형 파일이고 도메인 사실을 담지 않는다. knowledge 파일은 입장을 적되 절차를 담지 않는다. 이 규칙 하나로 변경이 한쪽에 갇히고, 틀린 답의 원인을 「지식이 틀렸나, 절차가 틀렸나」 로 물을 수 있게 된다. 같은 구조가 progressive disclosure 를 만들어, 단계마다 그 단계의 지시와 지식만 context 에 실린다.

  • 입장 추가knowledge 파일 하나를 더하고 routing index 를 고친다. recipe 는 그대로다
  • 방법 수정recipe 를 고친다. knowledge 파일은 그대로다
  • 실패 귀속틀린 결과는 두 층 중 하나로 돌릴 수 있다. 10장의 진단이 이 성질에 기댄다
  • 약 80%턴당 token 감소. 비교 대상은 초기판, 즉 단일 평면 지시 파일에 모든 자료를 semantic search 로 싣던 구조다

recipe 는 서로를 부른다. 최상위 routing recipe 가 입력을 보고 하위 recipe 를 고르고, 하위 recipe 하나가 분석의 한 단계를 맡는다. B 는 이 구성을 주방장의 master recipe 가 소스와 가니시의 하위 recipe 에 일을 넘기는 것에 빗댄다. 단계마다 필요한 파일만 싣기 때문에 질의 하나가 건드리는 파일이 적고, 80% 감소는 그 결과다. B 는 같은 구조가 추론 품질도 높인다고 쓰지만 품질 쪽 측정은 내놓지 않는다.

사례: Claude Tag on-call(Anthropic, 2026-08-18). 같은 분리를 반쯤 한 공개 사례다. humans

사람의 자리: checkpoint 와 escalation

사람은 분석 도중 두 곳에서 개입한다. 정해진 checkpoint 에서 agent 가 중간 추론을 보여 주면 전문가가 확인하거나 고치거나 방향을 바꾸고, 입력이 모호하거나 근거가 두 해석을 다 지지하면 agent 가 escalation 으로 결정을 넘긴다. 이 개입 기록이 그대로 개선 루프의 입력이 되므로, 사람의 자리는 품질 관리이면서 학습 신호의 출처다.

  • 품질오류가 다음 단계로 번지기 전에 전문가가 잡는다
  • 신호교정과 escalation 하나하나가 자기 개선 루프의 입력이 된다
  • 신뢰최종 출력만이 아니라 중간 추론과 불확실성 표시를 보면서 전문가가 신뢰를 조금씩 쌓는다

이 설계에서 루프가 배우는 속도는 전문가가 교정하는 속도를 넘지 못한다. 전문가가 checkpoint 를 대충 넘기면 교정이 없고, 교정이 없으면 진단할 것도 없다. B 는 결정의 무게가 클수록 사람을 기본으로 루프 안에 두라고 권하고, 그 예로 compliance, 금융 위험 평가, 보안 검토, 엔지니어링 안전을 든다.

사례: Anthropic 보안팀(2026-07-21). 사람의 gate 가 무엇을 막는지 보여 준 사례다. 모델 업그레이드 뒤 사고 대응 agent 가 스스로 Slack 으로 다른 Claude 인스턴스에 연락해, 코드를 쓸 수 있는 그 agent 에게 수정을 push 하라고 요청했다. 이 요청은 설계대로 사람 리뷰 gate 에서 걸렸다. 보안팀의 결론은 경계를 지시가 아니라 권한과 행동에 그어야 한다는 것이었다. B 는 checkpoint 와 escalation 을 코드로 강제하는지 recipe 의 지시로 두는지 말하지 않는다. 지시로 둔다면 agent 가 지시를 따른다는 전제 위에 서므로, B 의 착지 단계(13장)처럼 PR 승인을 거쳐야 반영되는 곳과 구분해서 봐야 한다.

첨언: 원문

B §Keeping Humans in Control: “Checkpoints are defined points in the analysis where the agent surfaces its intermediate reasoning for expert review before proceeding, and the expert can confirm, correct, or redirect.” “Escalations trigger when the agent hits genuine ambiguity, whether from underspecified inputs or evidence that supports more than one defensible reading.” “Training signal: Every correction and every escalation becomes input for the self-improvement loop.”

Anthropic(c3) §Monitor: “Following a model upgrade, the incident response agent reached out over Slack to another Claude instance on its own initiative. It asked the agent, which could write code, to push the fix.” 결론: “this experience taught us to draw the boundary around access and actions, not around a model’s instructions or what we believe a model can do”

flywheel

자기 개선 루프: 진단, 컴파일, 평가, 착지

B 는 지식 유지보수를 compilation 문제로 다룬다. 전문가 대화에서 나온 교정은 근본 원인으로 진단되고, 최소 편집으로 컴파일되고, 표적 replay 와 회귀 시험을 통과해야 착지한다. 평가에서 떨어지면 컴파일로 돌아가고, 착지한 교정은 회귀 suite 에 새 시험으로 들어가 다음 변경을 막아선다. 모델은 재학습하지 않는다.

순환은 두 개다. 위쪽 귀환선은 한 교정 안에서 도는 재시도이고, 아래쪽 귀환선은 교정과 교정 사이를 잇는다. 둘째 귀환선 때문에 회귀 suite 는 교정이 착지할 때마다 한 칸씩 커지고, 나중 교정일수록 통과해야 할 시험이 많아진다. B 가 「compounding」 이라고 부르는 것이 이 누적이다.

첨언: 원문

§The Self-Improvement Flywheel: “We treat that maintenance as a compilation problem and automate it.” 본문 목록의 넷째: “Have domain experts review them.” 그림 캡션: “Expert corrections are diagnosed to their root cause, compiled into minimal verified edits, and evaluated against replay and regression tests before they are reviewed and landed.” B 가 내세우는 새로움: “Agents that auto-draft their own fixes are increasingly common; but we haven’t seen this level of validation rigor applied to a structured knowledge base without model retraining.”

diagnosis

진단: 교정을 근본 원인 하나로 귀속하는 질문

진단은 질문 하나로 교정을 셋으로 나눈다. 「agent 가 자기 자료로 맞는 결론에 이를 수 있었나」. 자료에 답이 있었는데 틀렸으면 recipe 문제, 자료에 답이 없었으면 지식 공백, 전문가끼리 답이 갈리면 모호함으로 보고 사람의 논의로 넘긴다. 이 질문이 작동하는 것은 07장의 분리 덕분이고, 대화의 형태로 원인을 짐작하던 첫 방식은 실패했다.

입력: 전문가 교정이 담긴 대화 trace
  + knowledge manifest  # 실린 파일 전부, 언제, 어떻게 쓰였나

1. 추출  교정에서 실질 신호를 빠짐없이 뽑는다
2. 귀속  실린 knowledge 파일을 실제로 읽고 묻는다:
         "자료로 맞는 결론에 이를 수 있었나?"
           자료에 답이 있었다, 그런데 틀렸다   → recipe 문제
           자료에 답이 없었다                → 지식 공백
           전문가끼리 답이 갈린다             → 모호함 → 사람 논의 (편집 없음)
3. 가중  빈도와 심각도 (그림에만 있음)
출력: improvement brief

처음 방식은 교정의 말투로 분류했다. 전문가가 정보를 주면 지식 공백, 방향을 틀면 절차 문제라고 본 것이다. B 는 이 방식이 틀린 이유를 이렇게 적는다. 결론을 고치는 전문가는 지식 공백을 드러낼 수도, recipe 결함을 드러낼 수도, 진짜 모호함을 드러낼 수도 있다. 그래서 추출과 분류를 떼고, 분류는 manifest 와 파일 내용을 보고 한다.

사례: SkillOpt 의 Skill-Aware Reflection(Microsoft 연구 블로그, 2026-07-14). 같은 갈래를 단일 skill 파일에서 한 연구다. 실패 궤적을 현재 skill 과 대조해, skill 자체가 틀렸으면(Skill Defect) skill 본문을 고치고, skill 에는 있었는데 agent 가 따르지 않았으면(Execution Lapse) 보호된 부록에 알림을 붙인다. B 의 「자료에 답이 있었나」 질문과 같은 축이다. 다만 SkillOpt 는 사실과 절차를 한 파일에 두므로 「recipe 냐 knowledge 냐」 의 갈래는 없고, 대신 부록이 무한히 커지는 문제를 consolidation 으로 다룬다.

첨언: 원문

B §Diagnosis: “This heuristic failed because conversational form is a poor proxy for root cause.” “First, extract every substantive signal from the expert alongside the agent’s full knowledge manifest (every file loaded, when, and how used).” 질문: “Could the agent have reached the correct conclusion from its source materials?” 세 갈래: “If the materials contained the right answer but the agent still erred: recipe problem.” “If the materials did not contain the right answer: knowledge gap.” “If experts themselves disagree on the right answer: ambiguity, flagged for human discussion.”

SkillOpt(c1) Part II: “that judgment can route a likely Skill Defect toward a targeted skill-body update and an Execution Lapse toward a protected appendix reminder” 부록을 정리하지 않으면 작은 모델에서 크게 떨어진 셀이 있었다. §2.2 는 성공과 실패를 모두 기록하는 같은 부록에 「20개를 넘으면 정리」 하나만 더해 비교하는데, gpt-5.4-mini SpreadsheetBench 에서 정리 없는 설정이 47.14%, 정리한 설정이 62.14% 였다(+15.00%p). 저자는 이 비교가 세 셀뿐이라 일반적으로 안전한 문턱을 정하지 못하며, 반복 seed 실험이 더 필요하다고 적는다.

「자료」 가 실린 파일만을 뜻하는지 지식 베이스 전체를 뜻하는지 B 는 정하지 않는다. 14장의 사례가 이 차이에서 갈린다.

컴파일과 리뷰: 최소 편집, 맥락 없는 리뷰어, 통과 아니면 실패인 linter

컴파일러는 진단된 문제 하나를 최소 파일 편집으로 바꾼다. 편집안은 두 검사를 받는다. 개선 이유를 전혀 모르는 새 context 의 agent 가 diff 만 받아 모순과 깨진 경계 사례를 찾고, 결정적 linter 가 끊긴 참조와 크기 예산 초과, 식별자 충돌, 의존 순환을 잡는다. 앞의 것은 확률적이고 뒤의 것은 아니다.

  • 영향 분석sub-agent 가 병렬로 cross-reference, 기존 입장과의 충돌, token 예산 영향, 시험 범위, 중복 위험을 본다
  • 적대적 리뷰입력은 지식 베이스에 대한 diff 뿐이다. 제안한 agent 와 맥락을 나누지 않으므로 그들의 맹점을 물려받지 않는다
  • linter끊긴 cross-reference, 파일 크기 예산 위반, 식별자 충돌, 의존 순환. 통과 아니면 실패다

리뷰어에게 개선 이유를 주지 않는 것이 이 설계의 핵심이다. 이유를 알면 리뷰어는 「이 교정이 그 문제를 고치는가」 를 보고, 이유를 모르면 「이 diff 가 무엇을 깨는가」 만 본다. 05장의 referenced_by 목록이 여기서 쓰인다. 리뷰어와 sub-agent 가 diff 의 영향 범위를 그래프로 얻으므로, 바뀐 position 을 인용하는 scoring 기준 파일을 빠뜨리지 않는다.

사례: Anthropic 의 PR 리뷰(2026-07-21). 코드 쪽에서 같은 원리를 쓴다. PR 하나에 좁은 주제의 리뷰 agent 여러 개가 붙고, 보안팀은 그 이유로 “They do not share biases and blindspots” 를 첫째로 든다. 또 리뷰 agent 에게 발견이 맞다는 증명을 쓰게 하자 실질 리뷰 의견이 달린 PR 비율이 16% 에서 54% 로 올랐다고 보고한다. B 의 적대적 리뷰어에는 이런 증명 요구가 없고, 리뷰어의 발견이 어떻게 처리되는지(편집안을 막는지, 컴파일러에게 돌려보내는지)도 B 는 쓰지 않는다.

첨언: 원문

B §Compilation: “Sub-agents analyze impact in parallel, examining cross-references, conflicts with existing positions, token budget impact, test coverage, and duplication risk.” “A separate agent, running in a fresh context with no knowledge of the improvement rationale, receives only the proposed diffs to the knowledge base.” “Because it shares no context with the proposing agents, it cannot inherit their blind spots.” linter: “A linter catches issues programmatically, dangling cross-references, file size budget violations, identifier collisions, and dependency cycles. This layer is not probabilistic. It passes or fails.”

Anthropic(c3) §Test (CI): “The share of PRs that get substantive review comments has grown from 16 to 54% as we’ve gained confidence in the findings by requiring the agents to write a proof that their finding is valid.” 두 수치의 기간과 표본 수는 글에 없다.

evaluation

평가: blind replay 와 회귀 벤치마크

평가는 두 단계다. 표적 replay 는 교정을 낳은 원래 시나리오를 agent 에게 다시 돌리되 시험이라는 사실을 알리지 않고, 무엇이 바뀌었는지 모르는 별도 판정자가 새 출력을 원래 교정과 대조한다. 회귀 시험은 그 도메인의 Q&A 벤치마크를 독립 세션으로 병렬 실행해 성능이 떨어진 곳을 찾는다. 어느 쪽이든 떨어지면 컴파일로 돌아간다.

  • replay원 시나리오 재실행. agent 도 판정자도 변경 내용을 모른다. 확증 편향을 막으려는 이중 blind 다
  • 회귀보통 구조화된 Q&A 쌍. 정답이 여럿일 수 있는 분석 도메인에서는 독립 LLM 판정자가 기준에 따라 사례마다 통과, 실패를 매긴다
  • 재시도replay 가 떨어지면 다시 컴파일한다. 회귀가 떨어지면 어디서 떨어졌는지와 원래 문제, 시도한 수정을 prompt 에 담아 다시 컴파일한다

이 사례로 B 의 평가 단계가 무엇을 막는지 예측할 수 있다. 교정 한 건을 반영한 편집이 원 시나리오에서는 맞는데 다른 질문에서 답을 망가뜨리는 경우다. replay 만 있으면 이 편집은 통과하고, 회귀 벤치마크가 있어야 걸린다. 반대로 회귀 벤치마크가 이 편집이 망가뜨린 종류의 질문을 담고 있지 않으면 B 의 gate 도 통과시킨다. gate 의 힘은 suite 가 얼마나 넓은지에 묶여 있다.

첨언: 원문

B §Evaluation: “Targeted replay runs the agent on the original scenario that triggered the feedback. The agent does not know it is being tested.” “A separate judge evaluates the new output against the original expert feedback without knowing what was changed.” “Regression testing runs multiple benchmarks for that domain, which are usually structured test suites of Q&A pairs.” “an independent LLM judge gives each test case a pass/fail based on certain criteria” 재시도: “If regression testing fails, compilation is retried with an updated prompt describing where the agent regressed, along with the original issue and attempted fix.” B 는 벤치마크의 문항 수와 판정자의 기준, 재시도 상한을 밝히지 않는다.

SkillOpt(c1) §3.1: “In a paired study with gpt-5.4-nano on SearchQA, the ungated run adopted a plausible but wrong rule—answer with the document title string verbatim—and fell from 55.4% to 2.6%. The gated run rejected all proposals and remained flat at 57.0%.” 저자 단서: “The two runs started from different measured baselines, so this is not evidence that they encountered identical candidate edits; it is an observed stress-case contrast.” 같은 글 Part I 은 강한 모델에서는 모든 편집을 받아들이는 정책이 평균 진단값이 더 높은 셀도 있었다고 보고하므로, gate 가 언제나 점수를 올린다는 증거로 읽으면 안 된다. 저자는 gate 를 「stability control」 로 부른다.

착지와 보강: PR 을 사람이 승인하고, 실패 사례가 시험이 된다

파이프라인의 출력은 감사 기록이 붙은 PR 이다. 전문가는 날것의 실패를 디버깅하지 않고 검증을 마친 수정을 검토한다. B 는 글 끝의 원리 절에서 개선 하나하나가 전문가가 30초면 검토할 수 있는 텍스트 편집이라고 쓴다. 승인되어 knowledge 파일이나 recipe 가 바뀌면, 원래 실패한 시나리오와 검증된 정답이 자동으로 회귀 suite 에 들어간다.

보강은 루프를 비대칭으로 만든다. 시험은 늘기만 하고 B 는 시험을 빼는 경로를 말하지 않는다. 그래서 교정이 쌓일수록 지식 베이스는 지난 교정 전부를 지키는 방향으로 묶인다. 의도된 효과이고, 15장에서 보듯 조직이 입장을 일부러 바꿀 때 비용이 된다.

사례: Claude Tag on-call 의 lessons.md(2026-08-18). 같은 착지를 사람이 하는 사례다. Claude 가 사건마다 lessons.md 에 원인과 수정, 기억할 함정을 스스로 덧붙이고, 같은 패턴이 「충분히 여러 번」 나오면 팀이 그 패턴을 조사 skill 로 승격한다. lessons.md 는 B 의 회귀 suite 처럼 누적되지만 시험으로 돌지 않고 다음 조사가 먼저 읽는 기록으로 쓰이며, skill 로의 승격에는 replay 나 회귀 같은 자동 gate 가 없다. case

교정 하나를 끝까지: 앱 밖 웹 결제로 파는 구독 기능

B 의 그림에 나온 ps-position-1(「Review Required for High-Risk Features」)을 써서 교정 하나를 루프 끝까지 따라가면, 진단 질문이 「자료」 를 어떻게 읽느냐에 따라 같은 교정이 지식 공백으로도 recipe 문제로도 분류되고 그에 따라 고칠 층이 갈리며, 회귀 시험이 지나치게 넓은 수정을 되돌려 보내는 지점이 보인다. 아래 사례는 B 에 없는 합성 예시다.

대화  제품: 자사 웹 결제 페이지로 월 구독을 파는 새 기능
       (앱 안 결제 아님, 외부 연동 없음, 기기 출시 아님)
       agent 결론: "일반 검토로 충분"
       전문가 교정: "반복 결제는 앱 밖이어도 High-Risk 검토 대상"

1 진단 manifest: ps-position-1 은 실리지 않았다
       ps-position-1 의 triggers 셋 중 어느 것에도 맞지 않고,
       ps-position-routing-index 에도 "반복 결제" → ps-position-1 연결이 없다
       ps-position-1 본문은 반복 결제를 High-Risk 로 친다 (합성)
       질문: "자료로 맞는 결론에 이를 수 있었나?"
         자료 = 실린 파일    → 답 없음 → 지식 공백 → knowledge 층의 싣는 장치를 고친다
         자료 = 지식 베이스  → 답 있음 → recipe 문제 → recipe 에 단계를 더한다
       여기서는 manifest 를 따라 앞의 갈래를 택한다
       싣는 장치가 triggers 인지 routing index 인지 B 는 정하지 않는다 (05장)
       여기서는 routing index 를 고친다

2 컴파일 편집안 A: routing index 에 "결제" → ps-position-1
       영향 범위: 새로 불릴 ps-position-1 의 referenced_by
                  (ra-scoring-criteria, ra-requirement-catalog)
       적대적 리뷰어(diff 만 봄): "결제가 있는 모든 기능이 High-Risk 가 된다"
       linter: 끊긴 참조 없음, 순환 없음 → 통과

3 평가 replay: 원 시나리오 → High-Risk 검토로 감 → 판정자 통과
       회귀: 기존 사례 "웹 결제 일회성 티켓 판매는 일반 검토" → 실패
       → 재시도 prompt: 회귀 위치 + 원 문제 + 편집안 A

2' 컴파일 편집안 B: routing index 에 "반복 결제(구독)" → ps-position-1
3' 평가 replay 통과, 회귀 통과

4 착지 PR(diff 1줄, 감사 기록) → 전문가 승인 → 반영
       회귀 suite 에 이 시나리오와 정답 추가

이 trace 로 독자가 자기 도메인에서 예측할 수 있는 것은 셋이다. 첫째, 입장은 이미 있는데 불리지 않아서 생긴 교정은 position 의 결론을 건드리지 않고 그 position 을 싣는 장치를 고친다. 이런 교정이 전체에서 얼마나 되는지는 B 에 없다. 둘째, 적대적 리뷰어가 지적한 과잉 범위는 리뷰어가 막지 않아도 회귀 시험에서 걸린다. 다만 「일회성 티켓」 사례가 suite 에 이미 있을 때만 걸린다. 셋째, 착지 뒤 suite 에는 「웹 구독은 High-Risk」 와 「일회성 티켓은 일반」 이 함께 들어 있어, 다음 교정이 둘 사이의 경계를 함부로 옮기지 못한다.

예측이 빗나가는 조건도 이 trace 에 있다. 진단 갈래가 「자료」 해석에 따라 바뀌므로, 같은 교정이 운영자에 따라 recipe 쪽 편집(「결제가 있으면 반복 여부부터 확인하라」 는 단계 추가)으로 갈 수도 있다. 갈래마다 고칠 층은 정해지지만, 두 편집은 모두 replay 를 통과할 수 있고 어느 쪽이 나은지는 B 의 gate 가 가리지 않는다. knowledge 쪽을 택해도 triggers 와 routing index 중 어느 것을 고칠지는 운영자가 정해야 한다.

첨언: 이 사례가 원문에 기대는 곳

파일 이름과 frontmatter 는 B 그림의 것이다(05장). ps-position-1 의 triggers 는 third-party integration, in-app purchases, hardware device launch 셋이고, 시나리오는 셋 다에 맞지 않도록 골랐다. 「웹 결제 구독」 시나리오, ps-position-1 본문의 내용, 두 편집안, 회귀 사례는 이 문서가 만든 것이다. 진단 질문의 원문은 “Could the agent have reached the correct conclusion from its source materials?” 이고 manifest 의 정의는 “every file loaded, when, and how used” 다. manifest 가 실린 파일만 담으므로 「자료 = 실린 파일」 로 읽을 근거가 있다. 그림 트리는 routing index 를 knowledge/investigation/ 아래에 두지만, B 본문은 routing index 가 “Routing indexes map input characteristics to the relevant positions and procedures” 라고 써서 절차까지 가리킨다.

limits

원리가 멈추는 곳: 입장 변경, 모호함, 판정자, 규모

루프는 교정이 「지난 판단이 틀렸다」 는 뜻일 때 잘 돈다. 조직이 입장을 일부러 바꾸는 경우, 전문가끼리 답이 갈리는 경우, 판정 LLM 이 틀리는 경우, 파일 수가 한 도메인을 넘어 커지는 경우에는 B 가 설명한 장치만으로는 결과를 예측할 수 없다.

  • 입장 변경규제가 바뀌어 ps-position-1 의 결론을 뒤집으면, 지난 교정으로 쌓인 시험 다수가 옛 정답을 요구한다. 회귀 gate 는 이 의도된 변경을 회귀로 읽고 컴파일로 돌려보낸다. 시험을 고치거나 빼는 경로는 B 에 없다
  • 모호함전문가끼리 답이 갈리면 편집 없이 사람 논의로 간다. 논의 결과가 다시 루프로 들어오는 경로를 B 는 쓰지 않으므로, 가장 어려운 사례에서 루프는 배우지 않는다
  • 판정자replay 와 회귀의 통과는 LLM 판정자가 매긴다. 결정적인 것은 linter 뿐이다. 판정자의 정확도를 잰 결과는 없고, 「회귀 0건」 도 같은 판정자가 센 것이다
  • 규모B 의 지식 베이스는 한 compliance 도메인, 파일 200개 이상이다. Karpathy 가 index 파일만으로 된다고 한 규모(수백 쪽)와 같은 크기이고, 그 위에서 routing index 와 의존 그래프가 어떻게 버티는지는 보고되지 않았다

첫째 항목이 가장 예측하기 쉽다. 시험이 늘기만 하는 suite 에서, 입장 하나를 바꾸는 비용은 그 입장을 건드린 지난 교정의 수에 비례해 커진다. 이 비용을 줄이려면 시험에 「어느 position 의 어느 판에 기댄 정답인가」 를 적어 두고, position 이 바뀌면 그 시험을 사람에게 다시 묻는 장치가 필요하다. B 의 frontmatter 는 파일 사이의 의존은 적지만 시험과 파일 사이의 의존은 적지 않는다.

첨언: 근거와 부재 확인

B 는 입장이 바뀐다는 것을 안다. §The Self-Improvement Flywheel: 지식 베이스를 바르게 유지하는 일이 “as it grows and as expert positions evolve” 어렵다고 쓴다. 그러나 시험 제거나 갱신을 가리키는 낱말은 B 사본에서 0건이다(retire, deprecat, delet, stale, expire, rollback, revert 검색). 「reversible」 은 한 번 나오지만 되돌리는 방법은 없다. 판정자: “an independent LLM judge gives each test case a pass/fail based on certain criteria” Karpathy(w3): “This works surprisingly well at moderate scale (~100 sources, ~hundreds of pages) and avoids the need for embedding-based RAG infrastructure.”

SDLC 렌즈 1: B 의 지식 수명주기가 빌려온 규율

B 의 루프는 playbook 이 코드 옆의 설정 파일(CLAUDE.md, skills, hooks)에 요구하는 규율을 지식 파일 자체에 적용한 것으로 읽힌다. 버전 관리된 산출물, 쓴 쪽과 승인하는 쪽의 분리, 설정 변경의 회귀 시험, 사고를 시험으로 남기기, 확률적 통제 뒤의 결정적 통제다. 두 글 모두 사람을 작성자에서 증거가 붙은 산출물의 검토자로 옮긴다. 이 대응은 이 문서가 만든 것이고, B 는 SDLC 를 언급하지 않는다.

  • 버전 관리B: 모든 변경이 버전 관리되고 diff 로 보이며 되돌릴 수 있다. playbook: 단계마다 산출물을 커밋하고 커밋의 사슬이 감사 기록이다
  • 직무 분리B: 제안한 agent 와 맥락을 나누지 않는 리뷰어, 그리고 사람 전문가의 승인. playbook: 코드를 쓴 agent 는 자기 코드를 승인할 길이 없고, 검증은 새 context 에서 한다
  • 설정 회귀B: 모든 편집이 도메인 벤치마크를 통과해야 한다. playbook: CLAUDE.md, skills, hooks 가 바뀔 때마다 eval suite 를 돌린다. agent 를 움직이는 설정도 코드만큼 회귀 시험을 받아야 하기 때문이다
  • 실패 → 시험B: 착지한 실패 사례가 회귀 suite 에 들어간다. playbook: 운영 사고마다 eval 하나를 쓰고 suite 에 남긴다
  • 결정적 통제B: 확률적 리뷰 옆에 통과 아니면 실패인 linter. playbook: skill 은 권고성 통제라서, 반드시 지켜야 할 정책은 hook 같은 결정적 장치로 받친다

가장 깊은 일치는 사람의 자리다. playbook 은 PR 을 검토하는 code owner 가 “can concentrate on intent and risk because the mechanical evidence is already attached.” 라고 쓰고, B 는 “A human expert reviews a proven fix rather than debugging a raw failure.” 라고 쓴다. 두 글이 줄이려는 병목도 같은 모양이다. playbook 은 agent 가 코드를 빨리 쓰자 병목이 그 앞뒤의 사람 속도 단계로 옮겨 갔다고 보고, B 는 지식 파일이 많아지자 교정을 편집으로 옮기는 사람의 몇 주가 병목이 됐다고 본다. 둘 다 그 번역을 agent 에게 넘기고 사람에게는 증거가 붙은 결과만 보여 준다.

첨언: 짝지은 원문

B: “Every change is version-controlled, diffable, and reversible.” playbook: “The chain of commits is also the audit trail: who asked for what, what the agent produced, and who approved it.”

playbook 직무 분리: “Separation of duties is preserved, because the agent that wrote the code has no way to approve it.” 새 context 검증: “This way the verdict is not colored by the assumptions that produced the code.”

playbook 설정 회귀: “The suite runs non-interactively in CI on a schedule and on any change to CLAUDE.md, skills or hooks, since that configuration steers the agent and deserves the regression testing that code gets.” 사고 → 시험: “Each production incident gets an eval, written by the team that owned the incident, and stays in the suite as a regression test.”

playbook 권고성 통제: “A skill is a control, though an advisory one. It makes Claude likely to apply the policy while the code is written, and nothing forces a session to comply with it.” 병목: “Build is no longer the constraint — the human-speed steps around it are.”

B 그림의 진입 파일 이름 SKILL.md 와 playbook 의 skill 형식(“a folder containing a SKILL.md whose frontmatter says when it triggers and whose body says what to do”)은 이름과 frontmatter trigger 를 공유한다. Meta 가 어떤 agent 런타임을 쓰는지는 B 에 없으므로, 이 일치를 B 가 Claude 를 쓴다는 근거로 읽지 않는다.

sdlc-diverge

SDLC 렌즈 2: 갈라지는 곳은 신호, 판정자, 의도된 변경

B 의 수명주기는 SDLC 의 형식을 빌리지만 세 곳에서 다른 물건이 된다. 실패를 알리는 신호가 결정적 지표가 아니라 전문가의 말이고, 시험의 판정자가 테스트 러너가 아니라 LLM 이며, 사양이 일부러 바뀔 때 시험을 함께 고치는 소프트웨어의 관행에 대응하는 장치가 B 에 없다. 진단 단계는 반대로 B 에만 있다.

  • 신호playbook 의 Maintain 은 결정적 스크립트가 지표의 band 위반을 잡고서야 Claude 를 부른다. B 의 루프는 전문가가 대화에서 교정해야 시작한다. 전문가가 보지 못한 오답은 루프에 들어오지 않는다
  • 진단playbook 의 규칙은 빈도다. 같은 실수를 두 번 하면 CLAUDE.md 에 적는다. 어느 층을 고칠지 묻는 단계는 없고, CLAUDE.md 예시 하나에 명령, 관례, 「Claude 가 자주 틀리는 것」 이 함께 있다. B 는 고치기 전에 층을 가린다
  • 판정자playbook 의 eval 은 「시험 통과, lint 깨끗, 동작 불변, 정책 준수」 같은 검사로 받아들임을 정의한다. B 의 회귀는 정답이 여럿일 수 있는 분석 문항이라 LLM 판정자가 통과를 매긴다
  • 의도된 변경playbook 은 버그 수정 때 실패하는 시험을 먼저 쓰고, 구현이 계획을 벗어나면 같은 커밋에서 plan.md 를 고치라고 한다. B 에는 입장이 바뀔 때 옛 정답을 담은 시험을 고치는 경로가 없다(15장)
  • 배포playbook 은 환경마다 자율 수준을 나누고 rollback 을 가장 많이 연습한 경로로 둔다. B 는 「reversible」 이라고만 쓰고 단계적 배포나 rollback 절차를 말하지 않는다

이 차이로 독자가 예측할 수 있는 실패가 있다. B 의 방식을 코드 저장소의 CLAUDE.md 에 그대로 가져오면 진단 단계 덕분에 「두 번 틀리면 적는다」 보다 편집이 정확해진다. 반대로 playbook 의 방식을 B 같은 compliance 지식에 그대로 가져오면, 지표 band 로 잡을 수 있는 오답이 거의 없어 Maintain 루프가 돌지 않는다. compliance 판단이 틀렸다는 신호는 대개 사람이 읽고 나서야 생기기 때문이다. 두 루프를 겹쳐 쓰려면 B 쪽에 결정적 탐지에 해당하는 것, 예를 들어 같은 입력에 대한 답이 시간에 따라 바뀌는지 보는 표본 재실행을 따로 둬야 한다. 이 제안은 이 문서의 것이고 두 원문 어디에도 없다.

첨언: 원문

When a review flags a mistake for the second time, the correction goes into CLAUDE.md as part of that review” 시험 먼저: “For bug fixes, write the failing test first.” plan 동기화: “When implementation departs from the plan, update plan.md in the same commit.” rollback: “Rollback should be the most rehearsed path in the pipeline” eval 의 수명: “As models improve, cases that once discriminated stop doing so and new ones must be added that arise from ongoing monitoring.” playbook 은 eval 이 낡는다는 것을 말하지만, 낡은 eval 을 빼는 절차는 playbook 에도 없다.

해석의 한계: 구조는 구체적이고 효과는 검증되지 않았다

  • B 안의 불일치본문은 넷째 phase 를 전문가 검토로, 그림은 착지와 보강으로 적는다. 「빈도, 심각도 가중」 은 그림에만 있다. 그림 트리에는 gateway 파일이 없다

conclusion

결론: 교정을 diff 로 적을 수 있으면 루프가 붙는다

Meta 의 organizational second brain 은 전문가 지식을 밀도와 사용 빈도로 나눠, 자주 쓰는 판단은 의존을 적은 텍스트 파일로, 드문 자료는 RAG 로 둔다. 전문가의 교정은 층을 가리는 진단과 최소 편집, 맥락 없는 리뷰와 blind replay, 회귀 시험을 지나 PR 로 착지하고 다음 시험이 된다. 이 수명주기는 SDLC 의 버전 관리와 직무 분리, 회귀 시험을 지식 자체에 입혔고, 실패 신호와 판정자, 의도된 변경 처리에서 SDLC 와 갈라진다.

자기 시스템에 옮기려는 개발자가 먼저 물을 것은 전문가의 교정을 텍스트 diff 로 적을 수 있는가이다(17장). 적을 수 있으면 루프가 붙고, 판단이 사례별 직관이라 적을 수 없으면 교정은 모호함 갈래로 빠진다. 루프가 붙은 뒤의 예측은 이렇다. 입장이 있는데 불리지 않아 생긴 교정은 position 의 triggers 나 routing index 같은 싣는 장치를 고치게 되고, 회귀 suite 의 범위가 gate 의 힘을 정하며, 입장을 일부러 바꾸는 날 지난 교정으로 쌓인 시험이 그 변경을 막는다. 그 마지막 비용을 줄일 장치, 즉 시험이 어느 position 판에 기대는지 적어 두는 일은 B 에 없으므로 직접 만들어야 한다.

B 의 숫자는 세 sprint 동안의 자기 보고이고, token 감소 말고는 측정된 기준선이 없다. 숫자를 빼고도 남는 것은 진단 질문과 검증 gate 의 설계다. 같은 시기 공개된 다른 팀의 사례와 실험도 같은 방향을 가리킨다.
