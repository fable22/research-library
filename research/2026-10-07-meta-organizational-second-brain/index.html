tl-dr

요약: 지식은 텍스트 파일에, 학습은 검증된 diff 로

Meta 는 전문가의 교정을 모델 가중치가 아니라 200개 넘는 텍스트 파일의 diff 로 반영하고, 그 diff 는 맥락 없는 리뷰어와 blind replay, 회귀 벤치마크를 통과해야 PR 이 된다. 효과 수치는 모두 자기 보고다(17장).

  • 구조자주 쓰는 고밀도 지식(입장, 용어, 라우팅, 진입 문턱)은 frontmatter 로 서로를 가리키는 파일에 두고 가끔 필요한 자료는 RAG 로 찾는다
  • 분리recipe 는 도메인 사실을 담지 않고, 지식 파일은 입장을 적되 절차를 담지 않는다. 그래서 틀린 답이 나오면 둘 중 어느 쪽을 고칠지 정할 수 있다
  • 루프진단이 원인을 지식이나 절차 쪽으로 돌리면 컴파일이 그쪽 파일을 최소한으로 고친다. 평가를 통과하고 승인되면 착지해 반영된다. 떨어지면 컴파일로 돌아가고 착지한 교정은 회귀 suite 의 새 시험이 된다
  • 빈 곳원문에 없는 것은 셋이다. 교정이 두 층에 걸치거나 두 파일이 모순될 때 어떻게 하는지, 판정 LLM 이 얼마나 정확한지, 조직이 입장을 일부러 바꿀 때 옛 정답을 담은 시험을 어떻게 고치는지다(12장, 16장)

playbook 에 견주면 Meta 의 루프는 여섯 단계 루프가 아니라, CLAUDE.md 와 skills 를 고치고 eval 을 통과해야 병합하는 곁 루프에 대응한다. 둘 다 변경을 버전 관리하고, 쓴 쪽과 리뷰하는 쪽을 나누고, 설정이 바뀌면 회귀 시험을 돌리고, 사고를 시험으로 남긴다. 고치게 만드는 신호도 둘 다 사람이 알아챈 실수다. 다른 점은 둘이다. Meta 는 고치기 전에 어느 층을 고칠지 진단하고, playbook 은 Maintain 단계의 결정적 탐지(지표 band)가 잡은 사고도 eval 로 곁 루프에 넣는데 Meta 에는 이 탐지가 없다. 판정자와 입장 변경은 차이가 크지 않다(20장).

같은 시기 사례가 빈 곳을 채운다. FINSKILLOPS 는 skill 에 버전을 매기고 흡수된 skill 은 제거 시험 뒤 퇴역시키며, 후보 33개 가운데 6개만 승격했다. PROCTOR 에서는 정답 label 하나가 뒤집혀 최적화기가 맞는 compliance 규칙을 지웠다. EvoPathBench 에서는 반대 증거를 받고 옛 규칙을 고치는 효과가 어느 방법에서도 Holm 보정 뒤 유의하지 않았다.

첨언: 확인되지 않은 것

Meta 는 도메인을 「a specific compliance domain」 이라고만 하고, 개선 사이클 수와 교정 건수, 표본 수, 판정 LLM 의 정확도를 밝히지 않는다. 측정한 기준선과 비교한 숫자는 token 감소 하나뿐이고(17장), 「useful almost all the time」 에는 숫자가 없다. 사례 열 건도 대부분 자기 보고이거나 작은 표본이다(23장).

problem

문제: 전문가의 판단은 문서에 없고, chunk 검색은 판단을 매번 다시 만든다

Meta 가 출발점으로 삼는 문제는 둘이다. 조직의 판단 기준이 몇 사람 머리에만 있어 같은 질문이 수백 번의 검토에서 되풀이되고, chunk 를 찾아 주는 agent 는 실행마다 그 판단을 원자료에서 다시 끌어내느라 느리고 들쭉날쭉하다.

Meta 가 드는 예는 compliance 다. “the same types of questions can arise across hundreds of product reviews, expert assessments take days of manual research, and inconsistency between assessments creates real organizational risk.” 범용 LLM 은 조직이 무엇을 할 수 있는지는 요약하지만, 과거 입장과 사업 방향에 비추어 무엇을 해야 하는지는 가리지 못한다고 Meta 는 쓴다.

“An agent that retrieves document chunks at inference time has to re-derive that reasoning from raw sources on every run, which is slow, error-prone, and inconsistent.” 그래서 Meta 는 판단을 미리 꺼내 둔다. 오프라인에서 오래 도는 과정이 원자료를 읽어 “distills them into structured knowledge files”, 조직이 그 도메인을 어떻게 해석하는지를 기계가 읽을 문장으로 남긴다.

증류하면 문제가 하나 더 생긴다. 파일이 수백 개로 늘어 서로 의존하면, 교정 한 건을 정확한 파일 편집으로 옮기는 데 사람 손으로 몇 주가 걸린다. “This process can take weeks because it requires understanding the full dependency graph, verifying nothing else breaks, and validating the fix actually works.”

첨언: 원문 위치

첫 인용은 원문 도입부, 둘째와 셋째는 §Building the Organizational Second Brain, 넷째는 §The Self-Improvement Flywheel 이다. could 와 should 의 구분은 §The Architecture at a Glance: “it will not be able to distinguish between what an organization could do (a summary of general information) and what it should consider doing (based on historic positions, company direction, business context, etc.)”

layers

네 층: 지식, 추론, 평가, 개선

Meta 의 시스템은 네 층이고 서로 기댄다. 파일 구조가 있어야 자동 편집이 되고, 절차가 명시돼야 실패가 어느 층 탓인지 가릴 수 있으며, 평가가 모든 변경을 거른다. Meta 는 한 층을 빼면 나머지도 약해진다고 쓴다.

의존은 양쪽으로 흐른다. 앞의 세 층이 개선 루프를 받치고 루프는 다시 지식 층과 추론 층을 고친다. 실패를 어느 층 탓으로 돌리는 일을 이 문서는 귀속이라 부른다.

첨언: 원문

§The Architecture at a Glance: “The knowledge system’s file structure makes automated editing possible. The reasoning layer’s explicit procedures make failure attribution tractable. The evaluation framework gates every change.” 이어서 “Remove any one layer and the others degrade.” 표 그림의 영어 원문 전체는 notes/figures.md 에 있다.

files

파일 분류: position, vocabulary, routing index, gateway

지식 층은 200개 넘는 파일을 position, vocabulary, routing index, gateway 네 종류로 나눈다. 모든 파일이 frontmatter 에 자기가 기대는 파일과 자기를 쓰는 파일을 적어, 한 파일을 고치면 영향받는 파일을 따라갈 수 있다.

  • position조직의 입장. 그 도메인의 질문을 어떻게 해석하기로 했는지와 제약, 경계 조건, 언제 적용할지 알려 주는 라우팅 함의를 담는다. 그림에서는 「Supreme authority articles」 다
  • vocabulary용어집. 개체 유형, 활동 범주, 분류 등급 같은 조직 용어의 정본을 두어 agent 와 조직이 같은 낱말을 쓰게 한다
  • routing index입력의 특징을 해당 position 과 절차에 잇는 색인. embedding 유사도에만 기대지 않아 어떤 파일이 왜 불렸는지 감사할 수 있다
  • gateway분석 영역에 들어가기 전에 통과해야 하는 문턱 시험. 전문 지식이 해당하지 않는 곳에 쓰이는 것을 막는다

ps-position-1 의 문장을 고치면 referenced_by 의 세 파일이 영향을 받고 그 셋을 쓰는 recipe 단계의 출력이 달라질 수 있다. 거꾸로 ps-position-5 를 고치면 ps-position-1 이 기대는 전제가 바뀐다. 자동 편집기가 한 파일만 보고 고치면 거기 기대는 파일과 모순이 생기는데, 그래프가 있으면 함께 확인할 파일 목록을 기계적으로 얻는다. Meta 가 계보로 드는 Karpathy 의 LLM Wiki 와 Google 의 OKF 도 파일을 링크로 잇지만, 의존과 사용처를 frontmatter 에 양쪽으로 적는 필드는 없다.

OKF 명세 v0.2(7월 24일, Meta 글보다 앞선다)는 두 군데에서 Meta 와 반대로 골랐다. 링크에 종류가 없어 의존인지 참조인지는 주변 문장이 말하고, 끊긴 링크는 아직 쓰지 않은 지식일 수 있으므로 소비자가 받아들여야 한다. Meta 의 linter 는 끊긴 cross-reference 를 실패로 친다. 조직 사이에 주고받는 형식이면 끊긴 링크를 허용해야 하고, 자동 편집기가 고치는 한 조직의 지식 베이스면 막아야 한다. OKF v0.2 에는 Meta 의 frontmatter 그림에 없는 수명주기 필드가 있다. 작성자(generated)와 확인자(verified)를 따로 적고 status 로 draft, stable, deprecated 를 가르며, stale_after 시각이 지나면 낡은 것으로 본다(21장).

빈 곳도 보인다. 「언제 이 파일을 싣는가」 를 정하는 장치가 position 의 triggers, routing index, gateway 셋이다. Meta 는 position 이 「언제 적용할지」 를 스스로 담는다고도, routing index 가 적용할 파일을 정한다고도 쓴다. 그러나 둘이 어긋나면 어느 쪽을 따르는지, gateway 의 문턱 시험을 LLM 과 코드 중 무엇이 판정하는지는 말하지 않는다. 그래서 「이 position 이 불렸어야 했다」 는 교정이 triggers 를 고칠지 routing index 를 고칠지 원문만으로는 정할 수 없다(15장).

첨언: 원문

§Building the Organizational Second Brain: “Every file declares its dependencies (depends_on) and consumers (referenced_by) in YAML frontmatter, forming a bidirectional dependency graph.” 그리고 “When one file changes, you can trace exactly what else might be affected, which matters when the self-improvement loop proposes automated edits.” routing index: “Routing indexes map input characteristics to the relevant positions and procedures, determining which files apply without relying on embedding similarity alone. This makes retrieval deterministic and auditable.” gateway: “Gateway files define threshold tests the agent must pass before entering an analytical domain, preventing it from applying specialized knowledge where it does not belong.”

Karpathy 의 LLM Wiki 는 index.md 와 log.md 두 특수 파일로 탐색하고 “This works surprisingly well at moderate scale (~100 sources, ~hundreds of pages) and avoids the need for embedding-based RAG infrastructure.” 라고 쓴다. Google 의 Open Knowledge Format(OKF) v0.1 은 “OKF requires exactly one thing of every concept: a type field.” OKF 는 개념 사이를 “Concepts link to each other with normal markdown links, turning the directory into a graph of relationships” 로 잇는다. 명세 v0.2 §6.1: “The specific kind (parent/child, references, joins-with, depends-on) is conveyed by the surrounding prose, not by the link itself.” 그리고 “Consumers MUST tolerate broken links: a link whose target does not exist in the bundle is not malformed; it may simply represent not-yet-written knowledge.” §5.2: “They are kept distinct because who *wrote* a concept need not be who *confirmed* it.” OKF 명세는 GoogleCloudPlatform/knowledge-catalog 저장소의 okf/SPEC.md 이고, 커밋 cd6fb05 판을 읽었다. position 의 라우팅 함의: “machine-actionable routing implications that tell the reasoning layer when to apply it.”

density

wiki 와 RAG 의 경계: 정보 밀도와 사용 빈도

밀도가 높고 거의 매 턴 참조되는 증류 지식은 wiki 에 넣고, 해당할 때만 깊이 중요한 희소 자료는 semantic 또는 lexical 검색으로 찾는다. 밀도는 높은데 드물게 쓰이는 자료의 자리는 원문에 없다.

RAG 를 남겨 두는 이유는 부피와 주의 분산이다. 희소 자료까지 wiki 에 넣으면 “Loading all of them into the wiki would bloat the system and dilute attention.” wiki 쪽은 조직의 생각이 바뀔 때마다 고쳐야 하므로 버전 관리와 검증이 쉬워야 하고 RAG 쪽은 원본 그대로 두어도 된다. Meta 가 드는 개선 루프의 편집 대상도 knowledge 파일과 recipe 이고 RAG 쪽 원자료를 고친다는 말은 없다.

사례 1: mimeo(arXiv 2609.00453v1, 2026-08-31). 한 전문가의 공개 글을 agent 가 싣는 파일 하나로 증류하는 오픈소스 도구로, 같은 원자료에서 증류 파일과 검색을 비교했다. 질문은 전문가 넷에 다섯 문항씩 20개이고, 문항마다 기록 한 건에서 뽑았다. 전문가별 증류 파일 넷은 함께 20개를 모두, 같은 캐시를 BM25 로 찾게 한 조건은 15~17개를 맞혔다. 저자는 쌍대 검정으로 이 차이를 가르지 못했고 증류의 이득은 아직 확인되지 않았다고 쓴다. 질문이 그 파일을 만든 원자료에서 나왔으니 만점은 설계에서 나온 결과이기도 하다.

사례 2: KUPAS MASTER(arXiv 2609.37673v1, 2026-09-29). 실무자의 작업 기록과 면담을 여섯 라이브러리(규칙, 제약, 모범 사례, 반례, 경계 사례, skill)로 증류하는 플랫폼이다. 실무자 20명의 원자료 1,576개 파일에서 177문항, 응답 531개로 평가했고 점수는 기반 모델 70.63, 원자료 RAG 79.75, 증류한 agent 89.58 이었다. 일곱 차원 rubric 의 가중합을 LLM 이 매긴 점수이고, 플랫폼을 만든 회사의 보고다.

두 사례를 합치면, 원문의 한 줄을 찾아오는 일에서는 증류와 검색의 차이가 작고, 판단의 틀을 미리 꺼내 두었을 때 증류가 낫다는 근거는 KUPAS 의 자기 보고뿐이다. mimeo 의 E6(원칙을 새 시나리오 16개에 적용)에서는 증류 파일이 없는 조건과 BM25 까지 모든 조건이 94~100% 에 몰려, 저자는 판단이 옮겨 가는지 판정하지 못했다. 이 문서는 Meta 의 경계를 정하는 것이 빈도 쪽이라고 읽는다. 그렇다면 시스템을 회사 전체로 넓힐 때 wiki 에 있는 position 일부는 「거의 매 턴」 쓰이지 않게 되어, RAG 쪽으로 옮기거나 routing index(05장)에서 싣는 조건을 좁혀야 한다.

첨언: 원문

Meta: “High-density, frequently referenced sources go into the wiki: Distilled files capturing how the organization reasons, such as positions, decision frameworks, boundary examples, and strategic interpretations. The agent consults these on nearly every turn.” 그리고 “Sparse, situationally relevant sources are served through semantic or lexical search (RAG): documents that matter deeply when they apply but are not needed in detail on most runs”

mimeo §Results: “Given only the question, a plain BM25 search over the same cached records answers 15--17. \mimeo{} leads by three to five questions and loses none, but exact paired tests do not separate them.” 그리고 “It does not yet establish a benefit from distillation.” 20문항과 증류 파일(부록 C.3): “each answers all five single-record questions about its expert; collectively, they answer all 20.” 판단 이전(E6): “Again, every condition, including no skill and BM25 retrieval, scores 94--100\% under all four graders.” 그리고 “E6 therefore gives no evidence either for or against judgment transfer.” KUPAS MASTER 초록: “Under common task inputs and scoring criteria, the base model, raw-corpus retrieval-augmented generation (RAG), and \product agent scored 70.63, 79.75, and 89.58, respectively.” 인용 안의 \mimeo{}, \product 는 두 논문 LaTeX 원문의 제품명 매크로다.

recipes

recipe: 아는 것과 추론하는 방법을 다른 파일에 둔다

recipe 는 분석 절차를 적되 도메인 사실을 담지 않고, knowledge 파일은 입장을 적되 절차를 담지 않는다. 이 규칙 하나로 변경이 한쪽에 갇히고, 틀린 답의 원인을 「지식이 틀렸나, 절차가 틀렸나」 로 물을 수 있다.

  • 입장 추가knowledge 파일 하나를 더하고 routing index 를 고친다. recipe 는 그대로다
  • 방법 수정recipe 를 고친다. knowledge 파일은 그대로다
  • 실패 귀속틀린 결과를 두 층 중 하나로 돌릴 수 있다(10장)
  • 약 80%턴당 token 감소. 비교 대상은 지시 파일 하나에 모든 자료를 semantic search 로 싣던 초기판이다

최상위 routing recipe 가 입력을 보고 하위 recipe 를 고르고, 하위 recipe 하나가 분석의 한 단계를 맡는다. 단계마다 그 단계의 지시와 지식만 context 에 싣는 progressive disclosure 가 여기서 나오고, 질의 하나가 건드리는 파일이 적어져 80% 감소로 이어진다. Meta 는 같은 구조가 추론 품질도 높인다고 쓰지만 품질을 잰 결과는 내놓지 않았다.

사례 1: Harvey 의 Playbook Review(2026-09-02). 계약 검토에서 같은 분리를 쓴다. 여기서 playbook 은 회사가 정한 계약 검토 규칙 모음으로, SDLC playbook 과는 다르다. 규칙 하나는 회사가 계약에서 원하는 이상적 조건(standard position), 받아들일 수 있는 이탈과 없는 이탈, 해석 지침, 조항이 없어도 되는지로 이루어진다. Meta 의 position 에 해당하는 이 지식은 고객이 쓰고, 검토 절차는 Harvey 가 따로 만든다. 규칙마다 고정 prompt 를 부르던 workflow 를 lead agent 가 규칙마다 sub-agent 를 띄우는 구조로 바꿨다. 계약서와 playbook 을 짝지은 내부 벤치마크는 그대로 두고 절차만 바꿔, 변호사의 rubric 으로 LLM judge 셋이 채점했다. 위험 분류는 59% 에서 77% 로, 수정안 rubric 점수는 53% 에서 87% 로 올랐고 평균 처리 시간은 2.6분에서 3.8분으로 늘었다.

사례 2: Claude Code 문서의 경계(2026-10-07 수신). playbook 이 링크하는 Claude Code 문서는 CLAUDE.md 의 한 절이 사실을 넘어 절차로 자라면 skill 로 옮기라고 하고, skill 본문은 쓸 때만 실린다. Meta 의 knowledge 파일과 recipe 와 같은 모양이지만 선을 긋는 이유는 context 비용이고, 실패 귀속은 목적이 아니다.

지시 파일 하나에 「이 API 는 v2 를 쓴다」(사실)와 「먼저 로그를 보고 가설을 세운다」(절차)가 섞여 있으면, agent 가 틀렸을 때 어느 문장을 고칠지 정할 근거가 없다. 두 문장을 떼어 두면 10장의 진단 질문 「agent 가 실은 자료로 맞는 결론에 이를 수 있었나」 에 답할 수 있다. 예라면 절차 파일을, 아니오라면 사실 파일을 고친다. 전문가끼리도 답이 갈린다면 고칠 파일이 아니라 사람의 논의로 넘길 일이다(10장).

첨언: 원문

원문 §Expert Reasoning via Composable Recipes: “Where knowledge files are declarative, recipes are imperative.” “Recipes reference knowledge files but contain no domain facts; knowledge files state positions but prescribe no procedures.” 80%: “Early versions used a single flat instruction file and loaded all sources via semantic search, pulling a large volume of mixed-relevance files into the context window on every run.” “After restructuring into recipe-driven stages, each query touches only a small, targeted subset, cutting tokens consumed per turn by around 80%.”

Harvey §Why Contract Review is Harder Than it Looks: “Standard position: the ideal term a company wants to see in their contracts” 결과 표(§Eval Results)는 위험 분류 59% → 77% (+18%), 수정안 rubric 53% → 87% (+34%), 평균 지연 2.6 → 3.8분(+47%)이다. 채점: “After sourcing the rubrics with lawyers, we set up an evaluation framework that uses LLM judges to score against these rubrics. We then used a committee of three frontier models to score independently and aggregate the votes.” 벤치마크의 문항 수는 글에 없다.

Claude Code skills 문서 도입: “Create a skill when you keep pasting the same instructions, checklist, or multi-step procedure into chat, or when a section of CLAUDE.md has grown into a procedure rather than a fact. Unlike CLAUDE.md content, a skill's body loads only when it's used, so long reference material costs almost nothing until you need it.” playbook 도 경계를 적는다: “The rule of thumb: write a skill for institutional knowledge that must be applied consistently; don't write a skill for components that belong in CLAUDE.md or a prompt.”

humans

사람의 자리: checkpoint 와 escalation

사람은 두 곳에서 개입한다. 정해진 checkpoint 에서 agent 가 중간 추론을 보여 주면 전문가가 확인하거나 고치거나 방향을 바꾸고, 입력이 모호하거나 근거가 두 해석을 다 뒷받침하면 agent 가 escalation 으로 결정을 넘긴다.

  • 품질오류가 다음 단계로 번지기 전에 전문가가 잡는다
  • 신호교정과 escalation 이 모두 개선 루프의 입력이 된다
  • 신뢰최종 출력만이 아니라 중간 추론과 불확실성 표시를 보며 전문가가 신뢰를 쌓는다

그래서 루프가 배우는 속도는 전문가가 교정하는 속도를 넘지 못한다. 전문가가 checkpoint 를 대충 넘기면 교정이 없고 진단할 것도 없다. Meta 는 compliance, 금융 위험 평가, 보안 검토, 엔지니어링 안전처럼 결정이 무거울수록 사람을 기본으로 루프 안에 두라고 권한다.

사례 1: Harvey(2026-09-02). Harvey 는 escalation 조건을 Meta 보다 구체적으로 적는다. 계약 검토 playbook 만으로는 거래의 맥락을 담을 수 없다고 보고, 상대가 중요한 고객이라 더 양보할지 같은 결정은 사람에게 넘긴다. 사용자가 수정안을 받아들이거나 고치거나 거절한 기록으로 팀의 선호를 배우겠다고 하지만 이 루프는 아직 계획이고, Meta 는 그 기록을 개선 루프에 넣는 단계까지 갔다.

사례 2: PROCTOR(arXiv 2609.02246v1, 2026-09-02). 법무와 상업 문서 검토의 프롬프트를 자동으로 고치는 루프를 운영한 보고로, 사람 checkpoint 대신 권한을 나눈다. 실패를 진단하는 agent 는 고칠 문장을 쓰지 못하고, 문장을 쓰는 agent 는 적용하지 못하며, 적용은 도구를 가진 orchestrator 하나만 한다. Meta 는 checkpoint 와 escalation 을 코드로 강제하는지, recipe 안의 지시로 두는지 말하지 않는다. 지시라면 agent 가 따라야만 작동하므로, PR 승인을 거쳐야 반영되는 착지 단계(14장)와 강제력이 다르다.

첨언: 원문

원문 §Keeping Humans in Control: “Checkpoints are defined points in the analysis where the agent surfaces its intermediate reasoning for expert review before proceeding, and the expert can confirm, correct, or redirect.” “Escalations trigger when the agent hits genuine ambiguity, whether from underspecified inputs or evidence that supports more than one defensible reading.” “Training signal: Every correction and every escalation becomes input for the self-improvement loop.”

Harvey: “Some decisions cannot be delegated: A playbook alone cannot capture the nuance of deal.” 루프는 앞으로의 일이다: “Closing the loop with self-improvement becomes possible. Every accepted, edited, or rejected redline helps agents understand a legal team's preferences.”

PROCTOR §2.3: “No component both proposes and applies. No component both judges and acts.” 도메인: “Nine of the ten are legal and commercial document review, which is where the bulk of our production use sits” 단일 저자의 현장 보고이고, 저자는 내부 인프라라 재현할 수 없다고 적는다.

flywheel

자기 개선 루프: 진단, 컴파일, 평가, 착지

Meta 는 지식 유지보수를 compilation 문제로 다룬다. 교정은 원인 진단과 최소 편집을 거쳐 표적 replay 와 회귀 시험을 통과해야 착지하고, 착지한 교정은 회귀 suite 의 새 시험이 된다. 모델은 재학습하지 않는다.

순환은 두 개다. 위쪽 귀환선은 한 교정 안에서 평가에 떨어져 컴파일로 돌아가는 재시도이고, 아래쪽 귀환선은 교정과 교정 사이를 잇는다. 아래쪽 때문에 회귀 suite 는 착지마다 한 칸씩 커지고, 나중 교정일수록 통과할 시험이 많다. Meta 가 「compounding」 이라 부르는 것이 이 누적이다.

첨언: 원문

§The Self-Improvement Flywheel: “We treat that maintenance as a compilation problem and automate it.” 본문 목록의 넷째: “Have domain experts review them.” 그림 캡션: “Expert corrections are diagnosed to their root cause, compiled into minimal verified edits, and evaluated against replay and regression tests before they are reviewed and landed.” Meta 가 내세우는 새로움: “Agents that auto-draft their own fixes are increasingly common; but we haven’t seen this level of validation rigor applied to a structured knowledge base without model retraining.”

diagnosis

진단: 원인이 어느 층에 있는지 묻는 질문

진단은 「agent 가 자기 자료로 맞는 결론에 이를 수 있었나」 라는 질문 하나로 교정을 나눈다. 자료에 답이 있었는데 틀렸으면 recipe 문제, 답이 없었으면 지식 공백, 전문가끼리 갈리면 모호함으로 보고 사람의 논의로 넘긴다.

입력: 전문가 교정이 담긴 대화 trace
  + knowledge manifest  # 실린 파일 전부, 언제, 어떻게 쓰였나

1. 추출  교정에서 실질 신호를 빠짐없이 뽑는다
2. 귀속  실린 knowledge 파일을 실제로 읽고 묻는다:
         "자료로 맞는 결론에 이를 수 있었나?"
           자료에 답이 있었다, 그런데 틀렸다   → recipe 문제
           자료에 답이 없었다                → 지식 공백
           전문가끼리 답이 갈린다             → 모호함 → 사람 논의 (편집 없음)
3. 가중  빈도와 심각도 (그림에만 있음)
출력: improvement brief

이 질문은 사실과 절차를 다른 파일에 나눠 두었기에 통한다(07장). 처음 방식은 교정의 말투로 분류했다. 전문가가 정보를 알려 주면 지식 공백, 방향을 틀면 절차 문제로 봤는데 실패했다. 전문가가 결론을 고칠 때 원인은 지식 공백일 수도, recipe 결함일 수도, 진짜 모호함일 수도 있어 말투로는 가를 수 없다. 그래서 Meta 는 신호를 뽑는 단계와 분류하는 단계를 떼고, 분류는 manifest(그 실행에 실린 파일 전부와 각 파일이 언제 어떻게 쓰였는지)와 파일 내용을 직접 보고 한다.

사례 1: TRACE(Amazon, arXiv 2608.09153v1, 2026-08-10). 사용자가 고쳐 주거나 되묻는 불만 신호에서 출발해 실패를 system prompt, knowledge base, tool 설명, skill 가운데 하나로 귀속하고, 지식 쪽이면 내용이 없는지(CREATE) 있는데 틀렸는지(UPDATE)를 가린다. Meta 의 「자료에 답이 있었나」 와 같은 질문이고, 귀속을 가설로 둔 채 실제 파일을 열어 확인하는 방법도 같다.

사례 2: PROCTOR(arXiv 2609.02246v1, 2026-09-02)와 FINSKILLOPS(arXiv 2609.19680v1, 2026-09-17). 두 시스템 모두 진단과 편집을 떼어 놓는다. PROCTOR 의 진단 agent 가 수정 문장을 제안할 수 없는 것(08장)은, 한 모델이 둘을 함께 하면 이미 하고 싶던 편집을 정당화하는 설명을 지어낸다고 저자가 보기 때문이다. FINSKILLOPS 에서는 LLM 이 세운 검색 계획을 결정적 grep 이 실행하고, 다른 LLM 이 찾아온 원문을 읽고 진단한다. 실패는 유형별로 묶여 한 유형이 문턱(12 라운드 기록에서는 8건) 이상 쌓여야 skill 제안으로 넘어가는데, Meta 그림의 「빈도, 심각도로 가중」 에서 빈도 쪽을 숫자로 정한 셈이다.

세 사례로 예측하면, 실패가 recipe 쪽이면 귀속이 쉽다. 어떤 절차 파일이 불렸는지 trace 에 남기 때문이다(TRACE 에서 skill 귀속 100%). 지식 쪽이면 후보 파일이 여럿이라 귀속이 흔들리고, 「없음」 과 「틀림」 을 가르려면 본문을 읽어야 한다. Meta 가 manifest 만 보지 않고 “read the actual knowledge files” 라고 쓴 이유다.

첨언: 원문

원문 §Diagnosis: “This heuristic failed because conversational form is a poor proxy for root cause.” “First, extract every substantive signal from the expert alongside the agent’s full knowledge manifest (every file loaded, when, and how used).” 질문: “Could the agent have reached the correct conclusion from its source materials?” 세 갈래: “If the materials contained the right answer but the agent still erred: recipe problem.” “If the materials did not contain the right answer: knowledge gap.” “If experts themselves disagree on the right answer: ambiguity, flagged for human discussion.”

TRACE 도입: “to recommend the correct remediation---CREATE (content missing) vs.\ UPDATE (content exists but wrong)---the agent must verify whether the content actually exists.” 층별 정확도 표의 캡션: “Skills and prompts achieve perfect attribution; KB and tools are harder due to ambiguous file boundaries.” TRACE 의 출력은 사람 검토로 끝난다: “Outputs a \texttt{CRUD\-Recommendation} for human review.”

PROCTOR §2.1: “Separating diagnosis from authorship prevents the common failure in which a single model invents an explanation that conveniently justifies the edit it already wanted to make.” FINSKILLOPS §3.2: “Deterministic grep executes this plan.” 문턱: “Failures are grouped by mode; modes whose frequency reaches a threshold $\tau$ proceed to skill proposal.” 부록 기록의 값: “The proposal cap is three per round, the supporting-failure threshold is eight per recorded operational mode, and the skill-text budget has a soft limit of 500 tokens.”

「자료」 가 실린 파일만을 뜻하는지 지식 베이스 전체를 뜻하는지 Meta 는 정하지 않는다. 15장의 사례가 이 차이에서 갈린다.

compile-review

컴파일과 리뷰: 최소 편집, 맥락 없는 리뷰어, 통과 아니면 실패인 linter

컴파일은 진단된 문제 하나를 최소 파일 편집으로 바꾼다. 편집안은 두 검사를 받는다. 개선 이유를 모르는 새 context 의 agent 가 diff 만 받아 모순을 찾고, 결정적 linter 가 구조 오류를 잡는다.

  • 영향 분석sub-agent 가 병렬로 cross-reference, 기존 입장과의 충돌, token 예산 영향, 시험 범위, 중복 위험을 본다
  • 적대적 리뷰입력은 지식 베이스에 대한 diff 뿐이고, 편집이 만든 모순이나 깨진 경계 사례를 찾는다. 제안한 agent 와 맥락을 나누지 않아 그들의 맹점을 물려받지 않는다
  • linter끊긴 cross-reference, 파일 크기 예산 위반, 식별자 충돌, 의존 순환을 잡는다. agent 의 리뷰와 달리 확률적이지 않고, 통과 아니면 실패다

리뷰어에게 개선 이유를 주지 않는 것이 이 설계의 핵심이다. 이유를 알면 「이 교정이 그 문제를 고치는가」 를 보고, 모르면 「이 diff 가 무엇을 깨는가」 만 본다. 리뷰어와 sub-agent 는 diff 의 영향 범위를 05장의 referenced_by 그래프에서 얻으므로, 바뀐 position 을 인용하는 scoring 기준 파일 같은 것을 빠뜨리지 않는다.

사례: PROCTOR 의 Teacher(arXiv 2609.02246v1, 2026-09-02). Meta 의 적대적 리뷰어 자리에 LLM 리뷰어(Teacher)를 두되 권한을 낮췄다. Teacher 는 patch 의 글을 rubric 으로 채점하지만 결과는 보지 못하고, 결정적 검사가 거절하면 Teacher 의 승인은 무효이며 그 반대는 없다. 자동 거절과 되돌림 13건 가운데 6건은 결정적 검사와 Teacher 를 모두 통과한 뒤 실제 평가에서 성능을 떨어뜨린 patch 였고, 한 suite 는 88.9% 에서 33.3% 로 떨어졌다. 그래서 저자는 리뷰어의 승인을 검증이 아니라 의견으로 읽는다.

그러니 Meta 의 리뷰어가 diff 를 통과시킨 것은 「이 편집이 맞다」 는 증거가 아니고, 그 증거는 13장의 replay 와 회귀 시험에서 나온다. Meta 는 리뷰어가 문제를 찾으면 편집안을 막는지 컴파일로 돌려보내는지 쓰지 않아, 리뷰어와 linter 가 엇갈릴 때 어느 쪽을 따르는지도 알 수 없다. 「linter 는 통과 아니면 실패다」 라는 문장으로 PROCTOR 와 같은 순서를 짐작할 뿐이다.

첨언: 원문

원문 §Compilation: “Sub-agents analyze impact in parallel, examining cross-references, conflicts with existing positions, token budget impact, test coverage, and duplication risk.” “A separate agent, running in a fresh context with no knowledge of the improvement rationale, receives only the proposed diffs to the knowledge base.” “Because it shares no context with the proposing agents, it cannot inherit their blind spots.” linter: “A linter catches issues programmatically, dangling cross-references, file size budget violations, identifier collisions, and dependency cycles. This layer is not probabilistic. It passes or fails.”

PROCTOR §1: “The second is \emph{deterministic gating}: the checks with final authority are mechanical rules, and a mechanical rejection overrides an LLM approval, never the reverse.” §5.7: “Of the thirteen automated rejections and reversions logged across our runs, six were metric-regression reversions: mutations that passed the mechanical pre-apply checks, were approved by the Teacher, and then measurably degraded performance when evaluated, in one case dropping a suite from 88.9\% to 33.3\%.” 저자는 수치가 모두 한 번씩 돌린 결과라고 적는다: “Single-run measurements.”

두 파일이 부딪칠 때: 두 층에 걸친 교정과 서로 모순된 지식

Meta 가 모순을 막는 장치 셋은 모두 새 diff 가 만드는 모순만 본다. 이미 모순된 두 파일, 같은 입력에 함께 걸리는 두 규칙, recipe 와 knowledge 를 함께 고쳐야 하는 교정은 원문이 다루지 않는다.

상황Meta 원문같은 시기 사례의 처리

세 장치는 컴파일의 sub-agent(기존 입장과의 충돌), cross-reference(영향 범위), 적대적 리뷰어(편집이 만든 모순)다. 예측하면 원래 모순되던 두 position 은 교정이 둘 중 하나를 건드릴 때까지 남는다. 교정이 A 를 고치면 리뷰어는 A 의 diff 만 받고, B 가 A 의 depends_on 이나 referenced_by 에 없으면 영향 분석도 B 를 열지 않을 수 있다. frontmatter 로 이어지지 않은 두 파일의 모순은 세 장치를 모두 빠져나간다. 루프는 교정 하나를 한 층으로 귀속하므로 두 층에 걸친 교정은 반쪽만 고쳐지고, 재시도에서 다른 층의 파일까지 고칠 수 있는지는 원문에 없다.

같은 시기 사례의 세 처리는 지키는 것이 다르다. FINSKILLOPS 는 모순 후보를 승격 전에 거절하고, 우선순위 규칙으로 두 규칙을 살려 둔 채 적용 순서를 정한다. Harvey 의 lead agent 는 두 규칙을 다 만족하는 편집을 매 검토마다 새로 써서 같은 충돌이 다음 계약에서 또 생긴다. KUPAS MASTER 는 범위가 겹치는 규칙을 사람이 판정할 때까지 비활성으로 둔다. Meta 의 루프에는 FINSKILLOPS 의 방식이 가장 잘 맞는다고 이 문서는 본다. 우선순위를 knowledge 파일의 한 줄 편집으로 적으면 그 편집도 replay 와 회귀 시험을 거치기 때문이다.

첨언: 원문

평가: blind replay 와 회귀 벤치마크

평가는 두 단계다. 표적 replay 는 원래 시나리오를 시험인 줄 모르는 agent 에게 다시 돌리고, 무엇이 바뀌었는지 모르는 판정자가 새 출력을 원래 교정과 대조한다. 회귀 시험은 성능이 떨어진 곳을 찾는다.

  • replayagent 도 판정자도 무엇이 바뀌었는지 모르는 이중 blind 로 확증 편향을 막는다
  • 회귀그 도메인의 벤치마크(보통 구조화된 Q&A 쌍)를 독립 세션에서 병렬로 돌린다. 정답이 여럿일 수 있는 분석 도메인에서는 독립 LLM 판정자가 기준에 따라 사례마다 통과, 실패를 매긴다
  • 재시도replay 가 떨어지면 다시 컴파일하고, 회귀가 떨어지면 떨어진 곳과 원래 문제, 시도한 수정을 prompt 에 담는다

원래 시나리오에서는 맞지만 다른 질문의 답을 망가뜨리는 편집은 replay 를 통과해도, 회귀 벤치마크에 그 질문이 있으면 걸린다. 못 막는 것은 판정자나 정답이 틀린 경우다. suite 의 정답 하나가 틀리면 루프는 거기 맞춘 편집을 「개선」 으로 받아들이고, 셋째 행 같은 정답 파일 누출도 점수로는 보이지 않는다. PROCTOR 에서 누출이 드러난 것은 작성 실수로 suite 에 들어간, 정직하게는 통과할 수 없는 사례를 agent 가 통과해서였고, 저자는 그 뒤 이런 사례(canary)를 suite 마다 일부러 심는다. Meta 는 판정자의 정확도를 재지 않았거나 공개하지 않았다. Decagon 은 자사 LLM judge 를 사람 label 과 운영 결과에 대어 정확도 99.5% 라고 보고하고, FINSKILLOPS 는 답 150개에서 judge 와 사람의 일치도(이진 κ 0.827~0.907)를 사람 둘 사이의 일치도(0.853)와 나란히 보여 준다.

gate 에는 대가도 있다. EvoPathBench(arXiv 2609.24663v1, 2026-09-21)에서 안전장치는 해로운 편집을 줄였지만 좋은 편집도 덜 골랐고, 저자는 안전장치가 더 나은 후보를 알아봐서가 아니라 덜 받아들여서 안정적이었다고 쓴다. FINSKILLOPS 에서도 후보 33개 가운데 6개가 승격됐다.

첨언: 원문

원문 §Evaluation: “Targeted replay runs the agent on the original scenario that triggered the feedback. The agent does not know it is being tested.” “A separate judge evaluates the new output against the original expert feedback without knowing what was changed.” “Regression testing runs multiple benchmarks for that domain, which are usually structured test suites of Q&A pairs.” “an independent LLM judge gives each test case a pass/fail based on certain criteria” 재시도: “If regression testing fails, compilation is retried with an updated prompt describing where the agent regressed, along with the original issue and attempted fix.” Meta 는 벤치마크의 문항 수와 판정자의 기준, 재시도 상한을 밝히지 않는다.

PROCTOR §4.1: “The loop converted a data bug into a capability regression: the optimized agent was measurably better by the metric and objectively worse at the task.” 용어 덧씌우기: “Measured reasoning-alignment pass rate jumped from 23.1\% to 80.0\%. The agent's actual precision in identifying defects did not change at all” 100% 와 68.1% 는 §3 Class D 의 D1 이다. 드러난 경위: “Exposure came via C2's accidental canary: the exploited runs \emph{passed the unpassable case}, which no honest agent can do.” C2 는 “The case was an authoring accident, but it became the most diagnostically valuable item in the suite” 이고, §5.5 L5 가 이를 정식화한다: “We plant intentionally unpassable cases inside evaluation suites, cases whose reference answer cannot be produced by honest analysis.”

Decagon §Simulation generation: “Since the judge determines whether an Autopilot fix is truly “correct”, we checked it against human-labeled ground truth and real production outcomes. Similar to sim improvement, judge quality quickly rose in August, reaching 99.5% accuracy.” 표본 수는 글에 없다. FINSKILLOPS 부록 Judge--Human Agreement: 이진 κ 는 Qwen3-Max 가 사람 A, B 와 0.827, 0.840, GPT-5.5 가 0.907, 0.893, 사람 A 와 B 가 0.853 이다. 저자는 annotator 가 저자 그룹의 두 사람이고 금융 전문가가 아니었다고 적는다.

EvoPathBench §4.4: “Overall, safeguards provide greater stability mainly by accepting fewer updates, rather than by identifying better candidates.”

landing

착지와 보강: PR 을 사람이 승인하고, 실패 사례가 시험이 된다

파이프라인은 감사 기록이 붙은 PR 을 내고, 전문가는 날것의 실패 대신 검증을 마친 수정을 검토한다. PR 이 승인되면 원래 실패했던 시나리오와 검증된 정답이 자동으로 회귀 suite 에 들어간다.

착지 뒤의 이 단계가 보강이다. 시험은 늘기만 하고 빼는 경로는 원문에 없어, 교정이 쌓일수록 지식 베이스는 지난 교정을 모두 지키는 쪽으로 묶인다. 의도된 효과지만 조직이 입장을 일부러 바꿀 때는 비용이 된다(16장).

FINSKILLOPS 는 착지한 지식에 버전을 매겨 새 버전이 옛 버전을 비활성으로 돌리고, 흡수된 skill 은 제거 시험 뒤 뺀다. Meta 는 모든 변경을 되돌릴 수 있다고만 쓰고 착지한 지식을 대체하거나 빼는 절차는 말하지 않는다.

사람의 승인은 병목이 되기 쉽다. FINSKILLOPS 는 사람 검토 경로를 두었지만 인력이 없어 승격을 자동 검사만으로 정했다. KUPAS MASTER 에서는 실무자 8명분의 교차 리뷰 37건이 후보 818개를 다뤘는데, 사람 확인을 마친 것은 9개이고 331개가 기다리고 있었다. Meta 는 글 끝의 원리 절에서 개선 하나하나가 전문가가 30초면 검토할 텍스트 편집이라고 쓰지만, 검토를 기다리는 PR 이 몇 개인지는 밝히지 않는다.

사례: Decagon 의 Duet Autopilot(2026-09-09). 고객 응대 agent 의 운영 절차(AOP)를 자동으로 고치는 시스템이다. 글의 예에서 수정은 시뮬레이션과 회귀 시험을 거쳐 사람 검토로 갔고, 운영 팀이 병합한 AOP 줄의 70% 를 이 시스템이 쓴다. 병합된 수정을 30일 뒤 다시 보니 절반 가까이는 첫 주 뒤에도 그대로였다. 통째로 되돌리거나 지운 것은 15% 미만이고, 나머지는 팀이 덧대거나 고쳤다. Meta 의 「회귀 0건」 이 착지 전의 시험만 센 것이라면, Decagon 의 되돌림 비율은 착지 뒤 사람이 철회한 것을 세므로 두 숫자는 재는 대상이 다르다.

첨언: 원문

원문 §Landing and Enrichment: “The output of the pipeline is a pull request (diff) with a complete audit trail. A human expert reviews a proven fix rather than debugging a raw failure.” 보강: “the original failing scenario and its validated correct answer are automatically added to the regression test suite” 30초는 §Applying This Architecture 끝에서 두 번째 문단, 원리를 말하는 “The deeper principle is straightforward” 문단에 있다: “Every improvement is a text edit that a domain expert can review in 30 seconds. Every change is version-controlled, diffable, and reversible.” 시험을 빼는 경로가 없다는 부재 확인은 16장 첨언에 있다.

FINSKILLOPS §3.3: “A promoted skill enters the registry with a version number. A revised version supersedes the earlier one, which becomes inactive. A skill whose behavior is absorbed by another and that stops activating is retired after a removal test.” 한계: “The financial-expert review route was not staffed, so admission decisions rested on the automatic checks, and the judge-agreement study uses annotators from the author group rather than independent domain experts.” 그리고 “its evaluation set was monitored every round, so it measures how the deployment improved rather than the isolated effect of skill text, and it does not establish blind generalization.” 보호 suite 는 120문항(이전에 맞힌 90, 고위험 30)이다.

KUPAS MASTER §Cross-review: “Human confirmation is recorded separately: 9 candidates had completed human verification and 331 were marked as awaiting it.” 같은 문단: “Records for 8 practitioners contain 37 completed cross-review jobs across the six libraries, covering 818 candidates.”

Decagon: “Nearly half of all changes remained fully intact after the first week. Over longer periods, complete reversions or removals represented less than 15% of changes, as teams were more likely to build on or reshape the original edit.” “Duet and Autopilot now author 70% of merged AOP lines across production teams.” 비교 대상 수정의 수는 글에 없다.

       싣는 장치가 triggers 인지 routing index 인지 Meta 는 정하지 않는다 (05장)
       여기서는 routing index 를 고친다

       영향 범위: 새로 불릴 ps-position-1 의 referenced_by
                  (ra-scoring-criteria, ra-requirement-catalog)
       적대적 리뷰어(diff 만 봄): "결제가 있는 모든 기능이 High-Risk 가 된다"
       linter: 끊긴 참조 없음, 순환 없음 → 통과

       회귀: 기존 사례 "웹 결제 일회성 티켓 판매는 일반 검토" → 실패
       (가정: 실린 ps-position-1 을 agent 가 본문의 반복 결제 조건보다
        넓게 적용한다. 합성)
       → 재시도 prompt: 회귀 위치 + 원 문제 + 편집안 A

4 착지 PR(diff 1줄, 감사 기록) → 전문가 승인 → 반영
       회귀 suite 에 이 시나리오와 정답 추가

옮겨 쓸 예측은 셋이다. 첫째, 입장은 있는데 불리지 않아서 생긴 교정은 position 의 결론을 건드리지 않고 그 position 을 싣는 장치를 고친다. 이런 교정이 얼마나 되는지는 원문에 없다. 둘째, 리뷰어가 지적한 과잉 범위는 리뷰어가 막지 않아도 회귀 시험에서 걸린다. 단, 「일회성 티켓」 사례가 suite 에 이미 있고 agent 가 실린 position 을 본문 조건보다 넓게 적용할 때만이고, 그렇지 않으면 편집안 A 도 회귀를 통과해 과잉 범위가 남는다. 셋째, 착지 뒤 suite 에 「웹 구독은 High-Risk」 와 「일회성 티켓은 일반」 이 함께 들어 있어, 다음 교정이 둘 사이의 경계를 함부로 옮기지 못한다.

예측이 빗나가는 곳도 있다. 운영자가 「자료」 를 달리 읽으면 같은 교정이 recipe 쪽 편집(「결제가 있으면 반복 여부부터 확인하라」 는 단계 추가)으로 갈 수 있다. 두 편집 모두 replay 를 통과할 수 있고 어느 쪽이 나은지는 Meta 의 gate 가 가리지 않는다. knowledge 쪽을 택해도 triggers 와 routing index 중 어느 것을 고칠지는 운영자가 정한다.

첨언: 이 사례가 원문에 기대는 곳

파일 이름과 frontmatter 는 원문 그림의 것이다(05장). 시나리오는 ps-position-1 의 triggers 셋 어디에도 맞지 않도록 골랐다. 「웹 결제 구독」 시나리오, ps-position-1 본문의 내용, 두 편집안, 회귀 사례는 이 문서가 만든 것이다. 진단 질문의 원문은 “Could the agent have reached the correct conclusion from its source materials?” 이고 manifest 의 정의는 “every file loaded, when, and how used” 다. manifest 가 실린 파일만 담으므로 「자료 = 실린 파일」 로 읽을 근거가 있다. 그림 트리는 routing index 를 knowledge/investigation/ 아래에 두지만, 원문은 routing index 가 “Routing indexes map input characteristics to the relevant positions and procedures” 라고 써서 절차까지 가리킨다.

limits

원리가 멈추는 곳: 입장 변경, 모호함, 판정자, 순서, 규모

루프는 교정이 「지난 판단이 틀렸다」 는 뜻일 때 잘 돈다. 아래 다섯 경우에는 Meta 의 장치만으로 결과를 예측할 수 없고, 같은 시기 연구 둘이 잰 입장 변경과 순서는 둘 다 루프에 불리하게 나왔다.

  • 입장 변경조직이 규제 변화로 ps-position-1 의 결론을 일부러 뒤집어도, 지난 교정으로 쌓인 시험 다수는 옛 정답을 요구하므로 회귀 gate 는 이 변경을 회귀로 읽고 컴파일로 돌려보낸다. 착지한 시험을 고치거나 빼는 경로는 원문에 없다. EvoPathBench 에서 배운 규칙을 뒤집는 반대 증거를 주었을 때, Holm 보정 뒤 유의한 수정 효과를 낸 방법은 없었다
  • 모호함전문가끼리 답이 갈리면 편집 없이 사람의 논의로 넘어가고, 그 결과가 루프로 돌아오는 경로를 Meta 는 쓰지 않는다. 가장 어려운 사례에서 루프는 배우지 않는다(KUPAS MASTER 의 처리는 12장)
  • 판정자replay 와 회귀의 통과는 LLM 판정자가 매기고, 결정적 검사는 linter 하나뿐이다. Meta 는 판정자의 정확도를 잰 결과를 내놓지 않았고, 「회귀 0건」 도 그 판정자가 센 숫자다. PROCTOR 에서처럼 정답 label 하나가 틀리면 루프는 맞는 규칙을 지우는 쪽으로 간다(13장)
  • 순서교정은 전문가가 일하는 순서대로 들어온다. Salesforce 가 재평가한 메모리 기반 자기 개선 방법 가운데 ReasoningBank 를 쓴 agent 는 기존 과제 순서에서 평균 +1.5%, 순서를 섞자 −4.5% 였다. 재평가한 두 방법에는 Meta 같은 gate 가 없어 Meta 에 그대로 옮길 수는 없다
  • 규모Meta 의 지식 베이스는 compliance 도메인 하나에 파일 200개 이상으로, Karpathy 가 index 파일만으로 된다고 한 규모(수백 쪽)와 같은 크기다. 그보다 커질 때 routing index 와 의존 그래프가 어떻게 버티는지는 보고되지 않았다

가장 예측하기 쉬운 것은 입장 변경이다. 시험이 늘기만 하는 suite 에서는 입장 하나를 바꾸는 비용이 그 입장을 건드린 지난 교정의 수에 비례해 커진다. 이 문서의 제안은 시험마다 「어느 position 의 어느 판에 기댄 정답인가」 를 적어 두고, position 이 바뀌면 그 시험을 사람에게 다시 묻는 장치다. Meta 의 frontmatter 는 시험과 파일 사이의 의존을 적지 않는다. KUPAS MASTER 가 규칙이 바뀌면 의존 관계로 재검증할 skill 을 찾는 것은 Meta 의 depends_on 을 시험까지 넓힌 모양이다.

첨언: 근거와 부재 확인

Meta 는 입장이 바뀐다는 것을 안다. §The Self-Improvement Flywheel: 지식 베이스를 바르게 유지하는 일이 “as it grows and as expert positions evolve” 어렵다고 쓴다. 그러나 시험 제거나 갱신을 가리키는 낱말은 원문 사본에서 0건이다(retire, deprecat, delet, stale, expire, rollback, revert 검색). 「reversible」 은 한 번 나오지만 되돌리는 방법은 없다. 판정자: “an independent LLM judge gives each test case a pass/fail based on certain criteria” Karpathy(w3): “This works surprisingly well at moderate scale (~100 sources, ~hundreds of pages) and avoids the need for embedding-based RAG infrastructure.”

SDLC 대조 1: Meta 의 지식 수명주기가 빌려온 규율

Meta 의 루프는 playbook 이 코드 옆의 설정 파일(CLAUDE.md, skills, hooks)에 요구하는 규율을 지식 파일 자체에 적용한 것으로 읽힌다. 이 대응은 이 문서가 만든 것이고, Meta 는 SDLC 를 언급하지 않는다.

  • 신호Meta: 전문가가 대화에서 고친 교정. playbook 곁 루프: Claude 가 같은 실수를 두 번 하거나 리뷰가 두 번째로 잡으면 CLAUDE.md 에 적는다. 둘 다 사람이 본 실수이고, playbook 의 eval suite 에는 결정적 탐지가 잡은 사고도 들어온다(20장)
  • 버전 관리Meta: 모든 변경이 버전 관리되고 되돌릴 수 있다. playbook: 단계마다 산출물을 커밋하고 커밋의 사슬이 감사 기록이다
  • 직무 분리Meta: 제안 agent 와 맥락을 나누지 않는 리뷰어와 전문가의 승인. playbook: 코드를 쓴 agent 는 자기 코드를 승인할 길이 없고, 검증은 새 context 에서 한다
  • 설정 회귀Meta: 모든 편집이 도메인 벤치마크를 통과해야 한다. playbook: CLAUDE.md, skills, hooks 가 바뀔 때마다 eval suite 를 돌린다
  • 실패 → 시험Meta: 착지한 실패 사례가 회귀 suite 에 들어간다. playbook: 운영 사고마다 eval 하나를 쓰고 suite 에 남긴다
  • 결정적 통제Meta: 확률적 리뷰 옆의 linter. playbook: skill 은 권고성 통제라서, 반드시 지켜야 할 정책은 hook 같은 결정적 장치로 받친다

가장 깊은 일치는 사람의 자리다. playbook 은 PR 을 검토하는 code owner 가 “can concentrate on intent and risk because the mechanical evidence is already attached.” 라고 쓰고, Meta 는 “A human expert reviews a proven fix rather than debugging a raw failure.” 라고 쓴다. 병목도 같은 모양이다. playbook 은 agent 가 코드를 빨리 쓰자 병목이 그 앞뒤의 사람 속도 단계로 옮겨 갔다고 보고, Meta 는 지식 파일이 많아지자 교정을 편집으로 옮기는 사람의 몇 주가 병목이 됐다고 본다. 둘 다 그 일을 agent 에게 넘기고, 사람은 직접 쓰는 대신 증거가 붙은 결과를 검토한다.

첨언: 짝지은 원문

Meta: “Every change is version-controlled, diffable, and reversible.” playbook: “The chain of commits is also the audit trail: who asked for what, what the agent produced, and who approved it.”

playbook 직무 분리: “Separation of duties is preserved, because the agent that wrote the code has no way to approve it.” 새 context 검증: “This way the verdict is not colored by the assumptions that produced the code.”

playbook 설정 회귀: “The suite runs non-interactively in CI on a schedule and on any change to CLAUDE.md, skills or hooks, since that configuration steers the agent and deserves the regression testing that code gets.” 사고 → 시험: “Each production incident gets an eval, written by the team that owned the incident, and stays in the suite as a regression test.”

playbook 권고성 통제: “A skill is a control, though an advisory one. It makes Claude likely to apply the policy while the code is written, and nothing forces a session to comply with it.” 병목: “Build is no longer the constraint — the human-speed steps around it are.”

원문 그림의 진입 파일 이름 SKILL.md 와 playbook 의 skill 형식(“a folder containing a SKILL.md whose frontmatter says when it triggers and whose body says what to do”)은 이름과 frontmatter trigger 를 공유한다. Meta 가 어떤 agent 런타임을 쓰는지는 원문에 없으므로, 이 일치를 Meta 가 Claude 를 쓴다는 근거로 읽지 않는다.

sdlc-diverge

SDLC 대조 2: 같은 곁 루프와 견주면 남는 차이는 진단과 탐지다

playbook 의 곁 루프와 견주면 신호와 판정자, 낡은 시험은 크게 다르지 않다. 다른 점은 둘이다. Meta 에만 고치기 전의 층 진단이 있고, playbook 에만 아무도 보지 못한 실패를 잡는 결정적 탐지가 있다.

항목Metaplaybook 의 곁 루프차이의 크기
실패 신호전문가의 교정. 그림에는 빈도와 심각도 가중이 있다두 번 한 실수, 리뷰가 두 번째로 잡은 실수, 운영 사고CLAUDE.md 쪽은 같은 종류이고 문턱만 다르다(한 번 대 두 번). eval 로 가는 사고는 결정적 탐지에서도 온다
진단진단 질문으로 recipe, 지식, 모호함을 가른다(10장)없다. 고친 내용을 CLAUDE.md 에 바로 적고, Claude Code 문서는 사실은 CLAUDE.md, 절차는 skill 이라는 경계만 준다Meta 에만 있다

「차이의 크기」 열은 이 문서의 판단이다. playbook 은 Maintain 에서 고친 사고마다 eval 을 더하라고 하므로, band 위반도 곁 루프 eval suite 의 입력이 된다. 그래서 신호의 차이는 「사람의 말 대 결정적 지표」 로 통째로 나뉘지 않고, 사람이 보지 못한 실패가 band 위반을 거쳐 suite 로 들어오는 길이 Meta 에 없다는 데 있다(마지막 행). 판정자는 playbook 도 gate 에 적대적 리뷰 agent 를 허용하므로 LLM 에 맡기는 비율만 다르다. 의도된 변경도 Meta 만의 빈 곳은 아니다. playbook 은 계획이 바뀌면 같은 커밋에서 plan.md 를 고치라고 하지만, eval suite 에는 같은 규칙을 두지 않는다.

예측하면, Meta 의 진단을 CLAUDE.md 관리에 가져오면 「두 번 틀리면 적는다」 만 쓸 때보다 편집이 정확해진다. 사실을 몰라서인지 절차를 안 따라서인지에 따라 고칠 곳이 CLAUDE.md 와 skill 로 갈리기 때문이다. 거꾸로 compliance 의 오답은 대개 사람이 읽어야 드러나 지표 band 로 잡기 어렵다. 그래서 Meta 의 루프는 전문가가 보지 않은 오답을 배우지 못한다. 이를 메우려면 같은 입력을 표본으로 다시 돌려 답이 시간에 따라 바뀌는지 보는 결정적 탐지를 따로 두어야 한다. 이 제안은 이 문서의 것이다.

첨언: 원문

playbook 곁 루프의 신호: “When Claude makes a mistake twice, the correction goes into CLAUDE.md.” 리뷰: “Review findings feed back into CLAUDE.md. When a review flags a mistake for the second time, the correction goes into CLAUDE.md as part of that review” 이어서 “Review also flags when a change has made CLAUDE.md outdated.” 사고: “Each production incident gets an eval, written by the team that owned the incident, and stays in the suite as a regression test.” gate: “Gate configuration changes on the results. A skill change that drops the pass rate gets reviewed before it merges.”

판정: “Write each task as an eval, meaning the prompt plus the checks that define acceptable (tests pass, lint clean, behavior unchanged, policy followed).” Maintain gate: “Stage 6: Maintenance runs headless, with an independent confidence gate between stages, a deterministic check or an adversarial reviewing agent, deciding whether the previous stage's output continues or is escalated to a human.” 탐지: “A deterministic script watches production and invokes Claude when a control band is breached.” 그리고 “The script is version controlled and unit tested, and detection stays entirely deterministic, with no model involved.” 탐지에서 eval 로: “When a fix ships, add an eval for the incident (the continuous evals play) to ensure that such issues are protected against going forwards.”

eval 의 수명: “As models improve, cases that once discriminated stop doing so and new ones must be added that arise from ongoing monitoring.” 코드 쪽 동기화: “When implementation departs from the plan, update plan.md in the same commit.” 시험 먼저: “For bug fixes, write the failing test first.” rollback: “Rollback should be the most rehearsed path in the pipeline”

Claude Code memory 문서도 CLAUDE.md 에 적을 신호로 같은 것을 든다: “A code review catches something Claude should have known about this codebase” 그리고 CLAUDE.md 는 “Claude treats them as context, not enforced configuration. To block an action regardless of what Claude decides, use a [PreToolUse hook](/docs/en/hooks-guide) instead.” Karpathy 의 LLM Wiki 도 낡은 주장을 찾는 Lint 를 둔다(12장 첨언). 낡은 지식을 찾는 장치는 세 자료에 다 있고, 낡은 시험을 찾는 장치는 어디에도 없다.

코드의 시험은 사양이 바뀌기 전까지 맞지만, 지식 시험의 정답은 전문가의 판단이라 처음부터 틀릴 수 있고 조직이 입장을 바꾸면 낡는다. 착지한 정답이 낡았다고 빼거나 고치는 절차를 적은 사례는 이번에 없다. 빌리지 못하는 이유는 셋이다. 첫째, 정답이 나오는 곳이 다르다. EvoPathBench 의 저자는 지금의 수용 규칙이 필요한 규칙 수정과 해로운 망각을 구분하지 못한다고 결론짓는다. 셋째, 결정적으로 갱신할 수 있는 것은 바깥 세계와 대조할 수 있는 지식뿐이다. Microsoft 의 curator 는 데이터베이스 스키마처럼 다시 물어볼 수 있는 사실을 환경에 대조해 고쳤지만, 조직의 입장은 물어볼 환경이 없어 사람이 판정해야 한다.

Meta 의 빈칸 가운데 채우기 쉬운 것은 폐기와 단계적 배포로, FINSKILLOPS 처럼 position 에 버전과 활성 상태를 두고 OKF 처럼 낡는 시각을 적으면 된다. 어려운 것은 시험 정답의 수명이고, 16장의 장치가 필요하다. 이 제안들은 이 문서의 것이다.

critique

해석의 한계: 구조는 구체적이고 효과는 검증되지 않았다

Meta 는 파일 분류, 진단 질문, 리뷰어의 맥락 분리, blind replay 를 따라 만들 만큼 구체적으로 적었지만 효과는 자기 보고뿐이다. 같은 시기 사례에서 gate 는 해로운 편집을 줄이지만 좋은 편집도 덜 받고, 판정자와 정답이 틀리면 틀린 쪽을 지킨다.

  • Meta 가 말하지 않는 것도메인 이름, 교정과 편집 건수, 기각률, 재시도 횟수와 상한, 회귀 suite 크기, 판정 LLM 과 그 정확도, 교정 하나당 LLM 호출 비용, 실패 사례, 두 파일이 모순될 때의 처리
  • 새로움 주장Meta 는 이 정도의 검증을 재학습 없는 구조화 지식 베이스에 적용한 예를 보지 못했다고 쓰지만 선행 연구를 들지 않는다. 같은 9월의 FINSKILLOPS 가 skill registry 에 진단, 보호 suite gate, negative control, 버전과 퇴역을 적었는데, 대상이 skill 하나하나라 Meta 의 의존 그래프와는 다르다
  • 원문 안의 불일치넷째 phase 와 「빈도, 심각도 가중」 에서 본문과 그림이 어긋나고(09장), 그림 트리에는 gateway 파일이 없다(05장)
  • 이 문서의 추론06장의 경계 이동 예측, 12장의 충돌 처리 제안, 15장의 사례, 16장과 21장의 시험 정답 수명 제안, 19~21장의 SDLC 대응과 「차이의 크기」 판단, 20장의 표본 재실행 제안은 이 문서의 것이고 원문에 없다
  • 사례의 성격Harvey, Decagon, KUPAS MASTER 는 자기 제품을 보고한 회사 글이라 Meta 와 같은 한계를 진다. PROCTOR 는 단일 저자의 재현할 수 없는 단일 실행 기록이고, TRACE 는 합성 trace 60개로 쟀다. FINSKILLOPS 의 사람 검토 경로는 비어 있었고 judge 일치도의 annotator 는 저자 그룹이다. EvoPathBench 는 시장 환경 한 종류다

한계를 걷어 내도 둘이 남는다. 첫째, 「agent 가 실은 자료로 맞는 결론에 이를 수 있었나」 라는 진단 질문은 Meta 의 숫자와 상관없이 옮겨 쓸 수 있다. TRACE 와 FINSKILLOPS 도 따로 같은 질문을 쓴다(10장). 둘째, 착지한 시험의 정답이 틀리거나 낡으면 회귀 gate 는 그 정답을 지키는 쪽으로 루프를 민다(16장). 운영에서는 PROCTOR 의 세금 규칙 삭제가, 실험에서는 반대 증거를 주어도 규칙을 고치는 효과가 유의하지 않았던 EvoPathBench 가 같은 방향을 가리킨다. Meta 의 「회귀 0건」 이 gate 덕분인지는 Meta 자료로 가릴 수 없다.

conclusion

결론: 교정을 diff 로 적을 수 있으면 루프가 붙고, 시험 정답의 수명은 따로 관리해야 한다

Meta 는 전문가의 교정을 진단과 최소 편집, 맥락 없는 리뷰, blind replay, 회귀 시험을 거친 텍스트 diff 를 PR 로 착지시키고, 그 사례를 다음 시험으로 만든다. playbook 의 곁 루프와 달리 진단이 있고 결정적 탐지는 없다.

자주 쓰는 판단은 의존을 적은 텍스트 파일에, 드문 자료는 RAG 에 둔다. 이 수명주기는 playbook 의 곁 루프와 같은 규율을 지식 자체에 적용했다(19장). 옮기려는 개발자가 처음 물을 것은 교정을 텍스트 diff 로 적을 수 있는가이고(18장), 적을 수 없으면 교정은 모호함 갈래로 빠진다. 루프를 붙이면 세 가지를 예상할 수 있다. 입장이 있는데 불리지 않아 생긴 교정은 triggers 나 routing index 같은 싣는 장치를 고친다(15장). frontmatter 로 이어지지 않은 두 파일의 모순은 세 검사를 모두 빠져나간다(12장). gate 가 얼마나 잘 거르는지는 회귀 suite 가 얼마나 넓은지와 정답이 얼마나 정확한지에 달렸다(13장).

가장 큰 빈 곳은 시험 정답의 수명이다. 지식의 폐기는 FINSKILLOPS 의 퇴역, OKF v0.2 의 deprecated 상태처럼 같은 시기 사례가 채우기 시작했지만, 착지한 정답이 틀렸거나 입장이 바뀌어 낡았을 때 그 시험을 고치는 절차는 Meta 에도, playbook 에도, 이번에 읽은 사례에도 없다(16장, 21장). 정답마다 기댄 position 판을 적는 장치는 직접 만들어야 한다. Meta 의 숫자는 세 sprint 동안의 자기 보고이고 token 감소 말고는 측정한 기준선이 없다(17장).
