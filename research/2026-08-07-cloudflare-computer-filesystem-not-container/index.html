Cloudflare computer: 에이전트에게 준 것은 컨테이너가 아니라 파일시스템이다

Cloudflare 가 2026년 8월 3일 공개한 @cloudflare/computer 는 에이전트에게 컴퓨터를 준다고 말한다. 저장소를 커밋 c7bdfcb 에서 열면 실제로 배포되는 것은 Durable Object 안의 SQLite 가상 파일시스템 하나와, 그 위에 갈아 끼우는 실행 백엔드 셋이다. 컨테이너는 그중 하나이고, 기본값 자리에서 내려왔다.

tl-dr

요약. 추상화의 경계가 샌드박스에서 파일시스템으로 내려왔다

기존 하네스는 에이전트 하나에 샌드박스 하나를 붙이는 것을 단위로 삼는다. computer 는 파일시스템을 단위로 삼고, 같은 파일에 대해 아이솔레이트와 컨테이너 중 어디서 명령을 돌릴지 호출마다 고른다. 그 선택은 모델이 한다. 정책 라우터는 없다.

실행 백엔드 3개 container-shell, worker-shell, worker-javascript. 블로그는 2개라고 쓴다
파일 청크 512 KiB sha256 콘텐츠 주소. packages/dofs/src/fs/writeFile.ts:25
패키지 버전 0.1.0-alpha.1 README 가 프로덕션 사용을 명시적으로 금지한다

Workspace 는 Durable Object 의 ctx.storage SQLite 위에 얹힌 가상 파일시스템이다. 여기가 유일한 진실이고, 실행 백엔드는 이 파일시스템을 보는 창이다. 컨테이너는 FUSE 로 마운트해서 보고, 아이솔레이트 셸은 Workers RPC 로 같은 SQLite 를 직접 읽고 쓴다.

그래서 workspace.fs.writeFile() 로 호스트에서 쓴 파일을 컨테이너 안 pandoc 이 평범한 파일로 읽는다. 두 실행 환경을 잇는 glue code 를 사용자가 짜지 않아도 된다. 이것이 이 패키지가 없앤 수작업이다.

대가는 백엔드마다 다르다. 파일시스템만 쓰면 Durable Object 하나로 되고, 아이솔레이트 백엔드는 Worker Loader 바인딩과 experimental 컴패터빌리티 플래그를 요구하며, 컨테이너 백엔드는 Cloudflare Containers 를 더 요구한다. 셋 다 Cloudflare 전용이다.

컴퓨터라는 이름이 가리키는 범위는 코드보다 넓다. 블로그는 실행 환경으로 아이솔레이트, 컨테이너, 웹 브라우저 셋을 들지만 브라우저 백엔드는 저장소에 없다. ⑪장 6번에서 검색 명령과 함께 다룬다.

problem

문제 정의. 에이전트마다 컨테이너를 하나씩 주면 대수가 모자란다

2026년 초의 기본형은 컨테이너를 띄우고 그 안에서 에이전트를 돌리는 것이었다. 최근 몇 달 사이 하네스는 루프와 실행을 갈라놓았다. 루프는 밖에서 돌고, 코드 실행만 샌드박스 도구로 넘긴다. Cloudflare 의 주장은 그 다음 단계에서 컨테이너 자체가 병목이 된다는 것이다.

across all the clouds, all the hyperscalers, there’s nowhere near enough compute in the world for every company to give each of their users’ agents their own containerized compute environment Matt Carey, Aron Carroll · Cloudflare Blog · 2026-08-03

컴퓨트 총량이 모자란다는 진술에는 수치 근거가 붙어 있지 않다. 블로그에도 저장소에도 이를 뒷받침하는 데이터가 없다. 아이솔레이트가 싸다는 것과 세계 컨테이너 총량이 부족하다는 것은 다른 주장이고, 이 문서가 확인할 수 있는 것은 앞의 것뿐이다.

architecture

구조. Durable Object 의 SQLite 가 파일시스템의 유일한 진실이다

Workspace 하나가 Durable Object 하나와 짝을 이룬다. 파일의 권위 있는 상태는 DO 의 SQLite 에 있고, 실행 백엔드는 그 상태를 각자의 방식으로 본다. 컨테이너는 FUSE 마운트로, 아이솔레이트 셸은 Workers RPC 로 본다. 백엔드가 하나도 없는 Workspace 도 만들 수 있고, 그때는 파일시스템만 남는다.

상태가 어디에 남는지는 백엔드마다 다르다. DO 쪽 SQLite 는 재시작을 넘겨 살아남는다. 컨테이너 쪽 VFS 는 프로세스 수명이라 컨테이너가 재시작하면 사라지고, 다음 push 가 DO 에서 다시 채운다. packages/computerd/README.md 가 이를 직접 적어 둔다. 디스크 영속성은 아직 없다.

저장 한도는 약 10GB 다. DO 스토리지를 파일시스템과 나눠 쓰기 때문이고, docs/README.md 가 모노레포 전체가 아니라 에이전트 규모의 작업 공간을 겨냥한 것이라고 명시한다.

이 그림은 백엔드가 하나씩 붙은 모습이다. Workspace 는 백엔드를 여러 개 등록할 수 있고, backend 를 생략하면 첫 번째로 등록된 것이 쓰인다. 그 선택을 권한 경계로 써도 되는지는 이 장이 다루지 않는다. ⑥장과 ⑪장 3번에 있다.

sync

동기화. 컨테이너로 건너가는 것은 파일이 아니라 512 KiB 청크의 해시 목록이다

컨테이너 백엔드를 고르면 트리가 두 벌이 된다. 두 벌을 맞추는 방식에 설계 문서 한 편이 통째로 붙어 있고(docs/02_sync_protocol.md, 551줄), git 의 haves/wants 협상을 그대로 가져왔다. 엔트리에는 바이트가 실리지 않는다. 해시만 보내고, 받는 쪽이 없다고 답한 청크만 뒤따라 보낸다.

node_modules 는 기본 ignore 다. 직접 목록을 넘기면 기본값을 확장하는 것이 아니라 대체하므로, 커스텀 목록에 node_modules 를 다시 넣지 않으면 npm install 결과가 통째로 wire 를 탄다. ignore 된 경로는 컨테이너 안에서는 정상으로 보이지만 Workspace.fs 에서는 stat 도 readFile 도 ENOENT 를 낸다.

routing

실행기 선택. 라우터가 없다. tool description 이 라우터다

어느 백엔드에서 명령을 돌릴지 결정하는 코드는 없다. createExecTool 은 백엔드 설명을 이어 붙여 tool description 문자열을 만들고, 그 안에 판단 기준을 자연어로 적어 모델에게 넘긴다. 모델이 backend 인자를 비우면 기본값이 쓰인다.

저장소가 이 메커니즘에 경고를 붙여 두었다. docs/05_runtime_interface.md:89 와 docs/18_runtime_migration.md:23 이 백엔드 선택은 라우팅이지 authorization 이 아니라고 쓴다. 공개 게이트웨이는 호스트가 가진 allowlist 에서 골라야 한다. 완화 요인은 packages/computer/src/tools/exec.ts:163 의 z.enum(backendIds) 로, 모델은 호스트가 등록한 id 중에서만 고른다. 임의 문자열을 넣지는 못한다.

이 문장이 얼마나 잘 먹히는지는 코드로 알 수 없다. 블로그는 frontier 모델이 판단을 아주 잘한다고 쓰지만, 라우팅 정확도를 재는 평가는 저장소에 없다. grep -rniE "accuracy|success rate|correct backend" --include='*.ts' --include='*.md' packages examples docs 에서 생성 파일 worker-configuration.d.ts 를 빼면 0건이다.

compare

비교. 같은 문제를 sandbox-sdk 는 컨테이너 한 대로 푼다

Cloudflare 위에서 에이전트에게 실행 환경을 주는 기존 방법은 @cloudflare/sandbox 다. 컨테이너를 하나 띄우고 그 안에서 명령을 돌린다. 저장소 안에 두 방식을 같은 과제로 나란히 돌리는 예제가 있어서, 무엇을 비교 대상으로 보는지가 코드에 드러나 있다.

examples/think-compare-runtimes 는 같은 Think 에이전트를 workspace 런타임과 sandbox 런타임 양쪽에 붙여 동일한 과제를 돌린다. 과제는 문서 작성이다. 기능 브리프와 스타일 가이드를 읽고 새 문서 페이지를 쓰고 네비게이션과 README 를 고친 다음 검증 명령을 돌리는, 파일 조작과 명령 실행이 섞인 작업이다.

이 예제에는 결과 수치가 없다. 두 실행을 UI 에 나란히 흘려 줄 뿐이고, 승패나 소요 시간을 기록하는 코드는 worker/ 에 없다. grep -rniE "duration|elapsed|winner|score" examples/think-compare-runtimes/worker examples/think-compare-runtimes/shared 는 9건인데 7건이 컨테이너 풀 타임아웃이고, 나머지 둘은 테스트 fixture 의 duration 필드다(worker/runtime/adapter.test.ts:75, worker/runtime/sandbox.test.ts:63). 프로덕션 어댑터는 이 필드를 쓰지 않는다. 위 표에서 성능과 관련된 칸은 ⑩장의 파일시스템 벤치마크에서 온 것이지, 이 예제에서 온 것이 아니다.

trace

추적. exec 한 번은 아이솔레이트를 왕복하고 SQLite 로 돌아온다

모델이 exec({ command: "git status", backend: "worker-shell" }) 를 호출했을 때 packages/computer 안에서 벌어지는 일을 따라간다. 패키지 경계를 넘지 않는 경로만 골랐다. 컨테이너 백엔드는 capnweb 으로 다른 패키지에 들어가므로 여기서 제외했다.

여기까지는 코드가 무엇을 담고 있는지다. 실제로 돌려서 확인한 것은 아니다. packages/computer/src/backends/worker-shell/ 에 테스트 파일 일곱 개가 있고 entrypoint.test.ts 가 543줄이지만, 이 문서는 테스트를 실행하지 않았다.

result-fs

성능. metadata 작업은 컨테이너 디스크보다 빠르고, 큰 파일 순차 I/O 는 최대 43배 느리다

느린 쪽의 원인을 문서가 직접 적는다. 쓰기 경로가 FUSE release() 마다 512 KiB 청크를 콘텐츠 주소 저장소로 해싱하기 때문이다. 이것은 ⑤장에서 본 증분 동기화와 중복 제거를 사는 대가이고, dd 류 처리량 수치에 그대로 나타난다.

빠른 쪽의 원인도 같은 문서에 있다. docs/19_performance.md:53 이 in-memory inode store 라고 쓴다. 디스크를 이긴 것이 아니라 RAM 이 디스크를 이긴 것이고, 그래서 조건이 붙는다. 벤치 인스턴스는 메모리 6 GiB 짜리 standard-2 이고, packages/computerd/README.md:43 은 컨테이너 쪽 VFS 에 디스크 영속성이 없다고 쓴다. 작업 트리가 컨테이너 메모리에 다 올라가는 동안만 이 수치다.

비율 열은 원문 표에서 그대로 옮긴 값인데, 같은 행의 두 ms 를 나눈 값과 맞지 않는 행이 14개 중 7개다. find 트리는 1813.6 / 4404.2 = 0.41 인데 원문 비율은 0.72x 이고, read 64 MiB 는 17.1 인데 39.72x 다. 같은 표의 tmpfs 비율 열은 자기 ms 와 맞는다. 어긋난 것은 원문의 disk ratio 열이고 원인은 알 수 없다. 헤드라인의 43배도 이 열의 값이라 같은 단서가 붙는다.

저장소 자체 측정이다. 인스턴스 한 대, 반복 3회이고 신뢰구간이 없다. 재현 스크립트 script/run-fs-bench.sh 가 있지만 이 문서는 돌려 보지 않았다. 원문 fs-bench 표의 시나리오 14개를 하나도 빼지 않고 옮겼다. 승리는 7개다. 원문 docs/19_performance.md:53 은 여덟 개라고 쓰면서 이름은 일곱 개만 든다. 그 일곱 중 npm init + 소규모 install 은 metadata 작업으로 보기 어려워서, 승리가 전부 metadata 라는 원문의 정리도 그대로 받기는 어렵다.

critique

한계. 동시 쓰기가 조용히 지워지고, 문서가 코드보다 뒤처진 자리가 있다

아래 여섯 가지 중 앞의 넷은 저장소가 스스로 적어 둔 것이고, 다섯째와 여섯째는 코드와 문서를 대조해서 나온 것이다. 도입 판단이 걸리는 항목만 골랐고, 문서 전체가 코드와 맞는지 훑지는 않았다.

  • 01컨테이너 둘이 같은 파일을 쓰면 나중에 도착한 push 가 이긴다. 오류도 경고도 없다. docs/02_sync_protocol.md 가 이를 잠금 없는 NFS 마운트나 조건부 PUT 없는 S3 버킷과 같은 의미라고 적는다. 에이전트 둘이 PLAN.md 를 공유하는 패턴은 지금 데이터를 잃는다. 저장소의 권고는 워크스페이스당 활성 writer 하나, 또는 네임스페이스 분할이다.
  • 02computerd 의 WebSocket 엔드포인트에 인증이 없다. 포트에 닿을 수 있으면 붙는다. docs/07_injected_service.md 의 open questions 가 이를 적고, Cloudflare Containers 에서는 해당 DO 만 포트에 닿을 수 있어 안전하지만 노출 범위가 넓은 provider 를 지원하는 순간 핸드셰이크에 auth 단계가 필요하다고 덧붙인다. 같은 절이 computerd 가 보통 root 로 돈다는 것도 적어 둔다.
  • 03동기화 프로토콜에 버전 협상이 없다. 요청과 응답 모양을 바꾸면 하드 wire break 라서 DO 와 computerd 를 한 쌍으로 같이 배포해야 한다. 이미지 태그를 따로 관리하는 배포 파이프라인이라면 이 제약이 먼저 걸린다.
  • 04Durable Object 는 아직 hibernate 하지 않는다. docs/11_lifecycle.md 가 오늘 코드는 ctx.acceptWebSocket() 이 아니라 server.accept() 를 쓴다고 밝힌다. 유휴 에이전트가 자원을 놓는다는 그림은 문서의 의도이고 오늘의 동작이 아니다.
  • 05백엔드 선택은 권한 경계가 아니다. docs/05_runtime_interface.md:89 와 docs/18_runtime_migration.md:23 이 라우팅과 authorization 을 구분하라고 쓴다. container-shell 을 등록해 두면 바깥 네트워크가 붙은 백엔드를 호출마다 모델이 고를 수 있다. 모델은 z.enum 으로 호스트가 등록한 id 중에서만 고르므로 임의 문자열은 아니지만, 어떤 id 를 등록해 두었는지가 곧 권한이다.
  • 06mount 는 미구현이라고 적혀 있지만 코드에 있다. docs/01_vfs.md 는 mount 서브시스템이 Workspace 에 배선되지 않았고 EROFS 를 던지는 프로덕션 호출부가 없다고 쓴다. 실제로는 packages/computer/src/mounts/ 에 인덱서와 R2 provider 가 있고, src/index.ts:37 이 R2Bucket 을 export 하며, packages/dofs/src/fs/mount-guard.ts:67 이 EROFS 를 던진다. examples/worker-shell 은 이미 R2 버킷을 /workspace/r2 에 읽기 전용으로 마운트한다. 문서가 앞서간다는 경고문과 반대 방향으로 뒤처진 자리다. .github/workflows/ci.yml 의 paths-ignore 가 docs/** 와 **/*.md 를 통째로 건너뛰므로 이 어긋남은 CI 가 잡지 못한다.
  • 07브라우저 백엔드는 저장소에 없다. 블로그는 코드가 아이솔레이트, 컨테이너 샌드박스, 웹 브라우저 중 어디서 도는지를 플랫폼이 처리한다고 쓰지만, 저장소에서 브라우저 런타임을 찾을 수 없다. grep -rniE "browser(-| )?(backend|runtime)|BrowserBackend" --include='*.ts' --include='*.md' packages examples docs 는 0건이다. 브라우저는 Cloudflare 의 다른 제품(Browser Rendering)이고, 이 패키지의 실행 백엔드 목록에는 없다.

읽기만으로 확인할 수 없는 것도 남는다. 모델이 실제로 싼 백엔드를 얼마나 자주 고르는지, FUSE 마운트가 실제 커널에서 어떻게 동작하는지, 동기화가 부하에서 수렴하는지는 코드에 답이 없다. 그래도 옮겨 쓸 수 있는 것이 있다. 청크 해시와 haves/wants 협상은 vendor 종속이 아니고, 실행기 선택을 tool description 에 자연어로 적고 실패 시 재시도를 지시하는 방식도 어느 하네스에서나 그대로 쓸 수 있다.

이 저장소의 성격은 네 가지 파일에서 드러난다. MIT 로 열어 두고, 요청 없는 PR 을 자동으로 닫고, 문서를 forward-looking spec 이라고 못 박고, 저장소가 자기 에이전트를 위한 .agents/skills/ 를 여섯 개 갖고 있다. 커뮤니티 프로젝트가 아니라 대규모로 에이전트를 돌리는 고객과 함께 배우려고 연 실험이라는 블로그의 진술과 어긋나지 않는다.

두 줄 수는 git ls-tree -r --name-only HEAD packages 로 뽑은 목록에 /src/ 필터를 걸고, 거기서 테스트 파일을 빼거나 남기는 두 가지로 센 값이라 범위가 같다. 지금 시작할 값어치가 있는 조합은 좁다. 파일 조작과 git 이 작업의 대부분이고, 컨테이너가 필요한 명령이 가끔이며, 에이전트가 죽은 뒤에도 작업 트리가 남아야 하는 경우다. 큰 파일을 계속 읽고 쓰는 작업이라면 ⑩장의 비율이 먼저 문제가 된다.

conclusion

결론. 이 프로젝트의 주장은 컨테이너가 비싸다가 아니라 실행 환경이 파일시스템보다 작은 단위여야 한다는 것이다

에이전트에게 컴퓨터를 준다는 말을 코드로 옮기면 파일시스템 하나에 실행기 여러 개가 된다. 파일시스템은 에이전트 수명과 함께 가고, 실행기는 명령 하나 수명이다. 이 분리가 이 저장소에서 가장 옮겨 쓸 만한 부분이다.

기계적으로 새로운 것

DO 의 SQLite 를 파일시스템의 권위 있는 상태로 놓고, 컨테이너를 그 상태의 FUSE 미러로 강등한 것. 컨테이너가 죽어도 작업 트리가 남는다는 결과가 여기서 나온다.

개념적으로 새로운 것

실행 환경 선택을 정책 코드에서 tool description 으로 옮긴 것. 설계 의도와 그 대가는 ⑥장에 있다.

아직 아닌 것

동시 쓰기 안전성, RPC 인증, DO hibernation, 백엔드 선택의 권한 경계, 브라우저 백엔드. 앞의 넷은 저장소가 스스로 적었고 마지막은 블로그에만 있다.

블로그가 내건 목표는 작업의 10% 미만에서만 컨테이너가 필요한 런타임이다. 오늘 코드가 그 목표에 얼마나 다가갔는지를 재는 장치는 저장소에 없다. 확인할 수 있는 것은 목표를 향한 구조가 실제로 만들어져 있다는 것까지다. 파일시스템은 하나고, 백엔드는 셋이고, 선택 지점은 호출마다 열려 있다.

읽은 것은 코드와 문서다. 렌더링된 페이지는 headless chromium 으로 밝은 테마와 어두운 테마 양쪽에서 확인했다. 벤치마크는 재현하지 않았다. ⑩장 수치와 ⑪장 1번 항목은 저장소가 스스로 밝힌 내용을 옮긴 것이지 독립적으로 측정한 값이 아니다.
