index

teamai-cli가 팀의 agent 설정을 PR 리뷰 하나로 묶는 방식과 그에 맞춘 팀 workflow

teamai-cli는 팀의 skill, rule, hook, MCP 설정을 git 저장소 하나에 두고 각자의 AI coding 도구에 도구별 형식으로 써 넣는 CLI다. 바꾸는 사람은 branch와 PR로 올리고 리뷰어가 merge하면, 다른 팀원은 다음 세션을 열 때 hook이 받아 온다. 그래서 팀 저장소의 PR 리뷰가 모든 팀원 agent의 동작을 바꾸는 관문이 된다. 세션에서 배운 learnings는 이 관문을 거치지 않고 별도 branch로 바로 올라가므로, 프로덕션 팀은 두 경로마다 검토할 사람을 따로 정해야 한다. merge된 hook과 MCP도 기본값에서는 확인 없이 설치되므로 꺼진 안전 설정을 켠다.

tl-dr

들이기 전에 알아 둘 것

팀 저장소에 merge된 것은 별도 확인 없이 모든 팀원의 agent에 닿는다. 팀이 새로 맡을 일은 그 merge를 누가 어떤 기준으로 하는지 정하고, 기본값으로 꺼진 안전 설정을 켜는 것이다.

  • 1변경은 teamai push가 만든 PR을 리뷰어가 merge할 때 팀에 들어가고, 팀원은 다음 세션 시작 때 받는다. 지금 열린 세션은 바뀌지 않을 수 있다 (올리는 길과 받는 길).
  • 2pull은 팀원이 고친 사본을 덮어쓰지 않는다. 고친 사람에게는 팀의 다음 수정이 닿지 않으므로 teamai status로 어긋남을 주기적으로 본다 (사본 규칙, 사례).
  • 3role을 정하지 않은 팀원은 모든 namespace를 받는다. 배포 범위를 나누려면 모든 팀원이 role을 정했는지부터 확인한다 (배포 범위).
  • 4learnings는 PR 없이 teamai-learnings branch에 올라가고 recall로 다른 agent에게 읽힌다. 이 경로의 검토자와 정리 주기를 팀이 정한다 (learnings 경로).
  • 5team hook과 MCP server는 기본값에서 다음 pull 때 바로 설치된다. autoApply: false, requireTeamScripts, MCP allowlist를 팀 저장소를 만들 때 정한다 (실행 조건).
  • 6사람별 개입 횟수와 token 사용량이 기본으로 팀 저장소에 쌓인다. 켜 둘지와 어디에 쓸지를 팀이 먼저 합의한다 (사용 기록).
  • 7CLI는 팀원끼리 버전을 맞춰 주지 않는다. 팀 저장소 형식을 바꾸는 기능은 모두가 업그레이드한 뒤에 쓴다 (성립하지 않는 곳).

역할 분담, 리뷰, 권한, 공유 컨텍스트별로 바꿀 일은 팀 workflow 장에 표로 모았고, 저장소에 근거가 없는 항목은 그렇게 표시했다.

problem

팀원마다 흩어지던 agent 설정

팀이 agent 도구를 여럿 쓰면 skill, rule, MCP, hook을 사람마다 도구마다 손으로 맞춰야 한다. teamai-cli는 그 원본을 팀 git 저장소 하나에 두고, 도구마다 다른 파일 형식과 위치로 바꿔 써 넣는 일을 맡는다.

README는 teamai-cli를 팀의 skill, rule, agent, learnings, model, MCP 같은 AI 자산을 git 저장소에서 관리하는 도구라고 소개한다. 같은 내용이라도 도구마다 받는 형식이 달라서, 예를 들어 팀 agent 하나가 Codex에는 .toml, Copilot에는 .agent.md, Kiro에는 .json, 나머지에는 .md로 써진다. 팀 문화를 적은 culture.md도 Claude Code에서는 .claude/rules/teamai-context.md로, Codex에서는 세션 시작 hook으로 들어간다.

팀 저장소의 자리담는 것팀원에게 닿는 방식

hooks/hooks.yaml, mcp/mcp.yaml팀 hook, MCP server각 도구의 설정 파일에 주입
env/env.yaml, env/secrets.yaml환경 변수, secret의 이름과 설명shell profile 블록과 teamai env exec. secret 값은 저장소에 없다
models/models.yamlmodel gateway 목록teamai models switch로 도구 설정에
learnings/, teamwiki/세션에서 배운 것, 코드 지식 그래프teamai recall로 검색 (beta, 기본 꺼짐)

README의 지원 표는 Claude Code, Codex, Cursor, CodeBuddy, GitHub Copilot CLI, OpenCode, Kiro 등 20개 도구를 열두 가지 자산 항목에 대해 표시한다. 도구마다 빠진 칸이 있어서, 예를 들어 Trae는 agents와 hooks 칸이 비어 있다. 쓰는 도구의 칸부터 확인한다.

mechanism-loop

올리는 길과 받는 길

변경은 teamai push가 만든 branch와 PR을 리뷰어가 기본 branch에 merge할 때 팀에 들어간다. 다른 팀원은 agent 세션을 열 때 SessionStart hook이 띄우는 teamai pull로 받으므로, merge된 변경은 대개 그다음 세션부터 보인다.

올리는 길에서 teamai push는 사용자 이름과 초 단위 시각으로 branch를 만들고, provider의 API로 기본 branch를 향한 PR을 연다. teamai.yaml의 reviewers가 있으면 그 사람들을 PR 리뷰어로 넣는다. 저장소 문서는 팀원이 branch를 올리고 PR을 열 수 있게 하되 기본 branch는 보호해 두라고 전제한다. 이 보호 설정은 git host에서 하는 일이라 teamai-cli가 확인하지는 않는다.

받는 길은 teamai init이 설치하는 기본 hook에서 시작한다. SessionStart의 pull은 background로 돌고 120초까지 기다리며, 세션 시작을 붙잡지 않는다. 그래서 rule과 MCP를 SessionStart hook보다 먼저 한 번 읽는 도구는 새로 받은 것을 그다음 세션에서야 본다고 CHANGELOG가 밝힌다. 오늘 merge한 rule이 지금 일하는 팀원의 agent에 바로 걸린다고 기대하면 안 되는 이유다.

기본 hook 이벤트하는 일
SessionStart팀 자원 pull, 세션 시작 기록, 최근 7일 안에 merge된 MR 알림, 팀 env 안내
PostToolUseskill 사용 기록
UserPromptSubmitprompt 기록 (교정 여부를 세는 데 쓴다)
StopCLI 업데이트 확인, 세션 종료 기록, learnings 공유 제안

delivery

pull이 팀원의 사본을 다루는 규칙

pull은 팀원이 고친 사본을 남겨 두고, 지운 사본은 다시 써 넣는다. 그래서 rule 하나를 손본 팀원에게는 그 뒤 팀이 그 rule을 고쳐도 새 버전이 가지 않고 경고 한 줄만 남는다.

pull은 자기가 마지막으로 쓴 파일의 hash를 checkout마다 기록해 둔다. 다음 pull에서 디스크의 파일을 그 기록과 비교해, 기록과도 다르고 지금 쓸 팀 버전과도 다를 때만 팀원이 고친 것으로 본다. 판정은 아래 표대로 갈린다.

팀원 쪽 파일 상태pull이 하는 일팀원에게 보이는 것
받은 그대로새 팀 버전으로 덮어쓴다없음
지웠다다시 써 넣는다없음. 지우는 것이 팀 버전으로 돌아가는 방법이다
고쳤고 팀 버전은 그대로남겨 둔다info 한 줄. push로 공유하거나 지우고 pull --force
고쳤고 팀 버전도 바뀜남겨 둔다warn 한 줄. 팀 변경을 직접 합친 뒤 push하라는 안내
기록이 없고 teamai가 쓴 것인지 증명할 수 없음쓰지도 지우지도 않는다warn 한 줄
팀 저장소에서 그 파일이 지워짐 (revert 포함)받은 그대로면 지운다. 팀원이 고친 사본과 팀원 저장소가 git으로 추적하는 사본은 남긴다남긴 경우 warn 한 줄

남겨 둔 사본을 가진 팀원이 teamai push를 하면, push는 팀 버전이 그사이 바뀌었으니 합치지 않으면 그 변경을 덮어쓴다고 경고한다. 경고에서 멈추고 PR은 리뷰어 앞으로 가므로, 이 경우를 걸러 내는 마지막 자리는 PR 리뷰다.

문서는 teamai.yaml의 sharing.rules.enforced에 넣은 rule을 팀원이 지울 수 없다고 설명한다. 이 커밋의 코드에서 enforced는 설정 schema에만 있고 그 값을 읽는 코드는 찾지 못했다. 지운 rule이 돌아오는 것은 위 표의 일반 규칙 덕분이고, 고친 rule이 그대로 남는 것도 enforced 여부와 상관없다. 보안 rule처럼 팀원이 바꾸면 안 되는 내용은 로컬 수정으로도 무력해질 수 있다는 전제로 운영한다.

case

보안 rule을 고친 날의 세 팀원

같은 merge 하나가 팀원 셋에게 서로 다르게 닿는다. 세션을 이미 연 사람은 다음 세션부터, rule을 손본 적이 있는 사람은 자기 사본을 지우기 전까지 받지 못하고, role이 없는 사람은 다른 팀의 namespace까지 받는다.

팀 저장소의 rules/backend/secrets.md를 고치는 PR이 오전 10시에 merge되었다고 하자. manifest/roles.yaml에는 backend와 frontend role이 있고, 원 자료에 없는 가상의 상황이다. 앞 장들의 규칙만으로 결과를 따라가면 이렇다.

  현재 세션   rule을 SessionStart 전에 읽는 도구라면 옛 내용 그대로

distribution

role과 project로 나누는 배포 범위

namespace 디렉터리에 둔 자산은 그 namespace를 선언한 role이나 project의 팀원에게만 간다. role을 정하지 않은 팀원은 필터 없이 전부 받으므로, 범위 제한을 쓰려면 모든 팀원의 role 설정이 먼저다.

role은 사람의 직무(frontend, backend)이고 project는 지금 일하는 서비스다. manifest/roles.yaml과 manifest/projects.yaml이 각자 받을 namespace를 적는다. 예를 들어 checkout project를 선언한 디렉터리는 rules/checkout/, skills/checkout/, hooks/checkout/hooks.yaml, mcp/checkout/mcp.yaml까지 받고, 같은 이름의 root 항목은 namespace 쪽으로 바뀐다. namespace 밖, 곧 root에 둔 파일은 모두에게 간다.

# manifest/roles.yaml
roles:
  - id: frontend
    resources:
      knowledge: [common, frontend]   # rules/<ns>/, claudemd/<ns>/
      skills: [common, frontend]
      agents: [common, frontend]
  • role 없음필터가 걸리지 않아 모든 namespace를 받는다. teamai init은 새 팀원에게 role을 고르게 하지만, manifest보다 먼저 들어온 팀원은 teamai roles set을 한 번 해야 한다
  • tag범위를 좁히지 않는다. 구독하면 그 tag가 붙은 skill과 rule이 더해질 뿐이다
  • workspace안에 있는 저장소들이 선택한 것까지 받는다. 같은 이름인데 내용이 다른 항목은 보류하고 이름을 알린다

이 구조가 팀의 역할 분담을 저장소 디렉터리에 옮겨 놓는다. 누가 어떤 namespace의 주인인지 정해 두면, 리뷰어 지정과 변경 범위가 함께 정리된다. 다만 namespace별 리뷰어를 강제하는 기능은 teamai-cli에 없고, git host의 CODEOWNERS 같은 장치로 따로 거는 일이다 (저장소에 근거가 없는 제안이다).

첨언: 원문

docs/guide/distribution.md:182 “Namespaces only filter for members who have set a role: a member with no `primaryRole` syncs everything”, 193행 “Tags never restrict: a subscription only adds matching tagged skills.” 문서는 role 을 정하지 않은 팀원에게 role 확인을 요청하는 rule 을 enforced 로 두라고 권하는데, enforced 가 코드에서 하는 일은 사본 규칙 장에 적었다.

learning-loop

리뷰를 거치지 않는 learnings 경로

세션에서 배운 것은 PR 없이 teamai-learnings branch에 바로 올라가고, recall을 켠 팀원의 agent가 작업 전에 찾아 읽는다. 실행 자산과 달리 올라가는 내용을 사람이 검토하는 지점이 없으므로, 이 경로를 쓰려면 검토자와 정리 주기를 팀이 정한다.

Stop hook은 세션의 마찰을 점수로 센다. 사용자의 중단, tool 거부, 교정이 각각 20점이고 기준이 20점이라 셋 중 하나만 있어도 넘는다. 다만 tool call이 15번 미만인 세션에는 점수와 상관없이 제안하지 않는다. 그래서 tool call 12번에 거부가 세 번 나온 짧은 세션은 조용히 끝나고, tool call 20번에 교정 한 번이 있던 세션은 공유 제안을 받는다. 마찰이 없어도 닿는 길이 하나 더 있다. 그 세션의 recall이 하나도 맞지 않았으면 20점, 맞았지만 최고 점수가 낮으면 10점을 더한다. 그래서 recall을 켠 팀에서는 tool call 30번에 마찰 없이 recall 결과만 0건이었던 세션도 공유 제안을 받는다. recall을 켜는 결정이 learnings가 올라오는 빈도까지 바꾸는 셈이다.

제안은 사용자에게 /teamai share를 실행해 보라고 권하는 문장이다. Claude Code는 Stop hook 출력을 화면에 바로 보여 주고, 그 출력을 버리는 도구에서는 다음 prompt 때 model에게 사용자에게 전하라고 넘긴다. 사용자가 실행하면 share skill이 sub-agent로 세션을 요약하고 teamai contribute로 올린다. skill에는 올리기 전에 요약을 사용자에게 보여 주는 단계가 없어서, 공유를 시작한 사람도 본문을 읽지 않은 채 올라갈 수 있다. 이 문서는 PR 없이 teamai-learnings orphan branch에 commit된다. 코드 주석은 그 이유를 보호된 기본 branch에 쓰기 권한이 없어도 기여할 수 있게 하려는 것이라고 설명한다. 이 경로에서 본문의 secret을 지우는 처리는 찾지 못했으므로, 요약에 token이나 내부 주소가 섞이면 그대로 팀 저장소에 남는다. share skill은 요약을 간체 중국어로 쓰라고 지시하므로, 한국어로 일하는 팀이라면 recall 결과의 언어부터 확인한다.

  • 0.90promote 후보가 되는 최소 confidence. recall에 걸린 횟수, upvote 수, 마지막 recall 이후 지난 날수로 계산한다
  • 5 / 2최소 upvote 5번, 서로 다른 사용자 2명
  • 14일learning이 쓰인 뒤 지나야 하는 최소 기간

recall은 기본으로 꺼져 있고, 꺼져 있으면 share skill도 그 사실을 알리고 멈춘다. 팀이 recall을 켜는 순간부터 리뷰되지 않은 문서가 다른 팀원 agent의 작업 앞에 놓이므로, 켜는 결정과 정리 담당을 함께 정하는 편이 맞다. teamai recall maintenance --prune은 confidence 0.15 아래 문서를 지우거나 --archive로 치운다.

guardrails

hook과 MCP가 팀원 기계에서 실행되는 조건

기본 설정에서는 merge된 team hook과 MCP server가 다음 pull에서 팀원의 확인 없이 설치된다. 실행 범위를 좁히는 설정은 모두 기본값이 꺼져 있어서, 프로덕션 팀은 팀 저장소를 만들 때 직접 켠다.

team hook은 agent 도구의 이벤트(tool call 전후, 세션 시작 등)에 맞춰 팀원의 shell에서 실행되는 명령이다. hooks/hooks.yaml에 한 줄을 더한 PR이 merge되면, 기본값에서는 다음 세션의 pull이 그 명령을 모든 팀원의 도구 설정에 넣는다. 그래서 팀 저장소의 PR 리뷰는 문서 리뷰보다 코드 리뷰에 가까운 기준으로 해야 한다.

설정기본값바꾸면
sharing.hooks.autoApplytruefalse면 pull은 대기 중인 hook 수만 알리고, 팀원이 teamai hooks inject를 해야 설치된다
sharing.hooks.requireTeamScriptsfalsetrue면 명령이 ~/.teamai/team-scripts/ 아래 script가 아닌 hook은 건너뛴다
sharing.mcp.autoApplytruefalse면 teamai mcp inject를 해야 설치된다
sharing.mcp.allowedCommands, allowedHosts빈 목록, 곧 제한 없음목록 밖의 stdio 명령과 host를 거부한다
TEAMAI_HOOKS_DISABLED=1없음그 기계에서만 team hook을 모두 끈다

설치할 hook 명령 목록은 pull이 silent가 아닐 때만 출력되고, 세션 시작 pull은 silent로 돈다. autoApply를 켜 둔 팀에서는 팀원이 새 hook의 존재를 모른 채 실행하게 되므로, 위 설정 중 하나는 켜 두는 편이 맞다. teamai.yaml의 scripts(preInit, postPull 등)도 pull 중에 팀원 기계에서 Node로 실행되고, 실패해도 pull은 실패하지 않는다.

secret 값은 저장소에 들어가지 않는다. 팀 저장소에는 이름과 설명만 두고, 값은 각자 teamai env set으로 넣는다. 세션 시작 hook은 agent에게 secret 값을 묻거나 읽거나 출력하지 말라는 문장을 context로 넣는데, 이것은 model에 대한 지시이고 파일 접근을 막는 장치는 아니다.

reporting

dogfood

teamai-cli 저장소가 자기 agent에게 거는 규칙

teamai-cli 저장소의 AGENTS.md는 agent가 코드를 바꿀 때 worktree를 쓰고, 동작이 바뀐 PR에는 실제 CLI 실행 기록을 붙이고, 리뷰 지적에는 근거에 따라 심각도를 매기라고 정한다. teamai-cli가 사용자 팀에 강제하는 것은 아니지만, 팀 저장소의 rule을 쓸 때 옮겨 올 만한 실례다.

  • 격리코드를 바꾸기 전에 worktree에 들어가고 main 작업 디렉터리는 고치지 않는다
  • 검증runtime 동작이 바뀐 PR은 build 뒤 실제 CLI로 끝까지 돌려 본 기록을 PR에 붙인다. type check와 unit test만으로는 부족하다고 적었다. 대표 실행 하나면 된다
  • 리뷰 등급실행 기록이 없는 PR은 [P1 blocking]이다. P1 지적은 구체적인 실패 상황이나 어긴 규칙을 대야 하고, 둘 다 없으면 P2 이하로 내린다
  • 범위바뀐 줄마다 PR 목표로 거슬러 올라갈 수 있어야 하고, 관계없는 수정은 지적한다
  • 자기 리뷰push 전에 마지막 변경이 아니라 branch 전체 diff를 보고, 공유 상태마다 읽는 쪽과 쓰는 쪽을 모두 적는다
  • agent 문서skill-data/는 agent가 실제로 읽는 글이라 문서처럼 다루고, 동작이 바뀌면 함께 고친다

이 규칙들은 리뷰하는 agent와 사람이 같은 기준을 쓰게 만든다. 팀 저장소에 code-reviewer agent와 rule을 올릴 때 이 형식을 빌리면, 리뷰 지적의 무게가 사람마다 달라지는 문제를 줄일 수 있다.

지금까지의 흐름은 SessionStart hook이 있는 도구, PR을 여는 provider, 팀원 모두 같은 CLI 버전을 전제로 한다. 셋 중 하나가 빠지면 변경이 늦게 닿거나 사람이 손으로 이어 줘야 한다.

  • hook 없음세션 시작 hook이 없는 도구는 팀원이 직접 teamai pull을 해야 받는다. README 지원 표에서 hooks 칸이 빈 도구(Trae, JoyCode 등)를 쓰는 팀원이 여기에 든다
  • provider git--provider git으로 init한 기계에서 push는 branch만 올리고 PR은 사람이 git host에서 연다. teamai review --branch가 그 branch를 읽기 전용으로 검사한다
  • --httpgit 없이 HTTP backend에서 받는 팀원은 읽기 전용이라 push 경로가 없다
  • 버전 차이옛 CLI는 새 형식을 모른 채 쓴다. CHANGELOG는 옛 버전이 공유 AGENTS.md에 블록을 다시 써 넣거나, model alias를 실제 model 이름으로 바꿔 push할 수 있다고 적었다

이 경계를 넘는 팀원이 있다면 teamai-cli가 자동으로 해 주던 일을 사람이 대신해야 한다. 도입 전에 팀이 쓰는 도구를 README 지원 표와 맞춰 보고, hook이 없는 도구를 쓰는 사람에게는 pull을 습관으로 정해 주는 편이 낫다.

critique

코드를 읽어서 알 수 있는 것의 한계

모든 동작은 고정한 커밋의 코드와 문서를 읽고 정리한 것이고 CLI를 실행하지 않았다. 도입 전에 시험용 팀 저장소 하나로 사례 장의 세 팀원 상황을 직접 재현해 보면 위 설명이 실제와 맞는지 바로 확인할 수 있다.

  • 실행 안 함hook 출력이 각 도구 화면에 어떻게 보이는지, background pull이 도구의 rule 읽기보다 먼저 끝나는지는 실행해야 안다
  • 문서와 코드sharing.rules.enforced는 문서가 약속한 동작을 하는 코드를 찾지 못했다. 다른 경로에서 읽는다면 test 디렉터리에 단서가 있을 텐데 열지 않았다
  • promotepromote가 새로 쓴 파일이 기본 branch로 가는 길은 추론이다. 명령이 publish하는 파일은 표시 하나만 확인했다
  • providerreviewers를 PR에 넣는 동작은 provider마다 구현이 다른데, 공통 interface만 읽었다
  • 지원 표README의 20개 도구 지원 표는 maintainer가 적은 것이고 도구별로 확인하지 않았다
  • 이력shallow clone이라 개발 속도, 기여자 분포, 릴리스 주기는 다루지 않았다. CHANGELOG에는 날짜가 붙은 릴리스가 있다

팀 workflow 장의 권고 가운데 근거 열에 저장소에 근거가 없다고 적은 항목은 저자가 덧붙인 판단이다. 특히 사람별 사용 기록을 평가에 쓰지 말라는 권고와 CODEOWNERS 제안은 teamai-cli 문서 어디에도 없다.

setup

읽은 커밋과 열지 않은 디렉터리

Tencent/teamai-cli 커밋 db0cb20의 파일 1,155개 중 약 50개를 열었다. test, codebase 지식 그래프, 세션 이전, dashboard, provider별 구현은 열지 않아서 그 기능은 다루지 않았다.

README의 대표 그림(assets/use-cases.png)은 도입 전후를 여덟 장면으로 보여 주는 일러스트라 옮기지 않았다. 메커니즘 그림은 docs/product-overview.md 의 두 줄 흐름을 코드로 채워 다시 그렸다.

첨언: 읽은 파일과 열지 않은 파일

읽은 것은 AGENTS.md, README.md, CHANGELOG.md, docs/product-overview.md, docs/guide 의 배포, 공유, 팀 문화, 팀원 안내, workflow, reference, knowledge, reporting 문서, skill-data 의 core와 share skill, 그리고 src 에서 push, pull hook, 사본 판정, hook 안전 설정, learnings 공유와 promote, workflow local driver, review branch 검사 경로다. 큰 파일은 해당 함수만 읽었다.

열지 않은 곳과 그 비용은 이렇다. src/__tests__(648개)를 열지 않아 각 동작이 test로 덮이는지 모르고, enforced 문제도 test에서 확인하지 못했다. src/wiki-engine, src/session-flow, src/dashboard, skill-data/wiki를 열지 않아 teamwiki와 세션 이전은 문제 장의 표에 이름만 있다. src/providers는 공통 interface만 읽어 provider별 PR 동작은 다루지 않았다. src/models, src/pkg, 나머지 src 최상위 파일 대부분, docs/designs(두 개 제외), docs/dev, 중국어와 다른 언어 문서, .github, scripts, examples의 일부는 열지 않았다. shallow clone이라 커밋 이력은 보지 않았다.
