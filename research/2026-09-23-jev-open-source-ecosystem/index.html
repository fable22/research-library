Jev open-source 대안: 출시 8일 만에 나온 로컬 typed-decision 모델과 세 리더보드

TypeSafe가 Jev를 공개한 2026-09-15 이후 여드레 동안 Jev의 /v1/systemone 계약을 흉내 낸 공개 프로젝트가 수십 개 생겼다. 이 문서는 그중 아홉 개와 세 독립 리더보드를 커밋 단위로 고정해 읽고, 2026-09-23 시점에 Jev 대신 로컬 모델을 쓸 수 있는지를 하드웨어와 용도별로 답한다.

요약(2) → 격차 검정(11) → 용도별 판정(19). 세 장이면 "무엇을 어디에 쓰나"가 나온다.

배경 문서

Jev 자체의 계약, RLCD, calibration 개념은 Jev System One: 문장 대신 판단과 확률을 반환하는 모델에서 다뤘다. 이 문서는 그 기제를 다시 유도하지 않는다.

대상: Kev, SemIf, decider, Laya, razorback16 OpenJev, Bespoke Nimble, Zefan-Cai Open-Jev, Von, openJev-verdict-2.0, 그리고 격차 검정을 통과한 유일한 후보라서 추가로 연 ekzhang/openjev-sglang. 리더보드는 JevBench, Decision Index, DecisionBench다. 성능 수치는 모두 저장소나 리더보드가 기록한 값이며 재현하지 않았다(8장).

범용 대체는 보류한다. 리더보드에 오른 대상 여덟 개 모두 적어도 한 리더보드에서 Jev보다 정확도가 5pp 넘게 낮거나 calibration 오차가 0.05 넘게 크다. Von은 세 리더보드 어디에도 없다. 한국어는 어느 프로젝트도 Jev 수준을 보인 기록이 없다. Laya 다국어 checkpoint가 MASSIVE 한국어 20지선다에서 0.450을 기록한 것이 유일한 수치다.

부분 채택은 가능하다. 라우팅은 Kev-4B를 자기 label 수백 개로 fine-tune하는 경로가 명령 단위로 문서화돼 있다. 다만 README 절차대로 학습한 checkpoint는 temperature 1.0으로 저장되므로 보정 스크립트를 따로 돌려야 한다(19장). 공식 SDK의 base_url만 바꿔 쓰는 테스트가 저장소 안에 있고 README 수치 238개를 CI가 원본 보고서와 대조한다. RAG 근거 검증은 DecisionBench의 retrieval_verification family에서 decider-2b가 0.857, Jev가 0.527이다. 한 리더보드의 한 family라서 시험 단계로만 쓴다.

리더보드 자체가 흔들린다. JevBench는 BETA 표시를 달고 있고 DecisionBench는 운영사 자신의 모델이 1위이며 결과 PR을 작성자 본인이 리뷰 없이 병합했다. 같은 모델의 순위가 세 곳에서 다르게 나온다. 한 곳의 숫자로 결정하지 말고 둘 이상을 겹쳐 읽어야 한다.

격차 기준(정확도 5pp, ECE 0.05)은 이 문서가 정한 선이다. 어느 리더보드도 이 기준을 쓰지 않는다. 기준을 10pp로 넓히면 Decision Index에서 decider-35b-a3b(격차 7.2pp, ECE는 Jev보다 낮음)가 들어온다.

problem

Jev의 빈자리는 접근, 조정, 데이터 위치, 언어

오픈 대안을 찾는 사람이 대는 이유는 대개 넷이다. 가입이 막혔고, 자기 데이터로 가중치를 바꿀 수 없고, 입력이 외부로 나가며, 한국어·중국어·일본어 품질이 공식적으로 약하다. 넷 모두 Jev 공식 문서나 공식 계정에 적혀 있다.

한국어 업무를 Jev에 맡길 때도 자기 데이터로 검증하라는 뜻이다. 오픈 대안이 이 빈틈을 메웠는지는 6장에서 본다.

가격은 이유가 되기 어렵다. Jev는 입력 100만 토큰당 $0.042이고 출력은 과금하지 않는다. JevBench는 결정 1,000개에 $0.0399로 계산한다. 로컬 GPU를 따로 돌리는 비용이 이보다 싸려면 호출량이 커야 한다.

이 장의 근거는 Jev 문서 세 쪽(models.md, api.md, confidence.md), TypeSafe 공식 X 글, Vercel changelog, DecisionBench의 Jev 레코드 model_meta.json이다.

taxonomy

대안은 네 갈래다. 확률을 어디서 읽느냐가 갈래를 나눈다

API 모양은 모두 Jev를 따르지만 확률이 나오는 자리는 다르다. encoder가 본문과 label을 함께 채점하는 갈래, 학습한 decoder가 한 위치에서 label을 읽는 갈래, 학습 없이 기성 LLM의 다음 토큰 logit을 읽는 갈래, diffusion LM의 빈칸을 읽는 갈래다. encoder 갈래는 배경 문서가 다룬 NLI·GLiClass 계보를 저장소가 직접 밝힌다. 나머지 셋을 PET·FIRST 계보에 잇는 것은 이 문서의 해석이다.

PET·FIRST에서 (b)(c)(d)로 가는 화살표 셋은 모두 이 문서의 해석이다. 대상 README 중 이 계보를 인용한 것은 Kev README 377행의 Related work 목록에 있는 FIRST 링크 하나이고, PET 인용은 어디에도 없다. (d)의 화살표는 PET가 masked LM의 빈칸 한 자리를 읽고 DiffusionGemma 읽기가 masked canvas의 답 자리를 읽는다는 구조적 유사성만 가리킨다.

readout

모두 confidence 필드를 돌려주지만
공식이 셋으로 갈리고, 보정은 대부분 사후 temperature다

Jev의 confidence는 확률 분포에서 계산한 통계이고 공식은 공개되지 않았다. 대안들은 최대 확률 pmax를 선택지 수 K로 재척도화하거나 분포의 entropy H(p)를 쓴다. 표의 T는 확률을 펴는 temperature다. 같은 0.7이라도 프로젝트마다 뜻이 다르므로 Jev에서 맞춘 threshold를 옮겨 쓰면 안 된다.

Kev README는 이 차이를 직접 적는다. "It's an approximation of TypeSafe's formula, which isn't public. Neither field is a measured accuracy rate." Nimble 서버는 API 설명에 "Confidence is entropy concentration, not calibrated accuracy."를 박아 둔다. razorback16 OpenJev는 label이 top-k logprob 밖에 있으면 최솟값에서 5를 뺀 값을 채워 넣는다(openjev/engine.py:424). 드문 선택지의 확률은 모델이 낸 값이 아니라 이 floor가 정한다.

사후 temperature는 argmax를 바꾸지 않는다. 정확도는 그대로이고 확률만 퍼진다. 그래서 temperature를 어느 분포에 맞췄는지가 중요하다. SemIf는 WANLI에서 T=2.50으로 ECE를 0.208에서 0.069로 내렸지만 자체 authored 셋에서는 1.23이었다. 한 값으로 두 workload를 다 맞추지 못한다고 저장소가 스스로 밝힌다.

표는 코드와 README에 적힌 정의다. 각 정의가 실제 calibration 수준으로 이어지는지는 10–11장의 리더보드 ECE로 본다. Jev의 RLCD가 사후 temperature와 무엇이 다른지는 배경 문서 calibration 장과 learning 장에 있다.

경로에서 읽히는 동작은 셋이다. 질문끼리는 서로의 행을 보지 않으므로 질문을 더하거나 빼도 다른 답이 바뀌지 않는다(README 214행, 병렬성 테스트는 tests/test_model.py). 같은 질문 안의 선택지 순서는 여전히 답을 바꿀 수 있다고 README 348행이 적는다. temperature는 추론할 때만 나누므로 argmax는 그대로다.

SDK 호환의 범위도 여기서 정해진다. 서버는 jev-latest를 받고 응답 model에 요청 값을 그대로 돌려준다(kev/serve.py:80). 기본으로 127.0.0.1에 묶이고 KEV_API_KEY를 넣기 전에는 인증이 없다. 한 번에 요청 하나만 처리한다(README 350행).

Qwen3.5 세대 Kev-4B·9B는 JevBench에 없고 decider-4b는 세 곳 모두에 없다. razorback16, Open-Jev, openjev-sglang은 Decision Index에 없다. 한 리더보드만으로 판정되는 후보가 많아서 "두 곳 이상" 조건이 품질보다 등재 여부를 먼저 거른다.

기준과 ECE 정의

5pp·0.05 기준은 이 문서가 정했다. ECE는 JevBench가 hard tier 10-bin, Decision Index가 요청 6개 중 1개 표본에서 선택 확률 기준, DecisionBench가 전체 행 기준이다. 세 값을 한 줄로 세우면 안 된다. 그래서 격차는 리더보드 안에서만 계산했다.

리더보드 운영

DecisionBench는 운영사 모델이 1위이고 결과 PR을 작성자 본인이 리뷰 없이 병합했다. JevBench hard 문항은 두 LLM이 쓰고 서로 검토했으며 영어뿐이다. Decision Index는 비공식이다. 셋 다 저장소와 artifact를 공개했기 때문에 이런 약점이 보인다.

읽기만으로는 알 수 없는 것

"SDK unchanged"는 Kev만 저장소 테스트로 뒷받침된다. 나머지는 README 문장이다. 서빙 메모리, Apple 16 GB에서의 Kev-4B 여유, 주입률은 실행하지 않고는 모른다. Jev의 주입 내성은 제3자 보고를 요약한 2차 자료 하나뿐이다(13장).

Jev도 기준점으로 완전하지 않다

Jev도 공개 choice 139문항에서 선택지 순서를 바꾸면 5.0%가 뒤집히고, DecisionBench guardrails_moderation에서 0.391이다. "Jev에 머문다"는 판정이 그 용도의 안전을 보장하지 않는다.

한국어

한국어 typed-decision 벤치마크는 코퍼스에 없다. Laya 다국어판의 MASSIVE 한국어 수치 하나와 중국어 합성 진단 64건이 전부이고 한국어 커뮤니티 논의도 GN⁺ 번역뿐이다.

남는 것이 있다. 정확도와 ECE를 같은 리더보드 안에서 함께 재는 격차 검정, 그리고 거절 행을 빼고 다시 읽는 방법은 새 프로젝트가 올라와도 그대로 쓸 수 있다. Kev의 verify_claims.py처럼 README 숫자를 CI에서 원 보고서와 대조하는 장치는 채택 전 다른 프로젝트에도 요구할 만한 조건이다.

conclusion

2026-09-23의 오픈 typed-decision 모델은
좁은 용도에 붙이는 부품이다

여드레 사이에 네 갈래의 구현과 세 개의 리더보드가 생겼다. 격차를 두 축으로 재면 결론은 한 줄로 줄어든다. 범용 교체는 아직이고 용도별 시험은 지금 할 수 있다.

  • 1범용 교체 불가. 대상 아홉 개 중 한 리더보드에서라도 정확도 5pp·ECE 0.05 안으로 Jev에 붙은 것이 없다. 두 곳을 통과한 openjev-sglang은 LICENSE 파일이 없다.
  • 2격차의 상당 부분은 받지 못한 입력이다. DecisionBench에서 거절 행을 빼면 SemIf, decider-2b, decider-35b의 정확도는 Jev와 1pp 안이다. 선택지 수와 입력 길이 한도를 먼저 확인하면 부분 채택의 범위가 보인다.
  • 3라우팅은 Kev, RAG 근거 검증은 decider-2b. 전자는 공식 SDK 테스트와 CI 수치 대조가, 후자는 4 GB와 retrieval_verification 0.857이 근거다. 둘 다 한 리더보드 근거라 자기 데이터 시험이 먼저다.
  • 4moderation·가드레일·한국어는 옮기지 않는다. 리더보드끼리 방향이 반대이거나 측정이 없다. logit 읽기 구조는 state 안의 설득 문장에 흔들리며 SemIf의 HN 사례가 그 예다.
  • 5숫자는 커밋과 날짜를 붙여 읽는다. JevBench 점수 공식은 이틀 사이에 바뀌었고 OpenJev라는 이름은 여덟 곳이 쓴다. 두 주 뒤에 이 문서를 다시 쓴다면 17장의 항목부터 확인한다.

Jev 자체의 판단 원리와 calibration 정의는 배경 문서에 있다. 이 문서의 판정은 Jev가 hosted로 계속 열려 있다는 전제를 둔다. 기존 가입자에게 서비스가 계속된다는 9/22 공지가 바뀌면 "Jev에 남는다"는 행이 먼저 무너진다.
