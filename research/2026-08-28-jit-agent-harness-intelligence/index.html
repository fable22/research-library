JIT-Agent: 하네스를 태스크마다 모델이 새로 조립하게 만든 27B 메타 모델

arXiv:2608.25593v1 (2026-08-26 게시, cs.CL/cs.LG, 저자 16인, LV-NUS Lab). 피어리뷰를 거치지 않은 프리프린트이고 게시 이틀째다. 코드는 bingreeky/JIT @ ababa06c, 가중치는 JIT-Agent/jit-27b @ 0705ca15 로 공개되어 있다.

이 저장소에는 하네스를 사람이 어떻게 짜는지 다룬 문서가 이미 넷 있다. DeepSeek Harness 의 플러그인 합성, LoopX 의 결정론적 제어 평면, SKILL.md 의 프론트매터 계약, omo 의 토큰 비용. 이 논문은 같은 대상을 반대편에서 잡는다. 하네스를 사람이 짜는 물건이 아니라 모델이 태스크마다 조립하는 물건으로 바꾸면 무엇이 드러나는가.

드러난 것 중 여러 개는 사람이 짜는 하네스에도 그대로 걸린다. 이 문서는 그것을 쓴다. 벤치마크 순위는 그 시사점의 근거가 되는 자리에만 넣었다.

9개 벤치마크 평균+8.8DeepSeek-V4-Flash 66.7 → 75.5. 백본은 같고 스캐폴드만 바뀌는데 baseline 쪽 스캐폴드가 무엇인지는 논문에 없다(12장)
케이스당 비용−36.0%통제 비교 6개 설정, 각 설정의 최저가 고정 하네스 대비 평균
Table 4 의 baseline 하네스0/5Claude Code, Codex, OpenCode, Hermes, NanoBot 중 공개 저장소에 구현이 있는 것

이 문서가 다루지 않는 것. 훈련 재현. 논문은 GPU 시간, 학습률, 에포크, 배치 크기를 하나도 적지 않는다(main.tex 전체 검색 결과 0건). 가중치는 받을 수 있지만 훈련을 되돌릴 근거는 논문에 없다.

tl-dr

요약. 고정 하네스 하나를 유지하는 값은 두 자릿수이고 JIT 의 이득은 더 넣어서가 아니라 덜 넣어서 나온다

백본을 고정하고 하네스만 바꾼 6개 설정에서 어떤 고정 하네스도 전 태스크를 지배하지 못한다. NanoBot 은 Qwen3.6-Flash DeepSearchQA 에서 1위지만 같은 백본 AgentIF 에서 JIT 에 14.8점 뒤진다. 그리고 JIT 은 6개 설정 전부에서 토큰과 비용이 최저다.

problem

문제 정의. 하나의 태스크 형태에 맞춘 하네스는 다른 형태에서 측정 가능하게 틀리고, 그 벌점이 두 자릿수다

논문은 백본을 고정하고 하네스만 갈아끼우는 통제 비교를 돌린다. 결과는 "어느 하네스가 좋다"가 아니라 "1등이 태스크마다 바뀌고, 바뀌는 폭이 크다"이다. 아래 표는 논문 Table 4 의 Qwen3.6-Flash 블록에서 DeepSearchQA 와 AgentIF 두 열만 뽑은 것이다.

단일 CLAUDE.md 하나, 스킬 세트 하나를 유지하는 사람이 실제로 감수하는 값이 이 숫자다. 하네스가 나쁘다는 말이 아니라, 태스크 형태가 하네스 설계보다 먼저 점수를 정한다는 말이다.

이 표의 baseline 하네스는 출시된 Claude Code 나 Codex 가 아니다. 논문이 그 스캐폴드를 Qwen3.6-Flash 위에 이식한 것이고("we instantiate each harness on DeepSeek-V4-Flash and Qwen3.6-Flash", main.tex:704) 공개 저장소에는 그 구현이 없다. 근거는 14장에 있다. 이 문서는 그래서 표에서 "스캐폴드"라고 표기한다.

typed-space

구조 1. 프로토콜을 고정하면 하네스 작성이 프로그램 합성에서 조립으로 바뀐다

모델에게 "에이전트를 하나 짜라"고 하면 생성 공간이 열려 있어 아무것도 보장되지 않는다. 논문은 그 공간을 네 겹으로 좁힌다. 좁히는 도구가 네 모듈 프로토콜이고 이게 이 논문에서 사람이 짜는 하네스로 가장 곧바로 옮겨가는 부분이다.

생성 공간은 네 겹이고 마지막 두 겹 사이의 간극이 repair 의 몫이다

arXiv:2608.25593v1 §3.1 (main.tex:212, :227, :243–249)

저자들이 이 설계의 값어치를 직접 쓴다. 인용 상대가 이 저장소에 이미 문서가 있는 DeepSeek Harness 다.

Composability is equally central to JIT generation: it turns harness construction from unconstrained program synthesis into assembly over a typed, recombinable design space.arXiv:2608.25593v1 §3.1 Harness Composability box, main.tex:215

스킬 라이브러리 설계에 그대로 걸린다. 스킬이 선언된 인터페이스를 가진 역할로 타입되어 있으면 재조합 대상이 되고 산문 덩어리면 안 된다. addyosmani/agent-skills 의 SKILL.md 24개가 프론트매터에 name 과 description 만 쓴다는 사실이 이 축에서 다시 읽힌다. 그 두 필드는 사람이 고르기에는 충분하지만 모델이 조립하기에는 타입이 아니다. 무엇을 받아 무엇을 돌려주는지가 선언되어 있지 않다.

이 좁히기는 표현력을 깎는다. 논문 §3.1 은 ReAct 를 (M_full, P_∅, A_react, F_all) 로, Codex 와 OpenCode 를 (M_compact, P_todo, A_react, F_all) 로 적어 좌표계 안에 들어온다고 주장하지만, 이것은 논문의 주장이지 그 두 런타임을 열어 대조한 결과가 아니다. 저자들도 자기 인스턴스화가 프로덕션 런타임보다 의도적으로 빈약하다고 따로 밝힌다.

split-axis

구조 2. 작업 단계로 쪼갠 스킬은 재조합되지 않는다. JIT 은 운영 기능으로 쪼갠다

이 저장소의 .claude/skills/ 는 source → doc → verify 로 나뉜다. 작업이 흘러가는 순서다. JIT 의 네 모듈은 memory, planning, action, capability 로 나뉜다. 한 스텝 안에서 동시에 사는 기능이다. 같은 대상을 다르게 자른 두 축이고 각각 무엇을 가능하게 하고 무엇을 막는지가 다르다.

축단위가능해지는 것막히는 것
작업 단계
source → doc → verify		시간단계 사이에 컨텍스트 경계를 그을 수 있다. verify 를 다른 컨텍스트에서 돌리는 것이 이 축에서만 성립한다두 단계를 섞을 수 없다. doc 을 쓰다가 필요한 memory 전략만 바꿔 끼우는 조작이 정의되지 않는다
운영 기능
M / P / A / F		스텝 내부모듈 하나만 갈아끼우는 것이 타입 수준에서 정의된다. 13개 seed 하네스가 같은 좌표계의 서로 다른 점이 된다단계 경계가 없다. 컨텍스트를 끊는 조작이 이 축에는 없고 논문도 그것을 다루지 않는다

이 대조는 논문에 없다. 논문의 네 모듈과 이 저장소의 skill 배치를 나란히 놓은 것이고 두 축이 경쟁하지 않는다는 점이 결론이다. 둘 다 필요하다면 두 겹으로 겹쳐야 하고 논문은 그 겹치기를 시도하지 않는다.

공개 코드에서 이 축은 파일 다섯 개로 고정되어 있다

harness_factory/harnesses/<name>/ 은 하네스 하나를 파일 다섯 개로 고정한다. memory.py, planning.py, action.py, tool_policy.py, prompt.yaml. 메타 모델이 생성할 때도 같은 다섯 개를 태그 블록에 담아 뱉는다(jit/harness_ops.py:30 의 SECTION_TAG_TO_FILE).

설명서와 생성 프롬프트가 같은 파일이다. 기본 모드(desc)에서 메타 모델은 11개 하네스의 설명서를 통째로 약 13K 토큰 받고, code 모드에서는 그중 셋을 무작위로 뽑아 전체 소스를 25K~46K 토큰 받는다(jit/README.md). 스킬 라이브러리를 문서로 쓰면서 동시에 프롬프트로 쓰는 구조이고 이 저장소의 .claude/skills/ 도 같은 성질을 갖는다.

논문 Table 2 는 seed 하네스를 13개로 적는다. 공개 저장소에 디렉터리가 있는 것은 11개이고 ReAct 와 AOrchestra 는 없다. README 의 카탈로그도 11행이고 plan_and_execute 를 "Linear ReAct. 최소 baseline"으로 설명한다. 논문이 13개를 다 돌렸는지 11개만 공개한 것인지는 저장소만으로 판단할 수 없다.

subtraction

per-step-f

구조 4. 도구와 스킬 노출은 전역 설정이 아니라 단계별 결정인데, 손으로 쓴 하네스는 전부 전역으로 쓴다

논문의 F 모듈 정의는 "각 단계에 어떤 외부 역량을 노출하나"다. 식으로는 C_t = F(C_τ, s_t, v_t, d_t) ⊆ C_τ 이고 매 스텝 레지스트리의 부분집합을 고른다. 공개 코드의 인터페이스도 그렇게 되어 있다. 그런데 그 인터페이스를 쓰는 구현이 seed 하네스에는 하나도 없다.

인터페이스는 단계별이다

class ToolPolicyStrategy(BaseToolPolicy):

네 모듈 중 이렇게 한 가지 동작으로 수렴한 것은 F 뿐이다. 11개 하네스의 파일을 모듈별로 해시해 보면 memory.py 는 서로 다른 구현이 10종, planning.py 는 8종, action.py 는 8종인데, tool_policy.py 는 파일이 7종이면서 동작은 1종이다. 설계 공간을 네 축으로 열어 두고 세 축에서만 실제로 움직인 셈이다.

F 를 실제로 단계별로 쓰는 것은 메타 모델이 생성한 하네스뿐이다. 논문 부록의 Turnstile 은 DynamicToolPolicy 로 아직 안 채운 증거 버킷에 맞는 검색 도구만 열고 final_answer 는 is_complete() 가 통과할 때까지 잠근다. Mulligan 은 DOCX 파일 하나를 다루는 태스크라서 Word 와 파일 조작만 열고 email, spreadsheet, PDF 도구를 숨긴다.

여기서 사람이 가져갈 것은 "스킬을 다 켜두지 마라"가 아니라 그보다 좁다. 노출 결정이 어느 시점에 내려지는지가 설계 변수라는 것이고 대부분의 하네스는 그 변수를 세션 시작 시점에 고정한 뒤 다시 건드리지 않는다. 이것은 6장의 덜 넣기와 같은 뿌리다. 다만 논문은 도구 노출만 따로 떼어낸 ablation 을 돌리지 않으므로, 절감의 몇 %가 F 에서 왔는지는 논문으로 알 수 없다.

repair

구조 5. 스키마를 통과한 설정과 실제로 도는 설정은 다르고, 훈련 3단계 중 한 단계가 통째로 그 간극이다

Stage I 은 프로토콜을 지키는 하네스를 뱉게 가르친다. 프로토콜을 지켜도 돌지 않는 것이 남고, 그 남은 것이 4장 그림의 안쪽 두 겹 사이다. Stage II 는 그 간극만 담당한다.

validation 은 결정론적 검사이고 repair 는 그 뒤에 붙는 별개의 모델 호출이다

arXiv:2608.25593v1 §4.2 · jit/meta_agent.py, jit/README.md @ ababa06c

훈련 쪽 Stage II 는 Stage I 에서 버려진 실패 하네스와 그 진단 보고서를 모아 repair 궤적으로 바꾼다. 채택 조건이 좁다. 두 번 안에 실행 가능해진 궤적만 남긴다.

We retain only trajectories that become executable within two repair rounds. … This keeps the corpus focused on realistic, locally recoverable failures instead of those requiring wholesale redesign.arXiv:2608.25593v1 §4.2, main.tex:502·508

두 라운드는 훈련 코퍼스에 무엇을 남길지의 조건이지 배포 시 상한이 아니다. 공개 저장소의 실행 경로는 상한을 5 로 잡는다. --max-repairs 기본값이 5 이고(scripts/run_jit.py:107) 루프가 total_rounds = max(1, max_repairs + 1) 로 그 값을 그대로 쓴다(jit/meta_agent.py:1454). 두 경로가 같은 것은 상한값이 아니라 repair 를 여는 조건 쪽이다. 예외가 나야 repair 가 돌고 점수가 낮다는 이유로는 돌지 않는다.

The meta model is not called again unless the run raises. On an exception, --max-repairs regeneration attempts are allowed; a harness that merely scores low is never repaired, since that would be optimising against the benchmark.jit/README.md:117, bingreeky/JIT @ ababa06c

이 저장소의 게이트도 pass/block 이고 경고 등급이 없다. check-doc.mjs, check-prose.mjs 는 규칙 위반을 알려주고 멈춘다. 고치는 것은 사람 몫이다. JIT 은 여기에 한 단계를 더 둔다. 검사기가 낸 진단 보고서를 프롬프트에 넣어 고치는 쪽까지 모델에게 학습시킨다. 생성하거나 조립한 설정을 쓰는 파이프라인이라면, 검사기를 붙이는 것과 검사 결과를 되먹이는 것이 서로 다른 작업이라는 점이 그대로 적용된다.

Stage II 에서 실제로 몇 %가 repair 로 살아났는지, repair 없이 몇 %가 처음부터 실행 가능했는지를 논문은 적지 않는다. 이 단계의 값어치를 재는 ablation 이 논문에 없다.

frontier

구조 6. 아카이브는 쓸모 있어 보이는 것을 저장하지 않는다. frontier 를 전진시킨 것만 저장한다

에이전트 메모리를 설계할 때 기본값은 "쓸 만해 보이면 남긴다"이다. Stage III 의 보존 규칙은 그 반대편에 있고 규칙 자체가 한 문장이다.

a candidate is retained only if it matches or exceeds the current reward frontier and then strictly improves at least one frontier dimension, either reward itself, latency, or cost.arXiv:2608.25593v1 §4.3, main.tex:605

세 축이다. reward, latency, cost. 조건이 둘로 나뉘어 있다. 먼저 현재 frontier 를 동등 이상으로 맞추고, 그 다음 세 축 중 최소 하나를 엄격히 개선해야 한다. 동점은 저장되지 않는다. 같은 규칙이 배포 시점의 streaming inference 에도 그대로 쓰이고 그때 모델 파라미터 θ 는 frozen 이고 하네스 뱅크 B_n 만 자란다.

후보의 성적rewardlatencycost저장
점수가 오름↑==저장
점수 같고 더 쌈==↓저장
점수 같고 다 같음===버림
점수 오르는데 훨씬 비쌈↑=↑저장
점수 떨어지고 훨씬 쌈↓=↓버림

이 표는 논문 §4.3 의 보존 규칙 한 문장을 경우별로 편 것이고 표 자체는 논문에 없다. reward 는 "동등 이상"이 문턱이므로 넷째 행은 저장되고 다섯째 행은 버려진다. 규칙이 비용에 대칭이 아니다.

이 규칙의 효과는 Static JIT 과 Streaming JIT 의 대조로 나온다. Streaming 은 DeepPlanning-Shopping, DeepPlanning-Travel, OfficeBench 세 스트림 전부에서 누적 정확도가 더 높게 끝나고 논문은 그 우위가 처음부터 있는 것이 아니라 피드백이 쌓이면서 나타난다고 적는다. 다만 논문은 그 그림(Figure 6)에서 끝점 수치를 본문에 옮겨 적지 않는다.

이 저장소에도 걸리는 데가 있다. LoopX 는 성과 없는 턴이 진행으로 계상되지 않게 막는다. 회계 단위가 턴이고 막는 대상이 "진행했다는 기록"이다. Stage III 의 규칙은 회계 단위가 하네스이고 막는 대상이 "저장할 만하다는 판단"이다. 두 장치가 막는 것은 같다. 진전이 없는 것을 진전으로 기록하지 않는 장치가 없으면 아카이브는 커지기만 한다.

Static 과 Streaming 의 격차가 세 스트림에서 몇 점인지, 스트림 길이가 얼마인지를 논문 본문은 밝히지 않는다.

trace

사례. Turnstile 은 memory 를 요약 장치가 아니라 실행 가능한 커버리지 계약으로 쓴다

논문 부록의 생성 하네스 여덟 개 중 하나다. 태스크는 여행 계획이고 날짜, 인원, 객실 수, 출발 시간대, 최고 평점 호텔, 명소, 식사, 일별 동선이 한꺼번에 요구된다. 네 모듈이 이 요구를 어떻게 나눠 가지는지가 이 사례의 전부다.

보통의 하네스에서 memory 는 궤적이 길어질 때 줄이는 장치다. 여기서 memory 는 줄이는 일을 하지 않는다. 무엇이 아직 없는지를 들고 있고 그 상태가 F 의 이번 스텝 결정을 정한다. 논문의 표현이 이렇다.

Here memory is not used primarily to compress a long trace; it acts as an executable coverage contract that prevents itinerary synthesis before the required travel facts have been collected.arXiv:2608.25593v1 부록 A, main.tex:871

같은 프로토콜에서 나온 다른 하네스는 전혀 다른 모양을 한다. Palimpsest 는 요구를 DAG 로 컴파일하고 폭과 깊이를 제한해 실행한다. Trapdoor 는 delegate 라는 도구를 합성해 다섯 스텝짜리 하위 에이전트를 열고, 돌아온 답만 부모 루프에 관측으로 넣는다. Abacus 는 집계를 언어 모델 추론에서 아예 빼내 shell 이나 Python 으로 넘기고 RESULT_JSON 을 파싱해 타입 있는 상태에 쓴다. 논문의 요약은 한 줄이다.

The shared protocol constrains interfaces, not behavior.arXiv:2608.25593v1 §6.7, main.tex:821

이 추적은 논문 부록 A 의 그림 설명과 본문 문단에서 왔다. 그 하네스의 소스는 공개 저장소에 없다. 저장소가 담고 있는 것은 손으로 쓴 seed 하네스 11개이고 생성된 하네스는 실행 시에 만들어져 runs/ 아래로 떨어진다.

Table 3 의 백본 baseline 이 어떤 스캐폴드에서 돌았는지를 논문은 "default scaffold" 라고만 적는다. 각 모델의 기본 스캐폴드가 무엇인지, 그것이 모델마다 얼마나 다른지는 논문에 없다. GPT-5.6 이나 Gemini 3.1 Pro 같은 frontier 모델 행도 마찬가지다. 즉 Table 3 은 "하네스만 바꾼 통제 비교"가 아니고, 그 통제가 되어 있는 것은 Table 4 쪽이다.

이 24쌍의 baseline 은 ReAct 다. 3장의 통제 비교에서 상대했던 Claude Code, Codex, NanoBot 같은 하네스가 아니다. "ReAct 대비 +7.6"과 "최강 고정 하네스 대비 +4.7"은 서로 다른 크기의 주장이고 둘을 섞어 읽으면 개선폭이 부풀려진다.

비교의 예산이 대칭이 아니다. 저장소 기준으로 JIT 은 케이스마다 하네스 3개를 temperature 1.0 으로 생성해 그중 하나를 골라 돌린다. seed 하네스는 --rollouts 1 이 기본이고 실행 모델 temperature 0 이다. 그리고 보고되는 토큰은 execute/ 단계의 것이라고 저장소가 명시한다. 하네스를 세 번 생성하는 데 든 토큰은 generate/ 아래에 따로 기록된다. 기본 모드에서 참조 자료만 약 13K 토큰이 매 생성 프롬프트에 들어가므로, 케이스당 실제 총 지출은 6장 표의 숫자보다 크다. 그 차이가 얼마인지는 논문도 저장소도 적지 않는다.

전부 저자 자체 평가다. JIT 이 자기 하네스를 만들고, 저자가 고른 벤치마크와 부분집합에서, 저자가 만든 어댑터로 채점한다. 게시 이틀째 프리프린트이므로 외부 재현은 아직 없다. 그리고 재현하려는 사람은 Table 4 의 baseline 다섯을 직접 다시 구현해야 한다.

"model scaling 과 직교"는 근거보다 넓다. 초록의 이 문장이 13장의 24쌍 실험 위에 서 있는데 그 실험이 보이는 것은 여섯 백본 각각에서 ReAct 대비 이득이 있다는 데 그치지 않는다. 백본을 키웠을 때 이득이 어떻게 되는지가 Figure 5 의 콜아웃 24개에 분해돼 있고, 세 계열 중 둘(DeepSeek V4, Qwen 3.6)에서 큰 변종이 덜 얻는다. 직교라면 나오지 않을 방향이다. 남은 하나인 Mimo 2.5 만 반대로 가고, 개선폭이 가장 작은 계열은 하필 메타 모델의 훈련 계열인 Qwen 3.6 이다.

한계를 다 걷어내도 남는 것이 하나 있고 그것이 이 문서가 논문에서 가져가는 부분이다. 고정 하네스의 순위가 태스크 형태에 따라 두 자릿수로 뒤집힌다는 사실은 baseline 의 이식 충실도와 무관하게 성립한다. 이식이 서툴렀다면 다섯 스캐폴드가 고르게 낮아야 하는데 실제로는 다섯의 순위가 열마다 재배열된다. Hermes 는 두 백본 모두 DeepSearchQA 에서 고정 다섯 중 꼴찌인데 AgentIF 에서는 둘째로 올라가고, NanoBot 은 두 백본 모두 DeepSearchQA 1위인데 AgentIF 에서 넷째(DeepSeek-V4-Flash) 와 셋째(Qwen3.6-Flash) 로 내려간다. 이 패턴은 이식 품질로 설명되지 않는다.

conclusion

결론. 이 논문의 주장은 Claude Code 를 대체하자는 것이 아니라, 태스크별 특화 축이 범용 런타임 축보다 덜 개발되어 있다는 것이다

저자들이 자기 4모듈 인스턴스화를 프로덕션 런타임보다 의도적으로 빈약하게 만들었다고 밝히고 JIT 패러다임이 프로덕션 하네스 엔지니어링과 상보적이라고 쓴다.

남는 결과는 셋이다. 첫째, 하네스를 타입 있는 재조합 공간으로 만들면 모델이 조립할 수 있고 그러지 않으면 못 한다. 둘째, 고정 하네스 하나를 유지하는 값이 태스크 형태가 바뀔 때 두 자릿수다. 셋째, 그 값을 되찾는 방법이 컨텍스트를 더 채우는 쪽이 아니라 비우는 쪽에 있다. 6개 통제 설정 전부에서 토큰과 비용이 최저이고 평균 36.0% 싸다.

이 저장소의 앞선 문서 넷은 전부 하네스를 사람이 어떻게 짜는가를 다뤘다. 플러그인 한 행이 에이전트 루프가 되는 구성, LLM 없이 턴을 승인하는 제어 평면, 강제를 코드가 아니라 산문에 맡긴 스킬 팩, 플러그인을 떠나 자기 호스트를 갖는 선택. 이 논문은 같은 대상을 반대편에서 잡아 보고, 그 결과로 사람이 짜는 쪽에도 그대로 걸리는 것 다섯을 노출한다. 타입, 덜 넣기, 단계별 노출, 검사 결과 되먹이기, frontier 만 저장.

따라 하지 말아야 할 것도 분명하다. Table 4 의 다섯 baseline 하네스는 공개 저장소에 구현이 없고 그래서 그 표는 지금 재현할 수 없다. 논문에는 분산도, 시드 반복도, 유의성 검정도, API 단가도 없다. 게시 이틀째 프리프린트이고 외부 검증은 아직 없다. 이 문서에서 인용한 절감률과 점수차는 전부 그 조건 아래의 숫자다.

다음에 확인할 값어치가 있는 것 하나. 논문에 F 만 떼어낸 ablation 이 없다. 36.0% 절감 중 도구 노출을 좁힌 몫이 얼마인지가 15장 표의 셋째 줄을 실제로 바꿀 수 있는지를 정한다. 지금은 정할 근거가 없다.
