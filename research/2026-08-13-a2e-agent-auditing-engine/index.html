A2E Agent Auditing Engine: 정답률은 0.11 폭에 몰리고 토큰은 최소 3.5배 벌어진다

백본 모델을 하나로 고정하고 9개 agent harness 를 23개 벤치마크에 태운 1,035회 실행 기록이다. 논문은 harness 를 세우는 파이프라인을 내놓고, 그 파이프라인으로 harness 사이의 차이가 어디에 나타나는지를 측정한다. 그 차이는 최종 정답률에 거의 나타나지 않는다.

읽는 순서

③~⑦ 엔진이 무엇을 하는가. ATP 로 벤치마크와 harness 를 떼어놓는 구조, OpenTelemetry span 으로 남기는 실행 기록, 실행 단계에 지표를 등록하는 방식.

⑧~⑪ 숫자가 무엇을 말하는가. 사례 하나를 끝까지 따라간 뒤 표 1 과 토큰 결과를 본다.

⑫~⑬ Claude Code 를 쓰는 쪽에서 이 논문을 어떻게 읽어야 하는가.

고정한 대상

논문 arXiv 2608.07346v2, Shanghai Artificial Intelligence Laboratory. 숫자는 arxiv.org/e-print 로 받은 LaTeX 원본의 표에서 읽었다.

코드 datamllab/A2E commit 679ea1f, shallow clone 2,725개 파일.

논문 표의 라벨과 코드가 어긋나는 지점은 ⑫에서 다룬다.

이 문서가 다루지 않는 것. A2E 를 설치해 돌려보지 않았다. 실행 방법, 설치 요구사항, UI 사용법은 저장소 README.md 쪽이 낫다. 여기서 다루는 것은 이 엔진이 무엇을 측정하고 그 측정이 무엇을 뒷받침하는지다.

tl-dr

요약. harness 를 바꿔도 평균 정답률은 0.11 폭에 갇히고, 토큰은 3.5배 벌어진다

A2E 는 벤치마크 어댑터와 harness 어댑터를 갈라 23×9 조합 전부를 코드 추가 없이 실행한다. 백본을 DeepSeek-V4-pro 로 고정한 1,035회 실행에서 harness 평균 correctness 는 0.57에서 0.68 사이에 몰린다. 그중 sandbox 를 뺀 855회를 토큰으로 다시 보면 2,063에서 7,319으로 벌어진다. 이 3.5배는 9개 전체의 폭이 아니라 토큰이 측정된 8개에서 나온 하한이다.

실행 횟수 1,035 23개 벤치마크 × 9개 harness × 5문항
harness 평균 correctness 0.57 ~ 0.68 최고 agno. 0.57 은 crewai 와 google-adk 둘이다 (표 1)
평균 토큰 격차 ≥3.5배 2,063 에서 7,319. 8개만 측정돼 실제 폭의 하한이다
셀당 점수 해상도 0.20 셀마다 5문항뿐이라 0.2 단위로만 움직인다
  • 1최종 정답만 보면 harness 선택이 보이지 않는다. 단일 턴 문제인 arc-challenge, openbookqa, humaneval 에서는 9개 harness 가 전부 같은 점수를 낸다. 차이는 여러 턴을 도는 문제에서만 벌어진다.
  • 2어떤 harness 도 전 구간을 이기지 못한다. openai-agents 는 traject-bench 에서 1.00 으로 1위지만 gdpval 에서 0.00 이다. 순위는 벤치마크를 바꾸면 유지되지 않는다.
  • 3같은 모델, 같은 과제인데 토큰이 9.6배 차이 난다. τ³-bench 한 문항에서 LangGraph 는 10,122 토큰, CrewAI 는 96,704 토큰을 쓴다. 차이의 대부분은 prompt 토큰 누적이다 (8,520 대 94,615).
  • 4표의 Claude Agent SDK 행은 Claude Agent SDK 가 아니다. 코드가 쓰는 것은 anthropic 패키지의 Messages API 를 도는 8턴 루프이고, 거기서 돌린 모델도 Claude 가 아니다. ⑫에서 근거를 편다.

이 요약이 감추는 것. 위 숫자 중 1,035회 실행과 정답률은 DeepSeek-V4-pro 결과이고, 9.6배 토큰 사례는 GLM-5.2 결과다. 두 실험은 모델이 다르므로 같은 축에 놓고 비교할 수 없다. ⑪에 어느 숫자가 어느 실험에서 왔는지 정리했다.

problem

문제 정의. 벤치마크 실행기와 관측 도구가 따로 있어서, harness 비교는 매번 손으로 이어붙여야 했다

논문의 진단은 기존 도구가 워크플로의 절반씩만 담당한다는 것이다. 한쪽은 벤치마크를 돌리고 채점하지만 외부 harness 를 붙이는 데 harness 별 어댑터와 모델 API 프록시를 요구하고, 다른 쪽은 실행 기록은 표준화했지만 벤치마크 실행기가 아니다.

도구갖춘 것논문이 지적하는 빈자리
Inspect AI 벤치마크 오케스트레이션, sandbox 실행, 채점 외부 harness 를 harness 별 어댑터와 모델 API 프록시로 붙인다. harness 인터페이스가 바뀔 때마다 유지보수가 따라가야 하고, 생성 파라미터나 호출 경로를 건드려 trajectory 충실도가 떨어질 수 있다
Phoenix (OpenInference 계열) native 실행에 대한 표준 관측 task orchestration 과 결과 검증을 갖춘 end-to-end 실행기가 아니다. 벤치마크와 harness 와 tracing 을 사용자가 직접 통합해야 한다

여기서 논문이 세우는 요구조건은 세 가지다. harness 에 개입하지 않을 것(minimally invasive), harness 종류를 가리지 않을 것(harness-agnostic), 그리고 벤치마크 실행과 trajectory 수집을 한 자리에서 할 것. A2E 는 이 셋을 Task, Monitor, Evaluation 세 층으로 나눠 담는다.

This motivates a lightweight, minimally invasive, and harness-agnostic substrate that unifies benchmark execution with faithful trajectory collection. 논문 §1 Introduction

이 진단은 논문의 related work 다. 논문은 Inspect AI 와 Phoenix 를 baseline 으로 실제로 돌려보지 않는다. 두 도구와의 비교는 서술로만 있고, 실험 절에 대응하는 수치가 없다. ⑦에서 이 점을 따로 본다.

task-layer

원리 1. 어댑터를 벤치마크 쪽과 harness 쪽으로 갈라 207개를 32개로 줄인다

조합마다 어댑터를 쓰면 23개 벤치마크 × 9개 harness 는 207벌이 된다. A2E 는 가운데에 Agent Task Protocol 이라는 고정된 경계를 두고 양쪽이 각자 그 경계에만 맞추게 한다. 벤치마크 어댑터 23개와 harness 어댑터 9개, 합쳐서 32개면 격자 전체가 실행된다.

실행은 벤치마크 키, harness 키, 모델 이름 세 개로 시작한다. registry 가 dataset loader, binding, agent runner, SDK 매핑을 찾아 붙이고, CLI 가 후보 split 에서 표본을 뽑는다. sandbox 과제라면 TaskInput 의 state 를 통해 살아 있는 컨테이너가 함께 붙는다. harness 는 자기 control loop 를 그대로 돌리고 TaskTrace 하나를 돌려준다.

registry 에 있다고 검증된 조합은 아니다. 논문이 §4.2 에 직접 적은 단서다. Registry support does not imply that each framework-benchmark pair has passed end-to-end validation. 207개 조합이 모두 돌아간다는 뜻이 아니라, 돌릴 수 있는 배선이 있다는 뜻이다.

monitor

원리 2. framework 차이를 span 으로 번역해, 기록 형식이 harness 마다 갈라지지 않게 한다

Monitor 는 harness 코드를 고치지 않고 framework 가 이미 노출하는 실행 지점에 붙는다. 세 층으로 나뉘는데, 새 framework 를 붙일 때 늘어나는 것은 맨 아래 한 층뿐이다. 기록 형식은 OpenTelemetry span 이라 이후 도구가 그대로 읽는다.

SDK layer

framework 별 model call, tool 실행, workflow 전이, 비동기 동작을 잡아 위층 표현으로 옮긴다. 새 framework 지원은 여기만 추가된다.

Semantic layer

잡힌 동작이 agent, chain, model call, tool, skill 중 무엇인지 정하고 입력과 출력, 정체를 붙인다. 런타임 이벤트를 agent 행동으로 읽히게 만드는 층이다.

Span layer

시작과 끝, 성공과 실패, 그리고 어떤 동작이 이 동작을 불렀는지를 기록한다. run 하나가 부모 자식 관계를 가진 tree 가 된다.

계측이 모든 harness 에서 같은 밀도로 붙지는 않는다. 논문 Figure 6 캡션이 crewai 를 토큰 그래프에서 빼면서 이유를 밝힌다. CrewAI 의 LLM span 에는 토큰 수가 실려 오지 않는다. 나머지 8개는 span 단위 prompt 와 completion 의 합이 기록된 지표와 정확히 일치한다고 적혀 있다. 즉 9개 중 8개만 토큰 비교에 들어간다.

metric

원리 3. 지표를 실행 단계에 등록해, 실패가 어느 단계에서 났는지 짚게 한다

최종 정답만 보면 run 이 실패했을 때 reasoning 이 틀렸는지 tool 을 잘못 썼는지 답만 못 만들었는지 알 수 없다. 논문은 지표마다 실행 단계와 세부 차원을 붙여 등록하는 분류를 제안한다. 새 지표를 넣을 때 benchmark runner 나 harness 를 건드리지 않는 것이 이 구조의 목적이다.

실행 단계세부 차원무엇을 본다
ReasoningTask, Flow, Logical과제를 어떻게 해석하고 풀이 과정을 어떻게 세웠는가. 목표 이해, 계획 완결성, 추론 일관성
ActionTool, Skill, Memory추론이 환경과의 상호작용으로 어떻게 바뀌었는가. tool 사용 행태, 능력 적용, 앞선 문맥의 충실한 사용
Final AnswerAnswer Correctness, Task Completion응답의 의미적 품질과, 과제가 유효한 종료 상태에 닿았는지
Runtime QualityEfficiency, Safetytrajectory 전체에 걸친 성질. 자원 소비와 운영상 위험

위 표는 논문 Figure 5 의 분류이고, 코드가 지표를 등록하는 구조는 이것이 아니다. eval/metrics_catalog.json 은 지표 23개를 두 범주(process_values, result_values)와 여섯 그룹(plan, skill, tool, correct, efficiency, safety)으로 등록한다. Reasoning · Action · Final Answer · Runtime Quality 라는 4단계도, Task · Flow · Logical 같은 세부 차원도 코드에는 없다. Memory 가 특히 분명하다. eval/core/metric_groups.py:64 가 "memory": "safety" 를 legacy alias 로 처리한다. 이 23개가 ②에서 말한 19,665 = 855 × 23 의 그 23이다.

지표를 계산하는 방식은 두 갈래다. rule 기반은 accuracy, task success rate, tool success rate, latency, token usage, cost, trajectory step 수를 실행 기록에서 직접 센다. LLM-as-judge 는 rule 로 표현되지 않는 것을 채점한다. 최종 결과 품질, 추론 품질, tool 사용 품질, 지시 준수, 관련성과 완결성, 안전성이다.

결과는 파일 대신 데이터베이스에 들어간다. trajectory 생성과 지표 계산이 분리되므로, 새 지표가 생기면 agent 를 다시 돌리지 않고 저장된 기록 위에서만 다시 채점할 수 있다. 논문이 incremental evaluation 이라고 부르는 것이 이것이다.

judge 모델이 논문에 나오지 않는다. 보고된 19,665개 점수 기록 중 LLM-as-judge 로 매긴 몫이 어느 모델로 채점됐는지 논문 본문과 표에 없다 (grep -rniE "judge model|judge_model|as-judge" src/sections/*.tex 는 2건을 낸다. §5 의 eval.tex:107 과 §2 의 overview.tex:85 인데 둘 다 모델명이 아니다). 코드에는 기본값이 있다. 채점 진입점 eval/core/deal_server.py:488 이 --llm-model 을 A2E_EVAL_LLM_MODEL → A2E_MODEL → qwen-max 순으로 떨어뜨린다. 즉 어떤 모델이 채점했는지는 실행 환경이 정하고 논문은 그것을 적지 않았다. judge 를 바꾸면 움직이는 점수라서 재현 시 같은 값이 나온다고 보기 어렵다.

compare

비교. 논문이 이름을 댄 두 도구는 baseline 으로 돌아가지 않는다

③에서 본 대로 논문은 Inspect AI 와 Phoenix 를 문제 정의의 상대로 세운다. 그런데 실험 절에는 두 이름이 없다. A2E 가 실제로 측정해 비교한 대상은 9개 harness 서로다.

주장했지만 재지 않은 것

논문 §1 은 A2E 가 substantially smaller core implementation 을 달성했다고 쓴다. 비교 대상은 Inspect AI 와 Phoenix 로 지목되어 있다.

그 문장에 수가 붙어 있지 않다. core implementation 이 무엇을 세는 단위인지도 정의되지 않아, 이 주장은 반증할 방법이 없는 형태로 남는다.

실험 절에서 두 이름을 찾으면 나오지 않는다 (grep -rni "inspect\|phoenix" src/sections/experiment.tex 는 동사 inspects 한 건만 반환한다).

실제로 잰 것

같은 백본, 같은 inference 설정, 같은 tool 구성, 같은 step 한도, 같은 timeout 아래에서 9개 harness 를 23개 벤치마크에 태운 격자다.

논문도 이 점을 숨기지 않는다. 표 1 의 목적을 격자 전체가 한 파이프라인에서 실행되고 채점된다는 것을 보이는 데 둔다.

정리하면 이 논문은 두 종류의 주장을 한다. 엔지니어링 주장(더 가볍고 덜 침습적이다)은 서술로만 있고, 측정 주장(harness 는 서로 다르고 그 차이는 정답률에 잘 안 나타난다)은 표로 뒷받침된다. 뒤쪽만 검증 가능하고, 이 문서가 ⑩과 ⑪에서 따지는 것도 뒤쪽이다.

이 장이 확인하지 못한 것. Inspect AI 와 Phoenix 를 직접 열어 A2E 와 코드 규모를 대보지 않았다. 따라서 "더 작다"가 틀렸다는 것이 아니라, 논문이 그것을 확인할 수단을 독자에게 주지 않았다는 것이 여기서의 지적이다.

trace

사례 추적. 같은 모델이 같은 문항에서 갈리는 지점은 진단을 어느 층에서 멈추느냐다

논문이 harness 효과를 분리하려고 고른 예다. GLM-5.2 하나로 τ³-bench 의 같은 과제를 LangGraph 와 CrewAI 가 각각 푼다. 모델도 과제도 초기 환경도 같으므로 남는 차이는 harness 의 실행 방식이다.

LangGraph 의 correctness 값이 논문 안에서 어긋난다. 본문 §6.3 은 LangGraph 가 correctness 1.0 이라고 쓰는데 Table 2 의 같은 칸은 correctness=0.0 이다. Table 2 의 그 칸 산문("Correctly identifies the suspended-line issue")과 본문이 둘 다 1.0 쪽이라 표의 수치 하나가 어긋난 것으로 읽힌다. 두 열에 함께 붙은 task_succeeded=1.0 은 모순이 아니다. 이 지표는 harness status 가 ok 인지만 보는 CODE 지표이고, 저장소 카탈로그가 not the same as correctness 라고 못박는다. 두 run 이 오류 없이 끝났다는 뜻이지 CrewAI 가 과제에 성공했다는 표시가 아니다.

result-correctness

결과 1. 9개 harness 의 평균 정답률이 0.11 폭 안에 들어가고, 그중 넷은 소수점 둘째 자리까지 같다

백본은 DeepSeek-V4-pro (FP4) 하나로 고정했고 inference 설정, tool 구성, step 한도, timeout 도 맞췄다. 벤치마크마다 5문항씩, 9개 harness 가 같은 task ID 를 받는다. 즉 독립 표본이 아니라 문항 단위로 짝지어진 비교다.

단일 턴 문제에서는 9개가 사실상 같은 점수를 내고, 여러 턴을 도는 문제에서만 폭이 벌어진다.

이 표의 셀은 규칙 채점이 아니다. correctness 는 저장소 지표 카탈로그에서 kind: LLM 이고, 채점기가 LLM 없이는 실행을 거부한다 (eval/core/deal_server.py:320). 프롬프트는 답이 사실로 맞고 완전한지를 묻고 correct 와 incorrect 중 하나를 고르게 한다. 따라서 ⑥에서 말한 judge 모델 부재는 이 표 207개 셀 전부에 걸린다.

논문 본문이 자기 표와 어긋나는 곳이 한 군데 있다. §6.1 은 단일 턴 문제의 예로 arc-challenge, gsm8k, openbookqa, humaneval 을 들며 all nine harnesses give identical scores 라고 쓴다. 넷 중 셋은 맞지만 gsm8k 는 crewai 가 0.80 이고 나머지 여덟이 1.00 이라 동일하지 않다. 단일 턴에서 차이가 사라진다는 큰 주장은 남지만, 그 근거로 든 목록 하나가 자기 표와 다르다.

result-cost

결과 2. correctness 가 0.1 폭일 때 토큰은 최소 3.5배 벌어지고, 둘 사이에 교환 관계가 없다

1,035회에서 sandbox 벤치마크 4개를 뺀 855회를 trajectory 로 읽으면 그림이 달라진다. correctness 는 8개 harness 에서 0.568 에서 0.663 사이에 머무는데 평균 토큰은 2,063 에서 7,319 로 벌어진다. 비싸게 쓴 쪽이 더 맞히는 것도 아니다.

정답률을 사려면 토큰을 더 써야 한다는 관계가 이 벤치마크 묶음에서는 성립하지 않는다. 비싼 쪽은 그냥 비싸다.

3.5배는 하한으로 읽어야 한다. 빠진 하나는 crewai 이고, 빠진 이유가 성능이 아니라 계측 실패다. LLM span 에 토큰이 실려 오지 않아 잴 수가 없었다. 측정된 8개 바깥에 값이 하나 더 있는 이상 9개 전체의 폭은 3.5배 이상이며, 그보다 좁아질 수는 없다.

세 패널의 성공률 격차는 GDPVal 0.20, MMLU-Pro 0.30, τ³-bench 0.66 으로 §6.3 본문에 적혀 있다. 과제가 길고 tool 상호작용이 많을수록 harness 의 실행 전략이 더 크게 작용한다는 것이 논문의 해석이다.

두 실험은 같은 축에 놓을 수 없다. ⑩의 표 1 은 DeepSeek-V4-pro 로 correctness 를 재고, 이 그림은 GLM-5.2 로 task success rate 를 잰다. 지표도 다르고 모델도 다르다. 토큰도 한쪽은 prompt 와 completion 의 합, 이 그림은 completion 만이다. 또한 Figure 6 의 correctness 0.568 에서 0.663 은 객관식 추출기가 빈 예측을 낸 44개 run 을 다시 채점한 값이라, Table 1 의 0.57 에서 0.68 과 정확히 같은 수가 아니다.

claude-label

표의 Claude Agent SDK 행은 Claude Agent SDK 로 돌린 것이 아니다

논문 Table 1 캡션은 Claude AS stands for Claude Agent SDK 라고 적고, Figure 6 과 Figure 7 도 Claude-Agent-SDK 라는 이름을 쓴다. 코드가 부르는 것은 anthropic 패키지이고, 그 위에 직접 짠 8턴 루프다.

확인 지점무엇이라고 되어 있나

논문 §2 OverviewSDK 기반 agent 를 열거하며 Claude-Agent-SDK 라고 쓴다 (overview.tex:55). 결과가 실리는 자리가 아니고 시스템 구조를 설명하는 자리다

저장소에 진짜 Claude Agent SDK 계측기가 없는 것도 아니다. monitor/instrumentation/openinference-instrumentation-claude-agent-sdk/ 가 있고 의존성은 claude-agent-sdk>=0.1.45, query() 와 ClaudeSDKClient 의 connect, query, receive_response 를 감싼다. 다만 벤치마크에 들어간 harness 가 쓰는 계측기는 anthropic 쪽이다. 같은 저장소 안에서 claude-sdk 라는 이름이 두 가지를 가리킨다.

저장소를 Claude Code 로 검색하면 실행 화면 경고문 하나가 걸린다. server/.../routers/a2e.py:349 가 claude-sdk agent 에 대해 claude-agent-sdk which spawns the Claude Code CLI subprocess 라고 적고 claude 바이너리가 PATH 에 있어야 한다고 안내한다. 그런데 같은 파일이 실행을 넘기는 키는 registry 의 claude-sdk 이고, 그 키가 만드는 runner 의 docstring 은 subprocess 를 쓰지 않는다고 적는다. 저장소 안내문 쪽이 실제 코드를 따라오지 못한 것으로 보인다. 어느 쪽이든 논문 결과를 만든 실행 경로는 anthropic runner 다.

이 행에만 출력 상한이 걸려 있다. 논문은 9개가 같은 inference 설정을 공유한다고 쓰지만 예외가 둘이다. max_tokens 를 넘기는 곳은 claude_sdk 하나뿐이고 (grep -rn "max_tokens" --include="*.py" task/agents/ → 1건), temperature 를 박아 넣는 곳도 llama-index 하나뿐이다 (같은 grep 으로 llama_index/agent.py:89 의 temperature=1.0 1건). 뒤쪽은 ⑩에서 19개 비sandbox 평균 1위로 지목한 harness 다. Anthropic Messages API 는 이 값을 필수로 요구하므로 구현자가 무언가는 골라야 했지만, 2048 이라는 값이 다른 여덟과 맞춰진 값은 아니다. 다만 이 상한이 2,063 이라는 최저값을 만들었다고 말할 근거는 없다. 8턴 × 2048 이면 completion 상한이 16,384 이고, 2,063 은 prompt 와 completion 을 합한 평균이라 상한에 닿은 run 이 있었는지를 이 문서는 보이지 못한다. 말할 수 있는 것은 inference 설정이 완전히 맞춰지지 않았다는 데까지다.

claude-code

Claude Code 관점. 이 논문에서 가져갈 것은 측정 설계다

Claude Code 는 이 실험에 없다. 논문에도 저장소 문서에도 Claude Code 를 돌렸다는 기록이 없고, ⑫에서 본 대로 그 이름이 붙은 행은 다른 것이다. 그래도 이 논문이 Claude Code 를 쓰는 쪽에 남기는 것이 세 가지 있다.

1 · 지표 선택

최종 정답률은 harness 를 가르지 못한다. 9개가 0.11 폭에 몰리는 동안, 토큰을 잰 8개는 최소 3.5배 벌어졌다.

자기 셋업을 평가할 때 pass rate 만 보면 바꾼 것의 효과가 측정되지 않는다. 토큰과 turn 수를 같은 화면에 놓는 것이 이 논문의 실질적 권고다.

2 · 어디에 투자할지

단일 턴 과제에서는 9개 harness 가 같은 점수를 낸다. harness 를 손보는 일이 값을 하는 구간은 다중 턴 tool 과제다.

일회성 변환이나 분류를 배치로 돌리는 작업이라면 harness 를 고르는 데 시간을 쓸 이유가 이 데이터에는 없다.

3 · 실패의 모양

CrewAI 가 진 방식이 일반적이다. completion 토큰은 1.3배 차이인데 prompt 가 11.1배로 벌어졌다.

비용이 튀는 원인은 모델이 길게 답해서가 아니라 문맥이 쌓여서다. 압축, subagent 격리, 명시적 종료 조건이 겨냥하는 지점이 정확히 여기다.

지금 하려는 일이 논문이 답하는 것답하지 않는 것
Claude Code 와 다른 agent 도구를 비교하는 중 없다 Claude Code 도 Claude Agent SDK 도 이 실험에 들어가지 않았고, 백본 모델도 Claude 가 아니었다
내 agent 셋업의 개선을 측정할 지표를 고르는 중 정답률 단독으로는 안 갈린다. 토큰, turn 수, tool 호출 수를 함께 어떤 조합이 최적인지. 논문도 나머지 process 지표는 이 벤치마크 묶음에서 잘 안 움직였다고 적는다
다중 턴 작업에서 비용이 튀는 원인을 찾는 중 prompt 누적을 먼저 볼 것. completion 이 아니다 내 워크로드의 원인. 사례는 τ³-bench 한 문항이다
Claude Agent SDK 앱에 trace 를 붙이려는 중 저장소에 OpenInference instrumentor 가 있다. query() 와 ClaudeSDKClient 를 감싼다 그 instrumentor 가 얼마나 검증됐는지. 논문 실험은 이걸 쓰지 않았다
단일 턴 배치 작업의 harness 를 고르는 중 고민할 값이 크지 않다. humaneval, arc-challenge, openbookqa 에서 9개가 동점이다 벤치마크 밖의 과제

"claude-sdk 가 가장 싸다"를 Claude 쪽 효율로 옮겨 읽으면 두 번 틀린다. 첫째로 그 행은 출력 2048 상한이 걸린 최소 루프이고 (8턴은 9개 공통이라 이 harness 만의 제약이 아니다), 둘째로 그 위에서 돈 모델은 DeepSeek-V4-pro 다. 실제로 모델을 GLM-5.2 로 바꾼 Figure 7 에서는 같은 harness 가 MMLU-Pro 와 GDPVal 두 패널에서 completion 토큰이 가장 많은 점으로 찍힌다 (그림에서 눈으로 읽은 위치라 근사치다). 토큰 상한이 어디서나 통하는 할인은 아니라는 뜻이고, 2,063 이라는 수도 그 조건에서만 나온 값이다.

critique

해석의 한계. 셀마다 5문항이라 표 1 은 순위표로 쓸 수 없고, 논문도 그렇게 쓰지 말라고 적는다

가장 큰 제약을 논문이 먼저 밝힌다. 벤치마크마다 문항이 5개뿐이라 점수가 0.20 단위로만 움직이고 셀 단위 분산이 크다. 아래는 논문이 스스로 적은 것과 이 문서가 확인해 덧붙이는 것을 나눠 놓은 것이다.

논문이 명시하는 한계
  • ·셀당 5문항이라 해상도가 0.20 이고 분산이 크다. 표의 목적은 격자 전체가 한 파이프라인에서 실행되고 채점된다는 것을 보이는 데 있다
  • ·registry 에 있다는 것이 그 조합이 end-to-end 로 검증됐다는 뜻은 아니다
  • ·crewai 는 LLM span 에 토큰이 실리지 않아 토큰 비교에서 빠진다
  • ·Figure 6 의 tool_invocation 과 hallucination 행은 계측이 정하는 값이지 harness 행동으로 읽으면 안 된다

  • ·벤치마크 이름이 실제 돌린 것보다 넓다. bbh 는 boolean_expressions subtask 하나만 돌리고, agieval 은 AQuA-RAT 부분집합만 돌린다. gpqa 는 원본이 gated 라 GPQA-diamond 미러(198문항), math 는 MATH-500 으로 바꿨다. 데이터셋 교체 네 건은 qa_suite/.../benchmarks.py 상단 주석에 있고, bbh 가 subtask 하나로 좁혀지는 것은 주석이 아니라 같은 파일 74행의 설정값에 있다. 표 1 은 이 치환을 적지 않는다

재현 여부도 아직 없다. v1 이 2026-08-07, 코드 공개가 2026-08-10 이라 (README.md:46) 외부 재현 보고가 나올 시간이 지나지 않았다. 문항마다 실행이 한 번씩이고 반복 실행이나 신뢰구간, pass@k 도 보고되지 않는다. 따라서 표 1 의 셀 하나하나는 점추정이며, 0.20 차이는 잡음과 구별되지 않는다.

한계를 통과해 남는 것. 표본이 작아 무너지는 것은 순위이지 패턴이 아니다. 단일 턴 문제에서 9개 harness 가 전부 같은 점수를 낸다는 관찰은 순위가 아니라 동점이라서 해상도 문제의 영향을 받지 않는다. case study 의 prompt 11.1배 대 completion 1.3배도 한 문항의 실측값이라 표본 크기와 무관하게 그 문항에서는 참이고, 문맥 누적이 비용을 만든다는 메커니즘은 다른 데서 다시 확인해볼 수 있는 형태다. ATP 처럼 어댑터를 양쪽으로 가르는 설계도 실험 수치와 독립적으로 남는다.

adopt

도입 판단. 순위를 얻으려고 쓰면 실망하고, 자기 격자를 돌리는 틀로 쓰면 값을 한다

A2E 가 내놓은 숫자를 그대로 인용하는 것과, A2E 를 자기 조건으로 다시 돌리는 것은 다른 결정이다. 논문 스스로 표 1 을 순위표로 쓰지 말라고 적은 이상 전자의 값은 크지 않다. 후자는 문항 수만 늘리면 바로 쓸 수 있는 형태다.

쓸 만한 조건

여러 harness 를 같은 조건에 세워야 할 때. 어댑터를 조합마다 쓰지 않아도 되는 것이 실질적 이득이고, 이 부분은 실험 수치와 무관하게 성립한다.

trajectory 를 OpenTelemetry 로 남기고 싶을 때. 기록이 표준 span 이라 이후 도구가 그대로 읽는다. harness 코드를 고치지 않는다.

지표를 나중에 추가할 때. trajectory 생성과 채점이 분리돼 있어 agent 를 다시 돌리지 않고 저장된 기록 위에서 재채점한다. 평가 기준이 자주 바뀌는 환경에서 이게 가장 큰 절약이다.

License 는 MIT 다. 테스트 파일은 818개 있다 (git ls-tree -r HEAD --name-only | grep -cE "(^|/)tests?/|_test\.py$|test_.*\.py$"). 있다는 사실만 센 것이고 무엇을 보장하는지는 열어보지 않았다.

맞지 않는 조건

harness 를 고르려고 순위가 필요할 때. 셀당 5문항, 해상도 0.20, 신뢰구간 없음. 논문도 순위 용도를 부정한다.

Claude Code 나 Claude Agent SDK 를 평가하려 할 때. 둘 다 이 실험에 없다. 계측기는 저장소에 있지만 논문 결과에는 쓰이지 않았다.

벤치마크 이름 그대로의 점수가 필요할 때. bbh 와 agieval 은 부분집합으로 치환돼 있어 다른 논문의 같은 이름과 나란히 놓을 수 없다.

공개 3일 차 코드라는 점. 이 커밋에 .github/ 가 없어 CI 설정이 없다. shallow clone 이라 못 하는 주장(커밋 빈도, 기여자)과 달리 이건 이 커밋에서 그냥 보이는 사실이다.

가볍게 얹어보려 할 때. AutoGen AgentChat 은 protobuf 충돌로 별도 uv 환경을 쓴다 (task/agents/autogen_agentchat/README.md:16, pyproject.toml:21). sandbox 벤치마크는 Docker 를 요구하고 이미지가 과제당 1GB 에서 3GB 다 (README.md:163).

정리하면 도입 판단의 갈림길은 A2E 를 결과의 출처로 볼 것인가 실행 틀로 볼 것인가다. 결과의 출처로는 약하다. 표본이 작고 라벨에 오류가 있으며 baseline 비교가 없다. 실행 틀로는 지금 상태로도 쓸 수 있고, 문항 수를 5에서 늘리는 것은 CLI 인자 하나다. 기본값이 40문항이라고 §4.3 에 적혀 있는데 실험은 5로 돌렸으므로, 올리는 쪽이 설계 의도에 오히려 가깝다.

다만 그 인자 하나의 대가는 작지 않다. 5를 40으로 올리면 실행 횟수가 1,035 에서 23×9×40, 즉 8,280 으로 여덟 배가 된다. ⑧의 사례에서 한 문항이 0.0051 에서 0.0430 이었으니 격자 전체를 다시 돌리는 비용은 그 규모로 늘어난다. 그리고 논문 스스로 registry 등록이 조합의 end-to-end 검증을 뜻하지 않는다고 §4.2 에 적었으므로, 내가 쓰려는 조합이 실제로 도는지는 저자도 보증하지 않는다.

이 판단이 확인하지 못한 것. 설치해 돌려보지 않았으므로 문항 수를 늘렸을 때 실제로 완주하는지는 모른다. 위의 "실행 틀로는 쓸 수 있다"는 코드 구조를 읽고 내린 판단이지 실행 결과가 아니다. scripts/start.sh 를 열지 않아 설치 요건도 README 의 진술에 기대고 있다.

conclusion

결론. 이 논문의 값은 "정답률로는 안 보인다"는 음성 결과에 있다

A2E 가 실제로 보여준 것은 어느 harness 가 낫다는 것이 아니다. 백본을 고정하고 9개를 같은 조건에 세웠더니 최종 정답률이 0.11 폭에 몰렸다는 것, 그리고 그중 855회를 토큰으로 보면 측정 가능한 8개 사이가 3.5배 벌어졌다는 것이다. 나머지 하나는 계측 실패라 이 폭은 하한이다.

  • 1최종 정답률은 harness 를 구별하는 도구로 해상도가 낮다. 단일 턴 과제에서는 9개가 동점이고, 전체 평균도 0.57 에서 0.68 사이다. agent 시스템을 평가하면서 pass rate 만 보면 바꾼 것의 효과가 측정되지 않는다.
  • 2차이는 비용 쪽에 있고, 정답률과 교환되지 않는다. 가장 잘 맞힌 agno 가 동시에 두 번째로 싸다. 비싼 harness 는 그 대가로 정답률을 사 오지 않는다. 토큰 폭 3.5배는 9개 중 8개만 측정된 값이라 하한이다.
  • 3비용이 벌어지는 자리는 prompt 다. 같은 문항에서 completion 은 1.3배 차이인데 prompt 가 11.1배로 벌어졌다. 문맥 누적을 다루는 설계가 harness 사이의 실질적 차이라는 뜻이다.
  • 4표의 라벨 하나는 신뢰할 수 없다. Claude Agent SDK 로 표기된 행은 anthropic 패키지 위의 8턴 루프이고, 그 위에서 돈 모델도 Claude 가 아니다. 이 행에서 Claude Code 에 관한 결론을 끌어낼 수 없다.

Claude Code 를 쓰는 쪽이 이 논문에서 가져갈 것은 무엇을 측정할지다. turn 수와 prompt 토큰을 정답률 옆에 두는 것, 그리고 harness 를 손보는 노력을 다중 턴 tool 과제에 몰아주는 것. 이 둘은 실험에 Claude 가 들어가지 않았어도 그대로 옮겨간다.

남는 질문. 문항을 5에서 기본값 40으로 올리면 표 1 의 동점과 격차가 어떻게 변하는지는 아직 아무도 보고하지 않았다. 단일 턴 동점이 문항 수를 늘려도 유지된다면 이 논문의 가장 중요한 관찰이 되고, 무너진다면 5문항의 산물이었다는 뜻이 된다. 이 문서는 그 실험을 돌리지 않았다.
