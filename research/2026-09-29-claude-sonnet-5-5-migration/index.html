Claude Sonnet 5.5: Sonnet 5 에서 옮길 때 바꿔야 하는 요청과 effort

Anthropic 이 2026-09-28 에 낸 "Introducing Claude Sonnet 5.5" 와 Sonnet 5.5 migration guide, thinking 문서 한 편을 하나의 질문으로 읽는다. Sonnet 5 에서 Sonnet 5.5 로 옮기는 개발자는 무엇을 바꿔야 하는가. 소개 글이 코드 변경을 행동으로 지시한 것은 thinking 을 끄던 사람은 between_tools 로 바꾸라는 한 문장이고, 계정 사이에 대화를 옮기는 경우는 문서를 가리키기만 한다. 나머지 변경은 migration guide 에 있다.

할 일만 필요하면 14장으로 바로 가면 된다. 고객 인용과 안전 평가처럼 코드 변경과 거리가 먼 원문 부분은 16장에 모았다. 같은 시기에 나온 Opus 5.5 의 변경은 Claude Opus 5.5 문서에 있다.

tl-dr

Sonnet 5.5 로 옮기면 thinking 을 끄던 요청과 tool_choice 를 강제하던 요청이 400 을 받고, 비용은 effort 를 어디에 두느냐로 갈린다

가격은 Sonnet 5 와 같아서 입력 $2, 출력 $10, 캐시 읽기 $0.20 이다. 원문은 태스크당 토큰이 줄어 대부분의 일에서 최대 30% 싸다고 쓰는데, 원문 차트를 같은 effort 끼리 놓아 보면 Terminal-Bench, FrontierCode, CursorBench 에서는 high 이하가 훨씬 싸지고 AA-Briefcase 는 비슷하며, max 에서는 네 벤치마크 모두 Sonnet 5 보다 비싸다.

  • 코드thinking 을 끄던 요청은 between_tools 로 바꾸고 tool_choice 의 any 와 tool 은 auto 와 strict tool 로 바꾼다. 대화는 append-only 로 두고 computer use 는 toolset 으로 옮긴다. advisor 로 Sonnet 5 를 쓰고 있었다면 짝을 바꿔야 한다 (04장부터 07장).
  • 응답tool call 사이의 긴 메모는 thinking 블록으로 오고 기본 설정에서는 비어 있어서, 진행 상황을 보여 주던 UI 가 조용해진다. 거부는 다섯 부류로 오는데, 그중 bio 와 reasoning_extraction, general_harms 는 fallback 이 다시 보내 주지 않는다 (08장, 09장).
  • 비용API 기본 effort 는 high 로 Sonnet 5 와 같은 이름이지만, 단계가 다시 조정돼 같은 이름에서 thinking 양이 다르다. 그래서 effort sweep 을 다시 돌려야 하고, 원문 차트에서 Sonnet 5.5 의 max 는 xhigh 보다 2.4~13배 비싸다 (11장, 12장).
  • 분담원문 스스로 복잡하고 열린, 판단이 오래 필요한 일에서는 Opus 5.5 가 "clearly stronger" 라고 쓴다. 따로, 차트에서도 FrontierCode 의 Opus 5.5 medium(54.6%, $0.80)은 Sonnet 5.5 의 어느 effort 점보다 높다. 신뢰구간이 없어 2.5pt 차이가 유의한지는 알 수 없다 (13장).

벤치마크 수치들은 모두 Anthropic 이나 평가사가 잰 값이고 고객 수치는 조건 없이 보고된 값이다. 이 문서는 그 수치를 재현하지 않았고, 원문과 migration guide 가 서로 맞는지 대조했다.

problem

Sonnet 5 는 Terminal-Bench 4.0 에서 max 로도 10.3% 에 그쳤고, 같은 일에 토큰을 많이 썼다

소개 글은 Sonnet 5.5 가 무엇을 고쳤는지 쓰면서 Sonnet 5 가 어디서 막혔는지를 함께 드러낸다. 옮기는 개발자에게 그 약점은 지금 코드가 어떤 우회를 품고 있는지 알려 준다.

터미널 과제

Sonnet 5 는 Terminal-Bench 4.0 에서 10.3% 였다. 원문 차트에서 Sonnet 5 는 low 3.2% 부터 max 10.3% 까지 모든 effort 에서 GPT-5.6 Sol 보다 낮다. Sonnet 5.5 는 max 에서 70.6% 로, 표의 Opus 5.5 값 66.4% 보다도 높다.

토큰

한 고객의 측정에서 Sonnet 5 는 같은 답에 토큰을 약 4배 썼다. Balyasny Asset Management 는 금융 과제 2,441개에서 답 하나에 Sonnet 5 가 497k 토큰을, Sonnet 5.5 가 약 121k 토큰을 썼다고 말한다. CodeRabbit 은 Sonnet 5 의 잦은 web search 와 높은 토큰 사용이 새 모델에서 사라졌다고 쓴다.

안전장치

Sonnet 5.5 는 가장 강한 모델의 것과 비슷한 cyber 안전장치를 단 첫 Sonnet 이다. 원문은 Sonnet 5.5 의 cyber 능력이 Opus 5 에 견줄 만해서, 가장 강한 모델을 위해 만든 것과 비슷한("like those") cyber 안전장치와 fallback 을 붙였다고 쓴다. Sonnet 5 에 어떤 cyber 안전장치가 있었는지는 소개 글도 guide 도 확정하지 않는다. 그래서 Sonnet 5 에서 돌던 보안 작업 일부가 옮긴 뒤에는 거부될 수 있다 (09장).

Sonnet 5 에서 thinking 을 끄고 쓰던 코드가 많았다는 것은 원문이 직접 쓰지 않았다. 다만 소개 글이 행동으로 지시한 코드 변경이 thinking 을 끄던 사람을 향하고 있어서, 04장을 가장 먼저 둔다.

api · between_tools

thinking 을 disabled 로 보내던 요청은 400 을 받으므로 between_tools 로 바꾸고, effort 는 high 이하에 묶어 둔다

Sonnet 5.5 는 Sonnet 5 처럼 thinking 필드가 없는 요청을 adaptive thinking 으로 돌리지만, Sonnet 5 가 받던 thinking.type 의 disabled 는 받지 않는다. 대신 받는 값은 adaptive 와 between_tools 둘이다. between_tools 는 가장 낮은 thinking 설정으로, 답하기 전의 thinking 은 끄고 tool call 사이의 진행 메모만 thinking 블록으로 남긴다. 도구가 없는 요청이라면 응답은 텍스트뿐이다.

between_tools 는 Sonnet 5.5 를 제공하는 모든 플랫폼에서 beta header 없이 쓸 수 있다. 하지만 Sonnet 5 에서 thinking 을 끄고 xhigh 로 돌리던 요청은 설정 하나만 바꿔서는 옮길 수 없다. migration guide 의 예시가 바로 이 경우인데, disabled 에 xhigh 를 쓰던 Sonnet 5 요청을 between_tools 에 high 로 바꿔서 effort 를 한 단계 내린다. xhigh 를 지키려면 thinking 을 adaptive 로 켜야 한다. 두 선택이 품질에 주는 차이는 guide 에 없다.

api · tool_choice

tool_choice 를 any 나 tool 로 강제하던 요청은 token counting 까지 400 을 받으므로, auto 와 strict tool 로 바꾸고 언제 부를지 프롬프트에 적는다

migration guide 에 따르면 guide 가 다루는 이전 모델은 모두 tool_choice 의 any 와 tool 을 받았다. Sonnet 5.5 는 둘 다 거부하고 요청 전에 토큰을 세는 token counting endpoint 에서도 같은 400 을 낸다. 대체는 auto 에 strict: true 를 붙이는 것인데, 이러면 모델이 도구를 부르지 않고 답할 수 있게 된다.

지금 보내는 것Sonnet 5.5 에서바꿀 것
tool_choice {"type": "any"}400. token counting 도 400tool_choice auto 로 바꾸고 도구에 strict: true 를 단다. 언제 부를지는 프롬프트에 적는다
tool_choice {"type": "tool", "name": ...}400위와 같다. 특정 도구를 꼭 부르게 하던 흐름은 모델이 도구 없이 답하는 경우를 처리해야 한다
Amazon Bedrock 에서 위 둘400Bedrock 에서는 strict tool use 를 포함한 structured outputs 를 Sonnet 5.5 에 쓸 수 없다. strict 없이 auto 만 보내고 도구 입력은 코드에서 검증한다
strict 의 한도

요청 하나에 strict tool 은 최대 20개다. MCP 와 computer use, browser use toolset 항목은 strict 를 받지 않는다. strict tool use 는 JSON Schema 의 일부만 지원하고 모든 object 에 additionalProperties: false 가 있어야 한다. 도구 목록이 길다면 꼭 필요한 도구에만 strict 를 단다.

왜 코드가 바뀌나

강제 호출은 응답에 tool_use 블록이 반드시 있다는 가정을 코드에 심어 둔다. auto 에서는 그 가정이 깨지므로, 도구 호출이 없는 응답이 왔을 때 다시 묻거나 텍스트를 그대로 쓰는 분기가 필요하다. guide 는 "say in the prompt when to use it" 이라고만 쓰고, 모델이 도구를 부르지 않는 비율은 적지 않는다.

Claude Managed Agents 를 쓰는 경우에는 이 장을 포함해 모델 이름 말고는 바꿀 것이 없다고 guide 첫머리가 적는다. 이 문서의 04장부터 09장은 Messages API 를 직접 부르는 코드에 해당한다.

api · preserved thinking

2026-08-31 이후 만든 계정에서는 앞선 대화를 고친 뒤 thinking 블록을 다시 보내면 400 이 오고, Sonnet 5.5 의 블록은 만든 계정 밖에서 쓸 수 없다

Sonnet 5.5 의 thinking 블록은 두 가지에 묶인다. 하나는 모델이고, 다른 하나는 그 블록 앞의 대화와 계정이다. 원문 Safety 절은 Sonnet 계열 최초로 reasoning extraction 을 막는 분류기를 달았고 preserved thinking 도 넓혔다고 쓰면서, 대부분의 개발자는 변화를 알아채지 못할 것이라고 덧붙인다.

모델에 묶임

Sonnet 5.5 는 Sonnet 5 와 Opus 4.8, Haiku 4.5, 그리고 그 이전 모델의 블록을 읽는다. Opus 5 와 Opus 5.5, 모든 Fable 과 Mythos 모델의 블록은 읽지 못한다. 읽지 못하는 블록은 API 가 버리는데, 요청은 여전히 200 을 돌려주고 버린 블록에는 과금하지 않는다.

그러니 Opus 5.5 에서 Sonnet 5.5 로 대화를 넘기는 라우터는 오류 없이 reasoning 을 잃는다. 반대로 Sonnet 5.5 의 블록을 읽는 다른 모델은 없다고 whats-new 문서가 쓰므로, Sonnet 5.5 에서 다른 모델로 넘겨도 reasoning 을 잃는다. Opus 5.5 쪽 규칙은 Opus 5.5 문서 05장에 있다.

대화와 계정에 묶임

Sonnet 5.5 의 thinking 블록마다 그 앞의 대화가 서명된다. 2026-08-31 00:00 UTC 이후 만든 계정에서는 Claude API, Amazon Bedrock, Google Cloud 모두 이 검사를 기본으로 켜서, 앞선 대화를 고친 뒤 블록을 다시 보내면 400 이 온다. 블록은 그것을 만든 계정이나 연결된 계정에서만 쓸 수 있다.

대신할 방법은 대화를 append-only 로 두고 지시나 도구를 바꿀 때는 mid-conversation system message 를 쓰는 것이다. 원문은 Claude Code 에서 세션 도중 계정을 바꾸는 경우도 영향을 받는다고 쓴다.

2026-08-31 이전에 만든 계정은 whats-new 문서에 따르면 thinking.block_binding.prefix_mismatch_behavior 를 보내야 검사에 들어간다. 블록을 400 대신 버리려면 beta header thinking-binding-controls-2026-08-01 과 함께 이 값을 "drop_block" 으로 두는데, block_binding 은 adaptive 에서만 받고 between_tools 에서는 400 이다. 그러니 컨텍스트를 줄이려고 대화를 고치는 파이프라인은 adaptive 로 두고 drop_block 을 쓰거나, 고친 턴부터 thinking 블록을 빼야 한다.

api · 도구 설정

Claude API 와 Google Cloud 의 computer_20251124 와 Sonnet 5 advisor 는 400 을 받으므로, computer use 는 toolset 으로 옮기고 advisor 는 Opus 5.5 같은 짝으로 바꾼다

두 변경 모두 Sonnet 5 에서 그대로 돌던 도구 설정이 요청 단계에서 막히는 경우다. computer use 는 플랫폼에 따라 받는 버전이 다르고, advisor tool 은 Sonnet 5.5 가 실행자일 때 받을 수 있는 조언자 모델이 줄었다.

조언은 암호화되어 온다

조언은 advisor_redacted_result 블록으로 암호화되어 오므로, 응답에서 그 내용을 읽을 수 없다. 조언 텍스트를 로그로 남기거나 사용자에게 보여 주던 코드는 옮긴 뒤에 읽을 수 없는 암호화 블록을 받는다.

Sonnet 5 를 조언자로 두고 Sonnet 5.5 를 실행자로 올리는 식의 부분 이전이 가장 먼저 깨진다. computer use 는 요청만 바꾸면 끝나지 않는다. whats-new 문서는 agent loop 도 member tool_use 블록과 batch action, 결과의 toolset_name 에 맞게 고치라고 쓰는데, 그 절차가 있는 computer-use 문서는 이 문서가 열지 않았다. 이미 toolset 을 보내는 코드는 computer use 쪽에서 바꿀 것이 없다고 guide 가 쓴다.

api · 응답 모양

tool call 사이에 모델이 쓰는 긴 메모는 thinking 블록으로 오고 기본 설정에서는 비어 있어서, 진행 상황을 보여 주던 화면이 오류 없이 조용해진다

Sonnet 5 에서는 tool call 사이의 텍스트가 모두 text 블록으로 왔다. Sonnet 5.5 에서는 한두 문장보다 긴 메모가 progress-update thinking 블록으로 오고 짧은 말만 text 로 남는다. display 기본값이 omitted 라서 그 블록의 내용은 비어 있다. 요청은 하나도 실패하지 않는다.

읽는 코드

응답이 thinking 블록으로 시작할 수 있으므로 content[0].text 를 읽던 코드는 깨진다. guide 는 Sonnet 5 코드라면 대개 이 처리를 이미 갖췄다고 보는데, thinking 을 끄고 쓰던 코드는 예외일 수 있다. 블록은 type 으로 골라 읽고 비어 있지 않은 thinking 블록은 바로 뒤의 tool_use 블록보다 먼저 화면에 그린다. tool-use 루프에서는 thinking 블록을 빈 것까지 바꾸지 않고 되돌려 보낸다.

과금은 display 와 무관하다

thinking 문서에 따르면 display 를 무엇으로 두든 과금은 같고 보이는 것만 달라진다. reasoning 에 쓴 토큰은 usage.output_tokens_details.thinking_tokens 로 확인한다. thinking 은 max_tokens 안에 들어가고 출력 토큰으로 과금되므로, max_tokens 도 다시 잡는다.

어느 길이부터 thinking 블록으로 가는지는 guide 가 "a sentence or two" 로만 적어서, 화면에서 사라지는 메모의 비율은 워크로드에서 재야 한다.

api · 거부와 fallback

Sonnet 5.5 의 거부는 stop_details 의 다섯 부류로 오고, server-side fallback 은 그중 cyber 와 frontier_llm 만 Sonnet 5 로 다시 보낸다

migration guide 는 Sonnet 5.5 가 Sonnet 5 보다 많은 부류에서 거부한다고 쓴다. 거부된 요청은 stop_reason "refusal" 로 오고, stop_details 에 부류 하나가 적힌다. 소개 글에 따르면 높은 위험의 cyber 작업은 Sonnet 5 로 눈에 보이게 넘어가고, 일상적인 버그 찾기와 수정은 막히지 않는다. API 에서 Sonnet 5 로 다시 보내는 server-side fallback 은 beta 이고 Claude API 에서만 된다.

cost · 가격

토큰당 가격은 Sonnet 5 와 같아서, 원문이 말하는 최대 30% 절감은 모두 태스크당 토큰이 줄어서 생긴다

소개 글은 Sonnet 5.5 가 Sonnet 5 와 같은 가격이지만 같은 일에 토큰을 훨씬 덜 써서, 테스트에서 태스크당 최대 30% 싸다고 쓴다. 가격표는 Opus 5.5 와 나란히 실려 있고 Opus 5.5 는 캐시 읽기를 뺀 세 항목이 두 배다.

effort 를 바꾸는 두 방법

thinking 문서에 따르면 effort 값이 프롬프트 안에 들어가기 때문에, 요청 사이에 top-level effort 를 바꾸면 캐시 breakpoint 가 무효가 된다. 기본값과 같은 effort 를 명시하는 것은 생략한 것과 같아서 캐시를 깨지 않는다. Sonnet 5.5 에는 Sonnet 5 에 없던 per-message effort(beta, header mid-conversation-output-config-2026-07-01)가 있어서, 메시지 단위로 effort 를 바꾸면 캐시가 유지된다고 effort 문서가 쓴다. between_tools 에서는 이 방법도 400 이다.

캐시 읽기는 Sonnet 5.5 와 Opus 5.5 가 똑같이 $0.20 이다. 캐시 적중이 청구서 대부분인 agentic 워크로드에서는 두 모델의 비용 차이가 가격표의 두 배보다 작아진다는 뜻이고, 이 추론은 이 문서의 것이다. 캐시 쓰기 $2.50 이 5분 캐시인지는 소개 글 표에 적혀 있지 않다.

cost · effort 재조정

API 기본 effort 는 Sonnet 5 와 같은 high 이지만, 단계가 다시 조정되어 같은 이름에서 thinking 양이 달라지므로 effort sweep 을 다시 돌린다

Opus 5.5 는 기본 effort 를 medium 으로 내렸지만, Sonnet 5.5 는 Claude API 기본값을 high 로 둔다. 이름은 같아도 guide 는 "a level doesn't produce the same amount of thinking as on Claude Sonnet 5" 라고 쓴다. 그러니 effort 를 적지 않은 코드도, 적어 둔 코드도 다시 재야 한다.

cost · 같은 effort 의 비용

같은 effort 끼리 놓으면 Sonnet 5.5 는 high 까지 대체로 훨씬 싸지만, max 에서는 네 벤치마크 모두 Sonnet 5 보다 비싸다

원문 차트는 모델마다 effort 다섯 단계를 점으로 찍는다. 원문 본문은 Sonnet 5.5 의 낮은 effort 점을 Sonnet 5 의 최고점과 비교하는데, 아래 표는 같은 effort 끼리 비교한 것으로 원문에는 없는 계산이다.

Sonnet 5 에서 옮기는 개발자가 할 일은 상황별로 열두 가지이고, guide 의 체크리스트 마지막 줄이 effort 를 다시 재고 비용 기준선을 새로 잡으라는 것이다

background · 고객 인용과 안전 평가

고객 인용 13개 가운데 수치를 든 인용은 대부분 토큰과 단계, 시간이 줄었다고 말하고, 원문의 안전 평가는 Sonnet 5.5 가 능력의 최전선을 넓히지 않는다는 전제에서 범위를 좁혔다

이 장은 질문에 직접 답하지 않는 원문 부분들을 모은다. 고객 인용은 Coding 절에 7개, Knowledge work 절에 6개다. 인용들에는 비교 조건과 시행 횟수, effort 설정이 적혀 있지 않다.

원문의 안전 평가

원문은 어떤 평가 묶음도 모든 실패를 믿을 만하게 잡지는 못한다고 쓰고, Sonnet 5.5 가 모델 능력의 최전선을 넓히지 않으므로 사용자의 이익에 반하는 행동과 사용자를 속이는 행동, 고위험 오용에 협조하는 행동처럼 능력과 상관없는 위험으로 평가를 좁혔다고 쓴다. 약 1,850개 시나리오의 자동 행동 감사에서 alignment 와 오용 저항, 정직성 대부분이 Sonnet 5 와 같거나 나았다. 새 containment 평가에서는 sandbox 탈출 시도가 가장 적은 Opus 5.5 에 가깝고, 컨테이너의 한계를 떠보는 경향은 Anthropic 모델 가운데 가장 낮다.

원문의 내부 시험

한 상장사의 분기 실적 자료와 콜 녹취, 슬라이드 템플릿을 주고 10장짜리 운영 리뷰를 만들게 했더니, 전문가 두 명이 첫 초안을 그대로 보내도 된다고 판단했다. GDPval-AA 에서는 44개 직업과 9개 주요 산업의 과제에서 Opus 5.5 와 거의 같고 Sonnet 5 보다 약 400점 높다.

고객 인용에서 effort 를 밝힌 것은 없고, Slack 만 프롬프트를 바꾸지 않았다는 조건을 적는다. 원문은 Opus 5.5 가 전체 감사에서 여전히 조금 낫다고 쓰면서도, Sonnet 5.5 가 사용자 의도와 충돌하는 목표를 좇는다는 증거는 찾지 못했다고 쓴다.

critique

원문은 벤치마크가 능력의 한 면일 뿐이라고 스스로 할인하고, 이 문서는 같은 effort 비교와 max 의 비용을 덧붙인다

원문이 인정한 한계와 이 문서가 주장하는 한계를 나눈다. 이 문서가 덧붙인 것은 원문 차트 점으로 한 계산과, 소개 글이 적지 않은 migration guide 의 변경이다. 이 문서 자신의 한계는 15장에 있다.

원문이 인정한 것
  • 1벤치마크 점수는 모델 능력의 한 면만 잡고, 복잡하고 열린 작업에서는 Opus 5.5 가 분명히 강하다고 쓴다 (13장).
  • 2FrontierCode 에서 max 가 xhigh 보다 낮고, 그 원인이 code-review skill 과 범위 밖 편집이라고 각주로 밝힌다.
  • 3GDPval-AA 와 AA-Briefcase 는 structured outputs 버그가 있는 배포에서 쟀다.
  • 4bio 분류기가 미생물학과 바이러스학 요청 일부를 잘못 걸 수 있고, 어떤 평가도 모든 실패를 믿을 만하게 잡지는 못한다 (09장, 16장).
이 문서가 주장하는 것
  • 1원문은 "최대 30% 절감" 이 어느 effort 기준인지 적지 않는데, 차트로는 max effort 에서 네 벤치마크 모두 Sonnet 5 보다 8~102% 비싸고 AA-Briefcase 는 high 에서도 5% 비싸다 (12장). 원문이 같은 effort 끼리 비교한 것은 FrontierCode high 한 칸(10점 높고 비용 약 1/15)뿐이다.
  • 2"At higher settings, it can perform comparably at a similar cost" 는 FrontierCode 의 max 에서는 맞지 않는다. Sonnet 5.5 max 가 Opus 5.5 max 보다 3.4배 비싸고 8.2pt 낮다 (13장).
  • 3소개 글이 행동으로 지시한 코드 변경은 between_tools 하나이고, 계정 이동은 문서를 가리키기만 한다. forced tool_choice 부터 거부 부류까지 나머지 변경은 migration guide 에 있다.
  • 4API 기본 effort 이름이 Sonnet 5 와 같은 high 라서 바꿀 것이 없어 보이지만, guide 는 단계가 다시 조정되었다고 쓴다 (11장).

하지만 한계를 지나서도 남는 것이 있다. high 이하에서 Sonnet 5.5 는 Terminal-Bench, FrontierCode, CursorBench 에서 Sonnet 5 보다 52~94% 싸면서 점수는 모두 높다. 원문 차트 점이 공개되어 있어서 누구나 이 비교를 다시 할 수 있다.

conclusion

Sonnet 5 에서 옮기는 개발자는 thinking 과 tool_choice 설정부터 고치고, effort 를 high 이하에서 다시 잰 뒤에 max 를 쓸지 정한다

소개 글만 읽으면 가격이 같고 더 싸고 빠른 모델로 보인다. 링크된 guide 까지 읽으면 Sonnet 5 코드에서 요청 단계로 깨지는 설정이 여럿이고, 비용은 effort 선택에 따라 방향이 바뀐다.

  • 1thinking 을 끄던 요청을 between_tools 로 바꾼다. 이 설정은 high 이하에서만 받고, xhigh 나 max 가 필요하면 adaptive 로 켜야 한다 (04장).
  • 2400 을 받는 도구 설정을 지운다. tool_choice 의 any 와 tool, Claude API 와 Google Cloud 의 computer_20251124, 조언자 Sonnet 5 다. 2026-08-31 이후 계정이라면 대화를 append-only 로 둔다 (05장부터 07장).
  • 3거부를 부류별로 처리한다. cyber 와 frontier_llm 은 Claude API 에서 server-side fallback(beta)으로 Sonnet 5 에 넘길 수 있지만, 나머지 셋과 다른 플랫폼의 거부는 코드가 받아서 처리해야 한다 (09장).
  • 4effort sweep 을 다시 돌리고 비용 기준선을 새로 잡는다. high 이하는 대체로 크게 싸지고, max 는 네 벤치마크 모두 Sonnet 5 보다 비싸다. FrontierCode 처럼 Opus 5.5 medium 이 Sonnet 5.5 의 최고점보다 싸고 높은 곳도 있어서, 어려운 일은 Opus 5.5 로 보내는 선택지도 같은 sweep 에 넣는다 (12장, 13장).

이 문서가 확인한 범위는 원문의 숫자가 원문과 차트에 그렇게 적혀 있고 migration guide 와 어긋나지 않는다는 데까지다. 비용 비교는 Anthropic 과 평가사의 벤치마크 점에서 나온 것이어서, 실제 워크로드의 청구서는 옮긴 뒤에 직접 재야 한다.
