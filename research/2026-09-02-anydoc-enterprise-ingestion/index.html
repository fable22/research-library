범용 OCR 대체재가 아니다. 사내 도입 가치는 Office attachment의 표·heading·note·link를 source field에서 회수하는 데 있다.

판단 범위: Office와 text-layer PDF attachment parser는 trial한다. image-only page, diagram, Atlassian body까지 해결하는 단일 제품으로는 채택하지 않는다.

tl-dr

source-native lane으로 한정하면 도입 이유가 선명하다

같은 파일을 OCR보다 무조건 정확하게 읽는 제품이 아니다. 원본 package가 가진 구조를 먼저 쓰고, 그 구조가 없을 때 OCR·VLM·source adapter로 넘기는 router의 한 component다.

채택

Office와 text-layer PDF

DOCX·PPTX·XLSX·legacy Office·ODF·RTF·EPUB·CSV와 모든 page에 text layer가 있는 PDF를 local 처리한다.

비채택

scan과 screenshot

PNG·JPEG는 입력 목록 밖이다. image-only PDF는 NeedsOcr로 중단한다.

별도 통합

Atlassian과 diagram

Jira ADF·Confluence body·draw.io topology는 각 source representation을 읽는 adapter가 필요하다.

권장 판단: 범용 document AI 구매가 아니라 내부 ingestion router의 source parser 후보로 평가한다.

problem

file extension보다 의미가 놓인 위치가 parser를 결정한다

사내 문서의 의미는 package XML, PDF text layer, rendered pixel, SaaS source API에 흩어진다. 한 engine으로 모두 읽으려 하면 이미 존재하는 구조를 버리거나 visual semantics를 놓친다.

package

DOCX·PPTX·XLSX

heading style, cell type, merge, hyperlink target, speaker note가 source에 명시된다.

text layer

text-layer PDF

모든 page에 extractable text가 있다. page별 image-only 여부를 먼저 판별해야 한다.

pixels

scan·screenshot

문자와 배치는 raster에만 남는다. OCR 또는 vision model의 영역이다.

source API

ADF·draw.io graph

node, edge, label, attachment 관계가 JSON/XML과 product API에 남는다.

용어: 모든 page에 extractable text가 있으면 text-layer PDF, image-only page가 하나라도 있으면 image-page PDF로 부른다. 확장자만으로 두 lane을 구분할 수 없다.

mechanism

Office parser는 typed Document를 만들고 PDF parser는 Markdown을 직접 낸다

모델 호출은 두 경로 모두에 없다. Office·ODF·RTF·EPUB parser는 source container를 공통 block과 asset으로 만들고 renderer를 거친다. PDF는 pdf-inspector가 직접 Markdown으로 바꾼다.

diagram의 아래 화살표처럼 PDF path는 공통 Document model을 우회한다. model과 network의 경계는 8장에서 따로 확인한다.

comparison-classic-ocr

Tesseract와 anydoc는 정확도 경쟁 전에 입력 공간이 다르다

classic OCR은 raster에서 glyph를 추정한다. anydoc는 source package에서 field와 relationship을 읽는다. 원본 DOCX를 image로 바꾸는 순간 heading style과 hyperlink target은 pixel 밖으로 버려진다.

OCR을 plain text 전용으로 묘사하면 틀리다. Tesseract도 hOCR·TSV로 위치와 confidence를 낸다. 차이는 구조의 출처다.

comparison-layout-ocr

pixel이 유일한 근거라면 layout OCR와 VLM의 범위가 더 넓다

modern document AI는 OCR 뒤에 layout model을 붙여 heading, table, selection mark, section structure를 추정한다. chart와 diagram의 visual relation은 별도 VLM 평가 대상으로 남긴다.

VLM 평가 후보

rendered page 이해

screenshot·chart·spatial grouping처럼 의미가 pixel에만 있는 corpus에서 승인된 model을 측정한다. source ID와 native edge 보존은 model 가정이 아니라 adapter의 별도 통과 조건으로 둔다.

source parser

anydoc

page layout를 추정하지 않는다. 대신 Office 내부 표·note·link·cached value를 model call 없이 읽는다.

“OCR보다 낫다”는 일반 명제는 성립하지 않는다. source package가 있고 필요한 정보가 package에 명시됐을 때만 anydoc 쪽 근거가 더 직접적이다.

result-advantage

source field에서 직접 회수되는 정보는 네 범주다

parser가 직접 회수하는 범위는 field value, native role, local data boundary, legacy format coverage다. 같은 문서를 OCR과 동시 측정한 accuracy 수치는 공개되지 않았다.

source field recovery

명시된 값은 추정하지 않는다

cell string, hyperlink target, footnote, speaker note, chart cached value를 source field에서 읽는다. glyph 오인식이 개입할 자리가 없다.

structure

native role을 Markdown role로 옮긴다

heading·list nesting·table·merge를 visual 좌표에서 다시 추론하지 않는다.

data boundary

core는 network와 model이 없다

Rust library, CLI, WASM path에서 지원 문서를 local 처리할 수 있다. strict environment에서 egress를 막기 쉽다.

format reach

legacy Office까지 같은 entry point로 읽는다

.doc/.xls/.ppt, OOXML, ODF, RTF, EPUB, CSV, PDF를 한 API로 받는다. PDF는 공통 Document를 거치지 않는다.

이 장점은 downstream answer quality를 자동 보장하지 않는다. Markdown chunking, asset indexing, ACL filter는 별도 품질 축이다.

result-limits

visual relation에는 OCR·layout model·VLM 또는 source adapter가 필요하다

anydoc는 pixel과 geometry를 해석하지 않는다. source field에 없는 정보는 visual lane이나 format-specific source adapter가 맡아야 한다.

enterprise-atlassian

Jira·Confluence에서는 body와 attachment가 서로 다른 pipeline이다

anydoc는 Atlassian connector가 아니다. REST API가 caller에게 허용한 object를 받은 뒤 content representation과 별도 authorization context로 갈라야 한다.

Confluence

page body는 storage·ADF·view representation이다. page attachment API는 download link와 pagination을 제공한다.

Jira

description과 rich text는 ADF JSON이다. attachment content API는 원본 bytes를 반환한다.

이 API는 호출자의 접근권한을 적용하지만 user·group ACL 목록을 attachment 응답에 실어 주지는 않는다. 별도 permission resolver와 identity mapping, revocation sync를 설계해야 한다.

enterprise-diagram

diagram은 screenshot보다 원본 graph를 먼저 읽어야 한다

draw.io는 graph topology를 source representation으로 제공한다. node와 edge가 이미 존재하는데 OCR로 label만 읽으면 핵심 관계를 버린다.

draw.io 공식 embed API의 structural JSON은 topology·label·metadata를 담고 style·geometry는 담지 않는다. 완전한 visual 재현에는 XML 또는 rendered asset도 함께 보관해야 한다.

enterprise-pdf

image-only page가 하나라도 있으면 local PDF conversion 전체가 중단된다

mixed fixture는 1쪽에 text layer가 있고 2쪽은 image-only다. local 실행은 부분 Markdown을 반환하지 않고 typed error를 냈다.

enterprise-security

local parsing만으로 사내 문서 보안이 완성되지는 않는다

ingestion은 원본 system 밖에 새 copy를 만든다. local conversion 여부와 별개로 provenance와 ACL lifecycle을 함께 설계해야 한다.

반드시 동반할 metadata
  • IDsource object·attachment ID와 canonical URL
  • VERversion, modified time, content checksum
  • AUTHpermission resolver가 만든 principal set 또는 source authorization handle
  • DERparser version, options, derived asset lineage
운영 control
  • REV권한 축소와 private comment 변경을 index에 동기화
  • DELsource 삭제 시 Markdown·chunk·asset을 함께 삭제
  • LIMbytes, page, cell, relationship depth에 resource limit 적용
  • ASTembedded object·asset을 quarantine하고 malware scan

service account 권한이 crawl 범위를 결정한다. source API가 ACL snapshot을 자동 반환한다고 가정하면 안 된다. downstream retrieval은 별도 resolver가 만든 authorization context를 확인해야 한다.

critique

feasibility 경계는 좁혔지만 production fidelity는 아직 측정하지 못했다

현재 근거는 source-native parser의 feasibility를 보여 준다. 다음 항목은 production fidelity와 integration risk로 남는다.

품질 공백
  • 01동일 문서를 anydoc·Tesseract·layout OCR·VLM으로 비교한 golden set이 없다.
  • 02한국어 조합, 한글 Office, 복잡한 수식·SmartArt·chart corpus를 시험하지 않았다.
  • 03PDF page reading order와 multi-column fidelity를 별도 측정하지 않았다.
통합 공백
  • 04Jira·Confluence body adapter와 ACL revocation을 live tenant에서 검증하지 않았다.
  • 05draw.io source adapter, asset OCR, VLM router는 권장 설계일 뿐 구현물이 아니다.
  • 06Node·Python·WASM binding과 hosted Parse OCR은 실행하지 않았다.

이 공백 때문에 현재 결론은 production 승인이 아니라 제한된 trial 승인이다.

adoption-architecture

사내 구조는 source-first router와 용도별 좁은 lane으로 나눈다

anydoc에 모든 입력을 강제로 넣지 않는다. body·diagram·package·page image·embedded asset마다 가장 직접적인 information source를 선택한다.

Atlassian / file share / upload
  │
  ├─ ADF · storage HTML ─────────→ body adapter
  ├─ draw.io XML · graph JSON ───→ diagram source adapter
  ├─ Office · ODF · RTF · EPUB ──→ anydoc core
  └─ PDF
       ├─ text-layer PDF ─────────→ anydoc core
       └─ image-page PDF ─────────→ approved local OCR

embedded assets
  ├─ image text ─────────────────→ asset OCR
  └─ visual relation ─────────────→ policy-approved VLM

all lanes → internal blocks + raw asset + provenance + auth ref → index
원칙 1

source before pixels

native role과 edge가 있으면 먼저 읽는다.

원칙 2

page/asset selective

OCR와 VLM 범위를 필요한 page·asset으로 좁힌다.

원칙 3

provenance intact

Markdown만 저장하지 않고 source·asset·authorization lineage를 보존한다.

common schema는 anydoc Document가 아니라 사내 normalized model로 둔다. pinned crate의 Format은 닫힌 enum이고 renderer는 public extension surface가 아니며 PDF는 Document를 우회한다.

adoption-production-gate

Production 승격 전에 golden manifest와 zero-tolerance failure를 승인한다

parser trial은 pinned artifact와 대표 Office·PDF golden set으로 시작한다. production 승격 때는 route별 원본 source와 rendered page를 reference로 두고 문서 owner·security owner·search owner가 필수 field와 허용 손실을 승인한다.

gate검사 대상통과 조건실패 시 조치
text fidelity한글·영문·숫자·link target·notegolden diff에서 의미 변경 없음format parser 보류

zero tolerance: ACL leak, source 삭제 미동기화, encrypted file 우회, 누락 asset 미탐지는 한 건도 허용하지 않는다. text·structure loss는 golden manifest의 field별 diff를 세 owner가 승인한다.

conclusion

anydoc를 source parser로 trial하고 universal document AI로는 보류한다

Office와 text-layer PDF attachment를 local Markdown으로 정규화하는 pinned Rust path는 source locator로 추적할 수 있다. image-page PDF·diagram·Atlassian body·ACL lifecycle까지 해결한다고 확대 해석하면 제품 경계를 넘는다.

지금 할 일

pinned Rust trial

261fc257 source와 lockfile로 internal image를 build하고 대표 Office·text-layer PDF golden set을 측정한다.

함께 할 일

router와 provenance

ADF·storage·draw.io·OCR lane을 분리하고 authorization context와 asset lineage를 끝까지 전달한다.

하지 않을 일

무근거 확장

score 81을 OCR accuracy로 쓰거나 hosted OCR을 self-host 기능으로 소개하지 않는다.

최종 판단: anydoc는 source parser lane에 한해 TRIAL이다. universal document AI와 hosted OCR self-host 기능으로는 HOLD다.
