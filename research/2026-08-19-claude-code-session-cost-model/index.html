Claude Code 세션 비용 모델: 토큰 하나의 가격과 세션이 보내는 토큰의 개수

에이전트형 코딩 도구에서는 같은 작업이 쓰는 방식에 따라 다른 값이 된다. 값을 정하는 것은 두 축이다. 토큰 한 개의 가격(모델 · 입력/출력 · 캐시)과 세션이 보내는 토큰의 개수(컨텍스트에 들어간 양 · 머무는 턴 수 · 동시에 돌리는 컨텍스트 수). 이 문서는 Anthropic 블로그 원문을 두 축으로 다시 세우고, 원문 도해 일곱 장을 그 자리에 놓았다.

출력 토큰 가격 ≈5배 입력 대비. decode가 GPU를 훨씬 오래 붙잡는다
캐시 읽기 0.1배 계산하지 않고 상태를 불러온다
캐시 쓰기 최대 2배 토큰당 한 번. 그 뒤 매 턴 0.1배로 회수
캐시 수명 1시간 구독 기준. API 키는 5분
읽는 법 좌측 목차 또는 ← → 키 · Space · Home / End 로 이동한다. 각 장은 독립적으로 읽히도록 썼다. 원문에서 그대로 가져온 도해는 흰 판(plate) 위에 두었고, 캡션에 무엇을 보는 그림인지 적었다. 21~24장은 원문에 없는 학습용 부록이다. 숫자 표, 치트시트, 운영 루틴, 자가 점검 문항.
원문 Lydia Hallie, “Maximizing the Value of Your Claude Code Sessions”, Anthropic, 2026-08-14. 원문에서 온 수치와 인용에는 추정을 섞지 않았다. 13~15장은 예외다. 임계값 30,000자는 원문에 있지만, 절단이 실제로 어떤 형태로 오는지와 그것이 토큰 회계에 어떻게 잡히는지는 이 문서가 직접 잰 것이다(25장).

tl-dr

원문이 앞에 두는 여섯 줄

글 전체는 이 여섯 개가 왜 그런지를 설명하는 구조다. 지금 외우고, 이유는 뒤에서 붙인다.

01 · clear

작업 사이에 /clear

이전 작업의 상관없는 컨텍스트를 모델에게 다시 보내지 않는다. 토큰 사용량이 줄어든다.

02 · model · effort

모델과 effort는 시작 전에 정한다

대화 도중에 둘 중 하나라도 바꾸면 프롬프트 캐시가 깨지고, 비용이 오를 수 있다.

03 · at-mention

파일은 이름 대신 @로 붙인다

파일이 메시지에 직접 첨부된다. Read 호출 한 번이 사라지고, Claude가 파일을 찾아다녀야 했다면 검색까지 사라진다.

04 · quiet

시끄러운 명령엔 조용한 플래그를, 아니면 서브에이전트로

명령 출력은 파일과 똑같이 대화에 추가되고, 세션이 끝날 때까지 남는다.

05 · context

새 세션에서 /context 한 번

무엇이 로드되어 있는지(CLAUDE.md, MCP 도구 정의) 보여준다. 필요 없는 것을 덜어낼 수 있다.

06 · compact

자리를 뜨기 전에 /compact

프롬프트 캐시는 한 시간 뒤 만료된다. 대화를 요약하는 일은 아직 캐시가 살아 있을 때 훨씬 싸다.

구독을 쓰는 경우 원문은 이 점을 분명히 한다. 구독에서도 똑같이 적용된다. 가격이 직접 보이지는 않지만, 한도를 깎아 내리는 것은 여기서 말하는 바로 그 요청들이다.

problem

작업 하나에 가격이 붙기 시작했다

얼마 전까지 코드를 쓰는 도구는 정액이거나 공짜였다. 에디터는 그날 오후에 테스트 하나를 고치든 쉰 개를 고치든 같은 값이었고, 그래서 개별 작업에는 자기만의 가격이 없었다. 에이전트형 도구에서는 생긴다.

같은 수정인데 쓴 토큰 수가 다르고, 그러는 내내 모델은 필요하지도 않은 열 개의 파일을 같이 생각하고 있어야 했다. “It’s the same fix, but you spent a different number of tokens on it, and the whole time the model was also having to think about ten files it didn’t need.”

오해하기 쉬운 지점 토큰을 효율적으로 쓴다는 건 전체를 적게 쓴다는 뜻이 아니다. 쓴 토큰이 실제로 요청한 그 일에 가도록 만든다는 뜻이다. 필요한 탐색까지 아끼면 그냥 일이 안 된다.

structure

비용은 두 축의 곱이다

글의 구조가 곧 계산식이다. 토큰 하나의 가격을 정하는 것이 셋, 세션이 그 토큰을 몇 개 보내는지를 정하는 것이 셋. 나머지는 전부 이 여섯 개의 파생이다.

축 A · 토큰 하나의 가격

청구되는 것은 토큰이지만, 실제로 지불하는 것은 추론이다. GPU가 그 토큰 위로 모델을 돌리는 시간.

  • 1어떤 모델을 돌리는가, 나머지 전부에 곱해진다
  • 2입력인가 출력인가, 출력이 약 5배
  • 3캐시되었는가, 읽기는 0.1배
축 B · 보내는 토큰의 개수

핵심은 하나다. 무엇도 한 번만 보내고 끝나지 않는다. 대화에 들어간 것은 그 뒤 모든 턴에 다시 실려 나간다.

  • 1컨텍스트에 얼마나 들어가는가
  • 2거기 몇 턴이나 머무는가
  • 3동시에 몇 개의 컨텍스트를 돌리는가

price · 1

모델: 나머지 전부에 곱해지는 계수

큰 모델은 입력 토큰에도 출력 토큰에도 더 많은 일을 한다. 어떤 일에 어떤 모델이 값을 하는지는 그 자체로 별도의 주제이고, 원문은 “Choosing a Claude model and effort level in Claude Code” 글에 넘긴다. 이 글에서 필요한 것은 하나다. 지금부터 다룰 모든 것에 모델 가격이 곱해진다.

읽어낼 규칙 문제가 정말로 어렵거나 모호할 때 큰 모델을, 일이 정형적일 때 작은 모델을 쓴다. 오른쪽 그림이 말하는 것은 반대 방향의 함정이기도 하다. 어려운 일에 작은 모델을 붙이면 토큰을 더 쓰고도 그 품질에 못 간다. 아끼려다 더 쓰는 경우가 여기다.

price · 2

입력과 출력: prefill 한 번, decode 토큰마다 한 번

요청은 GPU를 두 단계로 지나가고, 두 단계의 값이 다르다.

prefill · 입력 토큰

모델이 요청과 컨텍스트를 읽는다. 시스템 프롬프트, CLAUDE.md, 내 메시지, 그리고 그 뒤로 대화에 추가된 모든 것: Claude가 읽은 파일과 실행한 명령의 출력. 요청 전체를 한 번 훑는다.

decode · 출력 토큰

모델이 써낸다. thinking, 도구 호출, 눈에 보이는 텍스트. 한 번에 한 토큰씩이라, 200토큰짜리 응답은 모델을 200번 연달아 돌린 것이다. 토큰당 GPU를 훨씬 오래 붙잡고, 그래서 대략 입력의 5배로 매겨진다.

세션에서 나오는 출력 토큰의 상당 부분은 thinking 토큰이고, 턴마다 얼마나 생각할지를 정하는 것이 effort 레벨이다. 모델과 마찬가지로 /effort로 고른 값은 다음 세션의 기본값으로 남는다.

tip 새 세션에서 /model과 /effort를 한 번씩 쳐서 지금 무엇으로 돌고 있는지 확인한다. 둘 다 지난번에 고른 것을 기억하고 있고, 그 결정은 의도적이어야 한다.
tip 이번 세션이 단순 노동인 걸 이미 안다면 MAX_THINKING_TOKENS=0 claude로 그 세션만 thinking을 끈다 (Fable 5는 제외). /effort low 아래 한 칸이다.

price · 3

프롬프트 캐싱: 앞부분이 같으면 다시 계산하지 않는다

요청이 방금 처리한 요청과 정확히 같은 토큰으로 시작하면, 그 공유된 앞부분의 상태는 똑같이 나온다. 그래서 서버는 지난번 것을 들고 있다가 그 뒤에 오는 것만 프리필한다. 이것이 프롬프트 캐싱이다.

캐시에서 읽기 0.1배 계산하는 대신 상태를 불러오기만 한다
캐시에 쓰기 최대 2배 평소 입력보다 조금 비싸다. 상태를 붙들고 있어야 해서
회수 구조 1 : n 쓰기는 토큰당 한 번, 0.1배 읽기는 그 뒤 매 턴
켤 것은 없다

Claude Code가 매 요청마다 프롬프트 캐시를 관리한다. 켜고 끌 것이 없다. 다만 무효화할 수는 있다. 비용이 크게 오르는 지점이 거기라, 어떻게 하면 무효화되지 않는지를 알아야 한다.

구독에서도 가격이 직접 보이지 않을 뿐, 한도를 깎는 것은 똑같은 요청들이다. 캐시가 깨지면 구독에서도 그만큼 한도가 더 깎인다. 다만 한도가 배수를 가격과 같은 비율로 셈하는지는 원문에 없다.
자주 놓치는 것 오래된 세션을 resume 하면 거의 항상 전체가 다시 프리필된다. 그때쯤이면 캐시는 대개 사라졌고, 시스템 프롬프트는 실행 시점에 어차피 새로 만들어지기 때문이다.

trace

추적: “fix the failing test in utils.test.ts”

작은 수정 하나가 요청 다섯 번이 된다. 그리고 다섯 번 모두가 그 시점까지의 대화 전체를 담고 있었다. 원문의 단계별 서술을 표로 옮긴 것이다.

요청 새로 프리필 · 정가 ×1 캐시 읽기 · ×0.1 출력 · ×5
1 시스템 프롬프트(도구 정의 포함) + CLAUDE.md + 내 메시지 . 캐시에 아무것도 없어 전부 프리필되고 캐시에 쓰인다 없음 잠깐 생각한 뒤 utils.test.ts에 대한 Read 호출
2 Read 호출 + 읽어온 utils.test.ts 요청 1 전체 대상 파일에 대한 Read 호출
3 Read 호출 + 두 번째 파일 요청 1–2 Edit 호출
4 Edit 호출 + 적용 결과 요청 1–3 npm test 실행 호출
5 테스트 출력 요청 1–4 짧은 요약. 도구 호출이 없으니 덧붙일 것도 요청 6도 없다. 끝
이 표에서 가져갈 것 Claude Code의 루프는 “출력에 도구 호출이 있으면 → 결과를 대화 끝에 덧붙이고 → 전부 다시 보낸다”이다. 그래서 불필요한 턴을 줄이는 것이 곧 비용을 줄인다. 다만 턴을 줄이는 모든 수단이 그런 것은 아니다. 서브에이전트는 작은 일에서 오히려 오버헤드이고(18장), /compact는 턴을 줄이면서도 언제나 값이 든다(10장). @-mention이 Read 호출 한 턴을 없애는 것, 구체적인 요청이 grep 턴들을 없애는 것이 여기에 직접 걸린다.

mechanism

캐시는 요청 맨 앞부터 일치해야 한다

요청은 언제나 같은 순서로 나간다: 도구 정의 → 시스템 프롬프트 → 대화(그 맨 앞에 CLAUDE.md). 이 프리픽스 중 무엇이든 바뀌면 그 뒤에 있는 것이 전부 다시 프리필된다. 대화 끝에 붙는 도구 결과가 가장 이상적인 경우인 이유는, 뒤에 아무것도 없기 때문이다.

invalidation

캐시를 무효화하는 다섯 가지

요청의 앞쪽을 바꾸는 것, 또는 캐시가 무엇으로 키를 잡는지를 바꾸는 것.

원인왜 깨지는가결과
/model 모델마다 자기 캐시를 따로 갖는다 다음 턴에 대화 전체가 정가로 다시 프리필. opusplan도 포함. plan 모드에 들어가고 나올 때마다 모델이 바뀐다
/effort effort 레벨도 캐시 키의 일부다 같은 이야기. /model과 /effort 둘 다 대화 중간에 바꾸면 확인을 묻는 이유가 이것이다
fast mode 역시 키의 일부다 재프리필이 fast mode 가격으로 일어난다. 켤 거면 시작할 때 켠다. 끄는 건 캐시 관점에서 공짜
/compact 대화가 더 짧은 것으로 교체된다 대화 안의 무엇도 더는 일치하지 않는다(앞의 시스템 프롬프트는 살아남는다). 요약을 쓰는 일 자체는 옛 대화가 캐시에 있는 동안 싸다. 긴 휴식 전이 후보다 훨씬 싸다
시간 턴마다 시계는 리셋되지만, 캐시는 만료된다 구독 1시간 / API 키 5분(ENABLE_PROMPT_CACHING_1H=1로 1시간). 더 늦게 돌아오면 다음 턴이 대화 전체를 다시 프리필
결론은 “바꾸지 마라”가 아니다 모델이나 effort를 절대 바꾸지 말라는 뜻이 아니다. 싼 순간과 비싼 순간이 있다는 뜻이다. 싼 순간은 세션의 시작, 또는 /clear 직후. 비싼 순간은 긴 대화의 한복판.
tip · rewind vs compact 마지막 몇 턴이 원하지 않는 방향으로 갔다면 /compact 말고 /rewind로 그 직전까지 되돌린다. rewind는 끝에서 그 턴들만 잘라내므로 앞은 전부 캐시에 그대로 있고, 비용이 들지 않는다. compact는 대화 전체를 다시 쓰는 일이라 언제나 값이 든다.

count · 1

타이핑하기 전에 이미 들어 있는 것

여기서부터는 두 번째 축이다. 대화에 들어간 것은 무엇도 한 번만 보내고 끝나지 않는다. Claude가 읽은 파일이든 실행한 명령의 출력이든, 그 뒤로 세션이 끝날 때까지 매 턴 다시 전송된다.

캐시되어 있어도

그 재전송 하나하나는 싸다. 하지만 싼 것과 공짜인 것은 다르고, 동시에 모델이 매 턴 함께 읽어야 하는 컨텍스트 자리를 차지하고 있다. 비용만이 아니라 품질 문제이기도 하다는 뜻이다.

컨텍스트의 일부는 내가 무언가를 치기도 전에 이미 거기 있다. 도구 정의, 시스템 프롬프트, CLAUDE.md, 그리고 시작할 때 로드되는 나머지 전부.

tip · /context 새 세션에서 아무것도 치기 전에 /context를 실행해 무엇이 들어 있는지 본다. 그리고 셋을 한다.
  • 1CLAUDE.md는 구체적인 지시만 남긴다. 특정 워크플로에만 필요한 것은 skill로 옮긴다. skill은 쓸 때만 로드된다
  • 2이번 세션에 필요 없는 MCP 서버는 /mcp로 끈다. 안 쓰는 서버의 도구 정의도 첫 턴에 정가로 프리필되고, 그 뒤로는 매 턴 재전송되며 컨텍스트 자리를 계속 차지한다
  • 3그러고 나서 시작한다. 모델·effort를 바꿀 거면 여기서 바꾼다. 원문이 싸다고 적은 순간은 둘이다. 세션의 시작, 그리고 /clear 직후

“테스트가 깨졌어”라고 하면, 먼저 어떤 테스트인지부터 알아내야 한다. grep 한두 번, 어느 쪽이 관련 있는지 보려고 연 파일 몇 개. 그리고 그 결과들은 쓸모가 다한 뒤로도 한참 컨텍스트에 남아 있다.

명령 출력: 30,000자에 절벽이 있다

컨텍스트를 채우는 다른 하나는 Claude가 돌린 명령의 출력이다. 테스트든 빌드든 git log든, 찍힌 것은 Claude가 읽은 파일과 똑같이 대화에 덧붙고, 똑같은 수의 턴 동안 남는다. 그런데 여기엔 직관을 거스르는 임계값이 하나 있다.

먼저 · 30,000자가 무엇을 세는 값인가

가격도 토큰도 아니다. Claude Code(하네스)가 Bash 도구의 출력을 컨텍스트에 통째로 넣을지 파일로 뺄지 가르는 내부 임계값이다. 단위는 토큰이 아니라 문자이고, 대상은 명령 하나가 뱉은 출력이다(아래 측정은 stdout 만으로 했다). 모델은 이 판단에 관여하지 않는다. 도구 결과가 대화에 붙기 전에 하네스가 자른다.

  • ↑넘으면: 전문이 디스크의 파일로 빠지고, 대화에는 앞 2KB 원문 + 파일 경로만 들어간다
  • ↓못 넘으면: 아무도 잘라주지 않는다. 출력 전체가 대화에 들어가 세션이 끝날 때까지 매 턴 재전송된다
실측 · Claude Code v2.1.233에서 직접 확인

그 절단이 비용과 정보에 하는 일

잘린 출력은 청구에서도 사라지고, 정보에서도 사라진다. 앞쪽은 이득이고 뒤쪽은 대가다. 둘을 따로 본다.

그럼 청구는 어떻게 되나 · 이 세션의 트랜스크립트에서 뽑은 실제 수치

명령의 출력은 output token이 아니다. output token은 모델이 생성한 것(thinking · 도구 호출 · 텍스트)뿐이고, 명령 출력은 내 기계의 셸이 만든 것이라 모델이 쓴 적이 없다. 그것은 도구 결과로 대화에 붙어 다음 요청의 input token이 된다. ×5가 아니라 ×1, 그 뒤로는 ×0.1.

트랜스크립트(~/.claude/projects/…/<세션id>.jsonl)가 곧 매 턴 재전송되는 대화다. 거기 저장된 실제 값:

실행출력 크기트랜스크립트 저장량다음 요청의 캐시 기록
44,000자 · 절단됨44,000자2,235자1,194 토큰
29,920자 · 절단 안 됨29,920자29,920자30,928 토큰
  • 1요청에 들어간 것은 래퍼까지 합쳐 2,235자이고 그중 출력 본문은 1,990자다. 나머지 약 42,000자는 어떤 요청에도 들어가지 않았다. 로컬 디스크 파일에만 있다. 절단은 요청이 조립되기 전, 클라이언트에서 일어난다
  • 2원본이 1.5배 작은 쪽이 토큰은 26배다. 대부분은 임계값을 못 넘었기 때문이지만, 두 행은 페이로드가 달라(seq 출력 대 aaaa… 반복) 토큰화 차이도 섞여 있다
  • 3그 다음 턴의 cache_read가 179,650 → 210,578로 뛰었다. 차이가 정확히 +30,928. 이제부터 매 턴 다시 읽힌다는 것이 숫자로 그대로 보인다
  • 4다만 cache_creation 값에는 같은 턴에 새로 붙은 다른 내용도 섞여 있다. 30,928 전부가 이 출력이라고 읽으면 그만큼 과하다
  • 5같은 구간의 output_tokens는 내내 163~2,048이었다. 명령 출력은 여기 한 번도 나타나지 않는다
주의 · 토큰 환산을 일반화하지 말 것 29,920자가 30,928토큰이 된 것은 aaaa… 반복이라 토큰화가 비정상적으로 나쁘게 걸린 경우다. 1자 ≈ 1토큰으로 읽으면 안 된다. 보통 로그·코드는 3~4자당 1토큰 쪽이다.
앞부분만 남는다는 것의 대가 테스트 러너나 빌드 도구는 제일 중요한 줄을 맨 끝에 찍는다. 실패 개수, 요약, 종료 코드. 출력이 임계값을 넘으면 대화에 남는 건 앞 2KB뿐이라 그 결론이 컨텍스트에 없다. Claude는 파일을 다시 읽거나 명령을 다시 돌려야 하고, 둘 다 턴이 든다.

count · 3 · 위험 구조

왜 작은 출력이 더 위험한가

위험은 출력 크기에 비례해 오르다가 임계값에서 떨어진다. 그리고 임계값은 명령 하나당만 지켜준다. 합계는 아무도 지켜주지 않는다.

400줄이 왜 임계값 아래인가 · 산수 원문의 두 숫자만으로 바로 나온다. 30,000 ÷ 400 = 75자. 통과 테스트를 줄당 75자 미만으로 찍는 러너라면 400줄을 뱉어도 임계값을 못 넘고, 그 400줄이 남은 모든 턴의 일부가 된다. 조용히, 계속.
뒤집으면 수십만 자짜리 빌드 로그가 오히려 안전하다. 그건 잘려서 들어오기 때문이다.
그런데 폭발은 "큰 출력"이 일으키지 않는다

단일 명령 기준으로 최악은 임계값 바로 아래다. 임계값을 넘긴 출력보다 나쁘다. 그리고 임계값은 명령 하나당 적용되지, 세션 누적이 아니다. 실측에서 세 명령이 각각 독립적으로 판정되는 것을 확인했다. 아래 표는 그 규칙에서 따라 나오는 세 패턴이고, 세 줄을 각각 실행해 본 것은 아니다.

패턴잘리나컨텍스트에 남는 양
300,000자 한 번잘림2KB
29,000자 한 번안 잘림29,000자
3,000자 × 10번전부 안 잘림30,000자

세 번째가 실무에서 훨씬 흔한 경로다. 각각은 너무 작아 아무도 의심하지 않고, 하나도 잘리지 않는다. 임계값은 개별 명령만 지켜주지, 합계는 아무도 지켜주지 않는다.

그리고 크기만큼 언제 들어왔는가가 중요하다. 40턴짜리 세션이라면 같은 29,000자도 턴 3에 들어오면 남은 37턴 동안 재전송되고, 턴 39에 들어오면 한 번이다. 앞의 실측이 그대로 보여준 것이기도 하다. 한 번 들어온 30,928토큰이 이후 매 턴 cache_read에 얹혔다. 

# 얼마나 쌓이는가 (크기 감각. 정확한 비용식이 아니다)
Σ ( 임계값 아래 출력 크기 × 그 뒤 남은 턴 수 )
  들어온 턴은 정가, 그 뒤 재전송분은 캐시 읽기(×0.1)라 실제 금액은 이보다 훨씬 작다.
  줄여야 할 것은 금액이 아니라 매 턴 모델이 함께 읽는 양이다.

대책: 임계값에 기대지 말고 애초에 작게 만든다

임계값은 개별 명령만 지켜주고, 넘어가도 남는 것은 앞 2KB뿐이다. 어느 쪽이든 출력을 작게 만드는 것보다 낫지 않다.

주의 · 원문과 어긋날 수 있는 한 줄 원문은 임계값을 BASH_MAX_OUTPUT_LENGTH로 바꿀 수 있다고 적는다. 그런데 v2.1.2부터 디스크 저장 경로가 이 변수를 무시한다는 회귀 보고가 있다 (anthropics/claude-code 이슈 #17944, 변수를 크게 올려 두어도 그보다 작은 출력이 파일로 빠졌다는 내용, v2.1.6에서 보고, stale로 닫힘). 이 동작은 공식 설정 문서에도 없다. 이 문서가 code.claude.com/docs/en/settings를 열어 확인했고, 같은 부재를 지적하는 이슈도 따로 있다(#19901).
직접 확인하지 못한 부분이다. 이 세션의 환경에는 변수가 설정돼 있지 않았고, 하네스는 이 값을 자기 시작 시점에 읽으므로 Bash 명령 안에서 값을 바꿔 보는 방식으로는 검증되지 않는다. 값을 올려서 쓸 생각이라면 자기 버전에서 먼저 시험해 보고 믿는 편이 낫다.

Claude가 알아서 플래그와 tail로 처리해 주는 경우가 많고, 그걸 Claude에게 맡기고 싶지 않다면 시끄러운 명령을 실행 전에 다시 쓰는 작은 hook이 문서에 있다. 필요한 줄만 돌아오게 만드는 것이다.

tip · CLAUDE.md 하루 종일 쓰는 명령 두세 개를, 조용한 플래그까지 포함해서 내가 직접 칠 때의 모양 그대로 CLAUDE.md에 적어둔다.

거기 몇 턴이나 머무는가

긴 세션 하나는 같은 일을 짧은 세션 몇 개로 나눈 것보다 비싸다. 그것도 생각보다 많이: 40번째 턴은 그 앞의 39턴을 같이 다시 읽고 있기 때문이다.

세션 안의 컨텍스트는 짧고 관련 있는 것이어야 한다. 한 작업의 컨텍스트를 다음 작업으로 끌고 가지 않는다. 새로 시작할 때 /clear, 같은 작업의 앞부분이 끝났으면 /compact.

tip · 세 가지 나중에 이 세션이 다시 필요할 것 같으면 /clear 전에 /rename. /compact할 때는 무엇을 남길지 말해준다. 늘 같은 것이라면 CLAUDE.md에 “Compact instructions” 섹션을 둔다. 1M 모델을 쓰면서 자동 compact 안전망을 원래 자리로 돌리고 싶으면 /autocompact 200k (Claude Code v2.1.221+ 필요).
내가 타이핑하지 않는 턴 /loop은 그것을 걸어둔 세션에서 온전한 턴 하나로 발사된다. 매번 그 세션의 대화 전체를 끌고 간다. 게다가 마지막 턴에서 한 시간이 지났다면 거기에 캐시 미스까지 얹힌다. → 다른 터미널에서 새 세션을 열고 거기서 루프를 돌린다.

count · 5

서브에이전트: 다른 컨텍스트에서 일어나게 한다

무언가를 내 컨텍스트 밖에 두는 다른 방법은 그 일이 다른 컨텍스트에서 일어나게 하는 것이다. 서브에이전트가 그 용도다.

손해일 때

내 대화가 없다는 것은, 메인 세션이 이미 갖고 있던 것을 다시 읽어야 할 때가 있다는 뜻이다. 그러는 동안 자기 턴 값을 치른다. 작은 일에는 그냥 오버헤드다.

이득일 때

남길 필요 없는 출력이 많이 나오는 일, 로그를 훑는 것 같은. Claude가 알아서 서브에이전트를 꺼내 드는 경우가 많고, 안 그럴 때는 직접 요청하면 된다: “이 로그는 서브에이전트에서 훑어”.

대가 메인 세션은 서브에이전트가 보고하기로 한 것만 돌려받는다. 중간에 본 것은 남지 않는다.
tip · 반복되는 시끄러운 일 같은 일을 계속 넘기고 있다면 그 일에 전용 서브에이전트 정의를 만들고 model: haiku(또는 sonnet)를 지정한다. 그러지 않으면 메인 세션이 돌고 있는 모델로 실행된다.

critique

원문이 근거를 대지 않는 자리

이 글의 메커니즘 설명은 튼튼하다. 프리필과 decode, 캐시 프리픽스, 재전송 구조는 읽고 나면 스스로 검증할 수 있다. 약한 것은 숫자 쪽이다. 어디가 검증 가능하고 어디가 아닌지 갈라 둔다.

1 · 유일한 성능 그림이 근거가 아니다

모델 선택을 다루는 곡선 그림에 원문 스스로 “설명을 위한 것이고 실제 벤치마크 데이터가 아니다”라고 적었다. 모델과 effort 권고는 이 글 안에서는 방향만 있고 수치 근거가 없다. 정작 “나머지 전부에 곱해진다”며 가장 큰 영향으로 꼽은 항목이다. 원문은 이 주제를 별도의 글로 넘긴다(25장).

2 · 예시 숫자에 재현 조건이 없다

1.9배, 5요청 대 18요청, 6/1/0턴. 전부 도해에서만 나오고 어떤 저장소, 어떤 모델, 어떤 작업이었는지 적혀 있지 않다. 방향을 보여주는 삽화로는 충분하지만 재현하거나 반박할 수는 없다.

3 · 배수가 근사치로만 있다

출력은 “roughly 5x”, 캐시 쓰기는 “up to 2x”다. 모델별 실제 배수도, 어떤 조건에서 2배까지 가는지도 없다. 의사결정의 방향을 잡기엔 충분하지만 비용을 계산할 수는 없다.

4 · 자기 도구의 현재 동작과 어긋난다

임계값을 BASH_MAX_OUTPUT_LENGTH로 바꿀 수 있다고 한 줄로 넘기지만, v2.1.2부터 이 변수가 무시된다는 회귀 보고가 있다(16장). 근거가 닿는 범위는 어긋난다는 보고가 있다까지다. 그래도 한 줄로 넘길 자리는 아니었다.

원문이 열어 둔 질문 서브에이전트는 언제 손익분기를 넘는가. “작은 일에는 오버헤드, 로그에는 이득”까지만 말하고 경계는 없다. · /compact는 실제로 얼마를 아끼는가. 캐시가 살아 있을 때 싸다는 것만 말한다. · 컨텍스트가 길어질 때 품질이 언제 나빠지는가. “모델이 생각해야 할 것이 늘어난다”는 서술만 있고 측정은 없다.
그래서 이 문서가 한 일 네 구멍은 그대로 남는다. 곡선의 근거도, 예시 숫자의 재현 조건도, 배수의 실제 값도, 회귀 보고의 진위도 채워지지 않았다. 13~15장이 하는 일은 다른 것이다. 원문이 이미 적어 둔 값 하나가 실제로 그렇게 도는지를 확인한 것이고, 그 범위는 25장에 있다.

conclusion

어디부터 볼 것인가

원문이 마지막에 남기는 것은 우선순위 목록이다. 비용에 미치는 영향이 큰 순서로 대략 네 가지.

순서가 말해주는 것 가장 손이 많이 가는 조정(모델·effort)이 3번이다. 제일 먼저 손볼 것은 세션을 짧게 유지하는 습관과 컨텍스트에 뭘 들이지 않는 습관이다. 둘 다 명령 한두 개로 되고, 효과는 더 크다.

appendix · routine

세션 운영 루틴

앞의 스무 장을 순서가 있는 행동으로 접은 것이다. 원문의 tip들을 실행 시점 순으로 재배열했다.

세션을 열 때 · 여기서만 싸다
  1. /context: 타이핑 전에 무엇이 로드돼 있는지 본다
  2. /model · /effort: 지금 무엇으로 도는지 확인하고, 바꿀 거면 지금 바꾼다. 이 순간을 놓치면 대화 전체를 다시 프리필하는 값이 든다
  3. /mcp: 이번 세션에 안 쓸 서버를 끈다
  4. fast mode를 쓸 거면 지금 켠다. 끄는 건 나중에 해도 캐시 관점에서 공짜다
일하는 동안
  1. 파일은 @로 붙여서 요청한다. 같은 파일을 두 번 멘션하지 않는다
  2. “테스트가 깨졌어” 대신 어느 파일인지 말한다. 탐색 턴이 통째로 사라진다
  3. 시끄러운 명령은 CLAUDE.md에 조용한 플래그까지 적어둔다. 안 그러면 매 세션 반복된다
  4. 출력만 많고 남길 필요 없는 일은 서브에이전트로 넘긴다. “이 로그는 서브에이전트에서 훑어”
작업이 바뀔 때
  1. 나중에 찾을 세션이면 /rename
  2. /clear: 이전 작업의 컨텍스트를 다음 작업으로 끌고 가지 않는다
  3. 같은 작업이 길어지는 중이고 앞부분이 끝났으면 /compact, 남길 것을 말해주면서
  4. 마지막 몇 턴이 틀어진 것뿐이면 /compact가 아니라 /rewind
자리를 뜰 때 · 놓치기 쉬움
  1. 키보드에서 떠나기 전에 /compact. 캐시가 살아 있을 때 요약을 쓰는 게 훨씬 싸다
  2. 한 시간(구독) 이상 비울 거면 어차피 캐시는 사라진다. compact를 하고 가면 돌아왔을 때 다시 프리필할 양이 줄어든다
  3. /loop은 이 세션에서 돌리지 않는다. 다른 터미널에 새 세션을 연다
  4. 오래된 세션 resume은 거의 항상 전체 재프리필이라는 것을 감안한다
한 문장으로 바꿀 것은 세션 앞에서 바꾸고, 들일 것은 최소로 들이고, 끝난 것은 남기지 않는다.

appendix · self-check

자가 점검 8문항

답을 먼저 떠올린 뒤 펼친다. 여덟 개를 다 설명할 수 있으면 원문의 메커니즘은 다 잡힌 것이다.

Q1출력 토큰이 입력 토큰보다 비싼 이유를 GPU 관점에서 설명하라.
prefill은 요청 전체를 한 번 훑는다. decode는 토큰 하나마다 모델을 한 번씩 돌린다. 200토큰짜리 응답은 200번 연달아 실행한 것이고, 매번 그때까지의 요청 전체를 입력으로 받는다. 토큰당 GPU 점유 시간이 훨씬 길고, 그래서 대략 5배로 매겨진다.
Q2대화 한복판에서 /effort를 바꾸면 무슨 일이 일어나는가?
effort 레벨은 캐시가 키를 잡는 값의 일부다. 키가 달라지므로 다음 턴에 대화 전체가 정가로 다시 프리필된다. /model과 /effort 둘 다 대화 중간에 바꾸면 확인을 묻는 이유가 이것이다. 싼 순간은 세션 시작 또는 /clear 직후.
Q3캐시 관점에서 /compact와 /rewind 중 공짜인 것은? 왜?
/rewind. 끝에서 턴 몇 개를 잘라내기만 하므로 그 앞은 전부 캐시에 그대로 있다. 비용이 들지 않는다. /compact는 대화를 통째로 새 요약본으로 다시 쓰는 일이라 언제나 값이 든다 (앞의 시스템 프롬프트는 살아남는다). 마지막 몇 턴이 마음에 안 드는 것뿐이라면 rewind가 맞다.
Q4통과한 테스트 400줄이 30,000자를 넘는 로그보다 더 위험한 이유는?
30,000자를 넘으면 Claude Code가 출력을 파일로 쓰고 대화에는 짧은 미리보기와 경로만 넣는다. 사실상 안전하다. 400줄은 그 임계값 아래로 들어와서 통째로 대화에 남고, 남은 모든 턴에 다시 전송된다. 남는 미리보기는 앞 2KB 원문이지 요약이 아니고, 끝부분은 사라진다. 테스트 요약줄이 맨 끝에 찍히면 그것도 같이 사라진다. 근본 대책은 CLAUDE.md에 조용한 플래그를 적어두는 것이다.
Q5"fix @utils.test.ts"가 "fix utils.test.ts"보다 싼 이유와, 그 이득이 사라지는 경우는?
@는 무엇이든 전송되기 전에 파일을 메시지에 첨부한다. 첫 요청에 이미 들어 있으니 Read 호출 턴이 없다 (도해 기준 1턴 → 0턴). 이득이 사라지는 경우: 파일이 컨텍스트에서 차지하는 자리는 어느 쪽이든 같다. 그래서 대화당 한 번만 멘션하면 되고, 나중 턴에 같은 파일을 다시 @하면 대개 사본이 하나 더 붙는다.
Q6서브에이전트가 이득인 일과 손해인 일은? 그리고 그 대가는?
이득: 로그 훑기처럼 출력이 많고 남길 필요가 없는 일. 그 출력이 메인 컨텍스트에 아예 들어오지 않는다.
손해: 작은 일. 서브에이전트는 내 대화를 갖지 않아서 메인이 이미 읽은 것을 다시 읽어야 할 때가 있고, 그러는 동안 자기 턴 값을 낸다.
대가: 메인 세션은 서브에이전트가 보고하기로 한 것만 돌려받는다. 나머지는 버려진다.
(서브에이전트가 갖는 것: 자기 시스템 프롬프트, 도구, 내 CLAUDE.md. 갖지 않는 것: 내 대화.)
Q7요청이 조립되는 순서는? 그 순서가 왜 중요한가?
도구 정의 → 시스템 프롬프트 → 대화(그 맨 앞에 CLAUDE.md).
캐시는 요청의 맨 처음부터 앞으로 일치해야 하므로, 앞쪽에 있는 무엇이 바뀌면 그 뒤가 전부 다시 프리필된다. 대화 끝에 붙는 도구 결과가 이상적인 경우인 이유는 뒤에 아무것도 없기 때문이다. 다만 맨 앞이라는 것은 가장 안정적으로 캐시되는 자리라는 뜻이기도 하다. 안 쓰는 MCP 서버가 비싼 이유는 프리픽스 위치가 아니라, 첫 턴에 정가로 프리필되고 그 뒤로는 컨텍스트 자리를 계속 차지하기 때문이다.
Q8지금 쓰던 세션에서 /loop을 걸면 무슨 일이 일어나는가?
루프가 그 세션의 온전한 턴 하나로 발사되고, 매번 그 대화 전체를 끌고 간다. 게다가 마지막 턴에서 한 시간이 지났다면 캐시 미스까지 겹쳐 대화 전체를 정가로 다시 프리필한다.
→ 다른 터미널에서 새 세션을 열고 거기서 루프를 돌린다.
보너스 원문이 가장 강조하는 프레이밍 한 줄: 토큰을 적게 쓰는 것이 목표가 아니다. 쓴 토큰이 실제로 요청한 그 일로 가게 하는 것이 목표다. 필요한 탐색까지 아끼면 세션은 싸지지만 일은 안 끝난다.

원문이 넘긴 곳
“Choosing a Claude model and effort level in Claude Code”. 어떤 일에 어떤 모델이 값을 하는지는 별도의 주제이고, 원문은 그 글로 넘긴다. 이 문서에서 모델 장이 짧은 이유이기도 하다.
시끄러운 명령을 실행 전에 다시 쓰는 hook. 원문은 “문서에 작은 hook이 있다”고만 하고 코드를 싣지 않는다. 이 문서도 그 이상은 적지 않았다.
이 문서에서 원문에 없는 것

04장의 “턴 하나의 청구서” 블록은 원문이 추적 예시 끝에서 산문으로 요약한 것을 코드 블록 형태로 옮긴 것이다.
09장의 SVG 도해는 원문이 산문으로만 설명하는 조립 순서와 네 가지 상황을 직접 그린 것이다. 구간의 폭은 설명을 위한 것이고 실제 토큰 비율이 아니다.
21~24장(숫자 표 · 치트시트 · 운영 루틴 · 자가 점검)은 학습용으로 새로 만든 부록이다. 거기 실린 값과 규칙은 대부분 원문의 것이지만, 21장의 실측 행과 22장의 BASH_MAX_OUTPUT_LENGTH 행은 원문 밖에서 왔다. 행마다 어느 쪽인지 밝혀 두었다.

이 문서가 잰 것 · 13~15장 · Claude Code v2.1.233 임계값: 29,920자는 통과, 30,147자는 절단. 경계를 그 사이로 좁힌 것이고 30,000자를 한 자 단위로 짚은 것은 아니다.
절단 형태: <persisted-output> 래퍼, 미리보기 1,990자, 파일 경로. 요약이 아니라 원문 절단이고 꼬리는 없다.
토큰 회계(14장): 트랜스크립트 저장량 2,235자 대 29,920자, 캐시 기록 1,194 대 30,928토큰, cache_read 179,650 → 210,578, 같은 구간 output_tokens 163~2,048.
디스크 전문(13장): 저장된 파일을 열어 4,000줄 44,000자가 온전함을 확인했다.
같은 것을 자기 세션에서 보려면: 세션 기록은 ~/.claude/projects/<프로젝트>/<세션id>.jsonl 에 있다. 각 턴의 usage 에 cache_read_input_tokens·cache_creation_input_tokens·output_tokens 가 그대로 들어 있고, 시작 시점의 컨텍스트는 /context 로 본다.
명령별 독립 판정(15장): 세 명령이 각각 따로 판정됐다. 표의 세 패턴은 여기서 따라 나온 구성이지 각각 실행한 것이 아니다.
확인하지 않은 것 가격 배수(×5, ×0.1, ×2)와 캐시 수명은 측정하지 않았다. 원문의 서술을 그대로 옮긴 것이다. BASH_MAX_OUTPUT_LENGTH가 실제로 임계값을 바꾸는지도 확인하지 못했다(16장 주의 참고). /autocompact 200k의 버전 요구(v2.1.221+)처럼 시간이 지나면 달라질 값도 포함되어 있다.
미리보기 1,990자가 고정 한도인지 비율인지는 확인하지 않았다. 관측한 두 건이 모두 그 근처였을 뿐이다.
꼬리를 남기는 다른 경로가 있는지는 확인하지 않았다. 관측한 두 건이 모두 머리만 남겼을 뿐이고, “끝은 사라진다”는 13·14·21·24장에 단정으로 실려 있다.
명령 출력이 output token 이 아니라는 것은 트랜스크립트의 usage 필드를 읽어 얻은 해석이고, 청구서를 대조한 것이 아니다.
측정은 stdout 만으로 했다. stderr 가 합쳐질 때 같은 임계값이 걸리는지는 확인하지 않았다.
트랜스크립트가 곧 요청 본문이라는 것은 강한 추론이지 관측이 아니다. 실제 전송 페이로드를 가로채 본 것은 아니고, 14장의 회계 전체가 이 전제 위에 있다.
측정은 한 머신, 한 버전의 것이다. 같은 영역에서 v2.1.2 회귀가 이미 보고된 적이 있으니(위 #17944) 자기 버전에서 다시 재 보는 편이 낫다.
