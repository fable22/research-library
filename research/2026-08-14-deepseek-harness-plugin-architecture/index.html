7장이 Claude Code·Codex 와의 대비다. 공개 문서와 공개 저장소로 확인되는 것만 넣었고, 확인하지 못한 칸은 비워두지 않고 확인하지 못했다고 적었다.

읽는 순서 · 채택

12장이 한계, 13장이 도입 판단이다. 급하면 2장과 13장만 읽어도 결론은 전달된다.

화제성과 설계의 차별성은 같은 질문이 아니다. 앞의 것은 8장에서 관측 수치로만 답한다. 뒤의 것은 4~6장에서 코드로 답하고, 7장의 대비만 공개 문서와 공개 저장소 관찰이다. 저장소가 왜 눌렸는지, 그 동기 추정은 이 문서에 없다.

tl-dr

요약. 슬로건은 수사가 아니다. 부팅 루트가 실제로 빈 배열이고, 트리 전체가 패치 합성의 결과다

에이전트 루프, 모델 어댑터, 툴 레지스트리, 세션 로그가 모두 설정 파일의 한 행이다. 설정으로 갈아끼울 수 없는 코드는 런처와 커널을 합쳐 6,143줄이고, 이는 프로덕션 TypeScript 소스 205,749줄의 3.0%다. 커널은 자체 구현이 아니라 소스째 들여온 Cordis 이고, 벤더 계층 전체에 upstream 과 다른 곳 18군데가 로그로 적혀 있다.

슬로건이 코드에서 가리키는 것은 세 가지다. 첫째, apps/cli/src/profile-boot.ts:63 의 부팅 루트 상수가 문자 그대로 [] 다. 둘째, 그 위에 번들·프로파일·홈·--patch 순서로 패치 레이어가 쌓여 마운트할 행 목록이 만들어진다. 셋째, 런처는 어떤 capability 패키지도 import 하지 않는다. 부트 지원 패키지 네 개만 import 한다.

다만 차별성의 크기는 슬로건이 시사하는 만큼은 아니다. Codex 도 plugins·model_providers 설정 섹션을 가지고 있고, Claude Code 도 플러그인을 문서화한다. 실제로 갈라지는 지점은 교체 가능한 범주가 열거형인가 아닌가다. dsh 에서 에이전트 루프는 특별한 확장 범주가 아니라 id: agent-loop 이라는 행이고, 나머지 77개 행과 문법이 같다.

이 문서는 dsh 를 실행하지 않았다. 부팅 순서와 패치 합성은 소스를 읽어 확인한 것이고, 런타임에 실제로 그렇게 동작하는지는 확인하지 않았다. 실행해 확인해야 할 항목은 12장에 모아두었다.

problem

문제 정의. 하네스에서 바꿀 수 있는 것은 확장 범주의 목록이 정해 왔다

에이전트 하네스를 쓰다 보면 요구가 문서화된 확장 범주 밖으로 나간다. 세션 로그를 다른 형식으로 남기고 싶다거나, 모델 요청 직전에 컨텍스트를 다시 조립하고 싶다거나, 루프의 종료 조건을 바꾸고 싶다는 식이다. 그때 범주 목록이 곧 가능한 것의 목록이 된다.

  • CCClaude Code 의 플러그인 문서는 확장 대상을 skills, agents, hooks, MCP servers 네 가지로 적는다. "This guide covers creating your own plugins with skills, agents, hooks, and MCP servers." (code.claude.com/docs/en/plugins, 2026-08-14 조회)
  • CXCodex 의 설정 레퍼런스는 최상위 섹션으로 agents, hooks, mcp_servers, model_providers, plugins, permissions 등을 열거한다. 모델 제공자 추가와 훅은 설정으로 되고, 그 목록에 에이전트 루프는 없다.
  • ✗두 도구의 비공개 구현에 그 범주 밖 확장 지점이 있는지는 확인하지 못했다. 확인한 것은 공개 문서에 없다는 사실뿐이고, 이 문서는 거기까지만 주장한다.

dsh 저장소는 같은 문제를 자기 기여 규칙에 명시적으로 적어 두었다. AGENTS.md:108: "Plugins, not loop changes: new behavior goes on documented extension points; changing agent-loop requires updating docs/architecture.md." 루프를 고치면 아키텍처 문서를 함께 갱신해야 하는 일로 값이 매겨져 있다. 다만 이 값은 내부 팀만 치를 수 있다. CONTRIBUTING.md 가 "We are sorry that we cannot accept external pull requests at the moment." 라고 적는다. 외부 사용자에게 남는 경로는 저장소를 고치는 쪽이 아니라 자기 플러그인을 마운트하는 쪽뿐이다.

dsh 는 packages/hooks/hooks-claude-code 를 싣고 있고, 그 README 는 사용자가 이미 가지고 있는 Claude Code 훅 설정(hooks.json) 중 지원되는 command-hook 부분집합을 실행하는 브리지라고 스스로 설명한다(README.md:5, "runs the supported command-hook subset"). 기존 설정이 통째로 도는 것이 아니다. 확장이 훅이라는 좁은 통로로 몰려 있었다는 관찰이 이 패키지의 존재 이유다.

이 장은 "포크 말고는 방법이 없었다"고 주장하지 않는다. 실제로 사람들이 무엇을 했는지(포크 수, 이슈, 커뮤니티 논의)는 조사하지 않았다. 확인한 것은 각 도구의 공개 문서가 약속하는 확장 표면의 범위이고, 그 범위가 열거된 목록이라는 점이다.

kernel

구조 1. 플러그인 커널은 자체 구현이 아니라 소스째 들여와 고쳐 쓰는 Cordis 사본이다

README 는 "powered by Cordis" 라고만 적지만, 의존 방식이 npm 이 아니다. vendor/ 아래에 소스를 복사해 넣고 @deepseek-ai 스코프로 이름까지 바꿔 자기 이름으로 재배포한다.

왜 npm 의존이 아닌지는 저장소가 직접 답한다. vendor/README.md:3: "They are copied into this monorepo instead of being depended on via npm, so that the harness fully owns its framework layer (auditable, patchable, pinned)." 실제로 고쳤다. 같은 파일의 local-modification 로그는 18개 항목인데, 이 18은 커널 하나의 수가 아니라 위 9개 패키지 전체를 덮는 수다. vendor/README.md:31 이 로그를 빠짐없이 유지하라고, 즉 upstream 과의 모든 차이를 여기 적으라고 요구한다. 항목 이름으로 cordis/src 를 지목하는 것은 그중 셋(:38·:39·:47)이고, 거기에는 주석 정리(:39 JSDoc enrichment)뿐 아니라 커널의 해제 순서를 바꾸는 항목(:38, cordis/src/fiber.ts lifecycle hardening)이 들어 있다. 여러 벤더 패키지에 걸치는 항목 다섯(:34·:35·:36·:42·:49)도 커널에 닿지만, 18 이라는 수 자체는 커널의 것이 아니다. 패치 알고리즘 자체를 바꾸는 항목(:43)은 커널이 아니라 include 플러그인의 것이다.

패치 알고리즘 수정은 이 아키텍처가 성립하기 위한 조건이었다. vendor/README.md:43: "applyEntryPatches also indexes each inserted entry as it is added, so a later patch in the same list can configure or disable a row an earlier patch inserted; upstream built the id index once before the patch loop, leaving inserted rows silently unpatchable." upstream 그대로였다면 번들이 삽입한 78개 행을 사용자가 건드릴 수 없었다. 5장에서 볼 레이어 구조는 이 수정 위에 서 있다.

커널 소스 자체는 열지 않았다. vendor/cordis/src 는 9개 파일 2,693줄이고, 이 장의 진술은 파일 목록·줄 수와 vendor/README.md·docs/cordis-primer.md 를 근거로 한다. 수정 로그가 실제 코드와 일치하는지는 확인하지 않았다.

composition

구조 2. 부팅 트리는 빈 배열 위에 패치 레이어를 순서대로 쌓은 결과다

프로파일 디렉터리에 실제로 존재하는 cordis.yml 의 내용은 [] 다. 파일이 디스크에 있는 이유는 Loader 가 baseUrl 을 걸 실제 루트를 필요로 하기 때문이고, 부팅할 때마다 다시 덮어쓴다. 마운트할 행 목록은 그 빈 배열에 패치 리스트를 전부 적용해서 만든다.

행의 순서에는 로드 의미가 없다. packages/bundle/base/cordis.patch.yml:12-13 이 직접 적어둔다. "Row order carries no load semantics (activation is service-availability driven); the grouping is for readers." 무엇이 먼저 뜨는지는 각 플러그인의 static inject 선언이 정한다. 예를 들어 packages/core/agent-loop/src/index.ts:297 의 static inject = ['agents', 'sessions', 'llm', 'tools', 'systemPrompt'] 가 이 다섯 서비스가 준비될 때까지 에이전트 루프를 기다리게 한다.

이 합성이 런타임에 실제로 이 순서로 일어나는지는 실행해 확인하지 않았다. 저장소는 확인 수단을 제공한다. dsh --profile web --dump-config 가 부팅하지 않고 합성 결과만 출력하고, 그 경로가 applyEntryPatches 를 마운트 경로와 공유하도록 vendor/include/src/index.ts 를 고친 것이 4장의 수정 항목 11이다. 커널이 아니라 include 플러그인 쪽이다.

boundary

구조 3. 설정으로 갈아끼울 수 없는 코드는 6,143줄, 전체 소스의 3.0%다

"특권적 코어가 없다"는 docs/architecture.md:13 의 문장은 반증 가능하다. 코어가 있다면 그것은 어떤 플러그인도 거치지 않고 capability 를 직접 붙잡고 있는 코드일 것이고, 그런 코드는 셀 수 있다.

런처가 무엇을 import 하는지 세면 코어 여부가 갈린다. grep -rn "@deepseek-ai/dsh-" apps/cli/src/ 의 결과는 네 개뿐이다. dsh-app-boot, dsh-home-paths, dsh-launch-environment, dsh-cmdline. 모델 어댑터도, 툴도, 에이전트 루프도 없다. apps/cli/src/bin.ts:29-49 의 모드는 profile, plugin, dump-config 셋뿐이고, 나머지는 전부 트리 안이다.

에이전트 루프도 같은 검사를 통과한다. grep -rn "from '@deepseek-ai/dsh-agent-loop'" --include='*.ts' packages apps | grep '/src/' | grep -v 'packages/core/agent-loop/' | grep -v 'test-support' 는 1건을 낸다. packages/examples/agent-spine-demo/src/index.ts:36, 데모 패키지다. 프로덕션 코드에서 루프에 도달하는 경로는 설정 행뿐이다.

교체 가능성과 교체의 난이도는 다른 문제다. 이 장이 보인 것은 런처가 특정 구현을 붙잡고 있지 않다는 것이지, 예를 들어 agent-loop 을 다른 구현으로 갈아끼웠을 때 나머지 77개 행이 계속 동작한다는 것이 아니다. AgentLoop 이 AgentFactory 를 구현하고 다섯 서비스를 inject 한다는 것까지가 코드에서 읽은 범위다.

alt-compare

대안과의 비교. 세 도구 모두 플러그인이 있다. 갈리는 것은 교체 가능한 것이 열거형인가다

"플러그인을 지원하는가"로 물으면 셋 다 예다. Codex 설정에는 plugins 섹션이 있고 Claude Code 는 플러그인 작성 문서를 따로 둔다. 질문을 "에이전트 루프를 설정으로 바꿀 수 있는가"로 바꾸면 답이 갈린다.

이 대비는 dsh 저장소 안에서도 읽힌다. packages/hooks/ 아래에 hooks-claude-code 와 hooks-codex 가 둘 다 있고, 앞의 것은 사용자의 기존 hooks.json 을 읽어 ${CLAUDE_PLUGIN_ROOT}·${CLAUDE_PROJECT_DIR} 치환까지 재현한다. 그 README 는 이 브리지의 위치를 스스로 못 박는다. 네이티브 cordis 플러그인이면 같은 일을 타입 있는 반환값으로, 직렬화 경계 없이 더 잘 할 수 있다고 적은 뒤 이렇게 잇는다. "The bridge exists only as a compatibility path for the mapped CC command-hook subset; anything bespoke should be a native plugin on the same extension points."

확인하지 못한 칸을 채우지 않았다. Claude Code 와 Codex 의 비공개 내부에 루프 교체 지점이 있는지는 알 수 없다. 이 표의 "찾지 못함"은 code.claude.com/docs/en/plugins 와 Codex 설정 레퍼런스(learn.chatgpt.com/docs/config-file/config-reference)에서 해당 항목을 찾지 못했다는 뜻이며, Codex 공개 저장소에 codex-rs/plugin·codex-rs/core-plugins 크레이트가 존재한다는 것은 별개 사실이다. 그 크레이트가 사용자 확장 지점인지는 확인하지 않았다.

README 와 코드의 차이

Cordis 는 upstream 이 아니다. README 는 cordiverse/cordis 를 링크하지만 실행되는 것은 @deepseek-ai/cordis 로 이름을 바꾼 벤더 사본이다. 커널 소스를 이름으로 지목하는 수정 항목은 셋이고(vendor/README.md 의 :38·:39·:47), 그중 :38 이 해제 순서를 바꾼다. 플러그인을 만들 때 peer dependency 로 선언할 이름도 cordis 가 아니라 @deepseek-ai/cordis 다(AGENTS.md:100). upstream 문서를 보고 쓰면 어긋난다.

  • ✗실행하지 않았다. 부팅 순서, 패치 적용, 언로드가 런타임에 문서대로 되는지 확인하지 않았다. 4~9장은 전부 소스를 읽은 결과다.
  • ✗테스트를 열지 않았다. .spec.ts·.e2e.ts 파일이 821개 있다는 것만 세었다. 무엇이 덮이고 무엇이 안 덮이는지 이 문서는 모른다.
  • ✗이슈가 없다. has_issues: false, Discussions 만 열려 있다. 알려진 버그와 회귀를 저장소에서 읽을 방법이 없다. 응답 기대치만은 CONTRIBUTING.md:12 가 적어 두었다. "We are a very small team and may not be able to reply to every post, but we monitor them and consider them when allocating resources."
  • ✗라이선스가 최근에 바뀌었다. npm 의 0.0.1-rc.5(08-12)까지 BSD-3-Clause, 0.1.0-rc.2(08-13)부터 MIT 다. 공개 전에 설치한 사본은 다른 라이선스다.
  • ✗이 문서가 만든 비율은 원문에 없다. 6장의 3.0%, 8장의 나이 대비 비교는 여기서 계산한 것이다.

한계 밖으로 남는 것은 합성 결과를 부팅 없이 출력하는 경로다. dsh --profile web --dump-config 가 마운트 경로와 같은 applyEntryPatches 를 쓰도록 vendor/include/src/index.ts 를 고쳐 두었기 때문에(vendor/README.md:43), 위의 "읽기만 해서는 모른다"는 항목 중 어떤 트리가 뜨는가는 도구 하나로 검증된다. 이 설계는 dsh 를 안 쓰더라도 옮겨갈 만하다. 설정 합성기와 부팅기가 같은 함수를 공유하면 설정 문서가 코드에서 어긋날 자리가 없어진다.

설치가 남기는 것

$DSH_HOME/profiles/<name>/ 에 package.json, cordis.patch.yml, pnpm-workspace.yaml, 그리고 매 부팅마다 [] 로 덮어쓰는 cordis.yml. $DSH_HOME/profiles/node_modules/ 에는 설치본 의존 closure 만큼의 심볼릭 링크가 부팅할 때마다 다시 만들어진다. 텔레메트리를 켜면 $DSH_HOME/.anonymous-user-id 에 랜덤 UUID 가 생기고 export 의 user.id 로 나간다. $DSH_HOME 밖에도 남는다. cordis.patch.yml:175 의 기본 권한 모드가 workspace-write, :191 의 승인 정책이 ask 이고, :441 은 fs-sandbox 의 cwd 가 process.cwd() 기본이라고 적는다. 기본 실행에서 에이전트가 쓰는 범위는 dsh 를 띄운 디렉터리다. 전제조건은 Node ^22.19.0 || >=24.0.0 이고, 프로파일에 플러그인을 설치하려면 pnpm 이 PATH 에 있어야 한다(apps/cli/src/plugin.ts:137 이 없을 때 127 로 끝낸다).

되돌리기

프로파일 디렉터리를 지우면 구성이 사라진다. 세션 로그와 크레덴셜은 그 디렉터리 밖이라 남는다. cordis.patch.yml:101 이 세션 로그 루트를 dshHomePath('sessions') 로 잡고, :82 가 관리 문서를 $DSH_HOME/.credentials.yaml 로 적는다. profiles/node_modules 의 링크도 남는다. profile.ts:219 가 "a stale link to a vanished package stays until its name is reused (dangling links are invisible to resolution)" 라고 적어 두었다. 제3자 플러그인 설치는 별도 레지스트리가 아니라 pnpm 을 그대로 부르는 것이라(apps/cli/src/plugin.ts:2-7), 제거도 pnpm remove 와 같은 방식이다.

시험할 때 먼저 볼 것은 코드가 아니라 출력이다. dsh --profile web --dump-config 로 실제 마운트되는 행 목록을 받아, base 번들이 넣는 78개 행이 그 안에 다 있는지 대조하면 4~6장의 주장이 당신 기계에서 재현되는지 15분 안에 결론이 난다. 다만 78행이 다 있되 그중 24행은 disabled: true 가 붙은 채로 나온다. 설치가 잘못된 것이 아니다. 목록 길이도 78이 아니다. web 프로파일은 web-app 번들이 51개 행을 더 넣어 129행이고, 나머지 27개 패치는 행 수를 늘리지 않는다. 그 27개 중 24개가 방금 말한 base 행에 disabled: true 만 붙이고(hmr, tool-bash, tool-fs 등), 셋만 config 를 갈아끼운다(system-prompt, session-query-sqlite, tools).

conclusion

결론. 슬로건은 코드에서 확인되고, 차별성은 "무엇을 바꿀 수 있는가"가 열거형이 아니라는 데 있다

두 질문에 따로 답한다. 화제성은 관측되지만 원인은 이 문서의 근거로 특정할 수 없다. 설계의 차별성은 관측되고 위치도 특정된다.

화제성

공개 18시간에 star 71,700개, 관측 구간 시간당 3,526개. 다만 하루 만에 만들어진 프로젝트가 아니다. npm 공개가 2일 16시간 빠르고, HEAD 커밋 제목이 PR #2519 를 인용하며, contributors 22명 중 한 명이 5,235 커밋을 가지고 있다. 08-13 에 공개된 것은 저장소이고, 코드는 그 전부터 굴러왔다. 무엇이 star 를 눌렀는지는 이슈도 없고 반응을 읽을 표면도 없어 알 수 없다.

설계

"everything is a plugin" 은 부팅 루트가 [] 이고 트리 전체가 패치 합성의 결과라는 뜻이다. 설정으로 갈 수 없는 코드는 6,143줄이고, 그중 3,830줄(커널 2,693 + loader 1,137)은 남에게서 가져온 것이다. 커널은 소스째 들여와 고쳐 쓰는 Cordis 사본이다. 자체 구현과 단순 의존 사이, 벤더링해서 고쳐 쓰는 자리에 있다.

Claude Code·Codex 와의 차이는 "플러그인이 있는가"에서 갈리지 않는다. 셋 다 있다. 차이는 교체 가능한 것의 목록이 닫혀 있는가다. Claude Code 의 플러그인은 skills·agents·hooks·MCP 네 범주고, Codex 의 설정은 최상위 섹션 목록이다. dsh 에서 에이전트 루프는 id: agent-loop 이라는 한 행이고, 나머지 77개 행과 문법이 같다. 이 차이가 실제로 값을 하는 경우는 하나다. 바꾸고 싶은 것이 남의 확장 범주 목록에 없을 때다.

그 대가는 이미 저장소에 드러나 있다. 219개 패키지, seam 하나에 세 역할을 요구하고 역할마다 쪼개는 규칙, 프레임워크를 통째로 벤더링하고 18곳의 수정 로그를 유지하는 비용, upstream Cordis 문서를 그대로 믿으면 어긋난다는 사실이다. 확장을 유연하게 만든 만큼 이해해야 할 표면이 늘었다.

이 결론은 소스를 읽어 얻었고 실행으로 확인하지 않았다. 가장 크게 걸린 주장 둘 중 하나는 검증 방법까지 적어 두었다. dsh --profile web --dump-config 의 합성 결과에서 base 번들의 78개 행을 찾는 것이고(그 출력 자체는 129행이다), 12장과 13장이 그 절차다. 다른 하나, agent-loop 행을 다른 구현으로 갈아끼웠을 때 나머지 77개 행이 계속 뜨는가는 절차가 이 문서에 없다. 6장 말미가 그것을 확인하지 않았다고만 적는다.
