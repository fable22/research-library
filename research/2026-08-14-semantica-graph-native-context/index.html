semantica: 그래프는 RAG 위에 얹히고, 벤치마크는 저장소에 없다

semantica 는 스스로를 Graph-Native Infrastructure for Context and Accountable AI Systems 라고 부른다. 문서 청킹과 임베딩을 그래프로 갈아치웠다는 뜻으로 읽히지만, 코드에서는 청킹도 임베딩도 그대로 남아 있고 그래프가 한 갈래 더 붙는다. 이 문서는 그 구조를 검색 경로에서 확인하고, 저장소가 내세우는 강점 각각에 대해 뒷받침하는 실증이 저장소 안에 있는지 하나씩 대조한다.

읽는 순서: ④⑤ 가 구조, ⑥ 이 기존 RAG 와의 대조, ⑦⑧ 이 주장 대 근거, ⑨ 가 retrieve() 한 번의 추적, ⑩⑪ 이 에이전트 컨텍스트 관점이다. 도입 판단만 필요하면 ⑭ 로 바로 간다.

tl-dr

graph-native 는 vector 검색을 대체한다는 뜻이 아니라 그 옆에 갈래를 하나 더 둔다는 뜻이다

ContextRetriever.retrieve() 는 vector lane 을 조건 없이 먼저 돌리고, knowledge_graph 가 붙어 있을 때만 graph lane 을 추가로 돌린다. 두 결과는 hybrid_alpha 기본값 0.5 로 반반 가중되고, 마지막에 embedding cosine 유사도가 0.3 비중으로 전체 순위에 다시 섞인다. 청킹은 chunk_size 1000, overlap 200 이라는 통상적인 RAG 기본값 그대로다.

  • 1구조. 파이프라인은 Split → Extract → KG 를 거쳐 vector store 와 graph store 양쪽으로 나간다. 유지보수자가 직접 그린 ARCHITECTURE.md 다이어그램이 그렇게 되어 있다. 기존 RAG 를 빼고 대신 넣은 것이 아니라 그 위에 층을 얹은 구조다.
  • 2근거. README 의 Performance 표에 있는 6,000배, 6.98배, 63.6% 는 모두 CHANGELOG.md 의 한 줄로 거슬러 올라간다. 데이터셋도 스크립트도 붙어 있지 않다. README 가 직접 돌려보라고 안내하는 테스트 파일은 pytest 가 한 건도 수집하지 못한다.
  • 3없는 것. semantica.evals 는 __all__ = [] 인 stub 이고 문서도 그렇게 적어 두었다. 그런데 docs/modules.md 는 같은 모듈에서 네 클래스를 import 해 F1 을 출력하는 예제를 아무 단서 없이 싣고 있다.
  • 4세션. MCP 서버의 그래프는 프로세스 전역 싱글턴이다. 문서화된 복원 경로 SEMANTICA_KG_PATH 는 존재하지 않는 메서드를 호출하고, 실패는 warning 으로 삼켜진다. 저장 경로는 아예 없다.

뒤집히는 조건: benchmarks/ 디렉터리가 실제로 추가되고 CI 가 그것과 tests/ 를 돌리기 시작하면 ⑦⑧ 의 결론은 그날로 무효다. 구조에 관한 ④⑤⑥ 은 그와 무관하게 남는다.

problem

저장소가 지목하는 문제는 검색 품질이 아니라 감사 가능성이다

README 의 첫 문단은 벡터 검색이 부정확하다고 말하지 않는다. 결정에 이유가 남지 않는다고 말한다. 이 구분이 뒤의 모든 판단을 가른다. 검색 성능을 기대하고 들어온 사람과 규제 대응을 기대하고 들어온 사람이 서로 다른 것을 얻는다.

Most AI agents act without a trail. They store embeddings, not meaning: context that can't be explained, decisions that can't be audited. In lending, that gap is a compliance exposure, not an inconvenience.README.md:51

겨냥하는 수작업은 사후 소명이다. 대출 심사 에이전트가 몇 달 뒤 규제 기관의 왜 라는 질문을 받았을 때, 로그를 뒤져 판단 근거를 재구성하는 일을 없애겠다는 것이다. 그래서 semantica 가 일급 객체로 올린 것은 문서 조각이 아니라 결정이다. record_decision() 이 category, scenario, reasoning, outcome, confidence 를 받아 그래프 노드 하나로 남기고, add_causal_relationship() 이 결정 사이를 CAUSED, INFLUENCED, PRECEDENT_FOR 세 종류의 간선으로 잇는다.

여기까지는 벡터 스토어가 대신할 수 없는 일이 맞다. 임베딩은 유사도만 돌려주고 인과를 돌려주지 않는다. 다만 record_decision() 을 호출하는 것은 에이전트를 짜는 사람이다. semantica 는 결정이 기록될 자리를 제공하고, 무엇을 기록할지는 호출자가 정한다. 기록하지 않은 결정은 그래프에 없다.

이 장은 README 가 스스로 선언한 문제를 정리한 것이다. 그 문제가 실제로 해결됐는지는 ⑦ 에서 주장별로 대조한다.

architecture

Split 은 파이프라인에 그대로 남아 있고, 그래프는 KG 를 거친 뒤 저장 단계에서 갈라져 나온다

유지보수자가 ARCHITECTURE.md 에 직접 그린 mermaid 다이어그램이 이 질문에 대한 가장 좋은 답이다. Enriched KG 에서 저장소로 가는 화살표는 두 갈래로 나뉘어 Vector Store 와 Graph Store 로 동시에 간다. 둘 중 하나를 고르는 구조가 아니다.

semantica 파이프라인은 RAG 파이프라인을 포함한다

ARCHITECTURE.md:11-68 의 mermaid 다이어그램을 이 문서가 접어서 다시 그린 것. 원본에서 Parse 앞에는 ingest 소스 6종(:16-21)이, Vector·Graph Store 뒤에는 export 와 visualization 이 더 있고, Enriched KG 에서 Services(REST API · MCP Server · CLI · Knowledge Explorer, :67)로 나가는 세 번째 화살표도 이 그림에서 뺐다. 아래 KG 상자 하나에는 원본의 아홉 노드(충돌 탐지 · 중복 제거 · KG 구축 · Knowledge Graph · 온톨로지 · 추론 · provenance · context · Enriched KG, :44-58)가 접혀 있고, 저장소 갈래가 나뉘는 지점은 그 마지막 Enriched KG 다.

이 그림은 유지보수자가 그린 것이므로 의도의 증거다. 실제 실행 순서가 이와 같은지는 ⑨ 에서 코드로 따로 확인한다.

retrieval

검색은 세 갈래를 각각 돌린 뒤 점수를 섞는다. 마지막 재정렬은 다시 embedding cosine 이다

retrieve() 안에서 vector lane 은 조건 없이 실행되고, graph lane 과 memory lane 은 해당 저장소가 붙어 있을 때만 실행된다. 세 결과가 _rank_and_merge() 로 모여 lane 별로 정규화된 뒤 hybrid_alpha 로 가중된다. 그리고 병합이 끝난 전체 결과에 query embedding 과의 cosine 유사도가 0.3 비중으로 다시 얹힌다.

graph lane 은 vector lane 을 밀어내지 않고 옆에 선다

semantica/context/context_retriever.py:227-257, 763-776, 858-860 기준. 기본값은 같은 파일 148-150 행.

lane 별 가중치와 hop 수는 모두 생성자 kwargs 로 바꿀 수 있다. 위 숫자는 아무것도 넘기지 않았을 때의 기본값이다.

       병합 결과 전체를 embedding cosine 으로 다시 정렬한다
       semantic_sim = np.dot(query_embedding, content_embedding) / (query_norm * content_norm)
       result.score = result.score * 0.7 + float(semantic_sim) * 0.3
       → graph lane 으로 들어온 항목도 이 재정렬을 받는다

홉 4 가 이 추적의 핵심이다. graph-native 라는 말은 질의가 그래프 질의로 번역된다는 뜻으로 읽히기 쉽지만, 여기서 일어나는 일은 질의 문자열을 그래프 객체의 query() 에 그대로 넘기는 것이다. 그래프가 기여하는 부분은 그 뒤 홉 5 의 이웃 확장이다. 즉 그래프는 무엇을 찾을지가 아니라 찾은 것 주변에 무엇을 더 붙일지를 정한다.

홉 4 에서 knowledge_graph 에 query 속성이 없으면 dict 기반 fallback 으로 내려간다(380행 이후). 이 문서는 ContextGraph 를 붙인 경우만 따라갔고, 외부 graph store 를 붙였을 때의 경로는 열지 않았다.

budget

컨텍스트 윈도우에 무엇이 올라갈지는 토큰이 아니라 건수로 정해진다

에이전트에게 돌아가는 양을 제한하는 값은 max_results 이고 기본값은 5다. 토큰 예산은 검색 경로에 없다. 저장소 전체에서 토큰을 세는 곳은 agent_memory.py 의 단기 버퍼 하나뿐이고, 그마저 tokenizer 가 아니라 문자 수 나누기 4다.

검색 경로 · 토큰 예산 없음

ContextRetriever.retrieve() 의 상한은 max_results: int = 5 다. 반환되는 RetrievedContext 각각의 content 길이는 제한되지 않는다. 청크 하나가 1000자 기준으로 잘렸으므로 대략적인 상한은 있지만, graph lane 이 붙여 보내는 related_entities 는 2 hop 안의 이웃 전부이고 개수 제한이 없다.

단기 메모리 · 유일한 토큰 예산

token_limit 기본 2000, short_term_limit 기본 10건. 초과하면 오래된 것부터 pop(0) 으로 버린다. 토큰 계산은 len(text) // 4 다. split 모듈은 이미 tiktoken 을 의존성으로 갖고 있지만 여기서는 쓰지 않는다.

컨텍스트 윈도우 관리는 semantica 가 하지 않고 호출자가 한다. semantica 는 관련도 순으로 정렬된 5건을 돌려주고, 그것이 몇 토큰인지는 알려주지 않는다. 토큰 단위로 예산을 잡아야 하는 에이전트라면 반환값을 받아 직접 세고 잘라야 한다.

이건 결함이라기보다 층의 경계에 대한 선택이다. 다만 README 가 semantica 를 context layer 로 부르는 만큼, 컨텍스트 예산이 이 층 밖에 있다는 점은 도입 전에 알고 있어야 한다.

session

MCP 서버의 그래프는 프로세스와 함께 사라지고, 문서화된 복원 경로는 없는 메서드를 부른다

README 는 MCP 서버를 에이전트 연결 수단으로 앞세우고 MCP setup takes 30 seconds 라고 안내한다(README.md:1194). 그 서버의 상태 모델은 파일 47줄에 전부 들어 있다. 그래프는 모듈 전역 변수 하나이고, 서버 프로세스가 살아 있는 동안만 존재한다.

# mcp/session.py:17-41 (발췌)
_graph: Optional[Any] = None

def get_graph() -> Any:
    global _graph

        from semantica.context import ContextGraph
        _graph = ContextGraph(advanced_analytics=True)

        kg_path = os.environ.get("SEMANTICA_KG_PATH", "").strip()

# ContextGraph 가 정의하는 것: save_to_file(1051), load_from_file(1085)
# 상속 없음, __getattr__ 없음 → load 는 어디서도 오지 않는다

두 가지가 겹쳐 있다. 첫째, ContextGraph 에는 load 라는 메서드가 없다. 기반 클래스도 __getattr__ 도 없으므로 이 호출은 AttributeError 로 끝나고, 바로 아래 except Exception 이 그것을 warning 한 줄로 낮춘다. 서버는 정상 기동하고, 사용자는 빈 그래프를 얻는다. 둘째, 저장 쪽은 아예 구현이 없다. mcp/ 와 semantica/mcp_server/ 어디에도 그래프를 파일로 쓰는 코드는 검색되지 않는다.

그런데 MCP 문서는 이 환경변수를 이렇게 설명한다.

| SEMANTICA_KG_PATH | (in-memory) | Path to persist/load the graph (JSON file) |mcp/README.md:219

persist 는 구현되지 않았고 load 는 위 이유로 동작하지 않는다. 즉 MCP 로 semantica 를 붙인 에이전트에게 세션 간 상태는 없다. 대화가 끝나면 그동안 기록한 결정과 인과 간선이 모두 사라진다. 지속시키려면 Python 으로 save_to_file() 을 직접 부르거나, 외부 graph store 를 붙여야 한다.

여기까지는 저장소 루트의 mcp/ 를 읽은 것이고, pip install semantica 로 오는 것은 그 디렉터리가 아니다. pyproject.toml:259-261 의 [tool.setuptools.packages.find] 가 include = ["semantica*", "integrations*"] 이고 MANIFEST.in 은 recursive-include semantica/static * 한 줄뿐이라 mcp/ 는 wheel 에도 sdist 에도 들어가지 않는다. 설치하면 생기는 semantica-mcp 명령이 가리키는 것은 pyproject.toml:256 의 semantica.mcp_server:main, 즉 semantica/mcp_server/__init__.py 다. 그 파일 69-81행의 _get_graph() 에 같은 코드가 그대로 있다. 없는 load 를 부르고, except Exception 이 log.warning 으로 낮추고, 저장 쪽은 역시 없다. 판정은 두 경로에서 같고, 독자가 실제로 설치하는 쪽은 뒤쪽이다.

이 두 문장은 코드를 읽어 내린 결론이고 서버를 띄워 확인한 것이 아니다. 확인 방법은 SEMANTICA_KG_PATH 를 유효한 JSON 경로로 두고 서버를 기동한 뒤 로그에 Could not load graph 가 찍히는지 보는 것이다. 저장 부재는 grep -rn 'save\|persist' mcp/ semantica/mcp_server/ 가 세 줄만 돌려주는 것으로 확인했다. 셋 다 서술이고 호출이 아니다(mcp/session.py:6 docstring, mcp/README.md:219, semantica/mcp_server/__init__.py:38 docstring).

critique

문서 게이트는 표현의 완결성을 검사하고 사실 여부는 검사하지 않는다

이 문서가 찾은 문제 중 가장 구조적인 것은 개별 오류가 아니라 그것을 걸러낼 자리가 비어 있다는 점이다. docs_check.py 의 검사 열 개 중 여덟 개는 JSON 유효성·링크 해석·frontmatter·태그 균형 같은 구조 항목이다. 나머지 둘은 내용을 읽지만 좁다. 문서에 실린 코드를 import 해 보는 검사는 없다.

그래서 다음 일이 동시에 성립한다. docs/reference/evals.md:10 은 이 모듈이 구현되지 않았다고 경고한다. 같은 저장소의 docs/modules.md:465 는 아무 경고 없이 이렇게 시작하는 예제를 싣는다.

from semantica.evals import KGEvaluator, ExtractionEvaluator, PipelineEvaluator, RegressionTracker

두 문서는 클래스 이름조차 어긋난다. reference 쪽은 PipelineBenchmark 라고 쓰고 modules 쪽은 PipelineEvaluator 라고 쓴다. 둘 다 존재하지 않으므로 어느 쪽도 틀렸다고 말할 수 없다. 그리고 docs_check.py:183-196 의 검사 하나는 27개 모듈이 index.md 에 빠짐없이 등장하는지 확인하는데, 그 목록에 semantica.evals 가 들어 있다. 게이트가 미구현 모듈의 노출을 강제하는 셈이다.

내용을 읽는 검사 둘이 이 자리에 닿을 뻔했다. :147-165 는 없는 클래스 이름을 금지하는데, 방식이 (정규식, 파일) 쌍 열 개를 손으로 적어 둔 blocklist 다. 목록에 있는 것은 BaseIngestor·DataNormalizer·DeductiveEngine 같은 이름이고, 위에서 문제가 된 PipelineEvaluator 넷은 들어 있지 않다. :169-179 는 코드 블록 안을 읽지만 찾는 것은 list[ 같은 Python 3.9+ 타입 문법 하나다. 즉 걸러내는 자리가 있기는 한데, 무엇이 없는 이름인지를 사람이 미리 적어 넣어야 한다.

읽어서 확인한 것

파일에 무엇이 쓰여 있는가. 기본값, 호출 순서, 메서드의 존재와 부재, 워크플로가 무엇을 실행하는가. pytest 수집 여부는 AST 로 메서드 이름을 뽑아 기본 규칙과 대조해 확인했다.

확인하지 못한 것

런타임 동작 전부. 설치해서 돌리지 않았고 서버를 띄우지 않았다. 6,000배가 사실인지 아닌지는 이 문서가 판정하지 않는다. 판정한 것은 저장소 안에서 그것을 확인할 방법이 없다는 것뿐이다.

한계를 넘어 남는 것 하나. docs_check.py 의 검사 열 개는 그 자체로는 잘 만들어져 있고 문서 게이트를 만들려는 사람에게 베낄 만한 형태다. 빠진 것은 검사 항목 하나, 즉 실린 코드가 import 되는지다. 다만 이 게이트가 도는 조건은 좁다. docs.yml 은 main 으로의 push 와 main 대상 PR 에만, 그것도 docs/**·docs_check.py·CHANGELOG.md·RELEASE.md 가 바뀌었을 때만 돈다. semantica/ 만 건드린 push 에서는 문서가 코드와 어긋나도 이 게이트가 돌지 않는다.

되돌리기

Python 라이브러리라 pip uninstall 로 끝나지만 홈과 cwd 에 넷이 남는다. semantica init 이 만드는 ~/.semantica/config.yaml(cli.py:883-892, doctor 는 존재만 보고한다), server·explorer·mcp 를 start 로 띄우면 생기는 ~/.semantica/<name>.pid(cli.py:3994 가 경로를 정하고 4099·4161·4231 이 쓴다), 현재 작업 디렉터리의 semantica.log(utils/logging.py:89 기본값. server.py:33·worker.py:15 가 import 시점에 setup_logging() 을 부른다), 그리고 embedding 모델 캐시다. BAAI/bge-small-en-v1.5 는 wheel 에 든 파일이 아니라 이름이고, TextEmbedder 가 그것을 fastembed 에 넘겨 받아온다(text_embedder.py:137). 어디에 남는지는 돌려보지 않아 모른다. 그래프 데이터 자체는 직접 지정한 경로에만 쓰인다.

고착

저장소는 swappable 을 강조하고, 실제로 graph store 4종·triple store 5종·vector store 7종을 registry 로 감싼다. 벤더 고착 위험은 낮다. 대신 42개 의존성이 런타임 고착이다.

유지보수 활력에 관한 판단은 이 표에 넣지 않았다. 이 문서의 질문이 구조와 근거에 걸려 있어 그쪽을 읽지 않았기 때문이다. 자료가 아주 없지는 않다. shallow clone 이라 커밋 이력은 체크아웃에 없지만 CHANGELOG.md 에 날짜가 붙은 릴리스 22개와 PR 귀속 40건이 있다(⑫). 판단하려면 그것부터 열면 된다.

conclusion

구현은 있고 근거는 없다. 두 문장을 한 문장으로 합치면 이 프로젝트를 잘못 읽게 된다

semantica 는 빈 껍데기가 아니다. 372개 파일의 Python 패키지가 있고, 결정 기록·인과 간선·PROV-O provenance·Rete 와 Datalog 추론기가 실제로 구현돼 있다. 동시에 그 기능이 대안보다 낫다는 것을 보여주는 측정은 저장소 어디에도 없다.

  • 1graph-native 의 뜻. 청킹(1000자/200)과 임베딩(BAAI/bge-small-en-v1.5)은 그대로 있다. 그래프는 검색 진입점이 아니라 진입 이후 2 hop 확장 단계에 있고, 최종 순위에는 embedding cosine 이 30% 다시 들어간다. 대체가 아니라 병렬 추가다.
  • 2근거의 부재는 균일하다. 특정 주장 하나가 과장된 것이 아니라, 검색·추출·품질 어느 축에도 평가 코드와 데이터셋이 없다. semantica.evals 는 __status__ = "coming_soon" 이고, 벤치마크 워크플로는 존재하지 않는 benchmarks/ 를 실행하려 한다.
  • 3검사 계층의 공백. tests/ 에 4,704개의 테스트 함수가 있지만 어떤 워크플로도 pytest 를 실행하지 않는다. 워크플로 9개를 전부 훑으면 Python 쪽에 도는 것은 정적 분석과 빌드다. wheel 빌드(ci.yml), CodeQL, Bandit·Semgrep·Safety(security-scan.yml), pip-audit(security.yml), checkov(defender-for-devops.yml), docs_check(docs.yml). 코드를 실행하는 것은 explorer 의 npm 테스트 3종뿐이고(ci.yml:36-41), 그건 TypeScript 다. PR 템플릿은 pytest tests/ 를 적어 두었지만 Optional 로 표시했다.
  • 4그래서 무엇을 봐야 하는가. 이 프로젝트의 상태를 한 번에 알려주는 지표는 별 수나 README 길이가 아니라 benchmarks/ 디렉터리의 존재 여부와 ci.yml 에 pytest 가 들어오는 시점이다. 둘 중 하나가 생기면 다시 볼 값이 있다.

이 문서가 판정하지 않은 것: 6,000배가 참인지 거짓인지. 판정한 것은 저장소 안에서 그것을 확인할 방법이 없다는 것이다. 유지보수자가 사내 데이터로 측정했을 가능성은 이 결론과 모순되지 않는다.
