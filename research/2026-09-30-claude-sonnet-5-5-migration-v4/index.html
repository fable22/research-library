Claude Sonnet 5.5 이전 안내: Sonnet 5 코드에서 바꿀 곳

Sonnet 5 요청 코드에서 모델 ID 만 바꾸면 400 을 받는 다섯 곳, 조용히 달라지는 thinking 표시와 effort 비용, 그리고 다시 재야 할 것

  • →02 요약에서 바꿀 곳 전체를 보고, 04 지도에서 각 변경이 요청 한 바퀴의 어느 구간에 닿는지 본다.
  • →05~15장은 요청을 조립하는 순서, 응답을 읽는 순서, 기록을 되돌려 보내는 순서로 놓였다. 자기 코드에 해당하는 장만 읽어도 된다.
  • →17, 18장은 발표 글의 차트 넷과 표 둘을 다시 그렸고, effort 를 고를 때 쓴다.

tl-dr

요약: 400 이 나는 곳과 조용히 바뀌는 곳

Sonnet 5 요청에서 모델 ID 만 바꾸면 thinking 의 disabled, 강제 tool_choice, computer_20251124, Sonnet 5 advisor, 앞부분을 고친 대화 기록이 400 을 받는다. 요청이 성공해도 tool call 사이 메모는 빈 thinking 블록으로 오고, effort 는 이름이 같아도 비용이 달라서 발표 글의 네 벤치마크 모두에서 max 의 작업당 비용이 Sonnet 5 max 보다 높다.

  • 400thinking: {"type": "disabled"} → between_tools (06)
  • 400tool_choice 의 any, tool → auto 와 strict: true (07)
  • 400Claude API, Google Cloud 의 computer_20251124 → computer_toolset_20260801 (08)
  • 400Sonnet 5, Opus 4.8, Opus 4.7 advisor (09)
  • 4002026-08-31 이후 만든 계정에서, thinking 블록 앞의 기록을 고치고 다시 보낸 요청 (14)
  • 200tool call 사이 메모가 기본 display 에서 빈 thinking 블록으로 온다 (12)
  • 200거절 부류가 다섯으로 늘었고, server-side fallback 은 그중 둘만 Sonnet 5 로 다시 보낸다 (13)
  • 200Sonnet 5.5 thinking 블록을 다른 모델이나 다른 계정으로 보내면 API 가 그 블록을 버린다 (15)
  • 캐시effort 를 메시지 단위로 바꾸면 캐시가 남고, 최소 캐시 길이는 512 토큰으로 줄었다 (11)
  • 비용effort 를 다시 재고 max 는 평가에서 이득이 보일 때만 쓴다. AA-Briefcase 는 기본값 high 에서도 Sonnet 5 보다 비싸다 (10, 17)

400 과 200 은 migration guide 와 What's new 의 서술이고, 요청을 보내 재현한 결과는 아니다. between_tools 와 adaptive 가 답의 품질에서 얼마나 다른지 잰 수치는 corpus 에 없다.

problem

문제: 모델 ID 한 줄의 교체

Messages API 코드는 모델 ID 만 바꿔서는 옮겨지지 않는다. 다섯 곳은 요청이 400 으로 멈추지만, tool call 사이 메모, 거절, 다른 모델로 옮긴 thinking 블록, effort 비용은 요청이 성공한 채로 달라져서 테스트를 통과한 뒤에 발견된다.

바뀌는 것드러나는 방식찾는 방법
thinking, tool_choice, computer use, advisor 설정첫 요청에서 400한 번 호출해 보면 난다
대화 기록의 편집편집한 다음 요청에서 400기록을 고치는 코드 경로를 찾아야 난다
tool call 사이 메모200, 화면이 조용해진다응답의 블록 type 을 세어야 보인다
거절 부류와 fallback200, stop_reason: "refusal"stop_reason 을 세어야 보인다
다른 모델, 다른 계정으로 옮긴 thinking 블록200, 블록이 버려진다beta 헤더의 input_transformations 를 봐야 보인다
effort 단계의 비용200, 청구액이 달라진다같은 평가를 단계별로 다시 돌려야 보인다

Claude Managed Agents 위에서 도는 코드는 모델 이름만 바꾸면 되고, 아래 장들은 Messages API 를 직접 부르는 코드의 이야기다.

첨언: 원문의 분류와 적용 범위

What's new 첫 문단: “Five breaking changes affect code already running on Claude Sonnet 5”, 그리고 “One more change alters the response shape without failing any request: text between tool calls comes back in thinking blocks.” effort 는 같은 문서의 Behavior differences 절에 “Effort levels are recalibrated.” 로 있다.

migration guide 는 Messages API 코드가 대상이다. Claude Managed Agents 는 “no changes beyond updating the model name are required.”

map

지도: 요청 한 바퀴의 네 구간

바꿀 곳은 요청을 조립하는 구간과 기록을 되돌려 보내는 구간에 있고, 400 은 모두 API 검사 구간에서 난다. 기록 편집(14장)만은 원인이 되돌려 보내는 구간에 있어서 편집한 다음 턴에야 400 이 난다.

model-id

모델 ID: claude-sonnet-5 → claude-sonnet-5-5

새 ID 는 날짜 접미사가 없는 claude-sonnet-5-5 다. Amazon Bedrock 만 anthropic.claude-sonnet-5-5 를 쓴다.

- model = "claude-sonnet-5"
+ model = "claude-sonnet-5-5"      # Bedrock: "anthropic.claude-sonnet-5-5"
  • 같음Claude API, Claude Platform on AWS, Google Cloud, Microsoft Foundry 는 claude-sonnet-5-5
  • 다름Claude in Amazon Bedrock 은 anthropic.claude-sonnet-5-5
첨언: 원문 문장

migration guide 「Migrating to Claude Sonnet 5.5 from Claude Sonnet 5」: “Replace your model ID with claude-sonnet-5-5, which has no date suffix.” 플랫폼별 ID 는 What's new 의 Availability 절에 있다.

Claude Code 에서 /claude-api migrate this project to claude-sonnet-5-5 를 실행하면 이 교체와 아래 장들의 파라미터 변경을 코드 전체에 적용하고, 사람이 확인할 목록을 남긴다.

thinking

thinking 끄기: disabled → between_tools

thinking: {"type": "disabled"} 는 Sonnet 5.5 에서 400 이다. between_tools 로 바꾸고, effort 는 high 이하로 두며 thinking 에 다른 필드를 붙이지 않는다.

  "model": "claude-sonnet-5" → "claude-sonnet-5-5",
- "thinking": {"type": "disabled"},
- "output_config": {"effort": "xhigh"},
+ "thinking": {"type": "between_tools"},
+ "output_config": {"effort": "high"},
  • 400effort 가 xhigh 나 max 인 between_tools 요청
  • 400display, budget_tokens, block_binding 을 같이 보낸 요청
  • 400대화 중간에 메시지 단위로 effort 를 바꾼 요청 (11)
  • 200tool 이 없는 요청은 text 만 온다. tool 이 있으면 사이 메모가 thinking 블록으로 온다 (12)

xhigh 나 max 를 계속 써야 한다면 thinking 필드를 빼거나 adaptive 로 보내고, 그러면 up-front thinking 이 다시 켜진다. thinking 과 effort 를 서로 다른 설정에서 읽는 코드는 두 값을 합친 뒤에 검사해야 한다. 따로 보면 둘 다 맞는 값이라도 합치면 첫 줄의 400 이 난다.

첨언: 원문 문장, 오류 메시지, fallback

migration guide 「Turn off up-front thinking」: “between_tools works on every platform that offers Claude Sonnet 5.5, with no beta header. It's accepted at low, medium, and high effort. At xhigh or max, it returns a 400 error.” “between_tools takes no other field: display, budget_tokens, or block_binding sent with it returns a 400 error.”

오류 메시지: “"thinking.type.disabled" is not supported for this model. Use "thinking.type.between_tools" for the lowest thinking setting, or "thinking.type.adaptive" and "output_config.effort" to control thinking behavior.”

위 diff 는 guide 의 Before/After 예제에서 모델, thinking, effort 줄만 옮겼다. 13장의 server-side fallback 으로 Sonnet 5 에 넘어간 between_tools 요청은 거기서 disabled 로 돈다.

tool-choice

강제 tool 호출: any, tool → auto 와 strict

tool_choice 의 any 와 tool 은 token counting endpoint 까지 포함해 400 이다. auto 로 바꾸고 tool 에 strict: true 를 붙인 뒤, 언제 그 tool 을 부를지 프롬프트에 쓴다.

  "tools": [{
    "name": "get_weather",
    "input_schema": { …, "additionalProperties": false },
+   "strict": true
  }],
- "tool_choice": {"type": "tool", "name": "get_weather"},
+ "tool_choice": {"type": "auto"},
  "messages": [{"role": "user",
    "content": "What's the weather in Paris? Use the get_weather tool."}]
  • 400{"type": "any"}, {"type": "tool", "name": …}
  • 200auto(기본값)와 none
  • Bedrockstrict tool use 가 없다. auto 만 보내고, 프롬프트에 호출 조건을 쓰고, tool 입력을 코드에서 검증한다
  • 대안tool 대신 스키마를 structured outputs 로 옮겨도 된다 (What's new)
  • 한도strict tool 은 요청당 20개까지. MCP, computer use, browser use toolset 항목은 strict 를 받지 않는다

auto 에서는 모델이 tool 을 부르지 않고 text 로 답할 수 있다. 응답에 tool_use 블록이 있다고 가정하고 그 입력을 꺼내던 코드는, 블록이 없을 때의 분기를 따로 가져야 한다.

첨언: 원문 문장

migration guide 「Forced tool use is not supported」: “Send tool_choice: {"type": "auto"}, and mark the tool strict: true so its input matches the schema. The model can then answer without calling the tool, so say in the prompt when to use it.” strict 는 JSON Schema 의 일부만 지원하고 “needs additionalProperties: false on every object.”

What's new: “For schema-valid tool input, keep tool_choice: {"type": "auto"} and set strict: true with strict tool use, or move the schema to structured outputs.” 오류 메시지는 “tool_choice: type "tool" and "any" are not supported for this model.”

computer-use

computer use: computer_20251124 → toolset

Claude API 와 Google Cloud 에서 computer_20251124 는 400 이다. computer_toolset_20260801 로 바꾸고, fine-grained-tool-streaming-2025-05-14 헤더를 떼고, agent loop 를 toolset 응답에 맞춘다. Amazon Bedrock 은 computer_20251124 를 그대로 받는다.

- "tools": [{"type": "computer_20251124", …}]
+ "tools": [{"type": "computer_toolset_20260801"}]
- anthropic-beta: fine-grained-tool-streaming-2025-05-14   # 보내고 있었다면
+ "eager_input_streaming": true                          # 필요한 tool 마다
  • 400Claude API, Google Cloud 의 computer_20251124
  • 400toolset 항목과 함께 보낸 fine-grained-tool-streaming-2025-05-14 헤더
  • 400모든 플랫폼의 computer_20250124
  • 그대로이미 toolset 을 쓰는 코드, browser use tool
  • 그 밖Microsoft Foundry, Claude Platform on AWS 는 migration guide 가 computer use tool 문서의 Compatibility 절로 넘기고, 이 문서는 그 절을 열지 않았다

agent loop 에서 바뀌는 것은 toolset 의 member tool_use 블록, batch action, 결과의 toolset_name 셋이다. 각각의 모양은 computer use tool 문서의 「Migrate from computer_20251124」 에 있고, 이 문서는 그 절을 열지 않았다.

첨언: 원문 문장

What's new: “Drop the beta header, replace the tools entry with {"type": "computer_toolset_20260801"}, and update your agent loop for member tool_use blocks, batch actions, and toolset_name on results.” Claude API 의 오류 메시지는 “'claude-sonnet-5-5' does not support tool types: computer_20251124.” 로 시작한다.

advisor

advisor tool: 받는 advisor 가 줄고 조언은 암호화된다

Sonnet 5.5 executor 에 Sonnet 5, Opus 4.8, Opus 4.7 advisor 를 붙이면 400 이다. 받아 주는 advisor 는 모두 조언을 advisor_redacted_result 로 암호화해 돌려주므로, 조언 text 를 읽던 코드는 읽을 것이 없어진다.

advisorSonnet 5 executorSonnet 5.5 executor
Opus 5, Opus 5.5, Sonnet 5.5, Fable 5, Fable 5.1, Mythos 5, Mythos 5.1이 corpus 에 없음200, 조언은 암호화
Sonnet 5, Opus 4.8, Opus 4.7200400
Opus 4.6, Sonnet 4.6이 corpus 에 없음400 (migration guide 만 적음)

advisor 를 지정하는 필드의 이름과 모양은 advisor tool 문서에 있고, 이 corpus 에는 없어서 diff 를 싣지 않았다.

첨언: 원문 문장과 두 문서의 목록 차이

What's new: “Claude Opus 4.8, Claude Opus 4.7, and Claude Sonnet 5 advisors work with a Claude Sonnet 5 executor, but with a Claude Sonnet 5.5 executor they return a 400 invalid_request_error.” “Every advisor that Claude Sonnet 5.5 accepts returns its advice encrypted, as an advisor_redacted_result block, so your client can't read the advice text.”

migration guide 의 400 목록에는 Opus 4.6 과 Sonnet 4.6 이 더 있다: “Claude Opus 4.8, Claude Opus 4.7, Claude Opus 4.6, Claude Sonnet 5, and Claude Sonnet 4.6 advisors return a 400 error.”

effort

effort: 옮기지 말고 다시 잰다

effort 단계는 이름이 같아도 다시 보정되어서, 같은 단계가 Sonnet 5 와 같은 양의 thinking 을 내지 않는다. Sonnet 5 의 값을 가져오지 말고 작업 종류별 시작값에서 평가를 다시 돌리며, 단계를 올릴 때는 max_tokens 에 thinking 이 들어갈 자리를 둔다.

작업시작 effort (migration guide)
일반high. Claude API 기본값이다
agentic coding, 여러 단계 tool use명세가 분명하면 medium, 어렵거나 길면 high
chat, 지연에 민감한 작업medium 이나 low
xhigh, max평가에서 품질 이득이 보일 때만
  • tokensmax_tokens 는 thinking 과 답을 합친 상한이고 thinking 은 output 으로 청구된다. agentic coding 은 128,000 으로 두고 stream 한다
  • tokenstool-use loop 에서는 요청마다 max_tokens 가 따로라서 턴 전체의 지출을 막지 못한다

단계별 점수와 비용이 어디서 갈리는지는 17장의 차트에 있다.

첨언: 원문 문장

migration guide 「Recommended changes」: “The levels are recalibrated, so a level doesn't produce the same amount of thinking as on Claude Sonnet 5.” Effort 문서의 Sonnet 5.5 권장 절: “Use xhigh or max only where your evals show a quality gain. Set max_tokens with room for thinking and the reply.” “For agentic coding, set max_tokens to 128,000, the model's maximum”

Steering thinking 「Cost control」: “In a tool-use loop, each request in the turn has its own max_tokens, so it doesn't bound the whole turn's spend.” thinking 에 쓰인 output token 은 응답의 usage.output_tokens_details.thinking_tokens 로 센다.

cache

캐시: effort 바꾸기와 최소 길이

Sonnet 5.5 에서 prompt cache 의 조건 두 가지가 달라진다. 대화 도중 effort 를 메시지 단위로 바꾸면 캐시가 남고(top-level output_config.effort 를 요청마다 바꾸면 처음부터 다시 쌓인다), 최소 캐시 길이는 1,024 에서 512 토큰으로 준다.

# anthropic-beta: mid-conversation-output-config-2026-07-01
"messages": [
  …지금까지의 기록…,
+ {"role": "system", "content": [], "output_config": {"effort": "low"}},
  {"role": "user", "content": "…"}
]
  • 200새 단계는 다음 user 턴부터 적용되고, 뒤에서 다시 바꿀 때까지 유지된다
  • 400between_tools 에서 지금과 다른 단계를 메시지로 보낸 요청 (06)
  • 캐시effort 를 모델 기본값 high 로 적어 보내는 것은 생략과 같아서 캐시를 깨지 않는다
  • 512Sonnet 5 에서 1,024 토큰이 안 되어 캐시되지 않던 prompt 도 512 토큰을 넘으면 캐시 대상이다
첨언: 원문 문장

Effort 문서 「Per-message effort (beta)」: “Add a role: "system" message with empty content and the new level in output_config.effort. The new level takes effect from the next user turn and holds until a later message changes it.”

Steering thinking 「Prompt caching」: “The resolved effort value is rendered into the prompt, so changing it between requests invalidates cache breakpoints”. Steering thinking: “Setting effort explicitly to the model's default is equivalent to omitting it and does not break the cache.” What's new 는 per-message effort 가 Sonnet 5 에는 없다고 적는다.

between-text

tool call 사이 메모: text → 빈 thinking 블록

Sonnet 5.5 는 tool call 사이에 쓰는 한두 문장보다 긴 메모를 progress-update thinking 블록으로 보내고, 기본 display 인 omitted 에서는 그 블록이 비어 있다. 요청은 200 이므로 이 메모를 사용자에게 흘려 보이던 화면만 조용해진다.

// Sonnet 5 응답
{"type": "text", "text": "…메모…"},  {"type": "tool_use", …}
// Sonnet 5.5, adaptive, display 기본값
{"type": "thinking", "thinking": "", "signature": "…"},  {"type": "tool_use", …}
// 고친 요청: 메모만 받는다
+ anthropic-beta: thinking-display-updates-2026-08-18
+ "thinking": {"type": "adaptive", "display": "updates"}
설정tool call 사이에 오는 것
adaptive, display 기본값 omitted빈 thinking 블록
adaptive, display: "updates" (beta 헤더)메모만 든 thinking 블록
adaptive, display: "summarized"메모와 추론 요약이 섞인 thinking 블록
between_tools (06)display 없이도 메모 text 가 든 thinking 블록
어느 설정이든, 한두 문장 이하의 짧은 말text 블록 그대로

화면 코드는 비어 있지 않은 thinking 블록을 뒤따르는 tool_use 블록보다 먼저 그린다. 기록에는 그 블록을 고치지 않고 되돌려 보낸다. What's new 의 between_tools 절은 되돌아온 progress-update 블록에서 모델이 요약이 아니라 자기가 쓴 메모 전체를 받는다고 적는다. summarized 와 omitted 는 보이는 것만 다르고 청구되는 output token 은 같다. updates 는 이 과금표에 없다.

첨언: 원문 문장과 과금

migration guide 「Text between tool calls is returned in thinking blocks」: “On Claude Sonnet 5 and earlier models, all text between tool calls comes back as text blocks. No request fails, but an interface that shows those notes goes quiet.” “Render each non-empty thinking block before the tool_use block that follows it.”

What's new 「Turn off up-front thinking with between_tools」: “A progress-update block you send back gives the model the full note it wrote, not the summary.” Steering thinking 「Pricing」: “What you're billed for is the same regardless of the display setting; only what you see changes”

한두 문장이라는 경계를 어떻게 세는지는 이 corpus 에 없다. thinking 문서의 progress updates 절에 있을 것으로 보이며, 이 문서는 그 절을 열지 않았다.

refusal

거절: stop_reason refusal 과 fallback

Sonnet 5.5 는 Sonnet 5 보다 많은 부류에서 거절하고, 거절은 HTTP 200 에 stop_reason: "refusal" 로 온다. Claude API 의 server-side fallback 은 cyber 와 frontier_llm 만 Sonnet 5 로 다시 돌리므로 나머지 셋은 코드가 처리한다.

stop_details 부류뜻server-side fallback
cybermalware, exploit 개발 같은 사이버 피해Sonnet 5 로 재시도
frontier_llm경쟁 AI 모델 개발 지원Sonnet 5 로 재시도
bio위험한 실험 방법 같은 생물학적 피해재시도 없음
reasoning_extraction내부 추론을 답에 그대로 옮기라는 요청재시도 없음
general_harms그 밖의 사용 정책 영역. 정상 작업도 걸릴 수 있다재시도 없음

fallback 은 fallbacks: "default" 로 켜는 beta 이고 Claude API 에서만 된다. SDK middleware 나 직접 만든 재시도도 쓸 수 있다. 출력 전에 난 거절이 청구되는지는 부류마다 다르지만 rate limit 에는 어느 부류든 잡힌다.

첨언: 원문 문장

What's new 「Refusals, fallback, and billing」: “A declined request returns HTTP 200 with stop_reason: "refusal" and a stop_details object naming the policy area.” “Whether a refusal that arrives before any output is billed depends on its refusal category, and it counts against your rate limits either way.”

migration guide: “"general_harms": The request falls under another usage-policy area. Benign work can also trigger this category.” 발표 글은 사이버 쪽을 이렇게 적는다: “higher-risk cybersecurity tasks will visibly fall back to Sonnet 5.” 부류별 과금표는 Refusals and fallback 문서에 있고 이 문서는 열지 않았다.

history

대화 기록: append-only 로 둔다

2026-08-31 00:00 UTC 이후 만든 계정에서, Sonnet 5.5 thinking 블록 앞의 system, tools, 이전 메시지를 고친 뒤 그 블록을 다시 보내면 400 이다. 지시나 tool 을 바꿀 때는 기록을 고치지 말고 mid-conversation system message 를 뒤에 붙인다.

# 400 대신 블록을 버리게 하는 요청 (adaptive)
+ anthropic-beta: thinking-binding-controls-2026-08-01
"thinking": {"type": "adaptive",
+   "block_binding": {"prefix_mismatch_behavior": "drop_block"}}
  • 400새 계정에서 블록 앞 기록을 고친 요청. Claude API, Amazon Bedrock, Google Cloud. Microsoft Foundry 와 Claude Platform on AWS 에서 검사하는지는 이 corpus 에 없다
  • 200beta 헤더와 block_binding 으로 "drop_block" 을 고르면 해당 블록만 버린다. adaptive 에서만 된다
  • 옛 계정기본은 검사하지 않고, prefix_mismatch_behavior 를 어느 값으로든 보내면 검사를 켠다
  • betweenblock_binding 이 400 이다. append-only 로 두거나, 고친 턴부터 thinking 블록을 지운다

이 corpus 에 있는 system message 예시는 11장의 effort 변경뿐이다. 지시나 tool 을 담는 메시지의 모양은 mid-conversation system messages 문서에 있고, 이 문서는 그 문서를 열지 않았다.

요청마다 system prompt 에 시각이나 사용자 상태를 새로 넣는 코드, 긴 대화의 앞부분을 요약문으로 바꿔 끼우는 코드가 여기에 걸린다. 둘 다 thinking 블록 앞의 기록을 바꾸기 때문이다.

첨언: 원문 문장

What's new: “The API also checks whether anything before a Claude Sonnet 5.5 thinking block has changed since the block was produced: the system prompt, the tools, or an earlier message.” “On older accounts, setting that field to either value opts the request in. block_binding works only with thinking: {"type": "adaptive"}.”

system prompt 에 시각을 넣는 코드가 걸린다는 것은 이 규칙에서 이 문서가 끌어낸 예이고, 원문이 든 예는 아니다.

긴 대화를 줄여야 한다면 앞부분을 직접 요약하지 말고 compact-2026-09-04 beta 의 compaction 블록을 쓴다. What's new 는 이 블록을 쓰면 남긴 턴의 thinking 블록이 조건에 따라 유효하다고 적는다.

model-switch

모델과 계정 이동: 400 없이 블록이 빠진다

Sonnet 5 에서 넘어온 대화의 thinking 블록은 Sonnet 5.5 가 읽는다. 반대로 Sonnet 5.5 의 블록은 다른 모델도, 연결되지 않은 다른 계정도 읽지 못하고, API 는 200 을 내면서 그 블록을 버린다.

기록에 든 블록보내는 곳결과

Opus 5, Opus 5.5, Fable, MythosSonnet 5.5200, 버려지고 청구되지 않는다

Sonnet 5.5연결되지 않은 다른 계정200, 모델이 보기 전에 버려진다

여러 모델을 오가며 한 대화를 잇는 라우터나 계정을 나눠 쓰는 배포라면, thinking-binding-controls-2026-08-01 헤더를 붙여 응답의 input_transformations 로 버려진 블록을 센다. 계정 불일치는 Claude API 와 Google Cloud 에서 reason: "organization_binding_mismatch" 로 적힌다.

첨언: 원문 문장

What's new: “So a conversation that moves from Claude Sonnet 5 onto Claude Sonnet 5.5 keeps its reasoning, and one that moves from Claude Sonnet 5.5 to any other model runs the turns after the switch without it.” “When another account sends one of these blocks, the API drops the block before the model sees it, and the request succeeds.”

발표 글은 이 계정 결속을 distillation 방어로 설명한다: “Sonnet 5.5 also expands preserved thinking, so Claude’s thinking cannot be decoupled from the account that created it.”

critique

해석의 한계: 400 목록은 문서끼리 대조되고, 비용은 Anthropic 의 측정이다

400 과 200 의 목록은 migration guide 와 What's new 가 같은 항목을 함께 적어 서로 대조되지만, advisor 목록은 두 문서가 다르다. 벤치마크 비용은 Anthropic 이 자기 설정으로 잰 값이라 사용자의 작업에서 같은 비율이 나온다는 근거가 corpus 에 없다.

  • 문서advisor 400 목록이 migration guide 는 다섯 모델, What's new 는 세 모델이다 (09)
  • 발표발표 글 첫 문단의 "up to 30% less" 는 대부분의 작업에 대한 말이고, max 에서는 차트가 반대를 보인다 (17)
  • 측정AA-Briefcase 와 GDPval-AA 는 structured outputs 버그가 있던 출시 전 배포에서 쟀다. Anthropic 은 영향이 작고 점수를 낮추는 쪽이라고 적는다
  • 비교Terminal-Bench 와 CursorBench 의 GPT 선은 GPT-6 Sol 이 아니라 GPT-5.6 Sol 이다
  • 고객발표 글의 고객 인용 13개는 측정 방법을 밝히지 않아 이 문서가 근거로 쓰지 않았다

발표 글 안에서 남는 결과는 medium 이다. Sonnet 5.5 medium 은 네 벤치마크 모두에서 Sonnet 5 medium 보다 점수가 높고 작업당 비용이 낮다. 다만 AA-Briefcase 의 비용 차이는 $1.64 대 $1.73 으로 작고, 이 결과도 Anthropic 의 측정이라 자기 작업에서는 다시 재야 한다.

conclusion

결론: 옮기는 순서

한 번 호출하면 드러나는 400 부터 고치고, 호출로는 드러나지 않는 기록 편집과 사이 메모를 코드에서 찾은 뒤, 마지막에 effort 를 다시 잰다. 순서를 바꾸면 비용 측정이 고치기 전의 설정 위에서 이루어진다.

1모델 ID, thinking, tool_choice, computer use, advisor (05~09)쓰는 설정마다 한 번씩 호출해 400 이 없는지 본다
