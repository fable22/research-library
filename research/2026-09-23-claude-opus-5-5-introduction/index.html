Claude Opus 5.5: Opus 5 에서 옮길 때 코드와 비용에서 바뀌는 것

Anthropic 이 2026-09-22 에 낸 "Introducing Claude Opus 5.5" 와 그 글이 링크한 플랫폼 문서를 한 가지 질문으로 다시 읽는다. Opus 5 에서 Opus 5.5 로 옮기는 개발자는 코드와 비용에서 무엇을 바꿔야 하는가. 원문이 직접 잰 숫자와 고객이 말한 숫자를 나누고, 원문이 한 문장으로 넘긴 API 변경은 링크된 문서에서 확인한다. 읽는 사람은 Claude 를 코딩 에이전트나 API 로 쓰는 개발자다.

원문 수치들은 모두 Anthropic 이 자기 벤치마크와 자기 하네스로 잰 값이거나 고객이 조건을 밝히지 않고 보고한 값이다. 이 문서는 그 수치를 재현하지 않았고, 원문과 링크된 문서가 서로 맞는지 대조했다.

problem

Opus 5 는 같은 일에 토큰을 더 썼고, agentic 작업과 코딩 비용의 대부분은 캐시 읽기에서 나왔다

소개 글은 새 모델의 장점을 늘어놓는 형식인데, 문단마다 Opus 5 의 어떤 점을 겨냥했는지가 드러난다. 그 문장을 모으면 Anthropic 이 지난 세대의 비용 문제로 본 것이 셋 나온다. 셋 모두 원문이 스스로 고른 문제다.

캐시 읽기

Opus 5 의 캐시 읽기는 1M 토큰당 $0.50 이었다. 원문은 캐시 읽기가 agentic 작업과 코딩 비용의 대부분을 차지한다고 쓰고, Opus 5.5 에서 가장 크게 내린 항목도 캐시 읽기다 (08장).

토큰

Opus 5 는 같은 일에 토큰을 더 썼다. Coding 절의 일화에서 한 early tester 는 200,000줄 코드베이스를 Opus 5.5 로 3시간 안에 감사하고 고쳤는데, Opus 5 는 같은 일에 20시간 넘게 걸리며 토큰을 2.5배 썼다. 내부 시험에서는 HAProxy 를 C 에서 Rust 로 옮기는 과제를 Opus 5.5 와 Fable 5.1 에 주었고, 둘 다 HAProxy 자체 회귀 테스트를 거의 다 통과했다. Opus 5.5 가 9.5시간 대 12시간으로 빨랐으며 비용은 51% 적었다.

장황함

Opus 5 의 글은 길고 읽기 어려웠다. 원문은 Communication 절에서 글쓰기를 "Opus 5 에 대해 가장 많이 들은 피드백 영역 중 하나" 라고 쓴다. 장황한 답은 출력 토큰으로 청구서에 그대로 잡히는데, Box 는 Opus 5.5 의 답이 40% 덜 장황하고 토큰은 Opus 5 의 1/3 이었다고 말한다.

하지만 Opus 5.5 에서 나빠진 항목도 있다. 사용자가 붙여넣은 텍스트 속 악의적 지시를 이전 모델보다 더 잘 따르는 경향은 시스템 카드에만 적혀 있고, 07장에서 다룬다. HAProxy 시험에서 "거의 다 통과" 한 실제 통과율은 원문이 밝히지 않았다.

원문에 없는 스펙

models overview 문서에 따르면 컨텍스트 1M 토큰과 최대 출력 128K, reliable knowledge cutoff 2026년 6월이 Fable 5.1 과 같다. retirement 는 2027-09-22 이전에는 없다. 이 약속은 Claude API 와 Claude Platform on AWS, Foundry 기준이고 Bedrock 과 Google Cloud 는 자체 일정을 따른다. Opus 5 는 legacy 로 계속 제공된다. 소개 글은 이 가운데 어느 것도 적지 않는다.

규정

이전 Opus 처럼 zero data retention 을 제공하지만, Cyber Verification Program(CVP)에는 zero data retention(ZDR) 조직이 참여할 수 없다 (도움말). EU AI Act 워터마크는 Fable 5.1 과 같다. 안전장치가 거부한 요청은 HTTP 200 에 stop_reason "refusal" 로 오고 stop_details 의 범주에 생물학 분류기와 reasoning_extraction 이 추가됐다.

다섯째 행은 whats-new 문서가 "요청을 실패시키지 않으면서 응답 모양을 바꾸는" 변경으로 따로 분류한 것이다. 진행 상황을 스트리밍하는 UI 는 오류 없이 조용해지므로 네 개의 400 보다 늦게 발견된다.

api · preserved thinking

2026-08-31 이후 만든 API 계정에서는 thinking 블록 앞의 system 과 tools, messages 를 고친 요청이 400 을 받는다

원문 Distillation 소절은 두 문단이다. 가짜 계정 수천 개로 모델 능력을 산업 규모로 뽑아내는 공격이 있고, 9월 threat intelligence report 에 그 사례가 실려 있다. 그래서 Fable 5.1 에서 도입한 preserved thinking 을 Opus 5.5 에도 켠다고 쓰고 나머지는 문서 링크를 통해 넘긴다. 링크된 문서를 따라가면 대화 앞부분을 고쳐 쓰는 통합이 바로 여기서 깨진다.

모델 검사는 방향에 따라 결과가 다르다. Opus 5.5 는 Opus 5 를 포함한 이전 Opus 와 Sonnet, Haiku 의 블록을 읽지만, Fable 과 Mythos 의 블록은 읽지 못한다. 거꾸로 Claude API 에서 Opus 5.5 의 블록을 읽는 모델은 Fable 5.1 과 Mythos 5.1 뿐이다. 도움말 문서는 영향받는 통합으로 client-side compaction 과 주입하는 system reminder, 세션 중 tool 변경을 들고 대신 서버 compaction(beta)과 mid-conversation tool 변경(beta)을 쓰라고 안내한다. Claude Code 와 Cowork, claude.ai 사용자는 바꿀 것이 없다. 같은 문서는 적용 범위를 Claude Platform 조직과 Bedrock 계정, Vertex AI 프로젝트, Foundry 프로젝트까지로 적는다.

api · 거부와 fallback

분류기에 걸린 요청은 제품에서는 다른 모델이 대신 답하고, API 에서는 개발자가 켜지 않으면 거부 응답으로 온다

소개 글은 cyber 와 생물학, distillation 세 영역이 "투명하게 다른 모델로 fallback" 한다고만 쓴다. cyber 가 Opus 4.8 로 간다는 것은 Safeguards 소절에, 생물학과 frontier LLM 개발이 Opus 5 로 간다는 것은 벤치마크 표 설명문에 있고, distillation 과 재래식 무기의 차단은 시스템 카드 §1.5 에 있다. fallback 은 first-party 제품과 API 에서 opt-in 한 개발자에게 적용되며, 다른 플랫폼은 다를 수 있다.

distillation 에서 두 출처가 어긋난다

§1.5 는 distillation 분류기에 fallback 이 없다고 써서 소개 글과 어긋난다. 소개 글이 말하는 distillation 안전장치는 05장의 preserved thinking 이고 §1.5 의 것은 분류기라서 둘은 서로 다른 장치를 가리킬 수 있다.

2026-09-23 의 CVP 와 LSVP

Anthropic 은 cyber 접근을 위해 Cyber Verification Program 을 3단계로 넓혀 Mythos 모델까지 열 계획이다. 그런데 원문이 링크한 CVP 문서는 첫 줄에 Opus 5.5 에는 아직 적용되지 않는다고 적고, ZDR 조직은 참여할 수 없으며 Bedrock 에서는 제공되지 않는다고 쓴다. 생물학의 Life Sciences Verification Program(LSVP)은 2026-09-17 발표문에서 Standard Use 를 Mythos 5.1, Opus 5, Sonnet 5 에 적용하고 새 모델은 출시되는 대로 포함한다고 쓰는데, Opus 5.5 를 이름으로 들지는 않는다. 원문 Introduction 의 "오늘 신청해 Opus 5.5 를 쓸 수 있다" 는 출시 모델이 자동으로 포함된다고 읽으면 어긋나지 않는다.

API 에서 fallback 을 켜지 않으면 걸린 요청은 HTTP 200 에 stop_reason "refusal" 로 온다. 시스템 카드 §3.2 도 "API 에서는 개발자가 automatic fallback 에 opt in 해야 한다" 고 쓴다. 따라서 이 흐름도의 fallback 화살표는 제품과 opt-in 한 API 에서만 성립한다.

api · prompt injection

Gray Swan 코딩 시나리오에서는 시행의 46% 를 fallback 으로 넘어간 Opus 4.8 이 답했다

원문의 "The most secure coding agent" 절은 두 문단이다. 첫 문단은 모델 밖의 장치 셋을 드는데, 모든 행동을 실행 전에 거르는 분류기와 보안팀이 감사할 수 있는 오픈소스 sandbox, 병합 전에 취약점을 잡는 코드 리뷰다. 둘째 문단은 모델 자체의 방어를 말한다. 시스템 카드를 같이 읽으면 코딩 에이전트가 받는 방어의 상당 부분은 첫 문단의 분류기 경로에서 나온다.

소개 글이 말하는 것

코딩과 tool use, computer use, 웹 브라우징을 포함해 시험한 모든 설정에서 Opus 5 와 같거나 낫다. Gray Swan 벤치마크에서는 Fable 5.1 과 함께 시험 대상 중 가장 낮은 prompt injection 성공률을 냈다.

시스템 카드 §5.2.1 의 공격 성공률은 공격을 k 번 시도했을 때의 값이다. k=1 에서 0.1% 로 Opus 5 의 0.4% 보다 낮고, k=10 에서는 0.7% 대 3.6%, k=15 에서는 1.0% 대 4.8% 다. 같은 절에 따르면 Opus 5.5 시행(rollout)의 18% 는 cyber 분류기 fallback 으로 Opus 4.8 이 답했고, 코딩 시나리오에서는 그 비율이 46% 였다. fallback 이 답한 1,310회에서 성공한 공격은 0 이다.

시스템 카드가 덧붙이는 것

행동 감사 §6.4.1 은 "prompt injection 에서 진짜지만 작은 퇴보" 와 "검증되지 않은 권한 주장을 받아들이는 현상" 을 예외로 든다. Executive Summary 는 "사용자가 자기 프롬프트에 붙여넣은 텍스트 안의 악의적 지시를 이전 모델보다 더 잘 따른다" 고 쓴다.

Executive Summary 의 Agentic safety 문단에 따르면 안전장치 없이 Claude Code 와 computer use 설정에서 시험했을 때 Opus 5.5 는 dual-use 과제와 양성 보안 과제를 가장 높은 비율로 도왔지만, 악의적 요청은 시험한 모델 중 가장 낮은 비율로 거부했다. §5.2.2.1 의 adaptive 공격에서는 prompt injection probe 를 끈 조건에서 유효 응답을 받은 Opus 5.5 요청의 64% 를 Opus 4.8 이 답했다. 그 fallback 응답의 공격 성공률은 85.73% 였지만, Opus 5.5 가 직접 답한 2,872건에서는 0 이었다. probe 를 켠 조건에서는 전체 성공률이 11.13% 로 Fable 5.1 의 8.70% 다음이고 Opus 5 의 19.53% 보다 낮은데, 성공한 공격은 모두 fallback 응답에서 나왔다. Gray Swan 비교도 조건이 같지 않다. Claude 모델은 prompt injection 전용 안전장치 없이 표준 차단 분류기와 fallback 만 켜고 평가했고, 타사 모델들은 공개 엔드포인트라서 추가 안전장치가 있을 수도 없을 수도 있다.

소개 글의 "모든 설정" 은 전용 prompt injection 평가에서 나온 말이다. "시험 대상 중 최저" 는 시스템 카드가 red-teaming 경쟁의 표적이었던 모델을 빼고 만든 집합에서 한 말이다. tool 결과나 웹 페이지로 들어오는 간접 prompt injection 을 받는 코딩 agent 라면, 공격이 성공한 자리가 cyber 분류기가 Opus 4.8 로 넘긴 응답이었다는 점을 알아 둬야 한다. adaptive 공격에서 성공한 공격은 모두 fallback 응답에서 나왔고, Gray Swan 에서는 fallback 응답 1,310회에서도 성공이 0 이었다. 오픈소스 sandbox 가 어느 저장소인지는 원문에 링크가 없어서 확인하지 못했다.

cost · effort 와 지식 노동

GDPval 에서 Opus 5.5 를 low effort 로 돌리면 다섯 모델의 low 점 가운데 가장 낮은 점수가 나온다

원문 Knowledge work 절은 내부 시험 둘과 벤치마크 셋을 싣는다. 첫 내부 시험은 분기 실적 보고서 작성이다. 실적 발표를 찾기 어렵게 만든 웹 사본만 주고 자동 채점기가 모든 수치와 인용을 출처와 대조했는데, Opus 5.5 는 effort 설정을 바꿔 가며 18회 중 16회 품질 기준을 넘었고, Fable 5.1 과 Opus 5 는 한 번도 넘지 못했다. 둘째 내부 시험은 가상 HR 회사의 합병을 분석해 Excel 모델과 발표 자료를 만드는 과제다. Opus 5.5 는 63분이 걸려 93분 걸린 Opus 5 보다 빨랐고 비용은 50% 적었다.

AutomationBench (Zapier)

Opus 5.5 는 모든 effort 에서 Opus 5 와 GPT-5.6 Sol 을 앞서고 최고점은 max 의 40.0% ($1.37) 다. GPT-6 Astra 는 41.4% ($1.77) 로 더 높은데, 원문 캡션은 Astra 를 비교 대상에서 뺀다. 각주 2 대로 fallback 없이 돌렸기 때문에 안전장치 개입은 실패로 잡혔다.

WANDR (Perplexity)

대규모 데이터 수집 과제다. max 에서 Opus 5.5 는 72.3% ($37.92), Fable 5.1 은 68.7% ($49.02), Opus 5 는 67.2% ($61.62) 다. 각주 4 는 오프라인 web search 와 web fetch 에 programmatic tool calling 과 코드 실행을 붙이고 980k 토큰 예산을 주어 돌렸기 때문에 Perplexity 공개 점수와 직접 비교할 수 없다고 쓴다. Opus 5.5 를 low 로 돌리면 31.2% 로 급락한다.

보고서 시험의 "품질 기준" 이 무엇인지와 18회가 어떤 effort 조합이었는지는 원문에 없다. GDPval 에는 각주가 없지만, 비용은 "추정" 이고 원문이 비교 조건이 같다고 쓴 것도 아니다. 합병 분석에서는 두 모델이 같은 결론에 이르렀고, 원문은 차이로 철저함과 가독성 그리고 Opus 5 의 사소한 오류를 든다. lowest effort 에 대한 고객 증언은 16장에 모았다. Deloitte 와 Rogo 는 그 설정으로 Opus 5 high 를 이겼다고 말한다.

result · 벤치마크 표

원문 표는 Claude 를 max effort 로 쟀고, 각 모델의 최고 effort 끼리 놓으면 FrontierCode 에서 Opus 5 와의 격차가 6.4pt 에서 1.2pt 로 준다

원문 Performance and cost-effectiveness 절의 표를 그대로 옮겼다. Opus 5.5 는 9개 중 7개에서 1위이고 AutomationBench 와 Terminal-Bench-Science 에서는 GPT-6 Astra 가 앞선다. 표 아래 설명문에 따르면 Claude 값은 max effort 로 쟀고 Terminal-Bench 4.0 만 xhigh 이며 안전장치를 켠 채로 평가했다. 시스템 카드 Table 8.1.A 는 달리 적지 않으면 5회 평균이라는 조건을 더하고, 타사 값에 대해서는 "개발사가 발표한 system card 나 리더보드" 라고 적는다. 원문은 이 수준의 능력에서는 벤치마크 격차가 실제 차이를 가늠하는 데 덜 믿을 만해졌다고 쓰고, 자체 사용에서는 Fable 5.1 과의 격차가 점수보다 좁다고 덧붙인다.

adopt · 체크리스트

Opus 5 에서 옮기는 개발자가 할 일은 상황별로 열한 가지이고, 첫째는 effort 를 명시하는 것이다

Opus 5.5 는 이쪽에 속한다. 미래 모델을 위해서는 RL 환경 필터링을 강화하고 (결함 있는 환경이 misalignment 의 주요 원인이다) alignment 보상을 고친다. 안전 훈련용 시나리오를 자동으로 만들고 보안과 모니터링, interpretability 기반 평가를 강화해서 chain-of-thought 감사에 덜 기대려 한다. AI 연구 자체를 자동화할 수 있는 모델에는 더 높은 기준이 필요하다며 "we do not assume the measures described above will meet that safety standard on their own" 이라고 쓴다. "pacing" 은 Amodei 의 글에서 훈련을 멈추는 것이 아니라 능력 향상의 속도를 늦추는 것이고, "회사가 모델을 align 하고 안전장치를 붙일 시간을 충분히 갖고 제3자 평가자가 이를 확인하는 것" 으로 정의된다. 그 글의 세 단계 가운데 Anthropic 이 단독으로 약속한 것은 embedded evaluators 뿐이다. 소개 글은 embedded evaluators 를 Accenture 발표 링크를 통해 정책 문단에 잇고, 출시 전 평가(METR 과 Frontier Design)는 그것과 별개의 관행으로 적는다.

85% 는 Figure 6.4.8.A 의 막대값으로 다시 계산된다. Opus 5 는 저위험 7.7% 와 중위험 이상 2.6% 를 더한 10.3% 이고 Mythos 5.1 은 8.7% 와 1.0% 를 더한 9.7% 다. Opus 5.5 는 저위험 1.5% 뿐이다. 1.5/10.3 은 85.4% 감소이고 1.5/9.7 은 84.5% 감소다 (이 문서의 계산). 28개 × 7회 = 196회에서 1.5% 는 약 3회다.

critique

원문은 벤치마크 격차를 스스로 할인하고, 이 문서는 effort 기준을 맞춘 비교와 원문에 없는 스펙을 덧붙인다

원문이 인정한 한계와 이 문서가 주장하는 한계를 나눈다. 원문의 각주와 표 설명문이 이미 단서를 많이 달아 두었기 때문에 이 문서가 새로 덧붙인 것은 기준이 섞인 비교를 바로잡은 계산과 원문에 없는 스펙이다.

원문이 인정한 것
  • 1이 수준의 능력에서는 벤치마크 격차가 실제 차이를 가늠하는 데 덜 믿을 만해졌다고 쓴다 (11장).
  • 2표는 max effort 로 쟀고 Terminal-Bench 만 xhigh 다. 안전장치가 개입하면 Opus 4.8 이나 Opus 5 가 푼 과제가 점수에 들어간다.
  • 3Terminal-Bench 표준오차는 ±2.6pt 이고 TB-Science 는 ±3.5~5pt 다. AutomationBench 는 fallback 없이 돌려 개입을 실패로 처리했고, WANDR 는 공개 설정과 비교할 수 없다.
  • 4alignment 평가가 모든 실패를 잡지 못하고 모델이 평가 중임을 자주 의심한다.
이 문서가 주장하는 것
  • 1FrontierCode 에서 Opus 5 와의 격차 6.4pt 는 max 기준이고, 각 모델의 최고 effort 기준으로는 1.2pt 다. 시스템 카드에는 두 값이 다 있는데, 소개 글은 앞쪽만 표에 넣었다. 같은 데이터에서 "같은 점수대를 1/5.8 비용에" 라는 읽기도 나오고, 옮길지 판단할 때는 이쪽이 더 직접적이다.
  • 2"40% 절감" 은 기본 설정 기준이고 그 기본 effort 가 medium 으로 내려갔다. effort 를 고정하면 high 는 32~86% 절감이지만, max 는 세 벤치마크에서 역전된다 (08장). 원문은 이 역전을 적지 않고, whats-new 는 같은 effort 에서 thinking 이 더 많은 경향이 있고 xhigh 와 max 에서 가장 그렇다고 쓴다.
  • 3prompt injection 에서 "모든 설정에서 Opus 5 이상" 은 전용 평가에서 나온 말이다. 행동 감사의 소폭 퇴보와 붙여넣은 텍스트 경로, 안전장치 없는 Claude Code 와 computer use 에서 악의적 요청 거부율이 가장 낮았다는 문장, 코딩 시나리오 46% 의 Opus 4.8 fallback 은 모두 시스템 카드에만 있다.
  • 4models overview 는 대부분의 워크로드를 Opus 5.5 로 시작하되, long-horizon agentic 작업이나 Opus 5.5 를 높은 effort 로 돌려도 부족할 때는 Fable 5.1 을 쓰라고 권한다. 원문의 "대부분의 일에서 Fable 5.1 수준" 옆에 있어야 할 단서다.
  • 5고객 인용 21개 중 "수치 없음" 으로 적은 것이 6개다. 나머지 15개 중 effort 를 적은 것은 다섯 (Deloitte, Rogo, Walleye 는 lowest, Factory 는 medium, Viktor 는 같은 effort) 이고 시행 횟수를 적은 인용은 하나도 없다.
  • 6컨텍스트 윈도우와 최대 출력, knowledge cutoff, 플랫폼별 모델 ID 는 소개 글에 없어서 04장 카드와 12장 표, 20장 목록에서 보충했다.

하지만 한계를 지나서도 남는 것이 있다. 코딩 차트 세 개의 점 70개는 원문이 공개한 데이터라서 누구나 같은 비교를 다시 할 수 있고, 그 데이터에서 "medium 이 max 보다 비용 대비 낫다" 는 결론은 Anthropic 의 캡션 없이도 나온다. 시스템 카드 §8.4 가 FrontierCode 의 두 기준을 다 적어 둔 덕분에 소개 글 밖에서도 그 표를 검증할 수 있다.

conclusion

Opus 5 에서 옮기는 개발자는 effort 를 먼저 적고, 400 을 받는 설정을 지우고, 대화를 append-only 로 만들고, 보안 작업의 거부 응답을 처리한다

원문과 링크 문서를 옮기는 순서대로 다시 놓으면 할 일이 넷이다. 넷 중 셋은 소개 글이 아니라 링크된 문서에서 나온다. 소개 글을 끝까지 읽어도 남는 것은 가격표 한 장과 기본값 하나다. 캐시 읽기 $0.20 이 청구서를 바꾸고 medium 기본값이 요청의 동작을 바꾼다.

  • 1모델 ID 를 바꾸기 전에 effort 를 적는다. 적지 않으면 high 에서 medium 으로 내려간다. effort 별 비용과 점수는 09장과 10장에 있고, GDPval 과 WANDR 의 low 점처럼 낮은 effort 가 늘 안전한 것도 아니다.
  • 2400 을 받는 설정 셋을 지운다. thinking 을 끄는 요청, tool_choice 의 any 와 tool, computer_20251124 다. 넷째인 prefix 검사는 3번에서 다룬다. tool call 사이 텍스트를 UI 에 흘리던 코드는 오류 없이 조용해진다.
  • 3대화를 append-only 로 만든다. 2026-08-31 이후 계정은 preserved thinking 의 prefix 검사를 기본으로 받고, 도움말 문서는 이후 모델 출시에 맞춰 모든 사용자로 단계적으로 넓힌다고 쓴다.
  • 4보안 작업과 ML 가속기 kernel 개발에서는 거부를 처리한다. 제품에서는 Opus 4.8 이나 Opus 5 가 대신 답하지만, API 에서는 fallback 이 opt-in 이라서 기본은 거부 응답이다 (06장과 12장). CVP 는 아직 Opus 5.5 에 적용되지 않는다.
