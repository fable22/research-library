TencentDB Agent Memory: 기억을 자산으로 등록하고 agent 에게 장착시키는 층

Chat Memory, Skill, Wiki, CodeGraph 네 종류를 하나의 자산 테이블에 등록하고, team / user / agent 세 축으로 격리한 뒤, agent 마다 다른 조합을 물려 주는 구조다. 공유와 대규모를 무엇이 실제로 떠받치고 있는지, 그리고 어디가 아직 비어 있는지를 코드에서 확인했다.

「자산 네 종류」 → 「컴포넌트 네 개」 → 「identity」 → 「요청 경로 추적」. 자산 등록이 어디서 일어나고 격리 필드가 어디서 채워지는지가 이 네 장에 다 들어 있다.

대상 커밋은 fe3230f 하나다. 기본 브랜치가 main 이 아니라 feat/server_team 이라서, GitHub 웹에서 보이는 것과 git clone 이 받아오는 것이 같은 브랜치다. 여기서 읽은 것도 그 브랜치다.

tl-dr

요약. 자산 등록은 끝까지 이어져 있고, 그 위의 두 방어선이 각각 다른 이유로 비어 있다

기억을 meta_assets 한 테이블에 등록하고 agent 에 바인딩해 프롬프트로 밀어 넣는 경로는 끝까지 이어져 있다. 그 위에서 restricted 등급은 권한 판정 함수에 도달하기 전에 잘리고, 기본 배포는 게이트웨이 인증 자체를 꺼 놓는다.

자산 종류 4종 코드의 union 타입 하나로 고정
가시성 등급 5단계 README 는 4단계만 적는다
인스턴스당 사용자 500명 팀은 100개. 코드 상수
기본 배포의 게이트웨이 인증 꺼짐 키 기본값이 빈 문자열이다
공개 트리의 테스트 0개 vitest 설정만 남아 있다
  • 1자산화의 실체는 결정론적 id 다. id 를 team 과 agent 로부터 계산하기 때문에 등록 경로에 재시도 로직도 분산 락도 없다. 어떻게 그렇게 되는지는 「identity」에 있다.
  • 2agent 가 무엇을 볼 수 있는지는 ACL 이 아니라 고정 바인딩이 정한다. 프롬프트 주입 경로는 meta_agent_fixed_assets 만 읽는다. 권한 판정 함수는 사람이 Panel 을 볼 때만 돈다.
  • 3restricted 는 비관리자에게 사실상 없는 등급이다. ACL 을 지연 로딩하는 최적화가 정확히 ACL 이 필요한 분기를 건너뛴다. 게다가 바인딩 검증 함수가 restricted 자산의 agent 장착을 거부한다. 「공유의 두 경로」에서 두 줄로 보인다.
  • 4대규모의 단위는 인스턴스다. 인스턴스당 사용자 500명이라는 상한이 천장으로 읽히지 않는 이유가 여기 있다. 분할 단위다.
  • 5도입 판단을 가르는 것은 코드 품질이 아니라 배포 기본값이다. 원클릭 배포는 게이트웨이 Bearer 인증을 꺼 놓고 0.0.0.0 에 바인딩한 뒤 포트를 호스트로 낸다. 프록시가 Bearer 를 보내지 않아서 켜는 것도 지금은 막혀 있다. 「도입 판단」이 이 사실 위에 서 있다.

이 문서는 코드와 배포 스크립트를 읽어 쓴 것이고 실행해 확인한 것은 없다. 그래서 성립하는 것은 "그렇게 쓰여 있다"까지다. 이 단서는 여기 한 번만 적고 뒤에서는 반복하지 않는다.

problem

문제 정의. 세션이 끝나면 무엇이 남을지를 정하는 자리가 없었다

agent 를 쓰다 보면 같은 설명을 매 세션 다시 한다. RAG 는 무엇을 찾을 수 있는지까지만 답한다. 무엇을 찾을 수 있는지는 답하지만, 누가 그걸 쓸 수 있는지와 어느 버전이 유효한지는 답하지 않는다.

이전에 사람이 하던 일

새 세션마다 프로젝트 맥락을 다시 붙여 넣는다. 팀에 새 agent 를 만들면 다시 처음부터 학습시킨다. 한 번 통한 작업 절차는 개인 메모에 남고 팀에는 남지 않는다. 문서를 읽히려면 매번 파일 목록부터 훑게 한다.

identity

identity 는 세 축이고, 소유자는 두 군데에 따로 적힌다

기억 한 줄이 어디에 속하는지는 team, user, agent 세 축으로 정한다. session 은 네 번째 축이지만 선택이다. 그런데 소유자 개념은 평면마다 다르다. 자산 평면은 user 를 소유자로 보고, Skill 데이터 평면은 agent 를 소유자로 본다.

데이터 평면 · isolation.ts:25 
export interface IsolationContext {
  teamId?: string;
  userId: string;
  agentId: string;
  sessionId: string;
  taskId?: string;
  sessionKey?: string;
}

L0 과 L1 의 모든 쓰기가 이 셋을 들고 간다. /v3 는 team, agent, user 셋을 필수로 보고 session 은 선택으로 둔다. session 을 안 주면 agent 단위로 가로질러 집계한다.

두 개의 소유자

자산 평면: AssetEntity.owner_user_id. 권한 판정의 첫 분기가 이걸 본다. 소유자면 무조건 통과한다.

Skill 데이터 평면: Skill.owner_agent_id. assertOwner 가 (team_id, agent_id) 쌍으로 판정한다. 같은 Skill 을 두 평면이 서로 다른 주체의 것으로 본다.

자동 등록 시점에 agent.owner_user_id 를 읽어 자산 쪽 소유자로 복사한다. 그래서 agent 의 소유자가 바뀌면 두 값이 갈라진다. 동기화하는 코드는 찾지 못했다 (grep -rn 'owner_user_id' MemoryCore/src/core/skill/ → 0건).

share

공유는 두 갈래로 갈리고, 사람 쪽 갈래에 닿지 않는 등급이 하나 있다

사람이 Panel 에서 자산을 볼 때는 권한 판정 함수가 돈다. agent 가 프롬프트로 자산을 받을 때는 고정 바인딩 테이블만 읽는다. 두 경로가 합쳐지지 않아서, ACL 로만 열리는 restricted 등급은 agent 에게 절대 도달하지 못한다.

왼쪽이 끊기는 이유. ACL 조회는 비싸서 지연 로딩한다. 먼저 빈 ACL 로 한 번 돌리고, 결과가 no_permission 일 때만 진짜 ACL 을 읽어 다시 판정한다. 그런데 restricted 분기는 빈 ACL 로 돌면 visibility_restricted 를 돌려준다. no_permission 이 아니므로 두 번째 판정이 일어나지 않는다. metadata-service.ts:1372 의 if (fast.reason !== "no_permission") return fast; 한 줄이다.

share-detail

다섯 등급 중 agent 에 실제로 장착되는 것은 셋뿐이다

README 는 네 등급을 적고 코드는 다섯을 선언한다. agent 장착은 private·team·agent 셋만 통과한다. 사람 열람은 누가 보느냐로 갈린다. 팀 admin 은 private 을 뺀 넷을 읽고, 일반 member 는 team·agent·task 셋만 읽는다.

등급별로 사람 경로와 agent 경로가 각각 어디까지 가는가

permission-checker.ts:66-114(사람)와 permission-checker.ts:158-172(agent 바인딩)를 겹쳐 본 것. 저장소에는 이 대조가 없다

visibilityREADME 에 있는가사람이 읽을 수 있는가agent 에 장착되는가
private있음owner 만. 팀 admin 도 불가같은 owner + 같은 team 이면 가능
team있음팀 멤버 읽기, admin 쓰기같은 team 이면 가능
agent있음team 과 동일같은 team 이면 가능
restricted있음admin 만. ACL 은 조회되지 않는다불가 (false 고정)
task없음읽기는 멤버, 쓰기는 admin불가 (false 고정)
deny 는 받아들여지지만 평가되지 않는다

HTTP 스키마는 z.enum(["allow", "deny"]) 로 deny 를 받는다 (v3-meta-schemas.ts:18). 판정 함수는 acl.effect === "allow" 인 것만 찾는다. deny 를 넣으면 저장은 되고 아무 일도 하지 않는다. 타입 선언 옆 주석이 1기에는 allow 만 쓰고 deny 는 예약해 둔다고 밝히고 있으니 의도된 미구현이다(types.ts:48).

reviewer 역할도 같은 상태다

팀 역할은 admin | member | reviewer 셋인데 판정 함수는 role === "admin" 인지만 본다. reviewer 는 member 와 똑같이 읽기만 된다. UI 쪽에서만 구분한다. ConsoleLayout.tsx:108 이 reviewer 에게 멤버 관리 메뉴를 감춘다.

이 경로의 테스트가 공개 트리에 없다 (git ls-tree -r --name-only HEAD | grep -c 'permission.*test' → 0). 판정 표를 재현해 볼 자료가 저장소 안에 없다는 뜻이다.

wiki-gist

Wiki 층은 Karpathy 의 gist 를 거의 그대로 구현하고, lint 하나만 빠뜨렸다

README 가 출처로 밝힌 gist 는 세 층(raw sources / wiki / schema)과 세 연산(Ingest / Query / Lint), 그리고 특수 파일 둘(index.md / log.md)을 제안한다. 코드를 대조해 보면 schema 층이 파일 두 개로 쪼개졌고, Lint 는 없다.

gist 의 제안과 MemoryKnowledge/src/engines/wiki/ 의 구현 대조

gist 는 2026-08-07 회수본, 코드는 커밋 fe3230f. 이 대조표는 양쪽 어디에도 없다

wiki-index

위키 인덱스를 메모리에서 걷어낸 이유가 코드 주석에 숫자로 남아 있다

처음에는 MiniSearch 로 전부 메모리에 올렸다. 지금은 위키마다 SQLite 파일 하나를 두고 읽기 연결만 LRU 로 묶는다. 바꾼 이유가 index-db.ts 헤더에 그대로 적혀 있다.

SQLite 는 연결을 여는 데 1밀리초가 안 걸리고 데이터를 page 단위로 지연 로딩한다. 열자마자 전부 메모리에 올리는 방식이 아니다. 그게 MiniSearch 의 20GB OOM 을 뿌리 뽑은 이유다. index-db.ts:17 의 중국어 주석을 옮긴 것
위키 하나당 index.db 한 개 · 테이블 4개

wiki_fts FTS5 역색인 · page_meta 페이지 메타 · graph_edge 유향 간선 · source 원본 파일 상태. 본문은 DB 에 넣지 않는다. 디스크의 .md 에 그대로 두고 메타와 snippet 만 색인한다.

메모리 상한을 위키 수와 분리한다

읽기 연결 풀 상한 POOL_MAX 는 300, 연결당 page cache 는 2MB. 곱해서 약 600MB 로 고정된다. 위키가 3개든 3000개든 같다. 대신 WAL 이 연결당 fd 3개를 먹어서 900개가 필요하고, 주석은 ulimit -n ≥ 2048 을 권한다.

읽기와 쓰기가 서로 다른 연결 전략을 쓴다

index-db.ts:12-20 의 연결 전략 주석을 그림으로 옮긴 것

검색 자체는 FTS5 BM25 이고 제목 가중치가 본문의 5배다. 중국어는 JS 쪽에서 bigram 으로 미리 쪼개 넣고 FTS5 는 공백 단위로만 자른다. link graph 확장은 기본값이 hop = 0 이라 꺼져 있고, 요청이 명시할 때만 켜진다.

critique

해석의 한계. 검증 장치가 저장소에서 빠져 있어서 읽은 것 이상은 말할 수 없다

공개 트리에 테스트 파일이 0개이고 PR CI 에는 타입 검사도 테스트 실행도 없다. 코드 주석이 참조하는 설계 문서도 대부분 빠져 있다. 그래서 이 문서의 주장은 전부 정적 읽기의 결과이고, 런타임 동작에 대한 것은 하나도 없다.

설계 문서 없음. MemoryCore/docs, MemoryProxy/docs, MemoryKnowledge/docs 가 모두 없다.

라이선스

LICENSE 파일 본문은 TencentDB Agent Memory is licensed under the MIT. 이고 그 아래 MIT 전문이 이어진다. 26줄이고 carve-out 은 없다. 트리 안의 유일한 라이선스 파일이다. CONTRIBUTING.md:145 도 기여물이 프로젝트 MIT 로 들어간다고 못박고 CLA 없이 DCO sign-off 만 요구한다. GitHub API 가 NOASSERTION 을 돌려주는 이유는 이 corpus 로 확인할 수 없다.

package.json 은 갈린다. MemoryCore·MemoryKnowledge·SDK 는 "license": "MIT" 인데 MemoryProxy·MemoryPanel·openclaw-plugin 은 license 필드가 없다. 루트 LICENSE 가 덮는다고 읽는 것이 자연스럽지만 명시되어 있지는 않다. CodeGraph 가 의존하는 @colbymchenry/codegraph 는 별도 확인이 필요하다.

붙이면 무엇이 남는가

컨테이너 3개(memory-core, memory-hub, proxy), named volume 2개, 도커 네트워크 1개, 호스트에 .admin-key(admin user_key 평문)와 .memory-core-config/·.proxy-config/ 두 디렉터리. 생성된 core config 에는 llm.apiKey 가 평문으로 들어간다. 그리고 coding agent 의 ANTHROPIC_BASE_URL 변경.

되돌리기는 잘 정리돼 있다. stop-all.sh --purge 한 줄이 볼륨·네트워크·키 파일·config 디렉터리 둘을 지운다(stop-all.sh:34-59). 컨테이너 삭제는 --purge 없이도 항상 돈다(:25-32).

의존이 생기는 곳. LLM API 두 벌이 필요하다(기억 추출용, 프록시 상류용). 기본 설정은 텐센트 api.lkeap.cloud.tencent.com 의 deepseek-v3.2 를 가리키지만 OpenAI 호환이면 무엇이든 된다. 바꿀 수 없는 쪽이 더 중요하다. MemoryCore 런타임이 텐센트가 배포하는 @tencentdb-agent-memory/tcvdb-text ^0.1.1 에 의존하고, CodeGraph 자산 전체가 개인 스코프 npm 패키지 @colbymchenry/codegraph ^1.2.0 하나에 걸린다. sqlite-vec 는 0.1.7-alpha.2 에 정확히 고정돼 있다. Node 요구 버전은 컴포넌트마다 다르다. MemoryCore 만 22.16 이상이고 MemoryProxy 와 웹 프런트는 engines 자체가 없다. 멀티노드로 가면 COS 가 사실상 필수가 되고(MemoryProxy/README.md:324), 타이머 스캐너가 Redis ZSET 위에 서 있어 Redis 도 따라온다. 단일 노드면 SQLite 와 in-process 타이머만으로 돈다.

대화 내용이 어디로 나가는지도 같이 봐야 한다. 프록시가 매 턴 대화를 MemoryCore /v3/conversation/add 로 밀어 넣고, MemoryCore 는 그것을 MEMORY_LLM_* 로 지정한 두 번째 LLM 에 추출용으로 다시 보낸다. coding agent 트래픽 전량이 L0 에 원문으로 남고 별도 endpoint 로 재전송된다. 관측 벤더(Langfuse, ClickHouse)는 전부 기본 꺼짐이다.

커밋 빈도와 기여자 분포는 shallow clone 이라 말할 수 없다. 릴리스 규율은 다르다. CHANGELOG.md 가 Keep a Changelog 형식으로 2.0.0(2026-08-03)과 2.0.0-beta.1(2026-07-21)을 기록하고, CONTRIBUTING.md 가 DCO sign-off 와 보안 신고 창구를 정한다. 다만 원클릭 배포가 띄우는 것은 이 커밋에서 빌드된 것이 아니라 Docker Hub 의 :latest 이미지이고, 이미지를 만드는 CI 는 저장소에 없다.

conclusion

결론. 자산화는 끝났고, 공유 판정은 두 경로가 아직 만나지 않는다

기억을 등록 가능한 자산으로 바꾸는 부분은 네 종류가 같은 테이블과 같은 등록 함수를 공유한다. 그 위에서 누가 무엇을 볼 수 있는지 정하는 부분은 두 갈래로 갈린 채 아직 합쳐지지 않았다. 네 달 된 저장소에서 예상 가능한 순서다.

  • ✓자산 평면과 내용 평면을 나눈 것이 이 설계의 중심이다. meta_assets 는 asset_id 를 만들지 않고 기록과 인가만 한다. 덕분에 네 종류가 서로 완전히 다른 저장소를 쓰면서도 같은 관리 화면에 들어온다.
  • ✓결정론적 id 로 멱등성을 산다. chat_memory-{team}-{agent} 는 분산 락 없이 여러 pod 이 동시에 등록해도 안전하다. 충돌을 정상 경로로 처리하는 것이 요령이다. 예외로 다루면 이 이득이 사라진다.
  • ✓대규모를 인스턴스 증식으로 푼다. 메타데이터 DB 를 인스턴스마다 나누고, 인스턴스당 500명 상한을 걸었다. Wiki 인덱스도 같은 발상으로 위키마다 파일을 나누고 연결 수만 상한을 뒀다.
  • ✗공유의 두 경로가 만나지 않는다. 사람 경로는 권한 판정 함수를, agent 경로는 고정 바인딩 테이블을 본다. ACL 로만 열리는 restricted 등급은 양쪽 모두에서 막혀 실질적으로 존재하지 않는다.
  • ✗격리를 강제하는 스위치가 기본으로 꺼져 있고 배포 설정에도 없다. 켜지 않으면 격리 필드가 빠진 요청이 거부되지 않고 공용 default 버킷에 쌓인다.

Karpathy 의 gist 는 The document's only job is to communicate the pattern. Your LLM can figure out the rest. 로 끝난다. 이 저장소는 그 패턴을 여러 팀이 쓰는 서비스로 옮기면서 무엇이 더 필요한지 보여 준다. 소유자, 가시성, 버전, 바인딩. 그 네 컬럼이 개인용 위키와 팀용 자산을 가르는 전부다. 그리고 그 네 컬럼을 실제로 강제하는 일이 컬럼을 만드는 일보다 어렵다는 것도 같이 보여 준다.
