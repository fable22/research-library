Claude Sonnet 5.5 이전 안내: Sonnet 5 요청 코드에서 바꿀 곳

Sonnet 5 코드에서 모델 ID 만 바꾸면 다섯 자리가 400 을 받고, 네 가지는 에러 없이 응답과 비용을 바꾼다. 이 문서는 그 자리를 요청 한 바퀴의 순서로 짚는다.

지금 코드가볼 장
thinking 을 disabled 로 끈다06
tool_choice 를 any 나 tool 로 둔다07
보낸 대화 기록을 고쳐 다시 보낸다08
대화를 다른 모델이나 다른 계정으로 옮긴다09
computer_20251124 를 쓴다10
advisor tool 을 쓴다11
tool call 사이의 텍스트를 사용자에게 보여 준다12
refusal 을 처리하거나 fallback 을 둔다13
effort 를 정해 두고 쓴다14, 16

04장은 이 자리들이 요청 한 바퀴의 어디에 있는지 그림으로 보이고, 05장은 Sonnet 5 에이전트 요청 하나를 필드 순서로 고친다. 15장은 무엇을 읽었는지 적는다.

tl-dr

요약

Sonnet 5 코드에서 모델 ID 만 바꾸면 thinking 의 disabled, 강제 tool_choice, 고친 대화 기록, Claude API 와 Google Cloud 의 computer_20251124, Sonnet 5 advisor 가 400 을 받는다. tool call 사이 메모가 빈 thinking 블록으로 오는 것, 다른 모델이나 계정으로 넘긴 thinking 블록이 버려지는 것, 거부 부류가 늘어난 것, effort 단계의 비용이 바뀐 것은 에러 없이 지나간다.

  • 400thinking: disabled → between_tools, effort 는 high 이하 (06)
  • 400tool_choice 의 any, tool → auto 와 strict: true (07)
  • 4002026-08-31 이후 만든 계정에서 앞 기록을 고친 뒤 thinking 블록을 다시 보낸 요청 (08)
  • 400Claude API 와 Google Cloud 의 computer_20251124 → computer_toolset_20260801 (10)
  • 400Sonnet 5, Opus 4.8, Opus 4.7 advisor (11)
  • 200다른 모델이나 다른 계정으로 넘긴 Sonnet 5.5 thinking 블록은 API 가 버린다 (09)
  • 200tool call 사이의 긴 메모가 기본 display 에서 빈 thinking 블록으로 온다 (12)
  • 200거부 부류가 다섯이고, server-side fallback 은 그중 둘만 Sonnet 5 로 다시 돌린다 (13)
  • 비용단가는 같다. Sonnet 5 의 단계를 이름 그대로 옮기면 max 는 네 벤치마크 모두 작업당 비용이 8~102% 오르고, low 에서 high 까지는 코딩 벤치마크 셋에서 52~94% 내린다. 점수는 같은 단계 20쌍 모두 Sonnet 5.5 가 높다 (16)

tokenizer 도 Sonnet 5 와 같아서 같은 텍스트의 토큰 수는 그대로다. 비용 숫자는 Anthropic 발표 글의 자체 측정이고, 지식 작업 벤치마크 AA-Briefcase 에서는 max 말고도 low, high, xhigh 에서 비용이 오른다(5~27%).

첨언: What's new 의 목록

What's new 는 400 을 내는 변경을 다섯으로 센다. “Five breaking changes affect code already running on Claude Sonnet 5” 그리고 응답 모양만 바꾸는 변경 하나를 따로 둔다. “One more change alters the response shape without failing any request: text between tool calls comes back in thinking blocks.” 이 문서는 거기에 거부 부류(13장)와 effort 재측정(14장)을 더했다. 두 가지는 migration guide 의 공통 체크리스트에 있다.

tokenizer: What's new “The tokenizer is the same as Claude Sonnet 5's, so the same text produces the same token counts.”

problem

모델 ID 만 바꿨을 때

Sonnet 5 에서 돌던 요청은 모델 ID 만 claude-sonnet-5-5 로 바꾸면 thinking, tool_choice, tools 필드와 대화 기록에서 400 을 받는다. migration guide 가 before/after 를 주지만 가이드는 기능별 절로 나뉘어 있어서, 내 요청의 어느 줄이 걸리는지는 요청을 필드 순서로 따라가며 찾는다.

  • 새 400thinking: disabled, tool_choice 의 any 와 tool, 고친 기록 위의 thinking 블록, computer_20251124(Claude API, Google Cloud), Sonnet 5 advisor
  • 이미 400thinking: enabled 와 budget_tokens, assistant prefill. Sonnet 5 도 받지 않던 설정이다
  • 예외Claude Managed Agents 는 모델 이름만 바꾸면 된다
  • 완화캐시할 수 있는 최소 prompt 가 1,024 토큰에서 512 토큰으로 내려가서, 그 사이 길이의 prompt 도 cache_control 을 달면 캐시할 수 있다
  • 그대로단가, tokenizer, 응답을 type 으로 읽고 thinking 블록을 돌려보내는 처리(adaptive 로 돌던 코드)

Sonnet 5 에서 thinking 을 끄고 돌던 코드는 사정이 다르다. thinking 블록을 받아 본 적이 없으므로, 06장의 between_tools 로 바꾸면 응답 처리도 같이 고친다.

첨언: 가이드가 적은 조건

Sonnet 5 가 받는 thinking.type 은 migration guide 표에서 “`"adaptive"`, `"disabled"`” 둘이다. prefill: “Claude Sonnet 5.5 rejects a prefilled last assistant turn with a 400 error, as Claude Sonnet 4.6 and Claude Sonnet 5 do.”

응답 처리: “Code that ran without thinking needs all three items. Code from Claude Sonnet 5 likely has the first two.” 세 항목은 content 를 type 으로 읽기, thinking 블록을 그대로 돌려보내기, max_tokens 다시 보기다.

Claude Managed Agents: “If you use Claude Managed Agents, no changes beyond updating the model name are required.”

Claude Code 에서는 /claude-api migrate 가 모델 ID 교체와 파라미터 변경을 코드 전체에 적용하고 손으로 확인할 목록을 낸다. 편집 전에 범위를 묻는다.

map

요청 한 바퀴에서 걸리는 자리

바뀐 규칙은 요청을 조립할 때, API 가 요청을 검사할 때, 앱이 응답을 처리할 때, 결과를 기록에 붙여 다음 요청으로 돌려보낼 때의 네 자리에 모인다. 400 은 모두 API 검사에서 나고, 기록이 다음 요청으로 되돌아가는 길에는 기록 편집과 모델 이동의 두 규칙이 걸린다.

테스트 순서도 이 그림을 따른다. 요청 조립을 고친 뒤 한 번 보내 400 이 사라졌는지 보고, 응답의 블록 구성을 확인하고, 마지막으로 여러 턴을 이어 보내 되돌아가는 기록이 통과하는지 본다.

trace

Sonnet 5 에이전트 요청 하나를 필드 순서로

thinking 을 끄고 tool 하나를 강제하며 computer use 를 쓰던 Sonnet 5 요청은 model, thinking, output_config, tools, tool_choice 다섯 필드와 beta 헤더 하나가 바뀌고, messages 에는 tool 을 언제 쓰라는 문장이 들어간다. max_tokens 는 그대로이고, 기록은 뒤에 붙이기만 한다.

// headers
- anthropic-beta: fine-grained-tool-streaming-2025-05-14   // toolset 과 함께면 400 (10)
{
-  "model": "claude-sonnet-5",
+  "model": "claude-sonnet-5-5",                    // 날짜 접미사 없음
   "max_tokens": 16000,                             // thinking 과 답을 합친 상한 (14)
-  "thinking": {"type": "disabled"},
+  "thinking": {"type": "between_tools"},           // (06)
-  "output_config": {"effort": "xhigh"},
+  "output_config": {"effort": "high"},             // between_tools 는 high 이하 (06, 14)
   "tools": [
-    {"name": "get_weather", "input_schema": {…}},
+    {"name": "get_weather", "input_schema": {…}, "strict": true},   // (07)
-    {"type": "computer_20251124", …}
+    {"type": "computer_toolset_20260801"}          // Bedrock 은 computer_20251124 유지 (10)
   ],
-  "tool_choice": {"type": "tool", "name": "get_weather"},
+  "tool_choice": {"type": "auto"},                 // (07)
   "messages": [ … ]                                // 언제 tool 을 쓰라는 문장을 넣고, 앞 턴은 고치지 않는다 (07, 08)
}

// 응답
   content 를 type 으로 거른다                     // thinking 블록이 text 앞에 올 수 있다
   thinking 블록은 빈 것도 그대로 돌려보낸다       // (06, 09)
   stop_reason "refusal" 이면 stop_details 를 읽는다   // (13)

이 요청은 migration guide 의 before/after 예시 둘과 computer use 표를 한 요청으로 합친 것이라서, 가이드에 이 모양 그대로 있지는 않다.

  • IDClaude API, Claude Platform on AWS, Google Cloud, Microsoft Foundry 는 claude-sonnet-5-5
  • IDAmazon Bedrock 은 anthropic.claude-sonnet-5-5
첨언: 원래 예시의 값

합친 예시는 thinking 끄기와 강제 tool use 의 before/after 다. thinking 예시의 before 는 xhigh, after 는 high 이고, tool 예시의 after 는 user 메시지 끝에 “Use the get_weather tool.” 을 붙인다.

모델 ID: “Replace your model ID with `claude-sonnet-5-5`, which has no date suffix.” 플랫폼별 ID 는 What's new 의 Availability 절에 있다.

thinking

thinking 끄기: disabled → between_tools

thinking: {"type": "disabled"} 는 Sonnet 5.5 에서 400 을 받는다. up-front thinking 을 끄려면 between_tools 를 보내고, effort 는 high 이하로 두며 thinking 에 다른 필드를 붙이지 않는다.

- "thinking": {"type": "disabled"},
+ "thinking": {"type": "between_tools"},
  "output_config": {"effort": "high"}      // low, medium, high 만. xhigh, max 는 400
  • 400effort 가 xhigh 나 max 인 요청. 이 단계가 필요하면 thinking 을 빼거나 adaptive 로 보낸다
  • 400display, budget_tokens, block_binding 을 같이 보낸 요청
  • 400메시지 단위 effort 를 지금 단계와 다르게 보낸 요청. 턴마다 바꾸려면 adaptive 로 돌린다
  • 200tool 을 쓰는 턴은 tool call 사이 메모가 요약 텍스트를 담은 thinking 블록으로 온다. tool 이 없으면 text 만 온다

Sonnet 5 에서 disabled 로 돌던 코드는 thinking 블록을 처리해 본 적이 없다. between_tools 에서는 tool 을 쓰는 턴마다 thinking 블록이 오므로, content 를 type 으로 읽고 그 블록을 assistant 턴과 함께 그대로 돌려보내는 처리를 이 변경과 같이 넣는다.

첨언: 원문, 에러 메시지, fallback

에러 메시지: “"thinking.type.disabled" is not supported for this model. Use "thinking.type.between_tools" for the lowest thinking setting, or "thinking.type.adaptive" and "output_config.effort" to control thinking behavior.”

migration guide: “`between_tools` works on every platform that offers Claude Sonnet 5.5, with no beta header. It's accepted at `low`, `medium`, and `high` effort. At `xhigh` or `max`, it returns a 400 error.” “`between_tools` takes no other field: `display`, `budget_tokens`, or `block_binding` sent with it returns a 400 error.”

돌려보내기: What's new “Pass those blocks back unchanged with the rest of the assistant turn. A progress-update block you send back gives the model the full note it wrote, not the summary.”

server-side fallback 으로 Sonnet 5 에 넘어간 between_tools 요청은 거기서 disabled 로 돈다. 발표 글도 이 전환을 옮기기 전에 할 일로 적는다. “If you run Sonnet with thinking off, you’ll need to switch to the new between_tools setting, which keeps up-front thinking off, before moving to Sonnet 5.5.”

tool_choice

강제 tool use: any, tool → auto 와 strict

tool_choice 의 any 와 tool 은 messages 와 token counting 두 endpoint 에서 400 을 받는다. auto 로 바꾸고 tool 에 strict: true 를 붙이며, 모델이 tool 을 부르지 않고 답할 수 있으므로 언제 부르라는 문장을 prompt 에 넣는다.

  "tools": [{
    "name": "get_weather",
    "input_schema": { …, "additionalProperties": false },
+   "strict": true
  }],
- "tool_choice": {"type": "tool", "name": "get_weather"},
+ "tool_choice": {"type": "auto"},
  "messages": [{"role": "user",
-   "content": "What's the weather in Paris?"}]
+   "content": "What's the weather in Paris? Use the get_weather tool."}]
  • 400{"type": "any"}, {"type": "tool", "name": …}
  • 200{"type": "auto"}(기본값), {"type": "none"}
  • 한도strict tool 은 한 요청에 20개까지이고, MCP, computer use, browser use toolset 항목은 strict 를 받지 않는다
  • Bedrockstrict tool use 를 포함한 structured outputs 가 없어서 strict 없이 auto 만 보내고 tool 입력은 코드에서 검증한다

tool_use 블록이 반드시 온다고 가정한 코드에는 text 만 온 응답을 처리하는 분기를 넣는다. strict 는 JSON Schema 의 일부만 받고 모든 object 에 additionalProperties: false 를 요구하므로 기존 스키마를 먼저 확인한다. 강제 tool 이 결과를 스키마대로 꺼내는 용도였다면 스키마를 structured outputs 로 옮기는 길도 있다.

첨언: 원문

에러 메시지: “tool_choice: type "tool" and "any" are not supported for this model.”

migration guide: “Send `tool_choice: {"type": "auto"}`, and mark the tool `strict: true` so its input matches the schema. The model can then answer without calling the tool, so say in the prompt when to use it.” “A request can have at most 20 strict tools, and the MCP, computer use, and browser use toolset entries don't accept `strict`.”

What's new: “For schema-valid tool input, keep `tool_choice: {"type": "auto"}` and set `strict: true` with strict tool use, or move the schema to structured outputs.”

history

대화 기록: 뒤에 붙이기만

Sonnet 5.5 의 thinking 블록은 그 앞의 system, tools, 메시지에 묶여 서명된다. 2026-08-31 00:00 UTC 이후 만든 계정에서는 앞 기록을 고친 뒤 그 블록을 다시 보내면 400 이므로, 기록은 뒤에 붙이기만 하고 지시나 tool 은 mid-conversation system message 로 바꾼다.

  messages: [ user, assistant(thinking…), user, assistant(thinking…) ]

✗ messages[0] 의 지시를 고쳐 다시 보낸다          // 400
✗ system 이나 tools 를 바꿔 다시 보낸다            // 400
✓ 끝에 {"role": "system", …} 메시지를 붙인다        // 200, mid-conversation system message
  • 4002026-08-31 이후 계정, Claude API, Amazon Bedrock, Google Cloud 의 기본값
  • 200thinking-binding-controls-2026-08-01 헤더와 thinking.block_binding.prefix_mismatch_behavior: "drop_block" 을 보내면 걸린 블록만 버린다. adaptive 에서만 된다
  • 옛 계정기본으로는 검사하지 않고, prefix_mismatch_behavior 를 보낸 요청만 검사한다
  • 지시mid-conversation system message 로 붙인다. 메시지의 모양은 그 기능 문서에 있다 (15장)
  • tool대화 중 tool 변경은 beta 다. What's new 는 inline-tools-2026-09-15 헤더와 tool_addition 블록으로 tools 를 고치지 않고 tool 을 더하거나 스키마를 바꾸는 방법을 적는다

기록을 요약하거나 잘라 내는 코드, 요청마다 system prompt 에 날짜나 상태를 끼워 넣는 코드가 여기에 걸린다. between_tools 는 block_binding 을 받지 않으므로, 기록을 고쳐야 하면 고친 턴부터 뒤의 thinking 블록을 지우고 보낸다. 긴 대화를 요약해야 하는 코드라면 What's new 가 적은 compaction on demand(beta)도 후보다.

첨언: 원문, 요약 기능

What's new: “The API also checks whether anything before a Claude Sonnet 5.5 thinking block has changed since the block was produced: the `system` prompt, the `tools`, or an earlier message.” “On older accounts, setting that field to either value opts the request in. `block_binding` works only with `thinking: {"type": "adaptive"}`. With `between_tools`, keep the history append-only, or strip the thinking blocks from the edited turn on.”

compaction on demand 의 beta 헤더는 compact-2026-09-04 다. 요약 블록 뒤에 남긴 턴의 thinking 블록이 유효한 조건은 compaction 문서에 있다 (15장).

테스트는 2026-08-31 이후 만든 계정에서 돌린다. 그 전 계정은 기록을 고쳐도 기본으로 통과한다.

binding

모델과 계정을 넘는 thinking 블록

Sonnet 5.5 의 thinking 블록은 다른 모델도, 만든 계정이나 그와 연결된 계정 밖의 계정도 읽지 못한다. API 는 그런 블록을 버리고 200 을 주므로, Sonnet 5.5 에서 다른 모델로 되돌리거나 계정 사이에 대화를 옮기는 코드는 그 뒤 턴이 앞의 추론 없이 돈다는 것을 에러로 알 수 없다.

  • 읽음Sonnet 5, Opus 4.8, Haiku 4.5 와 그 이전 모델의 블록. Sonnet 5 에서 넘어온 대화는 추론을 유지한다
  • 버림Opus 5, Opus 5.5, 모든 Fable, Mythos 모델의 블록
  • 버림Sonnet 5.5 블록을 다른 모델로 보낼 때. Sonnet 5 로 되돌리는 경우도 같다
  • 버림만든 계정과 연결된 계정 밖에서 보낸 Sonnet 5.5 블록

버려진 블록은 과금되지 않는다. 버려졌는지 알려면 thinking-binding-controls-2026-08-01 헤더를 보내고 응답 최상위의 input_transformations 배열을 읽는다. 계정 결속으로 버려진 블록은 Claude API 와 Google Cloud 에서 reason: "organization_binding_mismatch" 로 적힌다.

첨언: 원문

What's new: “No other model reads Claude Sonnet 5.5 thinking blocks.” “So a conversation that moves from Claude Sonnet 5 onto Claude Sonnet 5.5 keeps its reasoning, and one that moves from Claude Sonnet 5.5 to any other model runs the turns after the switch without it.”

발표 글은 이 결속을 distillation 방어로 설명한다. “Sonnet 5.5 also expands preserved thinking, so Claude’s thinking cannot be decoupled from the account that created it.” “If you move conversations between accounts, including switching accounts mid-session in Claude Code, our docs article explains the change.”

computer-use

computer use: computer_20251124 → toolset

Claude API 와 Google Cloud 에서 Sonnet 5.5 는 computer use 를 computer_toolset_20260801 로만 받고 computer_20251124 에는 400 을 낸다. Amazon Bedrock 에서는 computer_20251124 를 그대로 쓴다.

- anthropic-beta: fine-grained-tool-streaming-2025-05-14
  "tools": [
-   {"type": "computer_20251124", …}
+   {"type": "computer_toolset_20260801"}
  ]
  • 400Claude API, Google Cloud 의 computer_20251124
  • 400모든 플랫폼의 computer_20250124
  • 400toolset 항목과 같이 보낸 fine-grained-tool-streaming-2025-05-14 헤더. 필요한 tool 마다 eager_input_streaming: true 로 바꾼다
  • 200Amazon Bedrock 의 computer_20251124, 이미 toolset 을 쓰는 코드, browser use tool

agent loop 도 고친다. What's new 는 toolset 의 member tool_use 블록, batch action, 결과의 toolset_name 세 가지를 처리하라고 적고, 절차는 computer use tool 문서의 「Migrate from computer_20251124」 절로 넘긴다.

첨언: 원문

Claude API 의 에러 메시지는 이렇게 시작한다. “'claude-sonnet-5-5' does not support tool types: computer_20251124.”

What's new: “Drop the beta header, replace the `tools` entry with `{"type": "computer_toolset_20260801"}`, and update your agent loop for member `tool_use` blocks, batch actions, and `toolset_name` on results.”

advisor

advisor tool: 받는 advisor

advisor tool(beta)에서 Sonnet 5.5 executor 는 Opus 5, Opus 5.5, Sonnet 5.5, Fable 5 와 5.1, Mythos 5 와 5.1 advisor 만 받고, Sonnet 5, Opus 4.8, Opus 4.7 advisor 에는 400 을 낸다. 받는 advisor 는 모두 조언을 암호화된 advisor_redacted_result 블록으로 돌려준다.

  • 200Opus 5, Opus 5.5, Sonnet 5.5, Fable 5, Fable 5.1, Mythos 5, Mythos 5.1
  • 400Sonnet 5, Opus 4.8, Opus 4.7. Sonnet 5 executor 와는 되던 짝이다
  • 400Opus 4.6, Sonnet 4.6. migration guide 에만 적혀 있다

조언 텍스트를 로그에 남기거나 화면에 보여 주던 코드는 그 텍스트를 받지 못하므로, 그 기능을 지우거나 조언이 반영된 executor 의 출력으로 대신한다.

첨언: 원문

What's new: “Claude Opus 4.8, Claude Opus 4.7, and Claude Sonnet 5 advisors work with a Claude Sonnet 5 executor, but with a Claude Sonnet 5.5 executor they return a 400 `invalid_request_error`. Every advisor that Claude Sonnet 5.5 accepts returns its advice encrypted, as an `advisor_redacted_result` block, so your client can't read the advice text.”

migration guide: “Claude Opus 4.8, Claude Opus 4.7, Claude Opus 4.6, Claude Sonnet 5, and Claude Sonnet 4.6 advisors return a 400 error.” advisor 를 지정하는 필드 이름은 advisor tool 문서에 있다 (15장).

between-text

tool call 사이 텍스트: text → thinking 블록

Sonnet 5.5 는 tool call 사이에 쓴 한두 문장보다 긴 메모를 thinking 블록으로 돌려주고, 기본 display("omitted")에서는 그 블록이 비어 있다. 에러 없이 그 메모를 보여 주던 화면만 조용해지므로, adaptive 에서는 display 를 바꾸고 긴 메모를 text 블록 대신 thinking 블록에서 읽는다. between_tools 에서도 메모는 thinking 블록으로 온다.

  "thinking": {
    "type": "adaptive",
+   "display": "updates"        // beta 헤더 thinking-display-updates-2026-08-18. 메모만 온다
  }                              // "summarized" 는 메모와 추론 요약이 섞여 온다
  • text한두 문장 이하의 짧은 말은 Sonnet 5 처럼 text 블록으로 온다
  • thinking그보다 긴 메모. 기본 display 에서는 thinking 필드가 비어 있다
  • 순서비어 있지 않은 thinking 블록을 바로 뒤의 tool_use 블록보다 먼저 그린다
  • betweenbetween_tools 는 display 없이도 thinking 블록에 요약 텍스트를 담아 준다. display 를 붙이면 400 이다 (06)

Steering thinking 의 과금 표는 summarized 와 omitted 의 청구 토큰이 같고 보이는 텍스트만 다르다고 적는다. updates 는 그 표에 없다.

첨언: 원문

migration guide: “On Claude Sonnet 5.5, notes longer than a sentence or two that the model writes between tool calls come back as progress-update `thinking` blocks, empty at the default `display`. Shorter remarks stay `text`.” “No request fails, but an interface that shows those notes goes quiet.”

Steering thinking: “What you're billed for is the same regardless of the `display` setting; only what you see changes”

refusal

refusal: 다섯 부류와 fallback

Sonnet 5.5 는 Sonnet 5 보다 많은 부류에서 거부하고(어느 부류가 새로 생겼는지는 가이드에 없다), 거부는 HTTP 200 에 stop_reason: "refusal" 로 온다. server-side fallback(beta, Claude API 전용)은 cyber 와 frontier_llm 거부만 Sonnet 5 로 다시 돌리므로 나머지 세 부류는 코드에서 처리한다.

stop_details 부류걸리는 요청server-side fallback
cybermalware, exploit 개발처럼 사이버 피해로 이어질 수 있는 요청Sonnet 5 로 재시도
frontier_llm경쟁 AI 모델 개발을 돕는 요청Sonnet 5 로 재시도
bio위험한 실험 방법처럼 생물학적 피해로 이어질 수 있는 요청재시도 없음
reasoning_extraction모델의 내부 추론을 응답 텍스트로 옮겨 적게 하는 요청재시도 없음
general_harms그 밖의 사용 정책 영역. 정상 작업도 걸릴 수 있다재시도 없음

응답 텍스트에 추론 과정을 적으라고 시키던 prompt 는 reasoning_extraction 에 해당하므로 먼저 고친다. fallback 은 fallbacks: "default" 로 켜는데 Claude API 에서만 되므로, 다른 플랫폼에서는 What's new 가 함께 적는 SDK middleware 나 자체 재시도를 쓴다. 출력 전에 난 거부의 과금 여부는 부류에 따라 다르고, 어느 경우든 rate limit 에는 잡힌다. fallback 으로 Sonnet 5 에서 도는 요청이 앞 턴의 Sonnet 5.5 thinking 블록을 버리는지는 이 corpus 에 적혀 있지 않다(09장의 규칙을 따른다면 버려진다).

첨언: 원문

migration guide: “Claude Sonnet 5.5 declines in more categories than Claude Sonnet 5.” “It doesn't retry `"bio"`, `"reasoning_extraction"`, or `"general_harms"` declines.”

What's new: “A declined request returns HTTP 200 with `stop_reason: "refusal"` and a `stop_details` object naming the policy area.” 발표 글: “higher-risk cybersecurity tasks will visibly fall back to Sonnet 5.”

stop_details 안의 필드 경로와 부류별 과금은 refusals and fallback 문서에 있다 (15장).

effort

effort 다시 재기

Sonnet 5.5 는 effort 단계를 다시 맞춰서, 같은 이름의 단계가 Sonnet 5 와 같은 양의 thinking 을 만들지 않는다. Sonnet 5 에서 쓰던 값을 그대로 옮기지 말고 평가를 다시 돌리며, 시작점은 워크로드마다 다르다.

워크로드시작 단계올릴 때
agentic coding, 여러 단계의 tool usemedium더 어렵거나 긴 작업이면 high
채팅, 지연에 민감한 작업medium 또는 low원문에 기준 없음
그 밖high (Claude API 기본값)xhigh, max 는 평가에서 품질이 오를 때만
  • 상한max_tokens 는 thinking 과 답을 합친 상한이다. agentic coding 은 모델 최대치인 128,000 으로 두고 stream 한다
  • 캐시요청 사이에 최상위 effort 를 바꾸면 prompt cache 가 깨진다. 메시지 단위 effort(beta, mid-conversation-output-config-2026-07-01)는 캐시를 유지하지만 between_tools 에서는 400 이다
  • 측정thinking 에 쓴 토큰은 usage.output_tokens_details.thinking_tokens 에 있다

Claude Code 와 Claude 앱은 medium, Claude Platform(API)은 high 가 기본이다. Claude Code 에서 본 속도와 비용을 API 에 그대로 기대하면 한 단계가 어긋난다.

첨언: 원문

migration guide: “The levels are recalibrated, so a level doesn't produce the same amount of thinking as on Claude Sonnet 5.” “Start at `high` unless your workload is agentic or latency-sensitive. For agentic coding and multistep tool use, start at `medium` for well-specified tasks and move to `high` for harder or longer ones. For chat and other latency-sensitive work, start at `medium` or `low`.”

Effort: “Use `xhigh` or `max` only where your evals show a quality gain.” “For agentic coding, set `max_tokens` to 128,000, the model's maximum, and stream the response.”

발표 글: “In Claude Code and our apps, the default effort is set to Medium, while the Claude Platform defaults to High.”

setup

읽은 범위

Anthropic 공개 문서 다섯 편을 sha256 으로 고정해 읽었다. 개발자 문서 넷은 받은 바이트의 해시이고, 발표 글은 HTML 에서 뽑은 본문 텍스트의 해시다. API 를 호출해 400 을 재현하지는 않았으므로, 이 문서의 에러 조건과 대처법은 전부 문서가 적은 그대로다.

첨언: 고정 방법

발표 글은 HTML 에서 본문 텍스트를 뽑아 sha256 을 적었고, 차트의 점은 SVG aria-label 에서 옮겼다. 개발자 문서 넷은 text/markdown 으로 받은 바이트의 sha256 이다. 발표 글과 migration guide 는 Wayback 스냅샷 주소를 함께 적었지만 스냅샷 본문을 고정 사본과 대조하지는 않았고, 나머지 셋은 스냅샷이 없다. 그래서 문서가 바뀌면 이 문서의 인용을 대조할 원본은 고정 사본뿐이다. 식별자와 해시는 .research/2026-09-30-claude-sonnet-5-5-migration-v3/sources.jsonl 에 있다.

result-cost

effort 단계별 작업당 비용

발표 글의 차트 네 개에서 Sonnet 5 의 단계를 이름 그대로 옮기면, max 는 네 벤치마크 모두 작업당 비용이 오르고(8~102%) low 에서 high 까지는 코딩 벤치마크 셋에서 52~94% 내린다. 지식 작업 벤치마크 AA-Briefcase 는 max 말고도 low, high, xhigh 에서 비용이 오른다.

Sonnet 5 에서 max 를 쓰던 코드는 옮기기만 해도 비용이 오르고, 점수도 네 벤치마크 모두 오른다(Terminal-Bench 10.3% → 70.6%). 같은 점수를 더 낮은 단계에서 얻는지는 워크로드에서 재야 한다. FrontierCode 에서는 Sonnet 5.5 의 max 가 xhigh 보다 13배 비싸고($20.78 대 $1.59) 점수도 낮다(46.2% 대 52.1%). 점수가 낮은 이유로 발표 글은 max 에서 Claude Code 의 code-review skill 이 여러 subagent 로 나뉘어 돌며 시간 초과나 범위 밖 수정이 난 두 사례를 든다.

첨언: 점수, 각주, 발표 글의 요약 숫자

같은 단계의 점수 (Sonnet 5 → Sonnet 5.5), high 기준: Terminal-Bench 4.5% → 43.0%, FrontierCode 39.4% → 49.4%, CursorBench 30.8% → 47.8%, AA-Briefcase 1177 → 1634. max 기준: 10.3% → 70.6%, 42.4% → 46.2%, 34.1% → 55.5%, 1359 → 1811.

FrontierCode max 가 낮은 이유, 발표 글 각주 2: “At Max effort, Sonnet 5.5 more often ran Claude Code’s code-review skill, which splits the review across many subagents, and in two cases Cognition examined, this led to a timeout or to extra edits beyond the task’s scope, and therefore to a lower score.”

AA-Briefcase, 각주 3: 출시 전 배포에는 structured outputs 요청의 응답을 떨어뜨리는 버그가 있었다. “We expect the effect on Sonnet 5.5’s scores, if any, to be small and to understate its performance.”

발표 글 첫 문단의 “costs up to 30% less for most work” 는 단계별 비교가 아닌 요약 숫자다. 단가는 두 모델이 같다(입력 $2, 출력 $10, 캐시 읽기 $0.20, 백만 토큰당).

critique

한계

400 조건은 Anthropic 문서의 서술이고 비용은 Anthropic 의 자체 측정이라서, 이 문서의 어느 숫자도 독립적으로 재현된 것은 없다. 그래도 thinking 끄기의 between_tools 전환은 발표 글, migration guide, What's new 세 곳이 같게 적는다.

  • 재현요청을 보내 400 과 200 을 확인한 기록이 없다. between_tools 와 adaptive 의 답 품질 차이를 잰 수치도 이 corpus 에 없다
  • 측정16장의 비용과 점수는 Anthropic 이 고른 벤치마크 넷이고 신뢰구간이 없다. AA-Briefcase 는 버그가 있던 출시 전 배포에서 쟀다
  • 문서 차이advisor 의 400 목록이 migration guide 는 다섯(Opus 4.6, Sonnet 4.6 포함), What's new 는 셋이다
  • 시점문서는 2026-09-29 판이다. display updates, 메시지 단위 effort, server-side fallback, binding controls 는 beta 라서 이름과 조건이 바뀌면 이 문서의 해당 줄이 틀린다
첨언: 세 곳의 문장

발표 글: “If you run Sonnet with thinking off, you’ll need to switch to the new between_tools setting” migration guide: “On Claude Sonnet 5.5, `disabled` returns a 400 `invalid_request_error`” What's new: “On Claude Sonnet 5.5, a request that sends `thinking: {"type": "disabled"}` returns a 400 `invalid_request_error` whose message points to `between_tools`.”

conclusion

옮기는 순서

모델 ID 를 바꾼 뒤 400 을 내는 다섯 자리를 먼저 고치고, 에러 없이 달라지는 응답 처리를 확인한 다음, effort 를 내 워크로드에서 다시 잰다.

  • 1claude-sonnet-5-5 로 바꾼다. Bedrock 은 anthropic.claude-sonnet-5-5
  • 2disabled 를 between_tools 로 바꾸고 effort 를 high 이하로 둔다 (06)
  • 3tool_choice 를 auto 로, tool 에 strict: true, prompt 에 tool 사용 조건을 넣는다 (07)
  • 4기록은 뒤에 붙이기만 하고, 새 계정에서 여러 턴을 이어 보내 본다 (08)
  • 5Claude API 와 Google Cloud 의 computer use 를 toolset 으로 옮기고 beta 헤더를 뺀다 (10)
  • 6advisor 를 Sonnet 5.5 가 받는 모델로 바꾼다 (11)
  • 7모델이나 계정을 오가는 경로에서 thinking 블록이 버려지는지 input_transformations 로 본다 (09)
  • 8tool call 사이 메모를 보여 주는 화면이면 display 를 정한다 (12)
  • 9refusal 다섯 부류를 처리하고 fallback 을 정한다 (13)
  • 10effort 를 다시 재고, max 를 쓰던 곳은 비용부터 본다 (14, 16)
